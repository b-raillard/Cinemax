# Seerr requests

> Loaded when you work under `Shared/Seerr/` or on `RequestsSettingsScreen`. Spec (the long stories, the spike measurements): `docs/superpowers/specs/2026-11-06-seerr-requests-design.md`. The client itself lives in `Packages/CinemaxKit/Sources/CinemaxKit/Seerr/` (see `Packages/CinemaxKit/CLAUDE.md`). Lot 1a ships the base and Réglages → Demandes; lot 1b the first browse surface, the search section (its RULEs: `docs/rules/search.md`); lot 2 the fiches — missing seasons, saga, actor page (their RULEs: `docs/rules/media-detail.md`); lot 3 « Mes demandes », « À valider » (Réglages → Demandes) and the arrival message (RULEs below).

- **RULE — everything Seerr-only comes AFTER owned content, and the word « Seerr » appears only in Réglages and in the invitation to sign in.** Browse surfaces (search, Home, fiches) never name it; its rows sit below what the Jellyfin server owns.
- **RULE — an age-capped account gets NOTHING from Seerr: no call, no UI.** Capped = the device cap `privacy.maxContentAge` > 0 OR the server's `maxParentalRating` (`SeerrAccess.isAgeCapped`). An unknown policy counts as capped (fail closed). Lifting the cap reloads at once (`AppState.onAgeCapChanged`).
- **RULE — no Seerr call without Pro (`proAllowsProvider`, default fail closed), without `seerr.enabled`, or offline.** The one exception is the admin's own Réglages → Demandes page, which must work to enable it. Back online, a Pro tier change and a cap change all `reload`.
- **RULE — a stale answer is dropped, never applied.** Every `perform` checks `isCurrent` after its await; reads go through `snapshot()`; the account comes from `activeAccountKeyProvider`. A reload for the SAME account never resets what is on screen.
- **RULE — Seerr never answers 401 for a dead session: 403 ⇒ PROBE (`/auth/me`, or `/user/jellyfin/{id}` without `X-API-User`) before concluding.** A dead cookie and a refused key both answer 403. A dead cookie gets ONE silent re-sign-in (single-flight), and only to the configured address, never when that downgrades from an HTTPS Jellyfin (the Quick Connect RULE below); never a second attempt in a row.
- **RULE — the device API key and the session cookie are BOUND to the Seerr origin they were issued for (scheme+host+port+path) and never sent anywhere else.** A non-admin profile can rewrite its own `seerr.url`, so an unbound secret would be exfiltrated by typing an address. Mismatch ⇒ account mode, not an error.
- **RULE — `X-API-User` is mandatory in key mode and enforced by the TYPE** (`SeerrCredential.apiKey` requires a `SeerrUserID`); never build the header by hand.
- **RULE — CSRF is the client's job** (`_csrf` + `X-XSRF-TOKEN`, one refresh on a refusal); a call site never touches it.
- **RULE — `HTTPCookie` silently drops `Secure` cookies served over `http://`: always read and write cookies through `SeerrClient.cookies(in:)`,** never `HTTPCookieStorage` directly.
- **RULE — never logged: headers, cookies, the Quick Connect `secret`, the `/settings/jellyfin` body.** `LogScrubber` carries the markers as a net, not as permission.
- **RULE — « Tester la connexion » tests the TYPED address and saves it only when the report has no failure** (`SeerrConnectionTest.run` never saves; `SeerrActivationModel.setAddress` does). The cookie the test's sign-in stores is thus always bound to the saved address.
- **RULE — Quick Connect approval is only ever auto-given to the configured address, and the SILENT re-sign-in only when it does not downgrade from an HTTPS Jellyfin** (owner, 2026-11-07, `SeerrAccess.downgradesFromHTTPS`: Jellyfin `https` + Seerr `http`). There the dead session falls to `.notConnected` — at `reload` (`resolveBySession`) and in `perform` alike, both through `reSignInOnce` — and only the visible « Se connecter à Seerr » signs in again; « Tester la connexion » says so in account mode (`seerr.test.warning.httpSeerr`; key mode renews no session, so no warning). Every other pair (http→http, https→https, http→https) keeps the silent path. Residual risk, accepted (spec § Trust): a LAN man-in-the-middle on a plain-HTTP Seerr could swap in a code it initiated — no longer silently when Jellyfin itself is HTTPS, still on a tap the user makes. Never widen the auto-approval to any other address. Locked by `noSilentReSignInWhenJellyfinHTTPSAndSeerrHTTP` / `silentReSignInStillWorksOtherwise`.
- **RULE — tvOS: a Réglages → Demandes row whose action is in flight is never `.disabled`** (`RequestsSettingsScreen.busy(_:)`): disabling the FOCUSED row throws focus. Only DATA conditions disable a row there (no address typed, nobody enabled, no key typed); the row keeps its spinner and the action's own `guard !isX` ignores a second press. iOS disables and dims as usual.
- **RULE — a test never runs on a simulator holding a real session,** and never against the production server; the bench is the local Seerr + Jellyfin (`127.0.0.1`).
- **RULE — a browse surface loads through `loadSection` and writes a TERMINAL state on every path**: an answer ⇒ `.loaded`, an error or the deadline ⇒ `.hidden`, `nil` (the account moved) ⇒ `.hidden` too unless the task was cancelled (a newer load owns the state). Leaving `.loading` stranded would draw a skeleton once the next profile's Seerr becomes visible. The section also keeps the `Snapshot` it was loaded for and is drawn only while `seerr.snapshot()` still equals it (`SearchViewModel.seerrSection(for:)`).
- **RULE — an owned set that Seerr's answer is subtracted from must be WHOLE and carry `ProviderIds`, both decided by ONE `allowsSeerr()` read per pass** (saga members up to 100, an actor's filmography up to 200 — Jellyfin answers newest first, so a page cap offers older owned titles as « Demander »). Fetched without the ids ⇒ Seerr is not asked at all (`fetchedProviderIds`), even if it turned visible meanwhile. Rules per surface: `docs/rules/media-detail.md`.
- **RULE — « Se connecter à Seerr » outside the connection test goes through `SeerrSession.signInToSavedAddress`** (Settings and the search invitation): Quick Connect probed first, the SAVED address only, failures mapped by `SeerrAccess.signInFailure` to the connection test's messages.
- **RULE — a missing-title card's tap goes through `SeerrRequestPresenter.request(_:session:loc:toasts:)`, with the `SeerrMissingTitle`** (search, fiches, saga, actor page). Its EFFECTIVE badge (`badge(for:default:)`, so a request just sent counts) decides first: pending / in preparation ⇒ an info toast « Déjà demandé » + `seerr.request.already.*`, nothing opens; never asked or declined ⇒ the request. A film ⇒ `.movie`; a series ⇒ `/tv/{id}` first — ONE lookup per series at a time (`lookingUp`), repeated taps return at once — then `.series` with every missing season ascending, all ticked (`SeerrMissing.seasons`, specials per `enableSpecialEpisodes`); none left ⇒ `seerr.request.noSeasons`; a failed lookup — or one past its deadline (6 s, `lookupDeadline`, through `loadSection`, like a section) ⇒ a quiet toast that never names Seerr; an account change ⇒ nothing. Once a request is CREATED, the card's badge is the status Seerr answered (`badge(afterCreating:)`: pending ⇒ pending, declined ⇒ declined, approved / failed / completed ⇒ in preparation) — never guessed from the permissions, which only phrase the sheet's « what happens next » line (`nextStepKey`). Locked by `SeerrRequestEntryPointTests` / `badgeFollowsTheCreatedStatus`. **A missing SEASON (series fiche) goes through `request(season:among:of:…)` / `requestAll(_:of:…)`**: the same « Déjà demandé » rule on the season's effective badge (`tv-<id>-s<n>`), then `.series` over the seasons still REQUESTABLE (`requestableSeasons`: never asked or declined, ascending) with that season ticked, or all of them — no lookup, the fiche already holds the seasons. tvOS: when the draft ticks fewer seasons than it offers, the confirmation adds « Demander les saisons 4 à 6 » under « Demander la saison 4 » (nothing to tick there); season 0 alone reads « Demander les épisodes spéciaux », and a run from 0 takes the count, never « les saisons 0 à 2 ». Locked by `SeerrSeasonRequestTests`. **A saga's « Demander les N » goes through `requestAll(films:loc:toasts:)`**: `.films` over the films still requestable by their effective badge (`requestableFilms`), all ticked; none left ⇒ « Déjà demandé ».
- **RULE — `MissingTitlesRow`'s iOS header puts its count (« 3 films manquants ») and action (« Demander les N ») beside the title only when all fit (`ViewThatFits`), else UNDER it, the title then allowed two lines — never a truncated title.** Measured on the series fiche (iPhone, French, 2026-11-07): « Pas encore dans ta… » beside « Demander les 3 »; a saga's name is longer still. tvOS closes the row with the action as a card instead (`MissingActionCard`, shared with the saga cards appended to the « Fait partie de » row, where it closes the row on iOS too).
- **RULE — « Mes demandes » (`SeerrMyRequestsModel`, the FIRST section of Réglages → Demandes — second when requests wait for a manager, see the bubble RULE) shows for an account Seerr is enabled for AND connected — admin or not; an admin whose own switch is off sees none, a signed-out account sees the Connexion invitation instead — and ALWAYS passes `requestedBy=<my Seerr id>`** (without it a manager lists the whole household). `GET /request` carries no title: each row loads its own `/movie/{id}` or `/tv/{id}`, concurrently (at most the page's 20), AFTER the rows are published — a failed lookup reads « Titre indisponible » and keeps its status line; never block the list on titles. Pages of 20, `skip` = what the SERVER sent, rows de-duplicated by request id (`sort=modified` moves a request between pages — the `PaginatedLoader` RULE); an empty page ends paging. A row that does not decode (no asker, an unknown kind…) is skipped, never fatal to the page (`SeerrRequestPage` decodes rows lossily) — and still counts in `served`, which is what `skip` and « an empty page » read: counting only the decoded rows would re-ask the odd one forever. Status precedence (`statusKey`, locked by `SeerrMyRequestsTests`): media available or request `completed` ⇒ « Arrivée dans ta bibliothèque »; declined ⇒ « Refusée »; pending ⇒ « En attente de validation »; anything else — `failed` included (approved, the downloader hand-off failed, the admin retries) — « Approuvée · en cours de téléchargement ». « Regarder » only when the media is `available` AND Seerr knows its `jellyfinMediaId` ⇒ `appState.pendingDeepLinkItemId` (the one deep-link route: a modal over the tabs, Settings stays underneath). tvOS: EVERY row is one focusable unit, inert ones included (the remote scrolls by focus), and « Afficher plus » is never `.disabled` while it loads (focus would jump). **« Annuler la demande »** (owner 2026-11-08, recette Q2): only on a row `canCancel` reads as withdrawable — still « En attente de validation » (Seerr refuses its asker anything else: `DELETE /request/{id}` → 401, read in Seerr 3.5.1's route and tested on the bench). The row itself is the button on both platforms (like « Regarder »), and it opens a confirmation (« Annuler la demande « titre » ? », Annuler la demande / Garder) BEFORE any call. Done or 404 ⇒ the row leaves (`SeerrRequestPages.remove`) + « Demande annulée »; 401 ⇒ « Déjà traitée » and the first page is read again (the row shows its new status); any other failure keeps the row. One withdrawal at a time (`cancelling`); tvOS: focus goes to the row taking its place (`focusAfterWithdrawing`). **RULE — a focus hand-over after an action CONFIRMED in an alert never requires focus to be « still on the pressed row »**: the alert held focus and closing it leaves `focusedItem` nil, so that strict test always failed and the engine sent focus to the tab bar (measured on the tvOS simulator, 2026-11-08). Accept nil or the pressed row; a row the user moved to keeps it. Same for « Refuser » (`settle`, `wasOnButton`). Locked by `cancelRemovesRow` / `cancelRefused`.
- **RULE — Seerr's `/movie/{id}` carries NO `mediaType`** (measured on 3.5.1, 2026-11-07 — only search results and credits do): `SeerrClient.movie` decodes through `SeerrMovieDetails` (default kind `.movie`). A test fixture with `mediaType` hid it until Mes demandes became its first caller; never "fix" a fixture into a shape the server does not send.
- **RULE — the « Tester la connexion » report is cleared when the address field names ANOTHER address (`SeerrTestReport.stillApplies`, origin compare), never by a bare `onChange(of: addressText)`**: `runTest` writes the normalized address back into the field right after showing the report, which a plain change handler would wipe at once.
- **RULE — « À valider (N) » (`SeerrPendingModel`, right after Mes demandes — first when requests wait at opening) shows for a connected Seerr user who may MANAGE requests — `permissions.canManageRequests`, a Seerr admin passing — never the Jellyfin admin flag, and whatever the account's own switch** (an admin who validates without requesting still validates: the bench's `bench`). It never passes `requestedBy` (the queue is the household's), and N is that listing's own `pageInfo.results`, read from its first page (`filter=pending`, 20) — never `GET /request/count`, which counts every request of the server; the header says no number before the listing answered. Rows, titles and paging are Mes demandes' (`SeerrRequestPages`, `SeerrRequestTitles`), plus « Demandé par Léa · il y a 2 h » (`requestedLine`, `Date.RelativeFormatStyle` in `loc.locale`). « Approuver »: one tap; « Refuser » asks first (« Refuser « titre » ? », `declineCandidate`, product owner 2026-11-08, recette Q1 — Seerr's page asks neither); in flight ⇒ the row's buttons wait (iOS: disabled, a spinner; tvOS: still focusable — disabling the focused one would throw focus — the pressed one reading « Approbation en cours… », the model ignoring any press; VoiceOver reads that busy text on both platforms, `SeerrPendingModel.buttonTitleKey`); done ⇒ the row leaves, N drops AND the next page's `skip` drops with it (`SeerrRequestPages.remove` — the server's listing is one shorter, so keeping `skip` passes over a request nobody saw); 409 (« Only pending requests can be approved or declined. », measured on 3.5.1, 2026-11-07) ⇒ the row leaves too, with an info toast « Déjà traitée »; any other failure keeps the row and says so; an account change mid-call writes and shows nothing. tvOS: the row's two buttons are its focus units, side by side under the text — the deliberate exception to the Settings « one focusable unit per row » RULE, since one row carries two actions — and once a row leaves, focus goes to the same button of the row taking its place (`focusAfterSettling`) — left to itself the engine sent it back to the page's back row after every press (measured on the tvOS simulator, 2026-11-07). Locked by `SeerrPendingTests`.
- **RULE — a FAILED first page of a Réglages → Demandes list records no « loaded for » trigger** (`myRequestsLoadedFor` / `pendingLoadedFor` are written only on `.loaded`, recette R30): the next re-presentation tries again, and meanwhile the section reads « Seerr ne répond pas pour le moment. » with a « Réessayer » row — which stays in place, its spinner turning, while it retries (on tvOS the pressed row must not vanish under focus).
- **RULE — the arrival message (`SeerrArrivalWatcher.check`, which RETURNS the toast; `AppNavigation` shows it) runs right AFTER the reload of `AppState.onCurrentUserRefreshed`, never on a trigger of its own**: that hook IS launch (restore → `refreshCurrentUser`) and every return to the foreground (the short hop, or `handlePossibleSessionExpiry` → `.valid`) — plus sign-in, switch and `UserUpdated`, one more `/request` each, harmless. It asks nothing unless `isVisible(proAllows:isOnline:)` (connected, enabled, Pro, online, not capped — an admin whose own switch is off hears nothing either) and ALWAYS passes `requestedBy=<my Seerr id>`, `filter=available`, `take=20`, `skip=0` (most recently modified first). The seen set is per ACCOUNT on this device (`seerr.arrivals.seen.<accountKey>`, request ids): **absent ⇒ the first check ⇒ seed, no toast** (a new device never announces a backlog; a stored `[]` does announce); read AFTER the fetch and written before any other await, so two checks racing (foreground + `UserUpdated`) cannot both announce; the current page first, capped at the newest 200. A title requested twice (two requests of one series) counts once. One arrival ⇒ « <Titre> est disponible »: the name `getItem(jellyfinMediaId)` gives (id checked by `AppState.isValidItemId`), else Seerr's `/movie` / `/tv` title, else the counted sentence for 1; its button is « Regarder » (`SeerrMyRequestsModel.watch` ⇒ `pendingDeepLinkItemId`) when Seerr knows the Jellyfin id, else « Voir » (an admin marking a title available by hand — `POST /media/{id}/available` — sets no Jellyfin id; measured on the bench, Seerr 3.5.1, 2026-11-07, where that call also moves the request, pending or approved, to `completed` and into `filter=available`, but a SERIES marked so stays out of it). Several ⇒ « 3 demandes sont disponibles » (`loc.counted`) + « Voir » = Réglages → Demandes (`SeerrArrivalWatcher.openRequests`: Settings sub-pages cleared, `.requests`, `pendingDeepLinkTabId = settings`, after `PlayerPresentation.dismissPresentations`) — measured on the iOS simulator from Accueil and from inside Réglages → Apparence (the pushed category is replaced, back returns to the landing). Either button does nothing once the account has moved (`isCurrent(snapshot)` at tap time). The toast never says « Seerr » (browse rule) and only iOS draws its button: the toast window takes no input on tvOS, where the arrived title waits at the top of Mes demandes with its « Regarder ». **The toast is BEST-EFFORT**: `ToastCenter` holds one toast, so a later toast replaces it and an arrival is then never shown again — accepted, since the seen set has already moved and the title waits at the top of Mes demandes with its « Arrivée dans ta bibliothèque ». Forgetting an account on this device (`SeerrSession.forgetAccount`) also drops its seen set (and its dismissed search invitation), so the account added back starts with a silent first check. Locked by `SeerrArrivalTests`.
- **RULE — NO arrival check while the launch has not decided who is watching** (`SeerrArrivalGate`, a process singleton on `AppNavigation`, held from the start). On an Apple TV opening on « Qui regarde ? » (`AccountSwitchFlow.showsLaunchPicker`: tvOS, signed in, `accounts.askOnLaunch`, Pro's remembered accounts, ≥ 2 of them) the session restored is the PREVIOUS profile's: checking it toasted that profile's arrival over the picker and spent its seen set before anyone chose. The decision is read from the picker's own inputs right after `restoreSession` — never from `showWhoIsWatching`'s timing, since the launch refresh races it — and no picker ⇒ release at once (every iOS launch). A hook check that comes while held is skipped (no fetch, no write) and remembered; `release()` then runs ONE — after `restoreSession`, or from the picker's `onFinished` (a profile kept). A profile switched to from the picker runs its own check through `refreshCurrentUser`; the seen set keeps the two from announcing twice. Same precedent as « Quoi de neuf », held back by `!showWhoIsWatching`. Locked by `launchPickerHoldsArrivals`.
- **RULE — « Actualiser » on Réglages → Demandes (owner 2026-11-08, mockup approved) re-reads « Mes demandes » AND « À valider » side by side (`RequestsSettingsScreen.refresh()`, a task group; « À valider »'s listing writes the bubble's count), shown only when one of the two lists is on the page (`showsRefresh`). **iOS / iPadOS: the page owns its scroll view, title and bar** (routed outside `settingsDetailView`'s wrapper, like Administration): `.refreshable` only reaches the scroll view it is set on. Two ways in — pulling the list down, and a trailing bar button (`arrow.clockwise`, Liquid Glass draws it, no `.glass` style) that turns into a `ProgressView` while a refresh runs, pulled or pressed (owner: « consistent with Apple TV »). **The pull is NOT awaited** (`.refreshable { Task { await refresh() } }`): awaited, the navigation bar did not redraw while the pull's own spinner ran — measured on the iOS 27.2 simulator, the button kept its arrow over the skeleton (a probe log confirmed `refresh()` had flipped the flag); the pull lets go at once and the bar button + skeleton carry the progress. **tvOS: no pull on a remote** — a row « Actualiser » / « Actualisation… » (spinner) FIRST under the back button, never `.disabled` while it runs (the busy RULE above): it keeps the focus while the lists turn to their skeleton, and still holds it when they come back (measured). **Loading = skeleton, never a spinner row**: both lists show `skeletonPanel` (poster + two lines per row, `SkeletonBlock`'s shimmer, accessibility label `seerr.settings.loading`, not focusable) on their first load and on every refresh; « À valider »'s header drops its count meanwhile. A retry keeps its failed panel. Bench recipe to SEE it (it flashes by locally): `docker pause seerr-spike`, refresh, capture, `docker unpause seerr-spike`.
- **RULE — an ADMIN's Réglages → Demandes is a summary with pages (owner 2026-11-09, layout A); anyone else keeps the single page.** On top, ONE card for the connection and its one useful action, decided by the pure `SeerrSummaryCard.of(url:connection:usesDeviceKey:)`: no address ⇒ a welcome card whose button opens « Serveur Seerr » and nothing else; signed out ⇒ « Se connecter à Seerr »; Seerr not answering ⇒ « Réessayer » (`seerr.reload`, still nothing ⇒ the connection test's `.unreachable` toast); key mode with no Seerr user / a refused key ⇒ the fix, no action, no request rows. Then « À valider » / « Mes demandes » (each only when it applies once connected; both GREYED with the reason while signed out or Seerr is down — who manages requests is Seerr's to say), then « Administration »: « Qui peut demander » and « Serveur Seerr » (Connexion with « Se déconnecter », the address and « Tester la connexion », Sur cet appareil). **The pages are the screen's own sections**: iOS pushes `RequestsSubpageHost`, a standalone view that runs the section inside its own body (so its reads of the shared `@Observable` models are tracked there; a change of the screen's `@State` redraws the screen, which hands the destination a fresh copy — measured: the test report, sign-out and the decline confirmation all redraw on the pushed page). tvOS draws the page in place (`SettingsNavCoordinator.requestsPage`). **The three list loaders and the account-change reset sit on the OUTER container (`lifecycle`)**, never on the summary: drawn in place, a page replaces the summary, and a `.task` there would be cancelled — `loadPendingIfNeeded` then records nothing and the page stays empty. The confirmations (`RequestAlerts`) are presented by the TOP page only (`isActive`): the covered summary presents nothing. Not reachable on the bench: the welcome card (no way to clear an address) — `summaryCard` locks the decision. Locked by `summaryCard`.
- **RULE — « Validation automatique » (owner 2026-11-08, proposal B): in « Qui peut demander », a user's row opens their ACCOUNT PAGE (`SeerrAccountPage`) — « Peut demander » (the Jellyfin switch, `SeerrActivationModel.toggle`) then Films / Séries, which write that user's SEERR permissions** (`POST /user/{seerrId}/settings/permissions`, read in Seerr 3.5.1's `usersettings` route and measured on the bench). The write is a read-modify-write of the WHOLE set — `GET` the same route first, change only `autoApprove` / `autoApproveMovie` / `autoApproveTV` (`SeerrPermissions.settingAutoApprove`: both ⇒ 128, one ⇒ its own bit), keep every other bit, 4K included (measured: 32|65536 + Films ⇒ 65824) — through `session.perform` with the ordinary credential (`.credential`, i.e. the admin's own session or key-as-user), NEVER `.lookup(.adminKey)`, which `makeRequest` confines to the two lookup routes. ONE write per user at a time (`savingAutoApprove`). The switches are offered only when the SIGNED-IN Seerr user `canManageUsers` (MANAGE_USERS, a Seerr admin passing) — never inferred from Jellyfin's admin flag — and shown locked with a sentence (`SeerrAutoApprovalAccess`) for a Seerr admin or request manager (Seerr approves them anyway: `MediaRequest` ORs `MANAGE_REQUESTS` in, which `SeerrPermissions.autoApproves` now mirrors), for the caller's own account (Seerr answers 403, as for its owner, id 1, always an admin), and while the user's « Peut demander » is off. iOS pushes the page (`navigationDestination(item:)` on the page's scroll view; a standalone view reading the shared `@Observable` model, the busy sets living in that model so the pushed page redraws). **tvOS draws it in place, its user id on `SettingsNavCoordinator.requestsUserId`, so the « ‹ Demandes » row closes the page before the category** (measured on the tvOS simulator: the row used to leave the whole category); Menu goes through `.tvBackAction`; closing puts focus back on that user's row. Not verified: the Menu button itself (the simulator tool cannot press it). Locked by `settingAutoApprove`, `autoApproveIsAReadModifyWrite`, `autoApproveRefused`, `autoApprovalAccess`.
- **RULE — the « À valider » bubble (owner 2026-11-08, proposal A, accent colour) sits on the Réglages TAB and on the « Demandes » entry of Réglages, for a Seerr manager only** (`SeerrSession.pendingBadgeCount`: `SeerrPendingModel.isShown` — connected AND `canManageRequests` — plus Pro and not age-capped; `nil` otherwise). Nothing at 0, « 99+ » past 99 (`SeerrPendingModel.badgeLabel`). The number is `pendingCount`, re-read by `refreshPendingCount()` (`filter=pending`, `take=1`, the listing's total — never `/request/count`) right after the `reload` of `AppState.onCurrentUserRefreshed` (launch, every foreground; NOT held by `SeerrArrivalGate`), and by `MainTabView`'s `.task(id: showsPendingBadge)` whenever the bubble becomes possible again (back online, sign-in, Pro or the age cap back), and written by « À valider » itself (`notePendingCount` after each page and after each approval / refusal — a 404 there is « Déjà traitée », the request was withdrawn) and after a withdrawal in Mes demandes (re-read, plus `SeerrPendingModel.forget` drops the row from « À valider »). `reset()`, `forgetIdentity` and a change of Seerr address forget it — a number kept across a lost identity came back unread (recette 2026-11-08). **Writes are ordered**: `pendingCountWrites` counts them, and a read that started before a fresher write drops its answer. No polling. A failed read keeps the last number. `showsPendingBadge` checks `servesActiveAccount` like `credential()` — LAST: `accountKey` is not observed, and putting it first short-circuited the reads of `connection` / `pendingCount`, so the bar never redrew when the count arrived (no bubble at launch until a tab switch, recette 2026-11-08). **Not verified**: a library menu resolving to >5 tabs puts Réglages in iPhone's « Plus »; whether the « Plus » tab then shows the bubble is untested (the simulator test was blocked on 2026-11-08) — likely not, as SwiftUI badges the row inside More. **Colour: SwiftUI's `.badge` is the system red, and `UITabBarItem.appearance().badgeColor` is IGNORED by the iOS 27 bar** (measured on the simulator): `MainTabView.TabBarBadgeTint` sets `badgeColor` (`accentContainer`) and the text colour (`onAccentContainer`) on the bar's own items, found from the window, on every change of colour or label. **The iPad's floating bar (iPadOS 18+) ignores both**: its badge is its own `_UIBarBadgeView` inside `_UIFloatingTabBarItemView`, painted system red — found by class name and recoloured through public `UIView` properties (`paintFloatingBadges`; a renamed class just leaves it red; stays accent through rotation and the sidebar toggle, recette 2026-11-08). The iPad SIDEBAR shows the count as plain grey text, the system's own style: left alone. **tvOS has no `.badge` on `Tab` at all**: the same helper writes `badgeValue` on the Settings item, and the tab's title gets trailing en-spaces (`tvTabTitle`) — the tvOS bar draws its badge OVER the end of the title (« Réglage① », tvOS 27.2 simulator). The Réglages entry draws `SettingsCountBadge` (it reads `\.dynamicTypeSize` so a live text-size change re-renders its computed point size — and so does `SettingsScreen`, or the row titles kept the old size beside a resized bubble: big titles + small bubble, or the reverse, recette 2026-11-08; inverted on the focused tvOS pill, whose fill is the accent) and reads « 3 demandes à valider » as its VoiceOver value (`seerr.settings.pendingBubble`). On an admin's summary the « À valider » row is always the first row and carries the same bubble (the listing's total, once loaded); a non-admin manager's single page lists « À valider » first. Locked by `badgeLabel` / `refreshReadsTheTotal` / `noBubbleForARequester` / `listingAndApprovalUpdateTheBubble` / `olderReadLosesToAFresherNumber` / `forgottenIdentityForgetsTheCount` / `withdrawalAndNotFoundLeaveTheQueue`.
- **RULE — « Se déconnecter » wins over anything in flight (review 2026-11-10).** `signOut` bumps `reloadPass` and cancels `pendingReSignIn`, and a silent re-sign-in runs — and stores its cookie — only while the stored cookie is still the dead one (`reSignInOnce`, `finishReSignIn`).

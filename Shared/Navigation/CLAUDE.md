## Navigation

- `AppNavigation` → Keychain session check → `apiClient.reconnect()` + `fetchServerInfo()`. Injects `ThemeManager`, `LocalizationManager`, `ToastCenter`, `MenuConfigStore`; applies `.preferredColorScheme()` at root.
- Flow: no server → `ServerSetupScreen` → `LoginScreen` → `MainTabView` (top tabs tvOS, sidebar iPad, bottom tabs iPhone).
- **RULE — the tvOS Menu button has ONE owner: `MainTabView`'s single `.onExitCommand`, fed by `TVBackPolicy` + `TVBackCoordinator` (`Shared/Navigation/TVBackNavigation.swift`). Never add a second `.onExitCommand` inside the tab content — an ancestor handler wins on tvOS, so it would simply never run.** Four properties of `.onExitCommand`, all measured on an Apple TV 4K simulator (tvOS 26.2) on 2026-08-31 with a purpose-built probe app, none of them derivable from the docs: (a) a handler on the `TabView` fires when focus sits on the **tab bar** — the reported bug's setting, since a page whose content runs out of focusable rows (`PersonDetailScreen`, whose header isn't focusable) lets an Up press escape there, and tvOS's default from the bar is to **quit the app**; (b) it *also* fires when focus is inside a **pushed** screen and it **swallows `NavigationStack`'s own pop**, so wanting any custom Menu behaviour at the tab level means owning the pop too — there is no "handle this case, leave the rest"; (c) the **ancestor wins**, which is why the two handlers that drove the tvOS Settings sub-navigation moved onto the coordinator (`.tvBackAction`); (d) passing **`nil`** restores the system default, i.e. suspends the app — the only way to express « réduire l'app », since `UIApplication.suspend()` is private. A presented modal is unaffected: it is its own presentation context and the `TabView`'s handler never sees its Menu presses (measured — the cover dismissed, the handler stayed silent), so every existing modal `.onExitCommand { dismiss() }` keeps working. The rule, in the user's own order: **something stacked in this tab → back one level, wherever focus sits; a main page other than Accueil → Accueil; Accueil itself → minimise.** `TVBackPolicy.decide` is pure and locked by tests. Registration rides `onAppear`/`onDisappear`, which SwiftUI drives exactly as needed (measured): pushing B fires `B.onAppear` **then** `A.onDisappear`, so at most one entry per tab is live and it is always the visible screen; popping fires `A.onAppear` then `B.onDisappear`; leaving a tab releases the entry and returning re-arms it, so a tab that still holds a pushed screen needs no bookkeeping on the switch — and `canGoBack(in:)` is per-tab, which is what stops Menu on Films from popping something on Accueil. **A screen that is ONLY ever pushed carries `.tvPushedScreen()` itself** (`MediaDetailScreen`, `PersonDetailScreen`, `FavoritesScreen`, `PlaylistDetailScreen`); **a screen that doubles as a tab root is marked at the PUSH SITE instead** (`LibraryFolderBrowseScreen`, pushed from Home's playlists rail), or it would register itself as its own root. `MainTabView` also clears each tab's registration when its root appears — a self-heal, because a stale entry would leave Menu doing nothing at all on that tab root, exactly the dead input this exists to remove. A new pushed screen that forgets the modifier falls back to "Menu jumps to Accueil", never to quitting. **The PRE-AUTH screens are the one place outside `MainTabView` that also needs a handler** — `ServerSetupScreen` and `LoginScreen` are roots rendered straight by `AppNavigation`, with no `TabView` above them, so `MainTabView`'s handler is not in the hierarchy and theirs is uncontested. Each mirrors its own escape hatch: `ServerSetupScreen` cancels an add in flight (`restorePreviousServer()`), `LoginScreen` does the same for an add **or** a pending re-login rollback, and both pass `nil` otherwise (nothing to go back to ⇒ suspend, the pre-existing behaviour). Without them, « Ajouter un serveur » from Réglages lands on the add screen and Back **quits the app**, stranding the user in add mode with only the on-screen « Annuler l'ajout » as a way out.
- **RULE — All play buttons use `PlayLink<Label>`** (Button+coordinator on tvOS, `NavigationLink` on iOS) — never direct `NavigationLink` to `VideoPlayerView`. **One exception: context-menu playback**, which cannot push a `NavigationLink` (the menu hangs off a card inside a lazy container — see the lazy-container RULE). It routes through `CardActionPresenter` instead: tvOS calls the same `VideoPlayerCoordinator` `PlayLink` would, iOS raises a root-hosted `.fullScreenCover` onto the same `VideoPlayerView`. Both engines and every controller are therefore identical; only the SwiftUI host differs.
- **RULE — card → fiche pushes zoom on iOS through `CardZoomTransition.swift`, never a bare `matchedTransitionSource` / `navigationTransition`.** Three parts: `.cardZoomSource(_:)` on the card's ARTWORK (`PosterCard` / `WideCard` take `zoomSource:`, `LibraryPosterCard` applies it itself — never the whole card, same reason the context-menu preview lifts the artwork alone), `.cardZoomDestination(_:)` on the pushed `MediaDetailScreen`, and a `CardZoom` value carrying both ends. **The `@Namespace` lives on the HOST screen that pushes** (Home, library, search, favourites, watched history, person filmography, the fiche's own carousels): cards sit in lazy containers and cannot own it. Host-local card helpers build `CardZoom(zoomNamespace, surface:itemId:)`; reusable cards (`LibraryPosterCard`, `SearchResultCard`, `MediaDetailSimilarSection`) read it from the `.cardZoomScope(_:surface:)` environment. **The source id is `surface|itemId`, never the bare item id**: one title routinely sits in several rails of a screen (Home's Recently Added + Favorites + genre rows, a film under two library genres, "Part of" + "Similar" on a fiche), and duplicate ids in one namespace zoom out of whichever card SwiftUI picks. **Motion-gated**: `motionEffectsEnabled` off ⇒ the default push; the setting is frozen at push time because the two branches are different view identities and a live flip would rebuild a fiche still in a tab's stack. tvOS compiles all three helpers to identity (no zoom there); the modal deep-link fallback and PlayLink cards (Continue Watching / Next Up play, they don't push) carry none. The `.contentShape(Rectangle())` RULE stays: the source sits after it.
- **Session expiry / 401 — confirm before logout (RULE)**: a single 401 must NEVER log the user out directly (cold-wake sockets, transient server hiccups, a flaky proxy all produce spurious 401s on a still-valid token — the Apple-TV "disconnected overnight" bug). `JellyfinAPIClient.setOnUnauthorized` → posts `.cinemaxSessionExpired`; `AppNavigation` now runs `appState.handlePossibleSessionExpiry()` which **silently re-validates** the token (`ServerAPI.validateSession()` → `GET /Users/Me`, returns `SessionValidity {valid|invalid|indeterminate}`) with a bounded 0/0.4/0.8s retry, **gated on `NetworkMonitor.isOnline`** (offline ⇒ never logout) and **debounced** (`sessionRevalidationInFlight`). Only a confirmed `.invalid` calls `logout()` + posts `.cinemaxSessionConfirmedInvalid` (the toast). `.valid` ⇒ `refreshCurrentUser()` and stay signed in; `.indeterminate` ⇒ keep session. Same coordinator drives proactive re-validation on `scenePhase .active` after a >60s background gap. Detection is the precise `JellyfinAPIClient.isUnauthorized(_:)` SSOT — pattern-matches `Get.APIError.unacceptableStatusCode(401)` (Get is a direct dep) + `JellyfinError.unauthorized` (raw PlaybackInfo POST) + `NSURLErrorUserAuthenticationRequired`; **never** the old `(401)` substring (false positives). 6 hot paths + `getPlaybackInfo` call `notifyIfUnauthorized`. **Keychain** items use `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (readable on tvOS cold-boot relaunch; `migrateAccessibilityIfNeeded()` one-shot re-saves legacy items in `restoreSession`). **VLC player** observes background/foreground: a stream that died during sleep re-resolves a fresh `getPlaybackInfo(engine:.vlc)` and resumes from `positionAtBackgroundMs` (`reResolveAndResume`) instead of a terminal error.

### Custom menu / dynamic tabs (`MenuConfigStore`)

`MainTabView` consumes `menuConfig.resolvedTabs` (a memoized `private(set)` stored cache of the resolution of `mode` / `customKind` / persisted entry arrays / `availableViews`; recomputed via `recomputeResolvedTabs()` at the end of every mutator that changes an input — `setMode`, `setCustomKind`, `toggleInternal`, `move`, `moveBy`, `reset`, `refreshAvailableViews`, `activate`, plus `init` — NEVER a `didSet`, per the `@Observable` RULE; the recompute is equality-guarded so an idempotent refresh fires no spurious re-render). Three modes:

- **`.default`** — the canonical 5 tabs (Home, Movies, TV Shows, Search, Settings).
- **`.custom + .contentType`** — user picks which of the canonical 5 are enabled and in what order.
- **`.custom + .library`** — user surfaces individual Jellyfin libraries (returned by `getUserViews`) as tabs, filtered to video-bearing kinds (`movies`/`tvshows`/`homevideos`/nil **plus `boxsets`/`playlists`** — see `LibraryView.nonVideoCollectionTypes` blacklist; `music`/`photos`/`livetv`/`trailers`/`folders` excluded). `boxsets`/`playlists` are folders-of-folders, so they route to a different destination (see Collections/Playlists RULE below), not the flat-grid `MediaLibraryScreen`.

- **RULE — `resolvedTabs` NEVER resolves empty** (`computeResolvedTabs` falls back to the canonical default 5 when the custom/library resolution comes up empty): `MainTabView` renders exactly this array, and zero tabs = a `TabView` with no content = a fully black screen with no recovery affordance. The empty state is reachable legitimately — a `.custom + .library` profile whose views have never been fetched (fresh login on a newly added server, offline launch). Locked by `MenuConfigStoreTests` ("never empty" tests).
- **RULE — the library-mode view refresh has ONE owner: `AppNavigation.onChange(of: appState.currentUserId)`** — it fires on every transition that establishes/changes the signed-in user (cold-launch restore — `restoreSession` sets the id from inside `.task`; fresh login; user switch), gated on `newId != nil && oldId != newId` + library mode. The `.task` deliberately does NOT refresh (it attaches + `activate`s only) — re-adding a refresh there double-fires on restore, and the historical "skip `nil → some`, `.task` owns it" guard was the post-login black-screen bug: a server whose profile carries no cached views never re-fetched them and the bar resolved to zero tabs until relaunch.
- **RULE — the menu configuration is PER SERVER** (`MenuProfile`, one per `ServerEntry.id`, all under the single `menu.profiles` key): mode, custom kind, both entry arrays AND the cached views. `MenuConfigStore.activate(serverId:knownServerIds:)` swaps the whole profile in; there is **no `invalidateViews()` any more** — wiping the library entries on a switch is precisely what used to destroy the user's arrangement (and rebuilt it through `mergeLibraryEntries(existing: [], …)`, which appends Home/Search/Settings **last** and ignores the 5-tab cap, so a 5-library server came back with 8 enabled tabs in the wrong order). Keyed by server, **not** by user: two accounts on one server share a profile and `mergeLibraryEntries` drops the libraries the signed-in account can't see. A new server starts from `MenuProfile.factoryDefault`, never inheriting the current one. `activate` also prunes profiles whose server left the registry — but **never when `knownServerIds` is empty** (that means "registry not hydrated", not "no servers"). Migration is one-shot, idempotent and non-destructive, keyed on "the profile dict is empty" (same pattern as `migrateToMultiServerIfNeeded`): the first activated server inherits the legacy global `menu.*` keys, which are then never read again and never deleted. `activate(nil)` (signed out) keeps the loaded profile — Settings is unreachable while signed out, and re-logging into the same server must find its menu intact; `persistActiveProfile()` is the single persistence path. **RULE — while NO profile is active, the store reads AND writes the legacy global `menu.*` keys, i.e. degrades to exactly its pre-profiles behaviour.** `activeProfileId` is nil only before the first successful activation, but that state is reachable *while signed in*: `migrateToMultiServerIfNeeded` returns early when its `saveServers` write throws, so `getActiveServerId()` stays nil while the legacy mirror still restores a session — menu editor reachable, nothing to key a profile on. Both halves are load-bearing: `init` seeding from `legacyProfileSeed()` is what stops the factory-default menu being shown over the user's own, and `persistActiveProfile()` falling back to those same keys is what stops an edit being lost in silence. Because the fallback destination IS the key `legacyProfileSeed()` reads, such an edit round-trips through `init` and is adopted by the first server that activates, via the existing one-shot migration — no second storage namespace, no new key. Unreachable on the healthy path (a profile, once active, stays active for the process).
- **RULE — `MenuConfigStore.maxEnabledTabs = 5` caps the enable-*toggle*, NOT the resolved tab count**: the cap drives `applyCap` + the toggle refusal (`ToggleResult.refusedCapReached` → toast) so the *editor* won't push a menu past 5 enabled entries via the in-app toggles. But `.custom + .library` menus can still resolve to **>5 tabs** in practice (several libraries surfaced alongside Home/Search/Settings), and iPhone `TabView` in compact width then falls back to `UIMoreNavigationController` (the "More" overflow). **That overflow is tolerated, not a bug** (product decision) — a settled >5 library layout renders and navigates fine; its quirks are cosmetic: each More entry keeps its own nav stack (a pushed detail is retained when you revisit the entry) and a Back press can pop several levels at once. The hazard the cap actually guards against is a **live mutation crossing the 5↔6 boundary while the bar is on screen** (`UIScrollView does not support multiple observers … removing old observer <UIMoreNavigationController>`, user dumped back to the first tab) — a static overflow config never trips it. Don't "fix" a library menu into ≤5 tabs on the cap's account.
- **RULE — Library-mode tabs accept `parentId: String?` + `overrideTitle: String?` on `MediaLibraryScreen`** so each library tab scopes its queries to that view id. `BaseItemKind?` is nilable on `MediaLibraryScreen`/`MediaLibraryViewModel`: `nil` means "no `includeItemTypes` filter" — needed for `Mixed`/`Other` libraries where Jellyfin items aren't reliably typed.
- **tvOS glass**: `.glassPanel()` is the surface for a panel that floats over content — the library top bar (which sits directly over ~700 pt of hero backdrop, where an opaque fill would cut a hard band across it), `LibrarySortFilterSheet`'s tvOS body (a modal, over a dimmed rather than opaque page), and the search field. **Settings rows deliberately stay opaque** (`tvSettingsFocusable` keeps `surfaceContainerHigh`): they sit over the settings landing's 1200 pt accent bloom, and glass there would let it through behind text that has to stay readable — unverifiable without a device, so not changed on a guess.
- **RULE — Collections (BoxSets) + Playlists are folders-of-folders → `ResolvedTab.Destination.libraryFolders`**, not `.libraryView`. `MenuConfigStore.libraryTab` detects `collectionType == "boxsets"|"playlists"` and routes to `LibraryFolderBrowseScreen` (lists the folders; tapping one pushes a scoped `MediaLibraryScreen(parentId:)` for its contents). The flat-grid `MediaLibraryScreen` can't be used directly here — its cards open item *detail*, but a boxset/playlist card must drill into a *folder*. These appear only in `.custom + .library` menus on servers that expose Collections/Playlists views; not always-on tabs (keeps the 5-tab cap / focus machinery untouched).
- **RULE — Don't tag a tab with `role: .search`** on iPhone in this app: per Apple WWDC 2024, a search-role tab is force-placed at the trailing edge of the bar regardless of declaration order, which conflicts with user-reorderable menus and was the source of "redirected to Search" after a drag. Search is a regular `Tab` here.
- **RULE — Use `Tab(value:)` over `.tabItem + .tag` on both iOS and tvOS**: the pre-iOS-18 `.tabItem + .tag` pattern doesn't preserve child-view `@State` across a `ForEach` collection diff on tvOS — every `MenuConfigStore` mutation was remounting `SettingsScreen` and dropping its sub-nav before this migration. `Tab(value:)` builds identity off the `value` and survives collection mutations cleanly.
- **RULE — Settings sub-navigation state lives on `SettingsNavCoordinator`, not `SettingsScreen.@State`**: tvOS's `TabView` is bridged to `UITabBarController` which indexes child view controllers by **position**. Any layout shift in the tab bar (toggle off, reorder, kind change) — even with `Tab(value:)` — recreates the `UIHostingController` for the tab whose position changed, dumping the SwiftUI `@State` inside. `selectedCategory` / `selectedInterfaceSub` are stored on `SettingsNavCoordinator` (`@MainActor @Observable`) instantiated on `AppNavigation` (which never remounts during normal usage) and injected via `.environment`. `SettingsScreen` exposes thin computed-property pass-throughs (`get`/`nonmutating set`) so call sites keep using `selectedCategory = X`; the `$`-projection cases use `@Bindable var nav = settingsNav` + `$nav.selectedCategory`. iOS doesn't exhibit the position-remount bug but uses the same coordinator for symmetry.
- **RULE — `MainTabView` tvOS bar renders from a `@State displayedTabs` snapshot; iOS renders `menuConfig.resolvedTabs` LIVE (never freeze iOS)**: on tvOS, rendering off the live `@Observable` reconfigures the UIKit-backed bar on every fine-grained edit, which pulls focus off the row the user is touching onto the top-bar active pill (reads to the user as a "page reload"). The tvOS snapshot is **frozen while `settingsNav.selectedInterfaceSub == .menu`** so toggle / reorder / library-refresh edits keep focus stable inside the editor; **structural** mutations bypass the freeze and refresh live: `onChange(of: menuConfig.mode)` (covers Reset which forces `mode = .default`), `onChange(of: menuConfig.customKind)` (entire entry set is being replaced), and `onChange(of: menuConfig.activeProfileId)` (a server switch loads a whole different profile). The bar catches up the moment the user backs out of the editor. iOS has no focus engine to disturb — freezing it too was itself a bug (edits looked like no-ops while the editor was open); the 5-tab cap keeps live iOS mutations inside `TabView`'s happy path.
- Persistence is explicit (`SettingsKey.menu*`) via mutator methods on the store, **never** through property `didSet` (see Architecture RULE on `@Observable`). `refreshAvailableViews()` is idempotent (`if views != availableViews { ... }`) to avoid spurious Observation cycles during user interaction. Mandatory IDs: `[settingsID]` only — Home and Search are non-mandatory but default-on.
- **MenuSettingsScreen tvOS Mode / Kind rows use a single `CinemaToggleIndicator`**, not two pills — same shape as `tvGlassToggle` in Apparence (Dark/Light Mode). Icon + label flip with state (`rectangle.stack.fill`/`Par défaut` ↔ `slider.horizontal.3`/`Personnalisé` ; `film.stack`/`Par type de contenu` ↔ `books.vertical.fill`/`Par bibliothèque`). Each toggle fires a `menu.refresh.confirm` toast on flip — the bar rebuilds (entries swap, focus jumps), and the pill is the only signal that explains the re-layout to the user. **Do NOT** toast on the "Refresh libraries" row: the row already conveys status via spinner + `lastFetchError` subtitle, a duplicate pill on every tap is noise. `MenuConfigStore.lastFetchError` stores the raw `(any Error)?` (the store has no `LocalizationManager`) and logs it; **both render sites map it through `loc.userFacingMessage(for:)`** — never render it verbatim (localization RULE).

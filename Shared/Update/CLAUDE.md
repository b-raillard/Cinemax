## Launch version check (`Shared/Update/`)

Asks the App Store at launch whether a newer build exists, and says so once per version. Four files, the usual split: `AppUpdatePolicy` (pure decisions), `AppStoreLookup` (the network hop + a pure parse), `AppUpdateChecker` (`@MainActor @Observable` — storage, throttle, platform capabilities), `AppUpdateAlert` (the root-hosted `AppUpdatePresentation` modifier).

- **RULE — every uncertainty resolves to SILENCE.** No network, a storefront that has never heard of this bundle id, a malformed answer, a version string neither side can parse, an app that cannot read its own `CFBundleShortVersionString` — all of them produce `.none`. An update prompt that appears *because a request failed* would be the worst possible outcome of a feature whose entire purpose is to be helpful once in a while, and it would stand between the user and the film they opened the app for.
- **RULE — the comparator is `ServerVersion`, never a second one.** It already knows `2.10 > 2.9`, which is exactly the mistake a hand-rolled comparison makes; the type is named for Jellyfin but is a plain numeric 4-component compare. **What is COMPARED and what is DISPLAYED are different values**: `AppStoreRelease` carries both a parsed `version` and the Store's own `displayVersion`, because `ServerVersion.description` normalises to four components and would show a `2.1` release to the user as `2.1.0.0`.
- **RULE — the throttle is on the QUERY, not on the decision.** `AppUpdatePolicy.shouldQueryStore` gates the network call at one a day, but the newest release is persisted (`update.latestVersion` / `update.latestStoreURL`) and the decision is recomputed locally at every launch and every foreground — so a standing offer survives the throttled day instead of vanishing for it, and a cold launch costs zero requests. The stamp is written **before** the await, or a slow or dead Apple would let every foreground in the meantime start its own lookup. A clock that moved backwards (timezone edit, NTP correction) re-opens the window rather than muzzling the check until the future catches up.
- **RULE — « Plus tard » suppresses THAT version and no other.** Declining one update is not a standing instruction to stop mentioning every future one. The refusal is stored as the `displayVersion` string, so a later release is a new question.
- **RULE — the mandatory switch is `AppUpdatePolicy.minimumSupportedVersion`, a dev-time constant (`nil` today), and `.required` may ONLY ever name a release that genuinely exists on the Store.** `decide` refuses to return `.required` unless the Store is actually ahead of the installed build — a floor raised above what the Store serves would otherwise lock the user out of an app they have no way to repair. That guard is what makes the constant safe to set in a hurry, which is precisely when it gets set. A required update is also un-dismissible by construction rather than by a separate surface: `AppUpdateChecker.decline()` acts on `.offer` alone, so a dismissal leaves the decision standing and the alert returns.
- **RULE — « Mettre à jour » renders only when this device can actually open the Store page (`AppUpdateChecker.storeURLToOpen`), on both platforms.** iOS opens the lookup's `https` page. tvOS has no browser and no `SKStoreProductViewController`, but its App Store app answers `com.apple.TVAppStore://itunes.apple.com/app/id<ID>`; the id is read from that same `https` page (`AppStoreLookup.tvAppStoreURL(for:)`, pure, locked by `AppStoreLookupParsingTests`), and the button exists only when `canOpenURL` says yes — which needs `com.apple.TVAppStore` in the tvOS target's `LSApplicationQueriesSchemes` (`project.yml`), or it always says no. The simulator has no App Store app, so there the alert keeps `update.tvos.hint` (where to update) instead of a button that would do nothing — the project's dead-button rule; the hint is shown ONLY when there is no button. In the `.required` case tvOS also offers « Réessayer », which re-runs the check so somebody who has just updated from the system App Store gets out without relaunching. No "you are leaving the app" confirmation: leaving for the Store is exactly what the button says.
- **RULE — the lookup names the user's own storefront and this binary's own bundle id.** `itunes.apple.com/lookup` answers `resultCount: 0` for a storefront that does not carry the app, so `country=<device region>` is what stops an app published outside the US from looking unpublished; and the id comes from `Bundle.main.bundleIdentifier`, never a literal — iOS and tvOS are `com.cinemax.ios` / `com.cinemax.tvos` and a hardcoded one would have a platform quietly reading the other's release. Own ephemeral, cache-less `URLSession` with **no auth header of any kind**, same discipline as `ServerReachability`: a 401 is structurally impossible, so nothing here can ever reach `notifyIfUnauthorized` and start a session-expiry cycle.
- **Placement**: the check runs from `AppNavigation`'s root `.task` **after `hasCheckedSession = true`** (an alert over the launch screen would interrupt a session still being restored) in its own `Task`, so the round-trip to Apple can never delay the launch it rides on; and again on `scenePhase == .active`, where it is free on the common path. The presentation is a root modifier like every other app-wide one. `AppUpdateChecker` is deliberately **NOT** one of the `AppNavigation` process singletons — it holds two `UserDefaults` reads and a throttled hop, so a scene-event recreation costs nothing, and the standing offer is re-derived from storage rather than held in memory.
- **An alert, not a toast**: `ToastCenter` is for feedback and recoverable errors; this asks for a decision.
- **Deliberately NOT shown: the Store's release notes.** That copy is written for the Store listing, and the app has its own curated account of a version — the "what's new" narrative belongs to the post-update journey, not to this alert.
- Locked by `AppUpdatePolicyTests` (the decision truth table incl. the never-lock-anyone-out guard, and the query cadence) + `AppStoreLookupParsingTests` (the wire shape, incl. a non-`https` link being dropped while the version survives).

## What's new after an update (`Shared/Update/`)

The first launch on a new version shows « Quoi de neuf » — one page per new feature, swipeable on iOS, explicit controls on both. Four files: `WhatsNewPolicy` (pure), `WhatsNewCatalogue` (the data), `WhatsNewScreen` (the pager), `WhatsNewIllustration` (the drawn motifs).

- **RULE — the content is DATA, not code** (`WhatsNewCatalogue.releases`): one entry per version, each page a `WhatsNewPage(id:illustration:)`. **`id` is both the page's identity and its localization key** (`whatsNew.<id>.title` / `.body`), so publishing a version is one array entry plus two strings in each catalogue — there is no per-version view to write and therefore none to forget to update. A feature is announced once in the app's life, so ids stay unique across releases (locked by a test over the shipped catalogue).
- **RULE — `WhatsNewPolicy.decide` has THREE outcomes, and `.stampOnly` is the load-bearing one.** A genuine first run and a version that ships no pages at all (a pure bug-fix release) must BOTH move `whatsNew.lastSeenVersion` forward without showing anything. Skip it and the NEXT version's launch hands the user everything accumulated since — including the announcements for the version they started on, which is exactly the "greeted as a newcomer" failure `shouldStampSeen` exists to prevent on the onboarding side.
- **RULE — `lastSeenVersion == nil` is NOT "first run".** It is also every install upgrading from a build that predates the reel, and showing them what changed is the entire point. The two are told apart by `isFirstRun` — `OnboardingPolicy.shouldShow(...)`, computed in `AppNavigation`'s `.task` **from the very inputs the branch in `body` reads**, so the screen the user is about to see and the decision taken cannot disagree. The two screens answer one question between them and must never both speak; note `onboardingSeen` has already been latched by `shouldStampSeen` at that point, which is what makes an upgraded install « not a first run » and therefore the reel's audience.
- **RULE — the stamp is the INSTALLED version, never the newest entry in the catalogue.** An entry written while preparing the next version — the ordinary way a version is prepared — would otherwise silence the very announcement it was written for. For the same reason `WhatsNewCatalogue.pages` **excludes releases newer than this build**.
- **Ordering**: newest release first, capped at `maxPages` (6), so the cap drops the OLDEST pages — somebody who skipped three versions wants the latest, not a history lesson. The lower bound is exclusive (the version already seen contributes nothing).
- **RULE — the pager is `OnboardingScreen`'s, reused rather than reinvented**: one switched page plus explicit controls on both platforms, with the iOS swipe added on top. `PageTabViewStyle` does not exist on tvOS and a swipe is not an input there, so a `TabView` pager could never serve both — the app already answered this question once. The accent CTA takes focus on every page change, same reason. Its tvOS Menu handling is simpler than the onboarding's and needs no shared helper: this screen is ALWAYS dismissible (it is never the only thing between the user and their server), so Menu is « back one page, else out » with no `nil` branch. It shares the onboarding's iOS footer rule (equal slots, two buttons); « Passer » is tvOS-only here, since the iOS sheet's close button already does exactly that.
- **RULE — the illustrations are DRAWN (`WhatsNewIllustrationView`), never screenshots.** A captured screen goes stale at the next UI change and has to be re-shot per platform, per theme, per accent — which is how a "what's new" screen ends up showing an interface the user is not looking at. Same 100 × 100 grid convention and the same register as `CinemaIllustration` (accent halo, neutral tiles, one accent gesture, no strokes), but deliberately a SEPARATE enum: `CinemaIllustration` is the vocabulary of empty and error states, and folding feature art into it would make "which of these may an empty state use?" unanswerable from the type.
- **RULE — Presentation goes through `whatsNewPresentation` (`WhatsNewScreen.swift`), used by BOTH hosts: an iOS `.sheet`, a tvOS `.fullScreenCover`.** It was a full-screen cover on both platforms (« a moment, not a settings detail »); on a phone that read as a page the user had been sent to, so iOS now presents the app's usual sheet with the accent `xmark` close button top trailing (the `QuickConnectSheet` idiom) and a scrolling page body, centred when short, so a long body or a large Dynamic Type size stays readable. Closing it — the button, or a swipe down — goes through the binding's setter and therefore stamps exactly like finishing the reel. A tvOS `.sheet` renders cramped, and Menu is its close. Root-hosted, gated on `appState.isAuthenticated`, so an upgrade that lands on the login screen shows it once the user is actually in rather than over the sign-in form. The environment is re-injected by hand (a presentation is its own context and does not carry injected `@Observable` objects down — same reason `SettingsScreen.onboardingSheet` does it). `AppNavigation.finishWhatsNew()` is the SOLE writer of the stamp-and-close pair, so the reel finishing and the sheet being dismissed can never disagree.
- **Replay**: Réglages → Serveur → « Nouveautés », beside « Découvrir l'app ». It shows `WhatsNewCatalogue.allPages()` — the WHOLE catalogue, not this user's remaining slice — and **stamps nothing**: somebody who asks for it has not just updated, they are looking something up.
- Locked by `WhatsNewPolicyTests` (the outcome truth table, incl. downgrade and the silent-stamp cases) + `WhatsNewCatalogueTests` (the unreleased-entry guard, ordering, the cap, the exclusive lower bound, unique ids in the shipped catalogue).

## Admin (iOS-only — product decision)

`SettingsCategory.visibleCases(isAdmin:isTVOS:)` short-circuits when `isTVOS`; every `Shared/Screens/Admin/` file `#if os(iOS)`.

- **Gating**: `AppState.isAdministrator` (cached; refreshed on login/reconnect/user switch via `AppState.refreshCurrentUser()`). Server authoritative; client gating is UX. `AppState.currentUser: UserDto?` populated alongside.
- **RULE — Watch Together is granted PER USER by an admin, through the server's own `UserPolicy.syncPlayAccess`, never an app-side flag** (Admin → Users → *Accès* → « Regarder ensemble », a three-way `Menu` row mirroring the parental-rating one). Consequences that make this the right control rather than a convenience: the choice holds for **every Jellyfin client** the account uses, not just Cinemax; it needs no storage of our own; and it is the same value `LiveSessionsRow.canJoin/canCreate` read, so the admin screen and the feature cannot disagree. Setting it to `None` removes the whole « En direct » row for an account that also lacks the second permission below, which is what makes the social surface fully switchable per account for App Store review. The picker shows an absent value as `None`, matching `canJoin(nil) == false`: it must not claim a permission the app itself refuses to assume. Note `AdminUserDetailViewModel.save` posts the WHOLE policy (read-modify-write off the loaded user), so the new field rides along and nothing else is cleared.
- **RULE — the second per-user permission, « Voir En direct », rides `UserPolicy.enableRemoteControlOfOtherUsers`, and the coupling that comes with it is deliberate and documented, not an oversight** (`LiveSessionsRow.canSeeOthers`, Admin → Users → *Accès* → « Voir « En direct » »). It governs the `/Sessions` half of the row — the « untel regarde seul » cards — and the lobby's list of people to notify. **The gate it replaces was Cinemax's, not Jellyfin's**: `GET /Sessions` and `POST /Sessions/{id}/Message` both declare `DefaultAuthorization`, so reserving them to administrators was this client's own choice, taken because the endpoint hands out every account's activity and on some servers ignores its own `controllableByUserId` filter (jellyfin#5210). The answer is to govern it per user rather than keep it shut. Jellyfin models nothing narrower than "may act on other people's sessions", so **granting the view also grants remote control** — the admin footer says so in as many words, and the alternative (an app-side per-user flag) would need a shared store the server does not offer without a plugin. Two consequences to know: the server's own default for this flag is **false**, so on an untouched server the solo cards and the notify list stay hidden until an admin grants them — while the row ITSELF is on by default for everyone, since its group half rides `syncPlayAccess`, whose Jellyfin default is `CreateAndJoinGroups`; and an **absent** policy resolves to `false`, the same "unknown means unsupported" discipline as `canJoin` and `ServerVersion.serverSupports`. **RULE — the permission is only half of it: a NON-ADMIN's `GET /Sessions` MUST name the account as `controllableByUserId`** (`LiveSessionsRow.sessionsQueryUserId`, consumed by `HomeViewModel.loadActiveSessions` and `WatchTogetherLobby.loadInvitees`; `AuthAPI.getActiveSessions` carries the parameter). Jellyfin's `SessionManager.GetSessions` (verified on `release-10.10.z`, `release-10.11.z` and master) applies `EnableRemoteControlOfOtherUsers` **only inside its `controllableUserToCheck` branch**; the bare query takes the other branch — « request isn't from administrator, limit to "own" sessions » — whatever the policy says. So the client asked with the right permission and the wrong shape, got an answer holding only itself, filtered itself out, and drew nobody: found 2026-09-07, an administrator watching a series invisible from a non-admin account holding every permission. An administrator keeps the unfiltered shape (the controllable branch also drops sessions that never declared `SupportsRemoteControl`, and an admin is entitled to the whole list). **And `SupportsRemoteControl` is NOT a declaration — it is a declaration AND a live socket** (`SessionInfo.SupportsRemoteControl` reads `Capabilities.SupportsMediaControl` *and* asks every attached session controller, where `WebSocketController.SupportsMediaControl => HasOpenSockets`; verified on jellyfin `master` 2026-09-13). So a regular account sees a session only while its client is HOLDING an open socket: this app publishes the capability and opens one on foreground and drops it on background by design, which is why a backgrounded Cinemax reports `false` on BOTH flags and is absent from the row, while a playing one — necessarily foregrounded — is there. Same rule for everyone else: a client that never posts capabilities, or a Cinemax whose « Lire sur… » target toggle (`playback.remoteControl`) is off, is invisible to non-admins by the server's rule, not ours — and only devices its own device-access policy allows are listed at all. **Measured end to end on the reference server 2026-09-13** with a real non-admin account: before the permission the row showed nobody; after it, the same account saw every live session, including a Jellyfin Android TV mid-playback (`SupportsMediaControl = true`), while the backgrounded Cinemax next to it read `false`. The permission is the half an administrator grants; the open socket is the half the WATCHED client has to hold. A report saying « the admin sees everyone, a regular user sees nobody » is one of those two and nothing else — read `/Sessions` twice, bare then with `controllableByUserId`, and the pair of answers says which. Locked by `LiveSessionsRowTests.sessionsQueryShape` + `HomeViewModelTests.liveRowQueriesSessionsAsControllable`.
- **API surface**: `AdminAPI` slice. Device listing/revocation stays on `AuthAPI` (server returns full fleet to admins by caller identity).
- **Settings routing**: `.administration` (Dashboard + Metadata Manager) and `.advancedAdmin` (Users/Devices/Activity/Playback/Plugins/Catalog/Tasks/Network/Logs/API Keys). Hidden when `!isAdministrator`.
- **Scaffolds** (`Admin/Components/`): `AdminLoadStateContainer`; **RULE — `AdminFormScreen` every admin editor uses explicit save (never auto-save)** — admin changes have blast radius (policy revocations, password resets); sticky footer + `interactiveDismissDisabled(isDirty)` + discard confirmation. `AdminTabBar`, `AdminSectionGroup`. `AdminItemMenu` — shared `Menu` for one `BaseItemDto` (Identifier/Edit/Refresh/Delete); **does NOT host its own `.navigationDestination`** (silently ignored — lazy-container rule), fires `onSelectDestination(_:)`. `DestructiveConfirmSheet` (type-to-confirm) reserved for irreversible ops; reversible destructives use `.confirmationDialog` `.destructive`.
- **RULE — the type-to-confirm phrase is compared through `ConfirmPhrase.matches`, NEVER a raw `caseInsensitiveCompare`** (`Packages/CinemaxKit/.../Models/ConfirmPhrase.swift`): iOS rewrites the apostrophe the user presses into its typographic form as they type (`'` → `’` — smart punctuation, which **`.autocorrectionDisabled()` does not turn off**, as `GlassTextField` already carried), so a title Jellyfin spells `L'Odyssée` arrived here as `L’Odyssée`, the compare failed, and the confirm button stayed disabled **for ever** — with nothing on screen to say why and the two glyphs a few pixels apart. Every title carrying an apostrophe was undeletable, which in a French library is a large share of them. The hazard runs both ways (a title stored *with* the typographic form can only be typed with a straight one) and is not limited to quotes: French metadata routinely carries a narrow no-break space before a colon (« Mission : Impossible ») that no keyboard produces. So both sides are folded — quote and dash forms normalised, whitespace runs collapsed — then compared case- **and diacritic**-insensitively; this is a *confirmation* control, not an authentication one, so an English keyboard must not make a French title undeletable, and typing the title out is friction enough. A `required` phrase that normalises to nothing can never be confirmed (an empty field must never read as assent). The sheet also renders an explicit `admin.destructive.mismatch` line: the button coming alive was the only signal that the phrase took, and **nothing explained its absence**, which is precisely why the defect was reported as "the delete button does nothing". Its detent is `.large`, not `.medium` — medium clipped the confirm button below the fold, and the keyboard the sheet always raises took what was left. Locked by `ConfirmPhraseTests`.
- **Self-protection** (client-side; server enforces too): can't delete/demote/disable yourself; can't revoke current device (`KeychainService.getOrCreateDeviceID()` vs `DeviceInfoDto.id`, "THIS DEVICE" pill).
- **Performance**: Dashboard `async let` fan-out (partial render on single failure). Activity log infinite-scroll (50/page). Tasks live-poll 2s while running, self-cancels.
- **Identify flow** (`Admin/Identify/`): `IdentifyFlowModel` (`@Observable`) — standalone `IdentifyScreen` (form → grid → confirm) + composed in `MetadataEditorViewModel.identify`. Kind-aware (movies: IMDb/TMDb Film/TMDb Coffret; series: IMDb/TMDb/TVDb). Provider IDs under `"Imdb"`/`"Tmdb"`/`"TmdbCollection"`/`"Tvdb"`.
- **Metadata Manager**: five-tab editor (General/Images/Cast/Identify/Actions). Images use `downloadRemoteImage` (server fetches URL, no phone proxy). Delete via `DestructiveConfirmSheet` (title as confirm phrase).
- **RULE — « Identifier » and the artwork picker are DIFFERENT tools, and conflating them is the trap this feature exists to close.** Identify fixes *which work this is*: `ApplySearchCriteria` sets the provider ids and re-runs a full refresh, after which the **providers re-pick artwork by their own ranking** (language + provider order). The poster shown in Identify's result list is a **disambiguation preview from the search provider and is NEVER the image applied** — measured on device 2026-08-29: the `primaryTag` changes on every apply (`58f68…` → `6c170…`, i.e. the artwork really is re-downloaded, and an apply overwrote a hand-set poster), yet TMDb re-picks the same poster each time, so re-identifying an already-correct film is a no-visible-op. Choosing a SPECIFIC image is `MetadataRemoteImagePicker` (`GET /Items/{id}/RemoteImages` → `AdminAPI.getRemoteImages`), reached from Images → *Remplacer* / *Ajouter*; before it the app could only set artwork by pasting a URL, so any poster a user could see in Jellyfin's web UI was unreachable here. The URL entry survives inside the picker (« Par URL… ») — it is the only way in for artwork no provider lists. **RULE — Identify APPLIES the artwork of the result the user picked** (`IdentifyFlowModel.apply`): after `applySearchCriteria` returns, it calls `downloadRemoteImage(type: .primary, imageURL: result.imageURL)`. Jellyfin does NOT do this on its own — which is why picking the elephants poster over the Anthony Mackie one changed nothing — and "the poster I chose becomes the poster" is the only reading of that screen a user can have. **Order is load-bearing**: it runs AFTER the apply, because the server's own artwork download lands *during* `applySearchCriteria` and would overwrite ours. **Gated on `replaceAllImages`** — unticked means "keep my images", so forcing ours there would be the setting's exact opposite; a custom poster therefore still survives an Identify with the box unticked. A result carrying no `imageURL` applies metadata only and still succeeds; a FAILED artwork download fails the whole call rather than toasting a success over an unchanged poster, which is the defect this closes. Locked by `IdentifyAppliesChosenArtworkTests`.
- **RULE — the picker's ordering is the pure, unit-tested `RemoteImageCatalog.rank`** (`Packages/CinemaxKit/.../Models/RemoteImageCandidate.swift`), same discipline as `MediaSourceQuality`: language tier (preferred → **textless** → other — textless art is usable in any locale, a third language is not) → community rating → vote count → resolution → url. The order is **total** (it falls through to `url`) precisely so two loads of the same server response can't reshuffle under the user's finger. `RemoteImageCandidate` is a **scalars-only `Sendable` value type, never the SDK's `RemoteImageInfo`** — the ranking is `nonisolated` and the picker is `@MainActor`, so a non-`Sendable` SDK type crossing that boundary would be a region transfer (same rule as `LibraryAPI.fetchUserData` / `CardPlayTarget`). Blank urls are dropped and duplicates collapse, because the download endpoint addresses artwork **by url** — a tile without one could never be applied. Locked by `RemoteImageCatalogTests`.
- **RULE — the three image paths re-fetch through `reloadImages`, NOT `reloadItem`: an artwork change must not discard the user's unsaved General/Cast edits.** Both re-fetch the item — the image tags bust `CinemaLazyImage`'s URL-keyed cache — but `reloadItem` overwrites `original` as well as `item`, so `isDirty` fell back to **false** and a pending title/synopsis/cast edit vanished **in silence**, with `interactiveDismissDisabled(isDirty)` no longer guarding the sheet either. Pre-existing, but `MetadataRemoteImagePicker` made it the ordinary path rather than an edge. `reloadImages` splices only the fields an image mutation on THIS item can move (`imageTags`, `backdropImageTags`, `screenshotImageTags`, `imageBlurHashes`, `primaryImageAspectRatio` — a new poster of different proportions moves the last one, and a stale value mis-sizes every card); the `parent*`/`series*`/`album*` tags describe another item's artwork and are deliberately left alone. **It splices into `original` as well as `item`**, or the fresh tags would themselves read as unsaved changes and the editor would keep claiming them after the user had reverted everything by hand. A clean editor still takes the whole fresh DTO, i.e. exactly the previous behaviour. **`applyIdentifyResult` keeps the full `reloadItem` on purpose** — Identify is the user asking the server to rewrite title, overview, cast and provider ids, so unsaved edits there describe the identification they just discarded. Locked by `MetadataEditorEditPreservationTests`.
- **RULE — every image mutation posts tier-1 `.cinemaxShouldRefreshCatalogue`** (`applyRemoteImage`, `addImageFromURL`, `deletePendingImage`). `save`/`deleteItem` always did; the three image paths did not, so changing artwork told no one and Home / la bibliothèque kept the old poster until a relaunch — the same class of gap as the detail screen's missing tier-1 observer (PR #126). Artwork is catalogue *content*, so tier-2 cannot serve it: the image cache-buster tag moves, which is exactly what tier-1 exists to announce.
- **ImageType quirk**: CinemaxKit's `ImageType` narrower than `JellyfinAPI.ImageType`. Admin code uses `JellyfinAPI.ImageType` explicitly-qualified; `ImageURLBuilder.imageURLRaw(itemId:imageTypeRaw:)` string-keyed overload renders the wider set without widening `CinemaxKit.ImageType`.
- **RULE — API key security** (`Admin/ApiKeys/`, keys = passwords): masked by default (first 4 + last 4); `.privacySensitive()`; the hardened `copyToken` (`UIPasteboard.setItems` + `.localOnly` + 60s `.expirationDate`) is the only export path — no share sheet, and **never `.textSelection(.enabled)` on a token `Text`** (a long-press Copy there writes the raw token to the GENERAL pasteboard: no expiry, syncs via Universal Clipboard, bypassing `copyToken` entirely); `appState.accessToken` match → `CURRENT SESSION`, revoke hidden; `revokedKeyIds`/`revealedKeyIds` dropped on disappear. **Never log key values or send to analytics.** `revokeApiKey` takes the token itself as identifier (Jellyfin quirk); forget value on return.
- **RULE — a field Jellyfin 12.0 marks `[Obsolete]` is REMOVED from the admin UI (or version-gated), never merely left to warn.** Three were handled on 2026-09-10, and the split between them is the point. **Removed outright**: `SystemInfo.operatingSystem` / `operatingSystemDisplayName` (`"This is no longer set"`, serialised as `""`) and `systemArchitecture` (`"This is no longer set"`, a hardcoded `"X64"`) drove the Dashboard's OS and Architecture rows. Each was worse than absent rather than merely stale — an empty string is **non-nil**, so the OS row's `?? "—"` placeholder never fired and it rendered blank, and the architecture row reported x86 on an ARM server with full confidence. 10.x populates both, so this trades a real row on old servers for the absence of a lying one on new; a version gate was judged too much machinery for two cosmetic read-only rows, and their `admin.dashboard.operatingSystem` / `.architecture` keys were dropped from both `.strings` files. **Version-gated instead**: `NetworkConfiguration.enableUPnP` (`"No longer supported"`) is a real, working control below 12.0 — the server genuinely forwards the port — so Network → Features renders it when `apiClient.knownServerVersion()` is **known** and `< ServerVersion.upnpPortForwarding`, and hides it on 12.0+ **and on an unknown version** ("don't offer a switch we can't promise does anything"). Either way the stored value survives: the network save is a read-modify-write of the whole configuration.
- **RULE — `ServerAPI.knownServerVersion()` is what the UI layer asks; `serverSupports(_:)` stays internal to CinemaxKit.** The internal helper collapses "too old" and "not learned yet" into one `false`, which is right for a gate on a feature a NEWER server adds. `upnpPortForwarding` is the opposite shape — the feature exists BELOW the threshold — so its gate has to see the `nil` and treat it as "hide", which a `Bool` cannot express. The accessor is a plain lock-guarded read with a `nil` default on the protocol (mocks compile unchanged). It is **not** observable: the version is learned at connect / session restore, long before an admin can reach this screen, so a row that appears only on the next visit is not a case that occurs in practice.
- **RULE — a deliberate deprecated-SDK read is contained in a view whose `body` carries `@available(*, deprecated)`** (`UPnPToggleRow`, `AdminNetworkScreen.swift`). Swift has no pragma to silence one deprecation: the only suppression the language offers is that a reference made INSIDE a deprecated declaration is not flagged, and wrapping the read in a deprecated helper merely **moves** the warning to that helper's call site. The chain terminates only at a declaration nothing in our own code calls — a protocol witness. `body` is that witness (SwiftUI calls it, we never do), so the warning stops there and the annotation doubles as the explanation of why the read is intentional. The `Binding` must be built **inline inside `body`**: a separate computed property sits outside the deprecated context and warns again. Verified with a standalone `swiftc -swift-version 6` probe before adopting, both for the propagation and for the witness terminating it.
- **Poster-card admin overlay**: `LibraryPosterCard` paints ellipsis `AdminItemMenu` bottom-right when `isAdministrator`. Menu and detail-push `NavigationLink` are `ZStack` siblings (not nested).

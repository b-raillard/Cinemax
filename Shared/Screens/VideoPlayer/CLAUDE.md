## Video Playback

### Playback engine (VLC default — fixes the MKV/Dolby-Vision freeze)

Online playback defaults to VLC on iOS + tvOS. Settings → Playback **"Use Native Player"** (`SettingsKey.forceNativeAVPlayer`, default `false`) falls back to `AVPlayer`/`NativeVideoPresenter`.

**Why:** `AVPlayer` can't open MKV → Jellyfin forced into a 4K HEVC + DV→SDR re-encode the server can't do real-time → frozen playback. No `AVPlayer` device profile makes Jellyfin remux DV-in-MKV (DV only passes through on DirectPlay/DirectStream, never in a transcode). VLC DirectPlays the raw file → zero server transcode, 4K/HEVC/DV preserved.

- **RULE — Device profile split** (`JellyfinAPIClient+Playback.swift`): `getPlaybackInfo(... engine:)`. `.vlc` → `buildVLCDeviceProfile` (one broad DirectPlayProfile, **no container restriction** → `/Videos/{id}/stream?static=true`, no transcode). `.native` → `buildAppleDeviceProfile` (AVKit-safe codec profiles). **API default is `.native`** so internal AVPlayer-only calls are unaffected; engine chosen explicitly at `VideoPlayerCoordinator` (tvOS) / `VideoPlayerView` (iOS) from `forceNativeAVPlayer`.
- **Server-side escape hatch** (`scripts/remux-seek-heavy.sh`, ops tooling — not shipped in any target): inventories and losslessly remuxes seek-heavy containers to Matroska so Jellyfin DirectPlays them and the forced-transcode path below never fires for them. Dry-run by default, never deletes the source, validates every output (duration/stream-count/full decode pass) and deletes it again on failure. Its extension list must stay in sync with `isSeekHeavyContainer`. `--self-test` verifies the pipeline where a real ffmpeg exists.
- **RULE — a bare hvcC MKV forces SOFTWARE 4K decode on the VLC path** (`scripts/remux-bare-hvcc.sh` is the cure): some WEB-DL rips store the HEVC parameter sets in-band only — the Matroska CodecPrivate is a 23-byte hvcC with `numOfArrays = 0`. libVLC's videotoolbox decoder passes that hvcC **verbatim** to `VTDecompressionSessionCreate`, which fails (OSStatus **-4**, seen as `unknown vt session error (-4)` in the logs / `vdec avcodec` in the stats HUD) → software HEVC decode + swscale `I0AL→BGRA` per 4K frame → the A15 Apple TV drops/lates frames continuously while ffmpeg-based players (and beefier iPhones, by brute force) play the same file fine. Proven on-device 2026-08-05 (« 72 heures », Netflix WEB-DL). Fix is server-side: remux through the **raw HEVC ES** so mkvmerge rebuilds the CodecPrivate — **a plain mkvmerge MKV→MKV passthrough copies the defective hvcC verbatim** (verified; that trap is why the script exists). The fixed file keeps its exact filename so the Jellyfin item / watched state survive. Real fix belongs upstream in libVLC (videotoolbox should late-start when the extradata carries no parameter sets — `LateStartHEVC` only tests `i_extra == 0`); not reported yet.
- **RULE — seek-heavy containers force a server HLS transcode on the VLC path** (`isSeekHeavyContainer`: `avi/divx/wmv/asf/flv/vob/mpg/mpeg/mpe/m2v`): these keep their index at EOF, storming libVLC/origin with byte-range requests (raw AVI/XviD froze on the reverse-proxied server on BOTH direct and loopback-proxy paths — true remux impossible for XviD). On failure the code falls back to the raw stream. **RULE — the decision is made BEFORE the first `PlaybackInfo` POST**, off the container `getItem` already carried into `initialMediaSource` (`resolvePlayableEpisode` re-`getItem`s the resolved episode, so series/seasons carry it too). Reading it off the *response* instead — which is what the code did originally — cost every seek-heavy item two full round-trips (negotiate, discover the container, re-negotiate). The post-response check survives ONLY as the fallback for an item whose `getItem` carried no source/container; don't "simplify" it away, and don't move the decision back after the POST. **RULE — `_vlcTranscodingProfiles` asks for `container: "ts"` (MPEG-TS segments), NEVER `"mp4"` (fMP4)**: libVLC's MP4 demuxer probes the fMP4 init segment, finds no chunk table (`no chunk defined` / `STTS table of 0 entries` — normal for fragmented MP4, whose samples live in each media segment's moof), concludes `that media doesn't look interleaved, will need to seek`, and then random-accesses *inside every segment*. Over HTTP/2 that is one cancelled stream after another (`local stream N error: Cancellation (0x8)`, hundreds per session) and playback crawls — measured at ~9 s of picture in ~3 min on a server whose `hevc_qsv` job had already finished encoding the whole episode, i.e. **not** a transcode-speed or bandwidth problem (the same server DirectPlays 4K MKV). TS is a linear byte stream with no such structure to probe. **Neither transcoding profile sends `isBreakOnNonKeyFrames` any more** (removed 2026-09-10): Jellyfin accepts the field and **ignores** it ("Current HLS implementation doesn't support non-keyframe breaks") and 12.0 deprecates it, so it was describing a capability nobody reads. The SDK models it non-optionally (`Bool`, defaulted `false`), so dropping the argument does change the wire value from `true` to `false` — on a field the server ignores. Don't re-add it. **`_vlcTranscodingProfiles` sends `minSegments: 1`, deliberately**: Jellyfin's `WaitForMinimumSegmentCount` holds the playlist back until that many segments are actually ENCODED, so each one is real ffmpeg time before the first frame — raising it back to 2 doubles the pre-roll of every forced-transcode AVI for no benefit (`:network-caching=8000` already covers the buffer). **The forced-transcode profile (`buildVLCTranscodeProfile` → `_vlcTranscodingProfiles`) deliberately OMITS `mp1`/`mp2`/`mp3` from its `audioCodec` allow-list, precisely to FORCE the server to re-encode audio to AAC** — when the video is transcoded but a source MPEG-audio track is *copied* into the fMP4 HLS segments, MP3's encoder delay/priming is never re-timed against the new video, giving a constant audio offset (the "son décalé" on transcoded AVI/XviD); AAC muxes cleanly into fMP4 and stays locked to the re-encoded video. **Don't "widen" that list** — re-adding MPEG audio reintroduces the desync. The broad allow-list that DOES carry `mp1,mp2,mp3` is the separate **DirectPlay** profile (`_vlcDirectPlayProfiles`, used by `buildVLCDeviceProfile`), where nothing is re-encoded and copying is exactly the point — different profile, opposite goal.

Object-based track selection (no silence bug); **RULE — a USER audio-track switch goes through `selectAudioTrack(_:)`, which re-anchors playback with an `engineSeek` to the switch position, never a bare `player.selectedAudioTrack = …`**: libVLC has already demuxed `:network-caching` (8 s) worth of the stream past the playhead and dropped the packets of the track that was not selected then, so the new decoder only gets data from the demuxer's current position — the picture ran on for those seconds with no sound at all (measured on device 2026-09-04). The seek makes the demuxer re-deliver both tracks from the switch position; the picture holds under the seek settle spinner and resumes with sound, from where the user switched. Gated on `mediaConfirmedOpen` and skipped when the track is unchanged; the open-time server default (`applyServerTrackDefaultsIfNeeded`) stays a bare assignment since nothing has been demuxed past the playhead yet. **A subtitle switch goes through `selectSubtitleTrack(_:)` and re-anchors the same way when a track is turned ON** (a freshly enabled track otherwise stays blank for the whole caching window); turning subtitles OFF re-anchors nothing, there being no data to recover. Jellyfin defaults applied once on `.tracksChanged` by ordinal-within-type — **through `AudioTrackPolicy.defaultOrdinal`, never `info.selectedAudioIndex` verbatim; see the RULE below**. **libVLC 4.0 has no distinct `.ended`** — end-of-media is `.stopped`, disambiguated via `isTearingDown` flag + `lastPlayStart` (>1s) + near-end guard. **RULE — that disambiguation lives in the pure `PlaybackEndPolicy.decide(...)` (`PlaybackEndDecision.swift`) and has THREE outcomes, not two.** The old single `guard … else { return }` collapsed teardown, a media swap, a never-opened stream and a **premature stop** into one silent no-op — and the last is a defect: when the upstream dies mid-film libVLC reports a *clean* EOF, so `.error` never fires and the existing one-shot retry was unreachable. Nothing ran: no retry, no stop report, no alert, not even the spinner (95 s of black screen measured). `.unexpectedStop` (short of the end **and** `mediaConfirmedOpen`) now routes to `handlePlaybackError()`; `.ignore` keeps teardown, swaps and a never-opened DIRECT stream silent, since each has its own owner (the open watchdog owns the last). **An HLS stream that never opened gets its own outcome (#164)**: an origin HTTP/2 RST on the manifest fetch of a forced transcode leaves no demuxer, libVLC never re-requests a playlist, and it reports a clean `.stopped` with no `.encounteredError`, so the retry waited out the whole watchdog (15 s, then 30 s) on a frozen 0:00. `.failedOpen` (not confirmed open, `isAdaptiveStream` = the opened URL ends in `.m3u8` via `CinemaxStreamProxy.isManifest`, past the 1 s swap window) routes to `handlePlaybackError()` at once. A direct first attempt therefore reaches `noteDirectPlaybackFailed()` and retries through the proxy within about 1 s, and a second failure shows the alert. Inside the swap window the stop may still be the OUTGOING media, so `.recheck(after:)` asks again just past the window (`scheduleFailedOpenRecheck`), passing `engineStopped` from `player.state`: a swap has the new media `.opening` by then, a failed open is still `.stopped`. The recheck acts only on `.failedOpen` and only for the same `play()`. **`lastPlayStart` is nil from `beginOpenLoading()` until that open's `play()`**, and `decide` ignores every stop in that gap. That is what keeps a failed attempt's trailing `.stopped`, which follows its `.encounteredError` once the retry has begun, from counting as a second failure: that would put the alert over the retry and release the server session it is using. The give-up branch also returns early while `errorAlert` is up, so one failure never stacks two alerts. The HLS scoping is deliberate: a never-opened DirectPlay stop still waits for the watchdog, because only the HLS failure has been observed. **The 2000 ms end tolerance must NOT be tightened**: real natural ends were measured at 139 ms and 178 ms from `lengthMs`. Locked by `PlaybackEndDecisionTests`. **RULE — a DirectPlay stream URL goes out WITHOUT the token; only a DIRECT RETRY puts it back** (`VLCStreamPresenter.streamURL(_:token:isRetry:viaProxy:)`, pure, reached by all four open paths through `streamOpenURL`, keyed on `didRetry`; #184): `/Videos/{id}/stream` carries no `[Authorize]` on any supported server (10.9 → 12.0), so the `ApiKey` authenticated nothing and only landed in reverse-proxy and CDN access logs — while a future server that added the requirement costs one failed attempt, never a dead playback. A proxied open never needs it either (`CinemaxStreamProxy` sends `Authorization: MediaBrowser Token=…` upstream, reconnects included), and a forced-transcode `TranscodingUrl` keeps the server's OWN `ApiKey`, never doubled. Locked by `StreamURLTests`. Auth via the `ApiKey` **query param** (libVLC can't reliably inject the header) — **RULE — `ApiKey`, never `api_key`**: Jellyfin 12.0 ships `EnableLegacyAuthorization = false` (PR #15559 / #16992), which rejects `api_key`, `X-Emby-Token`, `X-MediaBrowser-Token`, `X-Emby-Authorization` and the `Emby` scheme; `ApiKey` is read unconditionally on every server since 10.8 (`AuthorizationContext.cs`, verified v10.8.13 → v12.0-rc7). The same spelling is what the server itself appends to every `TranscodingUrl` (`StreamInfo.cs`: `&ApiKey=`), so `authedURL` must test for it case-insensitively or the forced-transcode URL goes out with the token twice. Same rule for the `/socket` URL (`makeRealtimeSocketURL`). The Top Shelf image URLs carry no token at all any more (audit 2026-09-22, S5) — `GET /Items/{id}/Images/{type}` is anonymous on every supported server. Locked by `AuthedURLTests`. **What the legacy switch actually breaks, measured 2026-09-08 on 10.11.11 with `EnableLegacyAuthorization=false` and a pre-#133 build as paired control: the realtime socket (`/socket` → "Token is required", i.e. « Lire sur… » + Watch Together) and the Top Shelf images — NOT playback.** `GET /Videos/{id}/stream` carries no `[Authorize]` in `VideosController` (v10.11.11 and v12.0 alike — the DirectPlay URL is anonymous, its token is dead weight), and the forced-transcode `TranscodingUrl` already arrives with the server's own `&ApiKey=`, so `DynamicHlsController`'s class-level `[Authorize]` was satisfied even when the app appended a second, ignored `api_key=`. A "playback broke after the 12.0 upgrade" report therefore points somewhere else than the token. Full feature parity. **AirPlay-to-TV video** still impossible on any libVLC path — deferred.
- **RULE — broken-IPv6 servers route through a loopback proxy** (`CinemaxStreamProxy.swift`): libVLC's HTTPS access (`vlc_tls_SocketOpenTLS`) hardcodes `AF_UNSPEC`, ignores the `ipv4`/`ipv6` options, and has **no Happy-Eyeballs** — so a dual-stack server whose IPv6 (AAAA) is black-holed makes libVLC stall ~75s on the dead route (`URLSession` is immune; it races families). No libVLC media flag can force IPv4. `StreamTransportPolicy.shared` (`@MainActor` singleton) probes once in the background (from `AppNavigation` on launch / server change / foreground / `network.isOnline` flip): resolves the host's AAAA, opens a short NWConnection (TLS, SNI=host) to that IPv6, and sets `preferProxy` only if it **hangs** (neither `.ready` nor fast `.failed` within 4s — the genuine black-hole; an IPv4-only network fast-fails and must NOT proxy). When `preferProxy`, `startPlayback` opens `http://127.0.0.1:<port>/…` and `CinemaxStreamProxy` re-fetches each request from the real HTTPS origin via `URLSession` (Happy-Eyeballs → IPv4), streaming back with `Range` preserved. A watchdog→proxy fallback also catches black-holes the probe missed (the retry stays on the proxy, never the broken direct URL). Healthy servers keep the **byte-identical direct path** — the proxy only runs when `preferProxy` or a first direct attempt already failed. **RULE — the loopback handler (`forward`) admits a request only through the pure `CinemaxStreamProxy.admission(method:path:hostHeader:)`** — defense-in-depth on top of the 127.0.0.1-only bind: the path must be a well-formed `/s/<id>` (else 400); the `Host` header, **when present**, must be an EXACT loopback name via `isLoopbackHost` — `127.0.0.1` / `localhost` / `::1` / `[::1]`, optional `:port` stripped (else 400) — never a `hasPrefix` test, which is precisely what a DNS-rebinding host (`localhost.evil.com`, `127.evil.com`) walks through; and the method must be `GET`/`HEAD` (else 405), since anything else would be replayed to the real origin **with the account's token attached**. A missing `Host` stays allowed (libVLC doesn't always send one). Every legitimate stream URL is `http://127.0.0.1:<port>/s/<uuid>` fetched with GET, so none of this touches the real path. `admission`/`isLoopbackHost` are pure + `static` (like `parseRange`) and locked by `StreamProxyTests`.
  - **RULE — the proxy registers the origin's DIRECTORY, not one URL, so it serves a whole HLS tree.** `localURL(for:)` stores an `OriginDirectory` (scheme/host/port + the target's path minus its last component) and returns `http://127.0.0.1:<port>/s/<id>/<name>?<query>` — **keeping the media's own name and query**. That is the entire mechanism: libVLC resolves a master playlist's relative children against the URL it opened, so `main.m3u8?…` becomes `/s/<id>/main.m3u8?…` and a segment becomes `/s/<id>/hls1/main/0.mp4?…`, and `route(path:)` re-attaches each `rest` to the registered directory. One registration serves master + variant + every segment, **with no manifest rewriting**, and the 6-entry `targets` bound stays per-STREAM instead of blowing up per-segment. `OriginDirectory` derives the directory from the target's own path, so a sub-path-hosted server keeps its base path (see the `URLComponents+ServerPath` RULE). **Never go back to registering a single URL under a bare `/s/<id>`**: a manifest's children then hit an unknown id (502) or fail admission (400), and the open dies with `libvlc demux error: Failed to create demuxer 0x0 Unknown` on a frozen 0:00 screen — which is what every forced AVI/XviD transcode did.
  - **RULE — `route(path:)` refuses any `rest` component that is a dot-segment OR decodes to something containing a separator.** `rest` is re-attached to the registered directory and fetched from the origin **with the account's token**, so traversal would read arbitrary origin paths as the user. Checking only for a decoded `".."` is not enough: `%2E%2E%2Fsecret` is ONE component on the wire that decodes to `../secret`, and origins disagree on whether `%2F` separates — so the decision must not depend on the origin's decoding quirks. Components that merely *contain* dots (`..foo.mp4`, `main..m3u8`) are legitimate names and stay allowed. Locked by `StreamProxyTests`.
  - **RULE — `StreamTransportPolicy` sets `preferProxy` when `getaddrinfo` can't resolve the server host** (`hostResolvesForLibVLC`, checked before the IPv6 black-hole probe). libVLC resolves through the BSD resolver *only*; on some networks — measured on a corporate Wi-Fi — `getaddrinfo` returns `EAI_NONAME` for every URL while `URLSession` fetches the very same URL with 200 in the same second, so **nothing libVLC opens directly can work** and the loopback proxy (URLSession + a literal `127.0.0.1` peer, zero DNS) is the only path. Deliberately probed with `getaddrinfo` and **not** URLSession/Network.framework: the whole bug is that the two disagree, and libVLC only gets the former. Without this the fix still costs a failed open + a retry (~7 s of dead time) on every playback, since the condition is otherwise only discovered after libVLC has lost. `noteDirectPlaybackFailed()` is therefore unconditional again — latching is correct when the proxy is the only thing that works. A transient resolver failure costs one needless trip through the proxy (which works everywhere); the reverse mistake costs a dead playback.
  - **RULE — the loopback LISTENER can die without saying so, and three things make that survivable: a liveness check, a retry that waits for a rebuilt listener, and releasing the sticky proxy when a proxied attempt fails too.** Measured 2026-09-14 on an iPhone (diagnostics export, 2.0.0 build): « Lecture impossible » on every title until the app was killed. Every open went to `http://127.0.0.1:55961/…` and libVLC got `Connection refused` in 0.1 s — `localURL(for:)` hands out a URL only when `listenerPort` is cached, so the `NWListener` had never reported `.failed` while nothing listened on the port any more (most likely a listening socket reclaimed during a suspension; the app had been backgrounded several times — not proven). The retry went to the same dead port, and `directFailedThisSession`, set by an earlier direct failure, sent even an MKV there on its FIRST open (`preferProxy=false`, `voie=proxy`). The same shape on the Apple TV the same day: an AVI — always proxied through `sourceNeedsProxy` — played a whole episode, and the next one failed. Hence: (1) `CinemaxStreamProxy.restartListenerIfNotAccepting()` connects to the cached port and rebuilds the listener when refused (a refused `NWConnection` reports `.waiting`, not `.failed`) — only if `listenerGeneration` is still the one it read with that port, so a check racing a `stop()` (sign-out) or another restart does nothing — run by `StreamTransportPolicy.refresh()` on every foreground; (2) `handlePlaybackError`'s retry — whose retry / ignore / give-up decision is the pure `PlaybackRetryPolicy` (`PlaybackEndDecision.swift`, locked by `PlaybackRetryPolicyTests`; the method keeps only the effects) — awaits `StreamTransportPolicy.prepareProxyForRetry()` (check + bounded 1.5 s wait for the listener) before opening, with `beginOpenLoading()` armed BEFORE that await so the failed attempt's trailing `.stopped` is still ignored, and `pendingRetryToken` keeping a late error from that attempt out of the give-up branch until the retry's `play()` (cleared in `activateSessionThenPlay`, and by every `navGeneration` bump — a TOKEN, not a Bool, so an abandoned retry can never clear a newer retry's guard; a wake re-resolve that supersedes a retry and then fails to negotiate re-arms the open watchdog, which that retry had cancelled, or the spinner would never end); (3) the give-up branch calls `noteProxiedPlaybackFailed()` when its last attempt was proxied, releasing the sticky pin — the next playback tries direct and re-pins itself if direct fails. **Listener state callbacks are keyed on `listenerGeneration`** (bumped by `restartListener`, `stop` and every start), never on identity: an old listener's late `.cancelled` must not clear its successor's port, and a weak `===` compare reads `nil === nil` as a match. `restartListener()` keeps registrations and live requests — accepted connections don't depend on the listener, and a registration is addressed by its id. Locked by `StreamProxyTests` (`simulateSilentListenerDeathForTesting` reproduces the cached-port-but-refused state).
  - **DEBUG — `CINEMAX_FORCE_PROXY=1`** in the environment forces `shouldRouteThroughProxy`. The proxy path is otherwise unreachable on a healthy network, i.e. never exercised on a dev machine, and it is now load-bearing. Use `SIMCTL_CHILD_CINEMAX_FORCE_PROXY=1 xcrun simctl launch <udid> com.cinemax.ios` and confirm with the stats HUD (`Via proxy · …`) plus loopback traffic to the proxy port in the log.
  - **RULE — only `noteMediaOpened()` renews `didRetry`**, called from the two signals that prove a demuxer exists (a real `lengthChanged` > 0, a moving playhead) — the same two that stand the open watchdog down. **Never from `.playing`**: libVLC reports `.playing` as soon as the input starts, *before* the demuxer is built, so a stream that never opens still emits one. Renewing there voided the "retry once" bound — every watchdog fire re-entered the retry branch, looping silently every 30 s on a frozen 0:00 screen (HUD showing pause, i.e. "playing") instead of surfacing the error alert.
  - **RULE — the proxy's `URLSession` MUST use a CONCURRENT delegate queue** (`maxConcurrentOperationCount=8`, not the default serial one). The proxy applies backpressure by **blocking** `didReceive(data)` until each loopback `NWConnection.send` lands; MKV demuxing fires simultaneous `Range` requests (reads the SeekHead/Cues near EOF *while* the `bytes=0-` stream is still open). On a serial queue the main stream's blocked callback head-of-line-blocks the seek request → VLC times out the seek → `libvlc stream filter error: cannot seek` + `damaged file?`. URLSession still serializes callbacks per-task, so a concurrent queue is safe. One request per connection (`Connection: close`); each loopback URL carries a unique `/s/<id>` resolving to its own target so a retry/episode swap can't read the wrong stream.
  - **RULE — transparent mid-stream reconnect** (`UpstreamHandler`): a reverse-proxied / HTTP-2 origin routinely RSTs a long-lived range request mid-stream. On a non-cancelled error AFTER the head was sent, the handler re-issues the origin GET at `rangeStart + bytesDelivered` (a `Range` request) and **splices the body into the SAME loopback connection** — libVLC never sees EOF, just a brief feed pause absorbed by `:network-caching` (8 s), so a transient drop is **invisible** (this is the controllable version of `:http-reconnect`, which was removed because it hung libVLC silently). The reconnect's response head is NOT forwarded; a non-206 (origin ignored `Range`) bails to a clean close so libVLC re-opens. Bounded by `reconnectsLeft`, which renews ONLY after `progressRenewBytes` (256 KB) of progress since the last reconnect — a flaky-but-feeding stream recovers forever, a trickle-then-RST loop depletes the budget and gives up. **Before the head the only retry is for a MANIFEST (#164)**: libVLC re-requests a failed segment by itself, but a lost playlist is a dead open, so a `.m3u8` request (`CinemaxStreamProxy.isManifest` on the loopback `rest`) whose upstream fails before any response head is re-issued verbatim ONCE (`manifestRetriesLeft`, decided by the pure `shouldRetryBeforeHead`, locked by `StreamProxyTests`), invisibly to libVLC since nothing has been written to the connection yet. Everything else that fails before the head still gets the 502, and a cancellation (libVLC walked away) is never retried. `task` is lock-guarded (read on netQueue, written on the delegate queue during a reconnect); the other counters stay lock-free (per-task callbacks are serialized and strictly sequential across a reconnect). `finish()` is one-shot (a `.cancel` disposition re-fires `didCompleteWithError`).
- **RULE — a picture that stops while libVLC still says `.playing` (a wedged VIDEO DECODER, or the whole pipeline stalled) is invisible to every other guard in the player, and `PictureStallPolicy` (`Shared/Screens/VideoPlayer/`) is the only thing that sees it.** Measured on an Apple TV 2026-09-13, a 4K HDR10+ HEVC MKV in DirectPlay: the picture froze twice mid-film and NOTHING in the app reacted, because nothing looked wrong — libVLC stayed `.playing`, so the loading spinner never armed (it keys on `.opening` / `.buffering`); the clock kept advancing, so `PlaybackReporter` went on reporting a position that CLIMBED (the user watched it climb on his phone while the television was frozen); no `.stopped` was ever emitted, so `PlaybackEndPolicy` had nothing to judge; and the open watchdog covers the OPEN phase only, which had long since succeeded. A ±10 s seek did not recover it, which is the tell — **a seek re-anchors the demuxer, it does not rebuild the decoder**. So the detector cannot key on time or on errors: it keys on the one counter that actually stopped, libVLC's `displayedPictures`, which the stats HUD already reads and nothing else consulted, sampled on the EXISTING 1 s heartbeat (never a second timer). **RULE — the ENGINE STATE is the gate, not the clock**: « `.playing` and no new picture » is never legitimate whether the clock moves or not — a pause is `.paused`, a rebuffer `.buffering` (spinner), the end of media `.stopped`, and each leaves through the guard. It used to demand a moving clock, on the claim that « frames frozen AND clock frozen » always had another owner; **measured false on 2026-09-15** on the same Apple TV (Pat' Patrouille, then a Punisher episode): picture AND SOUND stopped, no spinner, a −10 s seek raised the spinner and never landed, and the server received NO diagnostic document — this guard had seen the frozen clock and stood down, and nothing else owns a pipeline that stalls while libVLC stays `.playing` (the open watchdog covers the OPEN phase, `PlaybackEndPolicy` needs a `.stopped`, no error fires). Same cure for both shapes, a rebuild opening a fresh connection as well as a fresh decoder; `stallClockMoved` records which shape a fire was, and the upload reason follows it (`picture-stall` / `playback-freeze`, each with its `-exhausted` twin). Four more refusals: no video track (an audio-only source displays no pictures for its whole duration), a seek settling (`SeekMachine.sampleSettle` owns that wait), before `mediaConfirmedOpen` (the open watchdog owns it), and absent statistics (« cannot tell » is never a stall). Recovery is `reResolveAndResume`, the wake path, because rebuilding the player is the only thing that hands the decoder — and the input — a new one. **The bound is load-bearing: `resetWindow()` — called from `beginOpenLoading`, i.e. from the recovery's OWN path — deliberately does NOT restore the recovery budget.** Only `budgetRenewSeconds` (60 s) of healthy frames does, which is proof the recovery worked; restoring it on every reopen would turn « at most 2 rebuilds » into an unbounded loop of server re-negotiations, the exact silent loop `didRetry` was tightened to prevent on the open path. It is a NET, not a cure — it restores playback without knowing why videotoolbox stopped — so every fire logs `clockMoved`, the picture counters, the demuxer's own complaints and the module chain (`VLCEngineFacts`), and the « budget spent » case logs once per episode rather than once per second. A `checkForVideoStall` attempt was abandoned earlier on a wip branch for regressions; this one differs by keying on the displayed-picture counter under a `.playing` state rather than on elapsed time alone. Locked by `PictureStallPolicyTests`.
- **RULE — the INPUT has its own watchdog, `FeedStallPolicy` (same file), and it fires ~20 s before the picture one can.** Measured on an Apple TV 2026-09-20 (« Just Play Dead », a 6.6 GB MKV in DirectStream through the reverse-proxied server): the origin cancelled the long-lived HTTP/2 stream mid-film — `peer stream 27 error: Cancellation (0x8)`, once preceded by a read that timed out (`got error 60`) — and **libVLC's own HTTP access has no mid-stream reconnect**, so nothing fed the demuxer again. The picture ran on from the buffer (18 s on the second of the two freezes), so every picture-keyed guard still saw a healthy stream; only once the buffer drained did `PictureStallPolicy` fire, i.e. after the viewer had been staring at a frozen frame, and its rebuild then re-opened DIRECT and fell into the same cut seven minutes later. The transparent reconnect the app owns lives in `CinemaxStreamProxy.UpstreamHandler` and a direct stream never goes through it. So this watchdog keys on `readBytes` — libVLC's input counter, sampled on the same 1 s heartbeat — and acts **while the picture is still playing**, which is what makes the cure cheap: `reanchorAfterFeedStall` seeks 1 s back, the one thing that makes libVLC open a FRESH connection without rebuilding the player (and the wrong cure for a wedged decoder, which a seek was measured not to fix — that stays `PictureStallPolicy`'s). **Four refusals, each answering a way a feed legitimately goes quiet**: an adaptive (HLS) stream fetches in per-segment bursts; a source whose every byte is read has nothing left to fetch (a short trailer buffers whole — hence `PlaybackInfo.sourceSizeBytes`, plumbed from `MediaSourceInfo.size` for this); a settling seek owns its own wait; and before `mediaConfirmedOpen` the open watchdog owns everything. Absent statistics are "cannot tell", never a stall. **The escalation needs no state**: if the re-anchor does not bring bytes back within `feedReanchorGrace` (8 s) the player is rebuilt through `reResolveAndResume` — an explicit follow-up precisely because the re-anchor opens a seek-settle window that both watchdogs stand down behind, which would otherwise hold for its own 30 s backstop with nothing watching. Budget: 2 re-anchors per playback, renewed by 60 s of a feed that actually delivers, same discipline as the picture policy's. Uploads a `feed-stall` document. Locked by `FeedStallPolicyTests`.
- **RULE — libVLC's own logs go through `VLCEngineLog`, never to stderr** (`VLCEngineLog.installOnce()`, called from `VLCStreamViewController.viewDidLoad`): libVLC's default *console* logger writes straight to stderr, and its volume is proportional to the number of HTTP transactions — a DirectPlay MKV opens one long connection and goes quiet, an HLS transcode runs a full access/TLS/demux cycle **per segment** for the whole film, which is the entire reason a forced-transcode AVI is noisy and a 4K MKV isn't (the app's own playback logging is event-driven and never fires on the 1s tick). Subscribing to `VLCInstance.shared.logStream(minimumLevel:)` is itself the fix: it installs `libvlc_log_set`, which *replaces and destroys* the console logger. The stream must therefore be consumed for the process's lifetime — its `onTermination` calls `libvlc_log_unset` and hands stderr back. Install is lazy (first playback) so `libvlc_new`'s plugin scan doesn't move to launch, and messages emitted during instance creation still reach stderr (documented libVLC limitation). **Messages are scrubbed before emission** (`VLCEngineLog.scrubbed`, unit-tested): libVLC logs the URLs it opens and some still carry the token as an `ApiKey` query item (a direct retry, every forced-transcode URL — DirectPlay opens no longer do, but the scrubber stays as defense in depth), so a raw message would write the token into the system log — same rule as `redactedURL`. The C shim formats every message before the level filter regardless, so the widened subscription adds only two `hasPrefix` checks per dropped line. Locked by `AudioTrackPolicyTests`.
- **RULE — the `AVAudioSession` is owned by `PlaybackAudioSession`, never activated inline on the main actor**: `setCategory`/`setActive` are synchronous XPC round-trips to `mediaserverd` (tens of ms, unbounded under load) — called from `@MainActor` they emit Apple's own `AVAudioSession_iOS.mm:978` / `SessionCore.mm:631` warnings and stall the player's open/teardown. - **RULE — `PlaybackReporter`'s start / progress / stop go out on ONE serial chain per reporter** (`enqueue` → `tail`, awaited by the `drain()` test seam; audit 2026-09-22, B12). Real remotes send a clean type-5 Back press, but the whitelist keeps the simulator (and any future stray press type) from breaking the peel — an unrecognized press maps to `nil` and is ignored. **A recognized wake press ALSO performs its action, not just reveal**: select/Enter → play/pause, left/right → skip ∓N s, up/down → reveal only. **Two exceptions pass the press through to the focused control instead**: a visible next-up card, and a SELECT while « Passer l'intro / le générique » holds focus (the one control that claims focus over bare video) — read as play/pause, that select paused the film and revealed the HUD, which moved focus to `tvScrub` before the button's `pressesEnded`, so the skip never fired (Apple TV, 2026-09-18). - **RULE — tvOS touch-surface scrubbing** (`TVScrubBar`): Siri Remote touchpad slide = variable scrub via an **indirect-only** `UIPanGestureRecognizer`. Must be **incremental** — consume `translation(in:)` then `setTranslation(.zero)` each `.changed` and accumulate; an absolute baseline gets stomped by the periodic tick → "jump then snap" glitch. Sensitivity is the `scrubGain` constant (0.2 = full swipe ≈ a fifth of the timeline; tune here — was 0.5, too fast on the Siri Remote 2nd-gen touch surface). Presses ignored while `isScrubbing`; `refreshTimeUI` returns early while scrubbing on both platforms.
- **RULE — the near-end guard lives in `engineSeek` (`SeekMachine`), the funnel, NOT in one caller.** `SeekCoalescer.clamp` had a single call site — `accumulate`, the ±N skip path — while the three other entries into `engineSeek` went through unbounded: the scrub release (`userEngineSeek`), the SyncPlay echo, and the resume-position seek. At the right edge `slider.value == 1.0`, so `scrubberDone` targeted `lengthMs` **exactly**; libVLC REFUSES that (`INPUT_CONTROL_SET_TIME @… failed`) and the input never recovers — frozen picture under a HUD still reading "playing", the spinner held to its 30 s backstop, then off, and every later seek dead too (defect H, measured on device 2026-08-21: `target=2503936` on a `lengthMs` of 2503936). The first reading of that log assumed the target was `lengthMs − endGuardMs` and concluded the fix was to raise the constant; **it is not — the constant was never consulted on that path**. `SeekMachine.accumulate` keeps its own `clamp` because it also PAINTS the clamped target into the HUD before the debounced commit; the double clamp is idempotent. `endGuardMs` stays 250 ms — a deliberate call, and note that value itself is **not** measured against the refusal: what is measured is that 90 % and 97 % succeed and `lengthMs` exactly fails. **No test can prove the wiring** (the funnel lives in the view controller); `SeekCoalescerTests` locks the property the fix rests on.
- **RULE — ±N skips are coalesced into one debounced seek** (`SeekMachine.skip(bySeconds:)` → `accumulate` → the debounced commit → `commitUserSeek`): EVERY skip entry point (iOS skip buttons, iOS double-tap, tvOS clickpad ±10s, chapter-chip taps) accumulates an ABSOLUTE target into `pendingTargetMs` and commits ONE `engineSeek` `SeekMachine.commitDelay` (0.3s) after the LAST press — never an immediate `player.seek(by:)` per press. Mashing the button used to fire N relative seeks, each tearing down + reopening libVLC's HTTP byte-range request → a storm that overloads a self-hosted / reverse-proxied origin and can stall the stream. **Don't "fix" the 0.3s delay away** — the HUD jumps to the projected position instantly (`paintPosition`) so it feels responsive; the delay is what collapses N requests into 1. The pending seek is cancelled (`SeekMachine.cancelPending`) on scrub takeover, media reload, episode swap, and teardown so a stale target can't seek the wrong position / a fresh episode. The pure seek math lives in `SeekCoalescer` (`clamp(target:lengthMs:)` / `relativeTarget(...)`, `endGuardMs = 250` — never seek within 250ms of length, libVLC treats end-seek as EOF), extracted for unit testing (`SeekCoalescerTests`); the view controller keeps debounce/HUD/engine ownership.
- **RULE — the seek settle window's progress test must be SAMPLING-RATE INDEPENDENT** (`SeekSettleTracker`, same file): it keeps its baseline until the playhead has advanced `SeekMachine.landedProgressMs` (120 ms) and only *then* re-baselines. The original compared each sample against the immediately previous one and rewrote the baseline on **every** call — but the settle sampling (now `SeekMachine.sampleSettle()`) is driven by `onEngineTimeChanged`, i.e. libVLC's time updates (several per 100 ms), so each comparison spanned 0–30 ms and the 120 ms threshold was unreachable: the more often it ran, the less it could ever succeed. Consequence, measured on device 2026-08-12: playback resumed at a true 1× **within 0.5 s** of a seek, yet `landed` never fired, so the spinner held to the backstop (20.2 s once, the full 30 s `SeekMachine.maxHold` the next) with `refreshTimeUI` deferring to the window and the bar pinned to the pending target — which reads exactly as "the player froze ~20 s after a fast-forward". **This, not the loopback proxy, is that symptom's cause**; after the fix the same 18-minute forward seek on the same server settles in 0.38–0.51 s. Locked by `SeekSettleTrackerTests`.
- **Chapter thumbnails** from `getItem().chapters`; requests skipped when `imageTag` nil. Blank ⇒ server hasn't run Jellyfin Dashboard → Scheduled Tasks → "Chapter image extraction". Degrades to `film` icon + title + timestamp. **RULE — the fetch batch is DEFERRED until `noteMediaOpened()`** (`pendingChapterThumbnails`): `fetchChapters` runs from `startPlayback`, i.e. exactly while libVLC opens the stream, so firing one request per chapter there put ~30 image GETs against the origin during the open window — time-to-first-frame the user waits through on a self-hosted / reverse-proxied server. - **RULE — `VideoPlayerView` (the iOS loading shell) re-checks `Task.isCancelled` after every `getPlaybackInfo` and presents nothing if the user closed it meanwhile; it hands the negotiated session back instead (`abandonNegotiation` → `closeLiveStream` + `stopEncoding`, the presenters' abandon pair).** The negotiation cannot be interrupted, so closing « Préparation du flux… » with ✕ used to let it land later and present the player anyway, over whatever screen the user had gone back to (measured 2026-09-23 against a paused server, 2/2). Retry goes through `.task(id: attempt)` rather than an unstructured `Task`, so SwiftUI cancels it on close exactly like the first attempt.
- **iOS controls** are the touch UI (`#if os(iOS)`: tap-to-toggle, `UISlider`, separate pickers, `pip.enter`). The SwiftVLC view is hosted with `isUserInteractionEnabled = false` so the `videoView` tap recognizer drives HUD toggles. **Swipe-down-to-dismiss** (iOS/iPadOS only, VLC path only): interactive `UIPanGestureRecognizer` on `videoView` — surface follows the finger (translate + fade + corner rounding; `.overFullScreen` keeps the app visible behind), dismisses past 25% height or a >900pt/s downward flick, springs back otherwise. Seeks route through the documented coalesced path (`iosSkipBack`/`iosSkipForward` → `SeekMachine.skip(bySeconds:)`), never a direct engine seek; `wantsPriorityOverSystemBehavior` stops the system swallowing space/arrows; VC is first responder (`canBecomeFirstResponder` + `becomeFirstResponder()` in `viewDidAppear`). Independent of the gesture/HUD stack.

### SyncPlay / Watch Together

`SyncPlayController.shared` (`@MainActor @Observable` singleton, `Shared/Screens/VideoPlayer/SyncPlayController.swift`) owns the whole session: current group, participants, the realtime socket, the client↔server `clockOffset`, and a `PlaybackBridge` injected by the player surface. Depends on `any SyncPlayAPI` + `LocalizationManager` + `ToastCenter`, set on activation.

> **STATUS — live again (1.2.x), gated on the SERVER's permission, not a kill-switch.** The `private static let watchTogetherEnabled = false` compile-time switch (dark 2026-07-15 → 2026-09-04, with no recorded reason) is replaced by `MediaDetailScreen.watchTogetherEnabled`, a computed property reading `LiveSessionsRow.canCreate(appState.currentUser?.policy?.syncPlayAccess)`. **Jellyfin has always modelled this permission** (`SyncPlayUserAccessType` = `CreateAndJoinGroups` / `JoinGroups` / `None`) and the client simply never asked, so it offered the feature to accounts the server would then refuse. `canJoin` is the looser right (see the Home row); `canCreate` gates starting a session from a title's page. An **absent** policy resolves to `false`, the same "unknown means unsupported" discipline as `ServerVersion.serverSupports`.
>
> **Five defects were found by reading the code before re-enabling; four are fixed, one is scoped out.** (1) Two sockets — fixed, see the one-socket RULE. (2) `PlayQueue` dropped, so a joiner never learned what to open — fixed. (3) `bindSyncPlayIfNeeded` guarded on `isInGroup` at open only, so a player already running never bound — fixed. (4) The echo-suppression flag was `defer`-reset around synchronous calls while the echo arrives asynchronously — fixed with a time window. (5) `NativeVideoPresenter` has NO SyncPlay binding at all: with `forceNativeAVPlayer` on, a group forms server-side and nothing moves. **Not fixed — refused instead**, with an explanation (`syncplay.needsVLC`), at both entry points, **and since #165 stated BEFORE the press**: the fiche's « Ensemble » entry is hidden (`MediaDetailScreen.watchTogetherEnabled` also reads `forceNativeAVPlayer` via `@AppStorage`), and on Home's « En direct » row a group card whose JOIN is blocked is dimmed (still a focusable button — `.disabled` would drop it from the tvOS focus chain) under ONE footnote naming the setting (`syncplay.needsVLC.footnote`; `LiveSessionsRow.Entry.isJoinBlocked` / `needsEngineFootnote`, locked by `LiveSessionsRowTests`). **A card the viewer is IN is never blocked** — its action is « Quitter », and leaving must work on any engine. The toasts stay as the backstop. **Still not built, deliberately**: any way to *invite* a person (Jellyfin has no invitation primitive; it would have to ride `DisplayMessage`, which every other client renders as a bare toast).

- **API**: SDK-routed. **The long-standing note that "the SDK doesn't model SyncPlay" was wrong for jellyfin-sdk-swift 0.6.0** — it ships every `Paths.syncPlay*` operation plus `Paths.getUtcTime` with a typed `UtcTimeResponse`, and the ~190 lines of hand-built `URLSession` plumbing were deleted. The two properties that plumbing existed to guarantee come free from the shared client: `urlCache = nil` (a cached `GET /GetUtcTime` would poison the clock offset) and the `notifyIfUnauthorized` + rethrow discipline, which each call keeps. **One property was deliberately dropped**: the old private session's 15 s per-request leash — `Get` has no per-request timeout hook, so a dead server now stalls a transport action for the shared 30 s instead. `syncPlayNewGroup` discards the `GroupInfoDto` the SDK returns **on purpose**: the socket's `GroupJoined` echo stays the single source of truth for group identity, and consuming the REST result would create a second racing writer. Realtime stays hand-built — `JellyfinSocket` (a Swift `actor` around `URLSessionWebSocketTask`, `wss?://…/socket?ApiKey=…&deviceId=…`, parsed `Sendable` frames via `AsyncStream`); the SDK models REST only. The URL comes from `RealtimeSocketAPI.makeRealtimeSocketURL()` — a **URL**, not a socket, because the app is allowed exactly one connection and `JellyfinSocketHub` owns it.
- **RULE — `SyncPlayGroup` keeps its hand-written `Decodable` conformance** even though REST now yields `GroupInfoDto` (mapped by `init(dto:)`): the socket's `GroupJoined` / `GroupLeft` updates carry an untyped JSON blob that `JellyfinSocket` decodes straight into this type. Dropping the conformance breaks the socket path only.
- **RULE — creating a session lands on `WatchTogetherLobby`, never straight in the player**, and that screen is also the app's ONLY exit from a group other than closing the player (`playbackDidDismiss` was the single caller of `leaveGroup`, so before it there was literally no way out). It shows who is present, explains that others join from the « En direct » row, and carries « Lancer la lecture » / « Quitter la séance ». **RULE — `WatchTogetherSheet`'s tvOS body follows the SAME page contract as this lobby** — `CinemaTVLayout.pagePadding`, capped at `readingMaxWidth`, centred, CTA at `ctaWidth`. The two screens are one journey (create here, wait there) and were built to different contracts: the sheet ran edge to edge at 1920 px, so its panel stretched across the screen, its accent CTA became a full-bleed slab whose focus ring drew over the panel's own corners, and the empty state floated in the middle of a column nothing else was centred in. Its create panel puts the name on the left and the CTA on the right of ONE row — stacked, a short name and a button spent the whole measure. Its group rows carry `TVFilterRowButtonStyle` (the documented "rangée" focus level): they had `.plain`, i.e. no focus treatment at all on the one focusable list of the screen. **RULE — the create sheet has NO name field on tvOS** (`MediaDetailWatchTogether.createSection`): a `TextField` there is drawn by the system as a bright white capsule that cannot be restyled — `.textFieldStyle(.plain)` is inert on tvOS, measured 2026-09-05 — so it sat inside the dark panel looking like a foreign object, and reaching it costs a full-screen keyboard driven from a remote to retype a name that already defaults to the work's title. - **RULE — every `Ready` / `Buffering` report must carry the queue's `PlaylistItemId`**, captured from the `PlayQueue` update (`SyncPlayGroupUpdate.playlistItemIds`, kept positionally aligned with `playlist`). Jellyfin matches a report against that entry id; this client sent `nil` unconditionally, so no participant was ever counted ready and the group would sit in `Waiting` forever — a black screen with nothing on it. **Not yet confirmed against a live server**: the simulator has no hardware HEVC decoder, so a solo test there stalls at `spinner ON` for reasons of its own. `CINEMAX-SYNCPLAY ▸` traces every session event (group created/joined, state transitions, PlayQueue, Ready sent with its entry id, commands applied) precisely so a real-device log can tell the two apart — names and ids only, never a URL or a token, same discipline as `CINEMAX-AUDIO`.
- **Invitations are notifications, not invitations.** Jellyfin has no invitation primitive: `POST /Sessions/{id}/Message` (`RemoteControlAPI.sendMessage`) delivers a plain toast carrying no join action, and enumerating other people's sessions needs `/Sessions`. So the lobby's "Prévenir" is gated on `LiveSessionsRow.canSeeOthers` (the same per-user permission as the row's solo cards, no longer `isAdministrator`) and merely points the recipient at their own « En direct » row; an account without it sees that explanation and no list, which is the honest shape — there is nobody we are allowed to name.
- **RULE — `SyncPlayController.onQueueChanged` is wired OUTSIDE `#if os(iOS)`** (`AppNavigation`'s root `.task`). It sat inside that block, between `purgeLegacyDownloads()` and the Live-Activity sweep — two genuinely iOS-only chores — and the Apple TV is the device this feature exists for. Measured with two accounts on 2026-09-05: a tvOS join received the frame (`CINEMAX-SYNCPLAY ▸ PlayQueue : item=… entrée=…`), had nowhere to hand it, and left the viewer on Accueil with the card merely flipping to « Vous y êtes » — wired-looking and inert, the same failure `MediaDetailScreen.consumeIntentPlaybackRequest()` carries its own cross-platform RULE about.

- **RULE — a group whose ONLY member is the viewer keeps its card** (`LiveSessionsRow.build`, `Entry.viewerIsParticipant`). The server keeps a SyncPlay membership across an app kill, so a relaunch finds the account in a group this process knows nothing about — and the old `guard !others.isEmpty` dropped exactly that card, i.e. the app's only exit, while everyone else's Accueil still listed the account as present (measured 2026-09-05: the Apple TV showed no row at all while the phone showed the session as still holding reviewer). `viewerIsParticipant` comes from `/SyncPlay/List`, NOT from `SyncPlayController.group`, and it is read FIRST when labelling the card — the local copy is nil after a kill, which had the card offering to « Rejoindre » a group the account had never left. `HomeScreen.leaveLiveSession()` therefore has two shapes: the controller owns the departure when it holds the session, and `apiClient.syncPlayLeaveGroup()` is called directly when it does not (the controller has no API client then — `prepare` was never called — so `leaveGroup()` would tear down nothing and tell the server nothing). A group with no other participants that the viewer is NOT in is still dropped.
- **RULE — the account's POLICY is re-read on every foreground, and on the socket's `UserUpdated` frame** (`AppNavigation`'s `scenePhase` observer; `RemoteControlListener` → `AppState.refreshCurrentUser()`). `AppState.currentUser` is a cache taken at login that nothing else refreshed for the life of the process, so an admin granting or withdrawing « Regarder ensemble » / « Voir En direct » reached a running client only at the NEXT LAUNCH — verified 2026-09-05, then verified fixed in the same process (pid unchanged across a background/foreground hop, « Ensemble » appearing on a fiche that had none). The `> 60 s` branch keeps owning session VALIDITY; the new `else` covers the short hop, one small request per foreground. The `UserUpdated` case is the immediate path **when the server sends it — not observed firing against Jellyfin 10.11 in this test, so the foreground refresh is the guaranteed floor** and the socket case is a free upgrade that cannot misfire.
- **RULE — a `Ready` report may only carry a position the engine has ACTUALLY reached** (`SyncPlayReadyPolicy`, `SyncPlayJoinStart.swift`; the gate is `VLCStreamPresenter.announceSyncPlayReadyIfPositionIsReal`, whose two inputs are `mediaConfirmedOpen` and `seeks.isSettling`). `Ready` is not a courtesy ping: Jellyfin reads its `PositionTicks` as *where that participant is* and compares it against the group's own position to decide whether everyone else must wait — so announcing a position the engine has not reached does not merely arrive early, it tells the server this session is a straggler and the server rebuilds the whole group's clock around it. libVLC reports `.playing` as soon as the input starts, **before the demuxer has reached the position the group asked for** — the same fact the `clearLoadingIfOpen` / `noteMediaOpened` RULE documents for the spinner, applied to the wrong consumer. Measured on 2026-09-06 against the real server, group queued at 1:36 (`position=964460000`): `engine-state opening` → 133 ms → `engine-state playing` → **`Ready envoyé position=0`** → 1.8 s later `seek-settle now=96446 landed=true`. The server read `0` against its own `964460000`, took `WaitingGroupState`'s « client is recovering » branch and set `LastActivity = now + 96.4 s`; from then on **every command it issued carried a `When` up to 96 s in the future**, and `SyncPlayController.schedule` slept on each one (capped at 30 s) before applying it — so pause, ±10 s and unpause all read as **dead buttons on iOS**, each new command cancelling the one still waiting. The group's `PositionTicks` stopped advancing too (`Math.Max(elapsed, 0)` clamps a negative elapsed to zero), so the `Pause` that eventually landed **dragged the picture from 2:45 back to 1:36**. Three cases, all load-bearing: not open ⇒ silent (the playhead is not a playhead yet); a seek still settling ⇒ silent, because `reportSeekSettled` owns that case and knows the arrival position; open with nothing settling ⇒ **speak**, because a group that starts at zero arms no settle window at all and would otherwise never leave `Waiting`. The open-time report is emitted from `noteMediaOpened()` on the false→true flip, since the `.playing` that would normally carry it has already been refused. Locked by `SyncPlayReadyPolicyTests`.
- **RULE — Home POLLS the « En direct » row while it is the visible tab** (`HomeScreen.liveRowPollInterval` = 20 s → `HomeViewModel.refreshLiveRow`). The row is the only door into a session someone else opened and **nothing pushes it**: Jellyfin broadcasts group updates over the socket to a group's own members only, so a non-member hears nothing; Home loads once behind `hasLoaded`; and tvOS has no pull-to-refresh. Measured 2026-09-05: a session opened on the phone never appeared on an Apple TV sitting on Accueil, while the host's lobby was promising « la séance y apparaît tant qu'elle est ouverte ». **Its three writes are equality-guarded** (`activeSessions`, `syncPlayGroups`, `currentUserName`): `@Observable` fires `withMutation` even for an identical value, so an unchanged poll was invalidating this row's focusable cards three times a minute on tvOS, where that pulls focus off whatever the user is standing on. `SessionInfoDto` is `Hashable` and `SyncPlayGroup` is `Equatable`, so the comparison is the server's own answer rather than a digest of it. It refreshes the ROW alone — never `reload()`, which flips `isLoading` and would drop the viewer's scroll position every interval — and costs nothing for an account whose permissions let neither source return anything (both fetches are gated before the network call). **It also re-asks on ARRIVAL, and on `.cinemaxLiveSessionsChanged`.** The loop used to sleep first, so the row only caught up a full interval after the viewer reached Accueil — which is exactly where the lobby's « Prévenir » message sends them, and on tvOS there is no pull-to-refresh to hurry it. The very first appearance is still left to `load()` (`liveRowPrimed`), so a cold launch issues no duplicate. `.cinemaxLiveSessionsChanged` is posted by `RemoteControlListener` on every inbound `DisplayMessage`, because that IS the invitation: Jellyfin has no invitation primitive, so « Prévenir » sends a plain toast saying « va sur ton accueil ». It is deliberately not narrowed to invitations — the socket carries no way to tell one message from another, and the refresh is one small permission-gated request. Home defers it while hidden (`pendingLiveRowRefresh`, consumed in `onAppear`), which is the ORDINARY path rather than the edge one: the message tells the person to go somewhere else, so by definition they are not on Accueil when it lands.
- **Group lifecycle**: `WatchTogetherSheet` (`MediaDetailWatchTogether.swift`) → `createGroup`/`joinGroup`. The socket comes up FIRST so the client hears the server's authoritative `GroupJoined` echo; create sets an optimistic placeholder refined by that echo. **v1 ties group lifetime to the player** — `playbackDidDismiss()` leaves the group on teardown, and a USER close in a group is asked about first (next RULE).
- **RULE — closing the player while in a group asks « Quitter la séance ? » first, but ONLY for a close the user asked for** (`SyncPlayLeaveConfirmation.mustConfirm(isInGroup:origin:)`, pure, locked by `SyncPlayLeaveConfirmationTests`; issue #175 — its "keep the group + toast" proposal was rejected by the product owner). Every self-close of `VLCStreamPresenter` goes through `closePlayer(_ origin:)`; the swipe keeps its own `dismiss(animated: false)` and asks through `askBeforeLeavingGroupIfNeeded`, springing back instead of sliding off. **`.user`**: iOS ✕, iOS swipe-down, tvOS Menu on bare video, end-of-series « Terminé » (tvOS card + iOS alert — Menu on that card was already a user close, so its other exit must not skip the question), the sleep prompt's « Arrêter » (it says "stop watching", not "leave the group"). **`.system`, never asked**: the error alert's « Fermer », the failed-autoplay alert, a film ending with no navigator — the playback is dead or over, and a question would only stand between the viewer and a player that cannot play. « Annuler » changes nothing (no pause, group untouched); « Quitter la séance » calls the same `dismiss` as before, so teardown → `playbackDidDismiss` → `leaveGroup` is unchanged. The alert cannot trigger teardown itself: `isBeingDismissed` on its way out is the ALERT's, and presenting it leaves the player's view in the hierarchy. While it is up the tvOS peel stands down twice over — `handleMenu` guards on `leaveConfirmationAlert`, and `pressesBegan` hands every press to `super` (a presented controller's next responder is its presenter, so an unconsumed press can bubble back into the peel); « Annuler » is `.cancel`, the action tvOS maps Menu to, and re-arms `lastMenuHandledAt` so the cancelling press cannot also peel. PiP is untouched — nothing in PiP closes the presenter. VLC presenter only: `NativeVideoPresenter` has no SyncPlay binding. Traced as `CINEMAX-SYNCPLAY ▸ fermeture du lecteur : confirmation demandée` / `annulée — la séance continue` / `séance quittée` (`SyncPlayController.trace` is internal for this).
- **Sync enforcement**: local taps never move the playhead directly. In a group, user play/pause/seek go to the server (REST); the server's `SyncPlayCommand` echo over the socket is what actually moves the playhead — all participants stay in lockstep. Commands carry a server-UTC `When` converted via NTP-style clock offset (3× `GetUtcTime` averaged, ~100ms accuracy); far-future timestamps capped at 30s. `Ready`/`Buffering` reports feed drift correction. **Transport-only** — content selection is NOT synced; each participant opens the item themselves.
- **RULE — a settled SEEK must re-announce readiness, through `SyncPlayController.reportSeekSettled(isPlaying:)`, and that report is deliberately NOT gated on `isApplyingRemoteCommand`.** A seek is what puts the group into `Waiting` server-side, and the server leaves that state only once every participant reports ready again. `reportReady`'s only two callers are engine state transitions (`.playing` / `.paused` in `VLCStreamPresenter.onEngineStateChanged`) — and **libVLC emits no state change when a seek settles on an already-open stream** (`seek-fire … state=playing`, `seek-settle … landed=true`, no `engine-state` line), so nothing ever fired. Measured on device 2026-09-06: after one ±10 s seek both clients went `Playing → Waiting` in the same millisecond, `grep -c "Ready envoyé|Waiting → Playing"` returned **0** over the following four minutes, and the full-screen « En attente d'un participant » veil stood for at least **7 min 41 s** over a picture playing at 1× — ended by tearing the players down, not by the app; it survived the other participant leaving. The paired control that proves the server is innocent: on the 9 observed exits from `Waiting`, all 9 were preceded by a `Ready envoyé` 78–102 ms earlier. The echo guard exists to stop an inbound command's *engine* echo looping back out; applying it to this report would defeat its purpose, since an inbound `Seek` is exactly the command that raises the 1 s window — the measured case settled at +2.3 s and squeaked through by luck, not design. The call site is the `landed || expired` branch of `SeekMachine.sampleSettle()` (→ its `onSettled` callback, forwarded by the controller only while in a group), the single point where a settle window closes; the backstop reports too, a stranded group being worse than a late report. **What replaces the echo guard is `groupState == .waiting`, and it is load-bearing, not a tidy-up**: reporting on EVERY settle — the first shape of this fix — closed a feedback loop, measured on device the same day, `Ready` at 220.067 s → server answers `Unpause` at 219.697 s → seeks backwards → settles → `Ready` again → … every 0.6 s for ever, the picture jerking back 0.4 s each time. A group already `Playing` waits on nobody, so there is nothing to announce; only `Waiting` is holding for the report — which is also exactly the protocol (a seek drives the group to `Waiting`, each participant answers `Ready`, the server unpauses when all have). Locked by `SyncPlayJoinAndReadyTests`, whose loop test asserts silence while `Playing`.
- **RULE — bridge closures call the engine directly and must NEVER re-emit** (an inbound command must not loop back out); `isApplyingRemoteCommand` suppresses buffering/ready echoes while a remote command is applied.
- **RULE — `startSocket` snapshots the previous socket before the async stop** — racing the reassignment kills the NEW socket. `SyncPlayDateParser` uses `Date.ISO8601FormatStyle` (Sendable), never `ISO8601DateFormatter` (race across actor/URLSession paths).
- **Platform reach**: the sync binding exists ONLY in `VLCStreamPresenter` — `NativeVideoPresenter` has NO SyncPlay integration, so sync works only when playback routes through libVLC. UI entry (gated on the server's `syncPlayAccess` AND on the VLC engine — see STATUS above): `MediaDetailScreen` `person.2.fill` chip (iOS secondary actions) / tvOS action row, online-only, accent when `isInGroup`; VLC HUD shows a participant-count pill.

### Flow (native/AVPlayer path)

1. `getItem()`. 2. Resolve non-playable: Series → `getNextUp()` or first episode; Season → first episode (**must resolve to Episode** — Series/Season have no media sources). 3. POST PlaybackInfo with `DeviceProfile` (`isAutoOpenLiveStream=true`, `mediaSourceID`, `userID`). 4. URL: `transcodingURL` (HLS) if present, else `/Videos/{id}/stream?static=true`. 5. Fallback: direct stream without PlaybackInfo session.

- **RULE — DeviceProfile**: DirectPlay mp4/m4v/mov + h264/hevc; transcode to HLS mp4 with `hevc,h264` only. **Never include `mpeg4`** — not a valid HLS transcode target on Apple; Jellyfin injects `mpeg4-*` URL params AVFoundation rejects. `maxBitrate`: 120 Mbps (4K) / 20 Mbps (1080p) via `@AppStorage("render4K")`.

### Native Player (`NativeVideoPresenter.swift`)

Both platforms `AVPlayerViewController` presented via UIKit modal. `@MainActor` sub-controllers in `Shared/Screens/VideoPlayer/`: `PlaybackReporter`, `SkipSegmentController`, `SleepTimerController`, `ChapterController`, `EndOfSeriesOverlayController`, `RemoteCommandController`, `NowPlayingInfoController`. Presenter keeps **one** `addPeriodicTimeObserver` (1s) fanning ticks to sub-controllers — sub-controllers never add their own.

- **RULE — MUST present via UIKit modal** — SwiftUI presentation corrupts `TabView`/`NavigationSplitView` focus on dismiss.
- **RULE — Dismiss detection**: iOS `PlayerHostingVC.viewWillDisappear(isBeingDismissed:)`; tvOS `TVDismissDelegate.playerViewControllerDidEndDismissalTransition`. **Do NOT embed `AVPlayerViewController` as a child VC on tvOS** — internal constraint conflicts + `-12881`.
- **Audio track menus**: via `transportBarCustomMenuItems` — first-class tvOS, ObjC KVC iOS (marked `API_UNAVAILABLE(ios)` but exists iOS 16+). Shows Jellyfin names not "Unknown".
- **Subtitles** — iOS: `enableSubtitlesInManifest:true` + `.hls` → WebVTT; `HLSManifestLoader` (`AVAssetResourceLoaderDelegate`, `cinemax-https://` scheme) strips `CLOSED-CAPTIONS` + ASS/SSA tags. Fallback `retryWithDirectURL` on `-12881` (no scheme; tags won't strip). tvOS: `HLSManifestLoader` does NOT work (causes `-12881`) → direct URL, ASS tags may appear. **RULE — `contentInformationRequest.contentType` must be a UTI not MIME**: `"public.m3u-playlist"`, `"org.w3.webvtt"`; skip for segment types.
- **Episode navigation**: `MPRemoteCommandCenter` prev/next; `EpisodeRef`/`EpisodeNavigator`/`buildEpisodeNavigation` in `PlayLink.swift`. `itemId`/`startTime` are `var`, rebound in `navigateToEpisode` (startTime → `nil`). Auto-play next via `didPlayToEndTime` when `autoPlayNextEpisode`.
- **RULE — `NativeVideoPresenter.navigateToEpisode` carries a `navGeneration` and recovers from a failed negotiation** (`handleFailedEpisodeNav`, audit 2026-09-22, B11), the VLC path's shape: a superseded nav writes nothing (two quick Next presses used to apply both results in arrival order); a manual press whose negotiation fails re-opens the current episode's server session at the live position (`reportStart`), since its `.episodeSwap` stop had already gone out; the autoplay hand-off (`isAutoplay: true`, from `didPlayToEndTime`) ends on the error alert, nothing being left to play.
- **Skip Intro/Credits**: requires **Intro Skipper** plugin. `getMediaSegments(... [.intro,.outro])`; time-based `checkSegments`, re-entry works, click seeks to `segment.end`. Rendering: iOS floating `UIButton`; **RULE — tvOS `AVPlayerViewController.contextualActions = [UIAction(…)]` is the ONLY mechanism producing a focusable button coexisting with the transport-bar focus context** (custom subviews/overlays/`preferredFocusEnvironments` unreachable while `AVPlayerViewController` on screen — applies to any future in-player affordance). **RULE — auto-skip is OPT-IN and decided by the pure `AutoSkipPolicy` (`AutoSkipPolicy.swift`), on both engines**: `playback.autoSkipIntro` / `playback.autoSkipCredits` (default `false`, Settings → Playback) make the button press itself. Three refusals are load-bearing and locked by `AutoSkipPolicyTests`: **once per segment per media** (`autoSkippedSegmentKeys`, keyed on type + start, reset with the segments — a rewind into the intro is honoured, not skipped again), **never while paused**, **never in a SyncPlay group** (the group owns the playhead, and a local seek would go out as a server Seek). The VLC path additionally refuses while a seek is settling (`seeks.isSettling` — the reported position may be the echo of a target not yet reached), and an outro with autoplay armed hands off through `navigateToEpisode(isAutoplay: true)` instead of seeking to the end; the AVPlayer path always seeks to the segment's end and lets `didPlayToEndTime` run its existing autoplay branch. Preferences are read once per media open (`AutoSkipPreferences.current()` in `fetchSegments` / `SkipSegmentController.load`), so a toggle flipped mid-session applies at the next episode. Each auto-skip logs one `auto-skip type=… action=…` line.
- **Chapters** (tvOS only): `BaseItemDto.chapters` → `AVPlayerItem.navigationMarkerGroups = [AVNavigationMarkersGroup(...)]`. `AVNavigationMarkersGroup` tvOS-only; iOS `#if os(tvOS)` no-op. **RULE — the thumbnail phase is DEFERRED until playback is running and CHUNKED at 6** (`ChapterController.pendingMarkers` + `startDeferredMarkers()`, released from the presenter's existing 1 s tick on `rate > 0`): `fetchAndApply` runs while AVKit is opening the stream, so one GET per chapter there put up to ~40 authenticated requests inside the window the user waits through for the first frame — the same lesson `VLCStreamPresenter` learned with `pendingChapterThumbnails`, which the native path had never adopted. Nothing is lost by waiting: AVKit is handed `navigationMarkerGroups` **once**, so the bar never appeared before every image had landed anyway. The item fetch and `onSeriesNameResolved` still run immediately — the end-of-series overlay needs that name.
- **Sleep timer**: `SleepTimerOption` (Off/15/30/45/60/90) via `@AppStorage("sleepTimerDefaultMinutes")`. On fire: pause + "Still watching?" - **Debug tooling** (Settings → Playback → Debug section, always visible): `debug.fastSleepTimer` (→15s); `debug.showSkipToEnd` (seeks to `duration−15s`); « Exporter les diagnostics » (iOS — see the Debug section under Settings).
- **Apple TV Remote widget metadata (`NowPlayingInfoController`)**: shared by Native and VLC paths. Owns `MPNowPlayingInfoCenter.default().nowPlayingInfo` (title / artwork / elapsed / duration / rate / `MPMediaItemPropertyAlbumTitle = seriesName` / `MPMediaItemPropertyArtist = "S{parentIndexNumber}E{indexNumber}"`). `attach` publishes a title-only placeholder immediately so the iPhone Lock Screen widget fills in <1s, then runs `getItem` (enrich series + S×E×). **RULE — artwork fetch is sequenced behind that same `getItem`, not fanned out in parallel**: only the resolved item exposes `primaryImageTagValue`, needed to cache-bust the poster URL now that it rides Nuke's disk cache (`AuthenticatedImageFetch`, see Image Patterns) — a tagless artwork URL would mask a server-side poster edit until LRU eviction. The `getItem` call is single-flighted + 10s-cached (Task 3), so the extra hop is normally a cache hit; the placeholder dict covers the visible gap. On enrichment failure the artwork still fetches, untagged, rather than being dropped. `update(elapsed:duration:rate:)` runs from each presenter's existing 1s tick (no second timer); both engines also call it from their play/pause state-change paths for sub-second widget sync. `RemoteCommandController` is the buttons; `NowPlayingInfoController` is the metadata — never merge them.
- **RULE — `MPMediaItemArtwork` request handler MUST be `@Sendable`**: MediaPlayer invokes it on a background queue. Without explicit annotation the trailing closure inherits the enclosing `@MainActor` Task's isolation and tvOS 26 traps it with `dispatch_assert_queue` ("Block was expected to execute on queue …"). Always write `MPMediaItemArtwork(boundsSize: image.size) { @Sendable [image] _ in image }`.
- **RULE — Episode-nav race guard on metadata fetch**: `NowPlayingInfoController` bumps an internal `generation: Int` at every `attach`/`detach` and re-checks it before writing back from the `getItem` enrich task and the artwork fetch task. A slow poster arriving after a next-track press must not overwrite the new episode's metadata — without the guard, the user sees the wrong artwork on the iPhone widget for several seconds.

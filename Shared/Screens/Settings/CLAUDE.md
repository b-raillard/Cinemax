## Settings Screen

Three-level navigation. Landing — tvOS: split (left brand, right nav pills, persistent accent bloom); iOS: vertical scroll + `NavigationStack`. Non-admin categories, in `SettingsCategory` declaration order: **Appearance / Interface / Playback / Account / Server** (admin adds Administration + Advanced admin, iOS only). Detail pages — tvOS `ScrollView` + back via `.tvBackAction` on the coordinator (NOT a local `onExitCommand` — see the tvOS Menu-button RULE under Navigation), iOS pushed. **Interface is itself a hub** of sub-pages (Main Menu / Home page / Library / Detail page — `InterfaceSubcategory` enum); iOS routes via a second `.navigationDestination(item: $selectedInterfaceSub)` on the landing scroll; tvOS uses the same state-machine pattern as the category level. Interface hub uses the same pill chrome as the Settings landing (`iOSInterfaceSubButton` mirrors `iOSCategoryButton`, with `accentContainer` fill on the first row).

- **Playback is top-level** (`settings.playback` = « Lecture », icon `play.rectangle`) — it was `InterfaceSubcategory.playback`, and `.playback`/`.debug` are gone from that enum. The page hosts `playbackToggleRows` + the sleep-timer row, then a « Débogage » section (`settings.debug` header + `debugToggleRows`). Both platforms, not admin-gated (`iOSPlaybackDetail` / `tvPlaybackDetail`).
- **RULE — no subtitle APPEARANCE settings (size, colour, outline, box); all four were removed on 2026-09-14 at the product owner's request, and must not be re-added without a way to reach ASS tracks.** Size (`libvlc_video_set_spu_text_scale`) and colour / outline / box (`--freetype-*` instance arguments, #162) only ever reached TEXT subtitles drawn by `freetype`. An ASS/SSA track — the ordinary format of anime releases — is decoded ONLY by `libass` in libVLC 4.0.6, which renders the file's own styles into bitmaps and reads none of those options: measured on the tvOS simulator (Dragon Ball Daima, settings at 200 % / cyan / opaque box) the log read `spu decoder = libass` and the picture showed plain white 100 % text. Forcing another decoder does not help: `:codec=subsdec,any` does reach the decoder (`looking for spu decoder module matching "subsdec,any"`), `subsdec` refuses SSA, and libass is picked anyway. The only remaining route — asking Jellyfin for the ASS track converted to SRT and loading it as a slave track, which also discards the ASS layout — was judged not worth its cost. Keys `playback.subtitleTextSize` / `.subtitleColor` / `.subtitleOutline` / `.subtitleBackground` may linger in existing installs' `UserDefaults`; nothing reads them. The player keeps running on `VLCInstance.shared` with `VLCEngineLog.installOnce()`.
- **Interface → Library** (`settings.interface.library`, icon `books.vertical`) hosts the library-layout row (`settings.libraryLayout`, now labelled « Disposition »/« Layout » — the old « Bibliothèque » label would repeat the sub-page title) and, tvOS only, the `dimUnfocusedPosters` toggle. Both moved OUT of Appearance.
- **Licences open source** (`LicensesView`) list hand-written versions — **bump them with every dependency upgrade** (they still said SDK 0.6.0 / SwiftVLC 0.3.0 a day after 3.1.0 / 1.0.0 shipped). CI fails on a mismatch with `Package.resolved` (`scripts/dependency-audit.py check`, see Dependencies in the root `CLAUDE.md`), and — since 2026-09-22 — also on an entry no longer resolved and on a resolved package the screen does not credit: the five Apache-2.0 packages the SDK links (swift-nio, -transport-services, -atomics, -collections, -system) are credited, `URLQueryEncoder` is gone. A transitive package ships in the binary just the same, so it is credited just the same. They live in the **landing footer** on both platforms (iOS `iOSLicensesFooter` under `iOSDeviceInfo`; tvOS `tvLicensesButton` under `tvSystemInfoBar`, reached by pressing down past the last category pill) — no longer on the Server page. Presentation is unchanged (`showLicenses` `@State` + the `.sheet` on the shared `body`).
- Landing composition is locked by `SettingsCategoryTests` (`Tests/CinemaxKitTests/MenuConfigStoreTests.swift`): `visibleCases` order, admin gating (the two admin categories are iOS-only), both-platform reach of `.playback`, and `InterfaceSubcategory.allCases == [.menu, .homePage, .library, .detailPage]`.

- **RULE — `MenuSettingsScreen+iOS` uses native `List` + `Picker(.segmented)` + `Stepper` + forced `editMode .active`**: these are deliberate exceptions to the "never system `Toggle` in settings" rule. The user explicitly requested native iOS chrome for the Mode/Kind selectors (Picker), font-size (Stepper), and always-visible drag handles (forced edit mode → native ≡ grip with no `EditButton` needed). Per-row enable/disable still uses `CinemaToggleIndicator` Button with `.buttonStyle(.borderless)` so the List cell doesn't intercept taps. Add new system controls in Settings only with the same explicit user mandate.
- **RULE — Settings detail screens (`SettingsScreen.iOSLayout`) must NOT wrap their body in a nested `NavigationStack`**: `MainTabView`'s `Tab` block + the `MoreTabScreen`-style overflow path each already provide one, and a third nested stack silently breaks `.navigationDestination(item:)` routing for sub-page pushes (Interface → Main Menu was unreachable through the More overflow until this was fixed). Pushed destinations attach to whatever stack is closest above.
- **RULE — `SettingsScreen.tvOSLayout` lifecycle gotchas**: SwiftUI re-presents this view whenever the `TabView` reorders (every `MenuConfigStore` mutation), even with the `SettingsNavCoordinator` keeping sub-nav alive. Two consequences must be handled inside this surface:
  - `.task { loadServerUsers() }` must guard against re-fires with `@State serverUsersLoadAttempted` — otherwise every menu edit re-hits `getUsers`/`getPublicUsers` and the failure path surfaces a toast on every interaction. Failure also silently falls through (no toast); `UserSwitchSheet` does its own fetch when the user actually opens it.
  - **Never** `.onAppear { proxy.scrollTo("settings.top") }` on the outer `ScrollViewReader` — it fires on every re-presentation and yanks the page to the top, dropping tvOS focus to the active tab pill. The two `.onChange(of: selectedCategory/Sub)` handlers already cover the only legitimate "scroll back to top" case (popping out of a category / sub-page detail).

- **RULE — tvOS focus**: each row is a single focusable unit (never individual sub-items). Accent/Language rows: left/right or select cycles (`onMoveCommand`).
- **Settings row SSOT** (`Settings/SettingsRowHelpers.swift` + platform extensions): every boolean toggle declared once as `SettingsToggleRow`, rendered both platforms from same list. Catalogues: `playbackToggleRows`/`homePageToggleRows`/`detailPageToggleRows`/`debugToggleRows`. Adding/renaming a toggle = one-line edit. Expanders: `iOSToggleRowsJoined(_:accent:animated:)`, `tvToggleList(_:)` (ignores `row.tint`; `tint:` is iOS-only debug-orange). `tvActionRow(...)`, iOS atoms (`iOSSettingsRow` etc.), tvOS `tvGlassToggle`.
- **Assets**: `AppLogo.imageset` — iOS `app_logo.png` (full); tvOS `app_logo_tv.png` (front parallax layer, transparent bg, no `clipShape`).
- **Profile** (`ProfileScreen`, Account section row → `showProfile`): the signed-in user's own account — avatar, name, server, password, and the playback preferences the SERVER holds for them. iOS `.sheet` / tvOS `.fullScreenCover`, same chrome split as Watch History.
  - **RULE — the password change goes through `AuthAPI.changeOwnPassword`, NEVER `AdminAPI.updateUserPassword`.** The latter is an admin resetting somebody ELSE's password: it carries no `currentPassword`, and `AdminAPI` is a privilege boundary gated on `AppState.isAdministrator` — routing a self-service change through it would put an ordinary user's own password behind an admin gate and hand the server a payload missing the proof of identity it is entitled to demand.
  - **RULE — a 401 on that call must NOT reach `notifyIfUnauthorized`.** Here it means the CURRENT PASSWORD was wrong, not that the session expired; routing it to the expiry coordinator would sign the user out for mistyping their own password. The client's implementation deliberately rethrows without notifying, and the screen matches the status itself.
  - **RULE — a failed preference READ must never become a WRITE** (`ProfileModel.preferencesLoaded`): the save posts the WHOLE slice, so saving from this type's unloaded default would clear the account's audio language, subtitle language and subtitle mode — on every Jellyfin client it has — because one read failed on the way in. The section is disabled and says so until a real read lands. **Saves are serialised** through a chained task: each picker fires its own, every save is a server-side read-modify-write, and two overlapping ones let the second read the configuration before the first has written it. The rollback target is read INSIDE the chained work, never captured at call time, or a late failure would restore a state predating a change the server already accepted.
  - **RULE — audio / subtitle language preferences are SERVER-side (`UserConfiguration`), never another `@AppStorage` key.** Jellyfin honours them when it builds `PlaybackInfo`, so setting them here sets them for every Jellyfin client this account uses — a local copy would be a second opinion that silently disagrees with all of them. The save is **read-modify-write** on the server's own configuration: it holds a dozen fields this app never shows, and posting one built from scratch would reset every one of them. `UserPlaybackPreferences` / `ServerCulture` are scalars-only `Sendable` value types rather than the SDK's `UserConfiguration` / `CultureDto`, for the usual region-transfer reason.
- **Watch History** (`WatchedHistoryScreen`, Account section row → `showWatchedHistory`): played movies + episodes, `getItems(filters:[.isPlayed], sortBy:[.datePlayed] desc, includeItemTypes:[.movie,.episode])`, paginated 40/page via `PaginatedLoader` (mirrors the library filtered grid — `.onAppear` last-card trigger, footer spinner). Grid + chrome mirror `FavoritesScreen`/`PrivacySecurityScreen`: iOS `.sheet` (`NavigationStack` + toolbar Done); tvOS `.fullScreenCover` (custom header + accent Done + `.focusSection()`; the always-present Done button is the focusable that loading/empty/error states need). Cards carry `.mediaCardContextMenu` (un-watch drops the item on the next span refresh — same `refreshLoadedSpan` split as `FavoritesScreen`, see there). Keys `settings.watchedHistory`, `watchedHistory.empty.{title,subtitle}`.
- **Servers** (`ServersScreen`, Server-detail row → `showServers`, under the active-server card and above Refresh Catalogue): the multi-server list — same iOS `.sheet` / tvOS `.fullScreenCover` chrome as Watch History. Logging out goes through `SettingsScreen.performLogout()`, which consumes `LogoutOutcome` and toasts the auto-hop. See the Multi-server section.
- **Quick user switch**: `UserSwitchSheet` — grid → password → re-auth, `apiClient.reconnect(url:accessToken:)` without clearing server URL. Distinct from a **server** switch: same server, different account. **RULE — user list has three fetch outcomes**: `getUsers()` is admin-only (401 for regular accounts), `getPublicUsers()` returns `[]` on hardened servers where the welcome screen is disabled (Jellyfin's secure default). When both yield nothing, the sheet falls through to an informative empty state (`switchAccount.noPublicUsers.*`) with a "Connexion manuelle" CTA → `manualEntryStep` (username `TextField` + password `SecureField` → same `authenticate(username:password:)` path). Also surfaced as "Utiliser un autre compte" under a populated grid for hidden-account login. Removing the manual path silently regresses the App Store reviewer scenario.
- **Refresh Catalogue (single trigger)**: Settings → Server `apiClient.clearCache()` + posts `.cinemaxShouldRefreshCatalogue` (Home + MediaLibrary observe). **No per-page refresh buttons** — Settings is SSOT. iOS also `.refreshable`.
- **RULE — two-tier catalogue refresh** (`Notification.Name` in `AppNavigation.swift`): **tier-1 `.cinemaxShouldRefreshCatalogue`** = catalogue *content* changed / cache cleared → FULL reload (Home `reload()`, MediaLibrary genre fan-out). Posted by Settings "Refresh Catalogue", parental-controls rating limit (`PrivacySecurityScreen.ageRow`), and all Admin metadata / identify / delete flows. **tier-2 `.cinemaxItemUserDataChanged`** = ONE item's watched / resume-position userData changed → *targeted* refresh. Posted by `MediaCardContextMenu` (watched), `MediaDetailViewModel` (item/season/episode watched toggles), `HomeViewModel.mutateResumeItem` (Continue Watching), `PrivacySecurityScreen.clearContinueWatching`, **and playback itself** — see the RULE below. **RULE — PLAYBACK IS A TIER-2 PRODUCER, and it is the reason the tier-2 contract is "userData changed", not "a toggle was tapped".** `PlaybackReporter.reportStop(reason:)` posts on `.sessionEnded` and stays silent on `.episodeSwap` (the position of the episode being left really moved, but the user is still watching, so refreshing every rail mid-session would cost a burst per episode and change nothing visible). **The post lives INSIDE the detached task, after the `reportPlaybackStopped` await**: that call is what persists the position server-side AND drops the client's userData caches, so it is the first instant at which a listener can refetch and get truth — posting at call time hands every consumer the pre-playback value, which is the bug this notification exists to fix, made intermittent by the race. Before this, playback was the ONE producer of userData change that announced nothing, so each surface invented its own post-playback hook (`MediaDetailScreen` had a tvOS `lastDismissedAt` observer plus an iOS `.task`-on-pop, `MediaLibraryScreen` had two more) and `HomeScreen` — which needs it most, for Continue Watching and Next Up — was simply forgotten: measured on device 2026-08-14, a film watched from the resume rail still read "1h 44m restantes" after playback had moved it to 1h 43m, and a tab round-trip didn't help. All four hooks and `VideoPlayerCoordinator.lastDismissedAt` are gone; every consumer now reacts through the one tier-2 observer it already had. Locked by `PlaybackReporterTests` (announced once, after the server report; silent on an episode swap). **A new surface that must resynchronise after playback subscribes to tier-2 — it does NOT add a lifecycle hook.** Favorite hearts stay on their own `.cinemaxFavoritesChanged` fast path (untouched). **Playlists have a third such fast path, `.cinemaxPlaylistsChanged`** (posted by both mutation paths of `AddToPlaylistSheet` and by a reorder, consumed by `HomeViewModel.refreshPlaylists`): creating a playlist changes no item's userData, so neither tier applies — what changed is the SET of playlists and their counts. Load-bearing rather than a nicety: the Home rail is the only route to a playlist on the default menu, so without it the surface that exists to make playlists findable would be the last place to hear about a new one. **Consumers**: Home runs `HomeViewModel.refreshUserDataRails()` on tier-2 (resume + next-up + favorites, then « Parce que vous avez vu » when switched on — NO genre fan-out / latest / sessions); Favorites + WatchedHistory reload for both. **RULE — `MediaDetailScreen` observes BOTH tiers, and tier-1 answers with the full `load()`.** It is the screen the admin metadata / identify / delete flows are LAUNCHED FROM — `IdentifyFlowModel.apply` posts tier-1 and then pops straight back onto it — and it was the only one of the five surfaces not listening, so an applied change stayed invisible on the very screen that ordered it until the app was relaunched. Tier-2's `refreshAfterPlayback` cannot serve tier-1: it re-fetches only the userData-bearing slices, while a metadata change moves title, overview, cast and the image cache-buster tags. Nothing else re-fetched it either — `.task` goes through `loadInitial`, latched by `hasLoaded` (see the RULE under **MediaDetailScreen**). Before `5306dcf` that `.task` re-ran a full `load()` on every reappearance, which masked the gap; removing it — correct for the player pop — left this hole behind. The double-load the latch was introduced to kill does not come back: the tier-1 `load()` sets `hasLoaded`, so the `.task` that runs on the pop returns immediately. **RULE — that Home refresh MUST fill in episode navigation for the cards it brings in** (`fillMissingEpisodeNavigation`). It used to skip it, on the stated grounds that the nav maps "only gate the in-player prev/next buttons and tolerate brief staleness". Both halves were wrong. A nil `episodeNavigator` also silences **autoplay-next and the end-of-series card** (`handlePlaybackEnded` gates both on it) — the same mis-assessment that left Search's card menus without navigation. And it isn't staleness but **absence**: `load()` builds the maps in one pass over the rails as they were then, so a card that ENTERS a rail later has no entry at all, and nothing ever creates one until a full reload. That is the ordinary path, not an edge case — finishing an episode posts tier-2, the rails refetch, and the freshly-arrived card is exactly what the user taps next. Measured on device 2026-08-21 with a paired control: the same Continue Watching card played with **3** transport buttons by simple tap and **5** from its context menu (which resolves its own navigation), then **5** by simple tap once Home had been fully reloaded. The fill is deliberately scoped to the **missing** entries — an existing one stays valid, since navigation depends on the season's episode list and not on the card's userData — so with nothing new in the rails it issues no request at all. Locked by `HomeViewModelTests`. **RULE — `MediaLibraryScreen` answers tier-1 with a full reload but tier-2 with `MediaLibraryViewModel.refreshUserData` (→ `PaginatedLoader.refreshLoadedSpan`), NEVER a full reload.** A full reload runs `applyFilter` → `filteredLoader.reset()` → page 0, and this grid's OWN card context menu raises tier-2 — so marking an item watched under the unwatched-only filter collapsed a grid the user had paged several screens into back to 40 items, at the top, under their finger. `refreshLoadedSpan` was written for exactly this and was wired on `FavoritesScreen`/`WatchedHistoryScreen` but not here: a missed surface, not a trade-off. **The browse layout answers tier-2 with `refreshHeroNavigation()` alone — never a reload either.** It has no paginated span, so it used to fall back to `performReload()`; but `isLoading` is what swaps the body for `loadingView`, which tears the `ScrollView` down and rebuilds it, so the same "yanked back to the top under their finger" symptom hit browse mode too (reproduced on device 2026-08-14: marking a film watched from a genre row jumped the page back to the hero + first genre row). And it changed almost nothing on screen: the hero's play target was the only userData-dependent thing there. **That is no longer strictly true** — `LibraryPosterCard` now draws a watched check and a progress bar (see the `MediaCardStatus` RULE) — but the conclusion stands: those badges wait for the next full reload rather than costing the user their scroll position and an 8-genre fan-out on every toggle — so the reload refetched the hero and fanned out up to 8 genre rows for nothing. The pending-while-hidden flags mirror the two tiers (`pendingReload` subsumes `pendingUserDataRefresh`). Locked by `MediaLibraryRefreshSpanTests`. **RULE — that browse-vs-grid split asks `shouldShowFilteredView`, the authoritative predicate of the layout, NEVER `filteredLoader.items.isEmpty`.** The loader is not a proxy for what is on screen and diverges from it in BOTH directions: `LibrarySortFilterSheet` calls `onApply` from all four of its exits — **« Réinitialiser » included** (`:59`, `:68`, `:126`, `:132`) — and `applyFilter` does `reset()` then reloads 40 **unfiltered** items without ever consulting `isFiltered`, so merely validating the sheet populates a grid nothing displays, **permanently for the life of the view model** (the project's only `reset()` is `applyFilter`'s own, and `reload` replays it only `if sortFilter.isFiltered`); conversely that same `reset()` empties the loader while a grid IS displayed. Consequence measured on device 2026-08-19: **two gestures** — open the sheet, press Appliquer, change nothing — froze the hero's play target, so its Play button replayed the position resolved at page load (8:34 reached, 5:31 replayed) and could reopen an episode the user had just finished. That is **defect A reopened**; it was not introduced by #114, which merely removed the unconditional `.onAppear { refreshHeroNavigation() }` that had been masking the same faulty predicate since `06900e3`. **Do NOT 'fix' it with `guard sortFilter.isFiltered` inside `applyFilter`**: that function's other caller is the `.task(id: viewModel.sortFilter)` which legitimately loads the grid, so an iOS grid in sort-only state (`isNonDefault` true, `isFiltered` false) would never load at all. The Films tab cannot test any of this — its hero is a movie, `refreshHeroNavigation` returns on `guard heroItem?.type == .series` before writing or logging, and the grid branch draws nothing in browse layout, so **both branches are silent** and a control written there passes either way. Discriminating requires the Séries tab plus the `hero-nav ready` debug line. **Deferral**: Home + MediaLibrary track `@State isVisible` (flipped in `.onAppear`/`.onDisappear`) — while hidden inside `TabView`, a notification only sets a pending flag and the reload runs on next `.onAppear` (a pending full reload subsumes a pending targeted one; several tier-2 events coalesce into one). Degrades safely: if `onDisappear` never fires, `isVisible` stays true and behavior is the old immediate reload. `mutateResumeItem` no longer calls `refreshResume` directly — it posts tier-2 and Home's own handler fetches the resume rail exactly once (no double-fetch).
- **RULE — `getItems` / `searchItems` take `enableTotalRecordCount` (default `true`), and a caller that doesn't READ the total passes `false`.** `totalRecordCount` costs the server a second query — a `COUNT` over the whole match, ignoring `limit` — and most call sites render a fixed page and never look at it: that was ~10 needless COUNTs per Home load and up to 5 per keystroke of search. `false` ⇒ `totalCount` comes back **`0`**, which means "didn't count", never "no results" — so **never pass it from a caller that paginates**: `PaginatedLoader` derives `hasLoadedAll` from the total and would stop after page 0. Passing `false`: Home (every rail **and** the per-genre rows), the library's OWN genre fan-out, the search fan-out, `getPersonItems`, the collection-children fetches, `LibraryFolderBrowseScreen`'s folder list and the admin metadata browser — i.e. **every call site that doesn't read the total**. Measured on the reference server 2026-09-10: a COUNT costs ~3 ms on a 257-row match and **+42,9 ms (~25 %) on 6 657 rows**, and is indistinguishable from noise below ~500 (the 132-row case came back 24 ms *faster* with the count ON). So it is scaling insurance, not a win on a small catalogue — which is also why nothing here is worth trading a correctness risk for. Keeping `true`: `PaginatedLoader`'s three grids and `MediaLibraryViewModel`'s « 503 films » header. That header's query also carries **`limit: 1`** — only `.items.first` is read, and `totalRecordCount` is the count BEFORE `limit`, which is exactly why one query can still serve both. Locked by `HomeRailGatingTests` (both directions).
- **RULE — `PaginatedLoader` de-duplicates each incoming page against what it already holds, and paginates on `loadedCount` (what the SERVER sent), never `items.count`.** Jellyfin paginates by offset, so any movement of the underlying list between two pages shifts the window and page N+1 re-delivers the tail of page N (2026-08-24: a title added at the head under a `dateCreated` sort, plus an item leaving a filtered set). `ForEach(items, id: \.id)` on duplicated ids is **undefined** in SwiftUI — it renders one view for the duplicated identity, so a card vanishes from the grid in silence while the header still counts it (defect N: 8 card buttons for 9 slots in the accessibility tree, no cell at all at the hole). The two counters must stay apart: paging on `items.count` after dropping *k* duplicates re-requests those same *k* on every later page, and `hasLoadedAll` — derived from a count that can then never reach the total — never becomes true, so the last card's `.onAppear` fires for ever. An empty page also ends pagination whatever the total claims. De-dup is opt-in via `identity:` at init (the three `BaseItemDto` loaders pass `{ $0.id }`); an element with no identity is KEPT, since it cannot be proven a duplicate. Locked by `LibraryPaginationIdentityTests`, whose paired control differs only by `identity:` — 80 items with a duplicate vs 79 unique.
- **RULE — `PaginatedLoader.loadMore` and `refreshLoadedSpan` share one guard and QUEUE behind each other; a call arriving mid-flight is never dropped** (`Packages/CinemaxKit/.../PaginatedLoader.swift`). They must not interleave their writes, but the arriving call used to return in silence — no queue, no re-arming, no trace — and that lost user state in both directions (found in the `Rafr L2`/`L3` adversarial scenarios; the window is a network round-trip, so it is NOT reachable by gesture automation — it is provable only with a barrier, hence `PaginatedLoaderInterlockTests`). A second watched-toggle raised while the first span refresh was in flight vanished, leaving the item on screen in an "unwatched only" grid the server already knew was stale — **the screen contradicting the server with nothing to signal it**; and a `loadMore` raised during a refresh vanished too, except that one is driven by the last card's `.onAppear`, a card that has **already appeared**, so nothing ever fired it again and pagination stayed stuck until the user scrolled two screens back up. `acquireGuard(_:)` now parks the caller and the finishing pass hands the flag over **directly** (`handOverOrRelease`), never clearing it in between, so no third call can slip into the gap. At most one call **per kind** queues — two refreshes ask for the same work, so they coalesce — and `reset()` drains the queue by resuming each waiter with "give up", since their request describes a list that no longer exists. **`isLoadingMore` is therefore `public private(set)`**: parking is bounded only by the in-flight pass ending, so an outside writer raising the flag with no pass behind it would strand every later caller (it hung the suite when a test faked it). `refreshLoadedSpan` reads its span **after** its turn comes, so a page that landed while it waited is covered too.
- **RULE — the parental lock (`ParentalLockController` + the pure `ParentalLockPolicy` in CinemaxKit) gates the WHOLE Privacy & Security screen and NOTHING else, and that scope is measured, not conservative** (#177). `privacy.maxContentAge` was a plain `@AppStorage` key whose picker sat one screen away with no protection, so the cap was cosmetic: a child holding the Apple TV set it back to « Sans restriction » in three taps. The issue proposed also gating `ServersScreen`, logout and the user switch, on the grounds that a child could reach an unrestricted account — **that premise is false here**: the cap is a GLOBAL client-side filter on the shared `JellyfinAPIClient`, re-applied from `UserDefaults` by the session transitions (`AppState.restoreSession`, `applyActiveServer`) and held by `JellyfinAPIClient` itself across every `reconnect`, so switching user, switching server and logging out then back in all keep it. None of those paths lift the cap, so gating them would be pure obstacle. The one in-app path that does is the age row — hence the gate sits on this screen, once, rather than per row (one prompt, and connected devices / « Effacer Reprendre » / the search-history switch are not a child's business either). **The chrome stays OUTSIDE the gate** so Done is always reachable: a challenge nobody can dismiss is a trap, and on tvOS a cover whose only focusable is a pad would also swallow the Menu press. Credential = salt + iterated-SHA-256 digest + throttle counters, one JSON blob in the **app-private** Keychain (`parental_lock`), never the shared extension group (the widget has nothing to unlock) and never `UserDefaults` (readable and writable from a paired Mac — the whole point is that the person restrained holds the device). **Stated limits, kept in the UI's own footer**: deleting the app drops the cap AND the session, so a reinstall costs the Jellyfin password; and anyone who can read the Keychain already holds the access token, i.e. owns the session outright — the robust control is the server's per-user `UserPolicy.maxParentalRating`, which Admin → Users already edits. The Widget / Top Shelf gap this once left open was closed by #230 (the cap rides the shared session blob — see *App extensions*).
  - **RULE — the server-side ceiling is the AGE ITSELF (`maxOfficialRating = "12"`), and a fiche reached by id is gated too** (audit 2026-09-22, S2/S3). Every supported server (10.9 → 12.0, `LocalizationManager.GetRatingLevel` / `GetRatingScore`) parses an integer rating straight into that age before any country table, so `ContentRatingClassifier.maxOfficialRatingCode` (and the widget's copy) returns `String(maxAge)`; the US codes it used to send scored above the cap (12 → `PG-13` = 13, 16 → `TV-MA` = 17 on 10.10+, and 10.9 scores even `TV-PG` at 13). `ContentRatingClassifier.age(forRating:)` (and its two extension copies) reads what providers actually write, not only its table: a bare age (`16`), a trailing `+`, a `Rated ` prefix and a country prefix (`FR-12` — TMDb's form for every non-US country, i.e. an ordinary French library — or `Germany: FSK-18`); the table still wins, so `PG-13` / `-12` are unaffected. `searchItems` additionally filters locally (it feeds Siri; the paginated grids cannot, their offsets would drift). And because lists are not the only way in — an inbound « Lire sur… » from another account, a Watch Together queue, a saved shortcut, a deep link all reach `MediaDetailScreen` by id and used to auto-play — `MediaDetailViewModel.isAgeRestricted` replaces the fiche with a restricted state and `consumeIntentPlaybackRequest` refuses the automatic playback (the requested episode is checked on its own rating too) — and when the request is a Watch Together join it also LEAVES the group, whose server-side state would otherwise wait for this session's `Ready` for ever.   - **RULE — every playback is age-checked in `getPlaybackInfo` itself (`enforceContentAgeCap`), BEFORE any stream is negotiated, and an episode is judged on its series' rating too** (audit lot 6, S3 remaining hole, 2026-09-25). A Home rail card (Continue Watching / Next Up), the library hero, a poster context menu, the player's next episode, a retry — none goes through the fiche, and an episode arrives unrated (`/Shows/NextUp` does not even return the field), so all of them used to pass. Product decision: an unrated episode INHERITS its series' rating, and both must clear the cap (`ContentRatingClassifier.passes(rating:seriesRating:maxAge:)`, the same two checks the fiche makes). Refused ⇒ `JellyfinError.contentRestricted`, which `loc.userFacingMessage` maps to `detail.restricted.subtitle` — iOS `VideoPlayerView` shows it, tvOS `VideoPlayerCoordinator` alerts it, and both players' next-episode failure paths name it too (VLC also LEAVES a Watch Together group then, as the fiche does for a restricted join: the group would wait for this participant's `Ready` for ever). Free without a cap; with one, an episode costs one cached `getItem` of its series. Checked BEFORE the POST on purpose: a refused negotiation would still open a transcode or a live stream server-side. The rails themselves still SHOW such an episode (hiding it would need the series' rating for every card) — the card just refuses to play. Locked by `ContentRatingClassifierTests`.
  - **RULE — biometrics use `.deviceOwnerAuthenticationWithBiometrics`, NEVER `.deviceOwnerAuthentication`**, and `localizedFallbackTitle` is emptied. The latter falls back to the DEVICE passcode, which on the family iPad the child being restrained very plausibly knows — it would be a bypass wearing the clothes of a stronger check. Our own PIN stays the fallback, so a broken sensor can never lock the parent out; `biometricsEnabled` is therefore a flag ON a mandatory PIN, not a third mode (a "Face ID only" mode would strand the user when the sensor fails). iOS only — `ParentalLockController.biometricsAvailable` is `false` on tvOS, which hides the row rather than offering a switch nothing can honour.
  - **RULE — the biometric shortcut is armed on the enrolled SET, and only the PIN arms it** (`ParentalLockCredential.biometricDomainState`, `ParentalLockPolicy.biometricsAllowed`; audit 2026-09-22, S4). The device passcode — the very thing the RULE above assumes the child knows — is enough to ADD a face (an alternate appearance) or a finger, after which the child's own face opened the lock. `domainState.biometry.stateHash` (the iOS 18 replacement for the deprecated `evaluatedPolicyDomainState`) is recorded at enrolment / when the switch is turned on / on every PIN unlock, and a mismatch refuses Face ID and falls back to the PIN pad. **A PIN unlock never RE-arms a changed set** — the parent typing the PIN right after Face ID refused would record the set that now holds the child's face — it switches the shortcut OFF (`biometricSetChanged`, explained in the Privacy screen's Face ID row, not a toast: that screen is a sheet above the root toast overlay), and turning it back on is an explicit `setBiometricsEnabled` behind the open gate. It only arms a shortcut that was never armed (a lock enrolled before this existed). The gate keys its Face ID button on `biometricsArmed`, so it never offers one that cannot succeed. The field is optional so a stored credential keeps decoding.
  - **RULE — an open back-off window refuses even the CORRECT PIN, and a throttled attempt is refused BEFORE hashing.** The early refusal is what stops a child mashing the pad from extending the window on every press, i.e. locking the parent out of their own settings. Biometrics are deliberately exempt (a face cannot be brute-forced, so allowing it bypasses nothing) and a biometric success clears the counters — that is the parent's escape hatch. Schedule: 5 free attempts, then 30 s / 60 s / 5 min / 15 min, plateauing at 1 h — unbounded escalation would turn fiddling into a week's lockout, while this curve still puts years between an attacker and the 10 000 four-digit PINs. Counters live in the credential so a force-quit cannot clear them. Locked by `ParentalLockPolicyTests`.
  - **RULE — the back-off window is measured on the MONOTONIC clock, never the wall clock** (`ParentalLockCredential.backoffAnchor`, `ParentalLockPolicy.backoffRemaining`; audit 2026-09-22, S9). The wall clock is the restrained person's to set: moving the date forward closed an open window at once. `CLOCK_MONOTONIC` keeps counting during sleep and cannot be set, but restarts at boot — so when a reading places the boot more than `clockTolerance` (10 s) away from where the anchor placed it (the date was set, or the device rebooted), the elapsed time is unknowable and the window **restarts with its full duration**: touching the clock can only lengthen a wait. Accepted cost: a parent rebooting mid-window waits it out again (≤ 1 h) or uses Face ID, which no window blocks. A window found over is CLEARED (else a later reboot would restart it). `lockedUntil` stays written for display and for credentials predating the anchor, which are re-anchored with their remaining time capped at 1 h. `ParentalLockController.throttledUntil` is a STORED property refreshed at launch, after each attempt, when the gate's countdown ends and on every `.active` (`refreshThrottle()`, which persists a re-anchor) — a computed one handed the gate's `.task(id:)` a new value on every render.
  - **RULE — a PIN is CHOSEN with 6 to 8 digits (`minPINLength`), but one of 4 or 5 digits enrolled before 2026-09-25 still UNLOCKS (`minUnlockPINLength`, `isUnlockCandidate`)** — rejecting it would lock the parent out of their own settings. The credential records `pinLength` (at enrolment; learned at the next PIN unlock of an older credential, unknown until then), and while it is below 6 the « Changer le code » row says so (`privacy.lock.change.tooShort`). The pad and dot row take their minimum from the screen: 6 to choose, 4 to type.
  - **RULE — `ParentalLockGate` reads its controller as a NON-optional `@Environment`, against the usual optional-`@Observable` discipline.** For a gate, `nil` would mean "no lock", so a forgotten injection would silently *unprotect* the screen; a non-optional read traps in development instead. The one host is `SettingsScreen.privacySecuritySheet`, which re-injects by hand like every sheet there. Symmetrically, a Keychain blob that fails to decode reads as "no lock" (fail-OPEN) — deliberate in the other direction, since the alternative strands the parent in a screen they can never unlock, and the item is written whole so a partial write cannot produce that state.
  - `ParentalLockController` is a **process singleton** on `AppNavigation` (4th member of that set): it reads the Keychain at `init` (a synchronous `securityd` XPC hop on the main actor) and its `isUnlocked` flag is session state a scene-event recreation would re-open or drop. The unlock is closed on `scenePhase == .background` **only** — `.inactive` also fires for an app-switcher peek or a Control Center swipe, and re-asking there reads as the lock misfiring. Hashing runs on a detached task (150 000 rounds would hitch the Apple TV's main thread), and PIN entry goes through a shared ten-key pad on both platforms rather than a `SecureField`: on tvOS a `TextField` is an unstylable white capsule raising a remote-driven keyboard (the documented reason the Watch Together sheet dropped its name field), and one pad keeps the dot row visible above the keys on iOS too. Enrolment is rendered **in place** inside the screen, never a nested presentation.
- **Connected devices** (`PrivacySecurityConnectedDevicesList`, from Privacy & Security): lists every signed-in device (`getDevices`) with per-row destructive sign-out (`deleteDevice` + confirmation). **RULE — the current device** (matched via `KeychainService.getOrCreateDeviceID()`) is highlighted separately with the revoke action hidden — revoking it would log this device out. **RULE — a tvOS screen pushed inside a `.fullScreenCover` must have ≥1 focusable view in EVERY state** (loading/empty/inert cards get `.focusable()` + `.focusEffectDisabled()`): with zero focusables, focus stays on the covered root screen, so a Menu press hits the root's `.onExitCommand` and tears down the whole cover instead of popping the push.
- **Debug section** (bottom of the Playback page) always visible (not `#if DEBUG`-gated) so QA doesn't need a custom build. Icons orange.
  - **Diagnostics export** (iOS — `DiagnosticsExportRows`, `Shared/Diagnostics/`): « Exporter les diagnostics » writes ONE `.txt` (tmp/Diagnostics, the previous one superseded), then the row turns into a `ShareLink` — two steps on purpose (`ShareLink` needs its item up front, and the ready row states the line count before anything is sent). Content: a greppable header (`app_version`, `device`, `os`, `server_version` via `knownServerVersion()` — `unknown` before the probe lands, `playback_engine`, `last_playback`, `log_window`, `metrickit`), the last 30 min of **this launch's** `com.cinemax` OSLog entries (`OSLogStore(scope: .currentProcessIdentifier)` — a crash takes its log with it, which is what MetricKit is for; measured on the simulator, device not yet checked: debug/info entries come back too, and interpolations logged WITHOUT `privacy: .public` come back IN CLEAR — log privacy levels do not protect the export, `LogScrubber` does, so titles, user names and server hostnames travel in the file while tokens do not), and every stored MetricKit payload. The text is deliberately NOT localized: it is read and grepped by key. `last_playback` is `PlaybackDiagnostics.last`, written by `VLCStreamPresenter.makeMedia` (every fresh open, with the proxy route) + its error retry, and by the three `NativeVideoPresenter` sites that set `currentPlayMethod` — needed because `CINEMAX-PLAYBACK` / `iOS play:` are `#if DEBUG` and the proxy route was never logged. tvOS has neither a share sheet nor MetricKit: it shows an explanatory row whose press toasts the same explanation. Not built: `PlaybackReporter` tick history, hostname scrubbing, `mxSignpost`.
  - **RULE — every exported or libVLC-logged line goes through `LogScrubber.scrubbed` (`Shared/Diagnostics/LogScrubber.swift`), the single scrubbing SSOT — never a second scrubber.** It was `VLCEngineLog.scrubbed` and moved out when the export became its second consumer, gaining the forms a log line can carry beyond `ApiKey=`/`api_key=`: `token=` (any name ending in "token" — the `Token="…"` field of a `MediaBrowser` Authorization header, `X-Emby-Token=`, `access_token=`), the header forms `X-Emby-Token:` / `X-MediaBrowser-Token:`, and quoted values (`Token="abc"` → `Token="***"`); since audit S11 also the JSON form (`"AccessToken":"…"`, `"ApiKey": "…"`) and the percent-encoded query forms (`ApiKey%3D…`, `%` ending the value). The admin log viewer (`AdminLogViewerViewModel`) runs every line through it too: the text stays selectable — copying an error line is that screen's use — so what can be copied carries no other user's token. `DiagnosticsReport.document` scrubs per LINE (and per payload), never the joined document: the scrubber re-searches every marker from its last hit, linear per line but quadratic over a megabyte with many hits. Locked by `VLCEngineLogTests` + `DiagnosticsTests` (incl. an in-process `OSLogStore` round-trip).
  - **RULE — a fault the user cannot report goes to the SERVER, through `DiagnosticsUploader` (`Shared/Diagnostics/`, `POST /ClientLog/Document`).** The export above is iOS-only — tvOS has neither a share sheet nor MetricKit — so an Apple TV writes its OSLog where nobody can reach it, and a log nobody can read is not a diagnostic. Jellyfin has accepted client documents since 10.7: they land in the server's OWN log directory as `upload_<client>_<timestamp>_<guid>.log`, and `GET /System/Logs` lists them, so whoever owns the server can fetch the file without pairing anything to a Mac. **RULE — hand-built with `Content-Type: text/plain`, NEVER the SDK's `Paths.logFile`**: Get encodes an `Encodable` body through its JSON encoder and the server stores that verbatim — measured 2026-09-13 against the reference server, a JSON body was written as ONE quoted, escaped line, i.e. exactly the document nobody can read. Callers are faults ONLY — the picture-stall recovery and its exhausted case (reason `picture-stall` when the clock still moved, `playback-freeze` when it froze too), the open watchdog firing (`open-timeout`, `scheduleOpenWatchdog` — « Lecture impossible » comes a whole retry later, 15 s + 30 s, and a viewer facing a spinner leaves before that: a hung open after « précédent » on an Apple TV on 2026-09-14 reached the server with no document at all), and the terminal « Lecture impossible » alert (`handlePlaybackError`'s give-up branch, i.e. once the single retry has ALSO failed), and the feed watchdog's re-anchor (`feed-stall`) — throttled to one upload per 5 min **per reason** per process (a global floor would swallow the `playback-failed` that follows an `open-timeout` a retry later), fire-and-forget so a diagnostic can never delay the recovery it describes, and capped at 256 kB keeping the **tail** — the end is the fault, the start is an open ten minutes earlier (300 kB was verified accepted). **Consent is server-side and stays there**: an administrator who turns `AllowClientLogUpload` off gets a 403 and nothing is stored; and a 401 deliberately does NOT go through `notifyIfUnauthorized`, because a diagnostic must never be what drives a session-expiry cycle. **The channel is INJECTED at the app root (`DiagnosticsUploader.client`, assigned once in `AppNavigation`'s root `.task`), never reached through the player's own client**: the presenters hold a narrowed `any LibraryAPI & PlaybackAPI` slice on purpose, and widening a leaf controller's type so it could call one server-wide route would undo exactly the narrowing the slice split exists for — the compiler catches the attempt (`argument type 'any LibraryAPI & PlaybackAPI' does not conform to expected type 'ServerAPI'`). `nil` ⇒ nothing is ever sent, which is what every test gets by default. `DiagnosticsFacts.reason` adds one `reason:` header line **and only when set**, which is what keeps the manual export's header byte-identical — its exact shape is locked by `DiagnosticsTests`. Locked by `DiagnosticsUploadTests`.
  - **MetricKit** (iOS only — the tvOS SDK ships the framework but marks every class `API_UNAVAILABLE(tvos)`): `MetricKitSubscriber` is registered once from `AppNavigation.init` (a `static let`, like `configurePipeline`). **Payloads arrive at most once per 24 h and only for App Store / TestFlight builds** — a build run from Xcode gets nothing unless *Debug → Simulate MetricKit Payloads* is used. The callbacks run off-main (voice-search RULE): the subscriber is a stateless `Sendable` `NSObject` that turns each payload into `jsonRepresentation()` inside the callback and hands `Data` to `DiagnosticsStore` (`Application Support/Diagnostics/`, excluded from backup). **RULE — retention reads FILE NAMES, never file timestamps**: `<UTC stamp>-<nonce>-metrics.json` / `…-diagnostic-c<crashes>-h<hangs>.json`, so a lexicographic sort is chronological (no `FileTimestamp` required-reason read) and the Settings crash/hang count comes from the typed payload at persist time, not from Apple's undocumented JSON keys. Cap = **10 per kind** (≤ 20 files): one shared cap would let three weeks of daily metric payloads evict the crash report that matters. Files the store did not write are neither counted nor deleted.

# App extensions (Widget, Top Shelf) and deep links

> Split out of the root `CLAUDE.md` on 2026-09-22 (audit lot 5), content moved verbatim. Loaded when you work under `Widgets/`; `TopShelf/CLAUDE.md` points here. Also read it before touching `DeepLinkRoute`, `AppState.handleDeepLink`, `ExtensionSessionBridge` or `MainTabView`'s deep-link modal. The root file's cross-cutting rules (Swift 6, `@Observable` without `didSet`, lazy-container navigation, base-path URLs, xcodegen, tests) still apply. Lines tagged **RULE** override default behavior.

## App extensions & deep links

- **Targets**: `CinemaxWidget` (iOS WidgetKit) and `CinemaxTopShelf` (tvOS Top Shelf). Both embed via target dependencies in `project.yml`; all four targets share App Group `group.com.cinemax.shared` (entitlements generated by xcodegen).
- **Widget kinds** (all in `Widgets/CinemaxWidget/CinemaxWidget.swift`, families `.systemMedium`/`.systemLarge`, 4-column poster grid with a trailing "See all" tile): **Continue Watching** (`/UserItems/Resume`), **Favorites** (`/Items?isFavorite`), **Next Up** (`/Shows/NextUp`), **Recently Added** (`/Items/Latest` — bare array, not the `{Items:[]}` envelope, so its own decode). All share one `CinemaxRailKind` enum + `PosterRailProvider` + `PosterRailWidgetView` pipeline; adding a kind = one enum case + one `loadEntry` dispatch + one `JellyfinLite.fetch*` + one `Widget` struct registered in `CinemaxWidgetBundle`. **RULE — widget display strings are inline `french ? … : …`** (the extension can't link the app's `LocalizationManager`), keyed off `Locale.preferredLanguages.first?.hasPrefix("fr")`.
- **RULE — only Continue Watching carries the Lock Screen / StandBy families** (`.accessoryRectangular` + `.accessoryCircular`; the other three rails stay `.systemMedium`/`.systemLarge`). One item is all an accessory fits, and « the thing I was watching » is the only rail whose first item is worth a glance — a lock screen showing one arbitrary favourite says nothing. Three things the accessory path needs that the system one does not: **`maxPosters(for:)` must case them to 1** (they fell into the `3` branch and paid two poster downloads nothing would ever render), **`widgetURL(_:)` replaces the per-cell `Link`** (accessory families do not honour `Link`, so the whole view is the tap target — the item, or `cinemax://home` when there is nothing to resume), and the container background must be `.clear` (`.black.gradient` comes out as a grey slab in a vibrant render). The three degraded messages moved into one `stateMessage` read by both paths — two copies would drift.
- **RULE — the Control Center / Action-button control runs an intent SHARED BY SOURCE, not the app's own** (`ResumeControl.swift`, listed in the `Cinemax` target's `sources` the only way to share a type with an extension that links none of our frameworks). `ControlWidgetButton(action:)` needs the intent TYPE inside the extension, and **`ResumePlaybackIntent` can never compile there**: it imports CinemaxKit and JellyfinAPI, resolves its session through `IntentSessionProvider` and routes through `AppState`. `openAppWhenRun` alone does not solve that — it decides where the intent RUNS (the app process), not where it must COMPILE. So the shim's body is compiled per target through **`SWIFT_ACTIVE_COMPILATION_CONDITIONS: $(inherited) CINEMAX_APP`** on the app target only (the project's first compilation condition): the app branch forwards to `ResumePlaybackIntent`, which stays the single authority for what « reprendre » means (session bootstrap, the `privacy.maxContentAge` cap, which item, the routing through `MediaDetailScreen`), and the extension branch is a bare `.result()` that satisfies the compiler and never runs.
- **RULE — an intent's `title` / `description` must be string LITERALS, in the widget too.** `appintentsmetadataprocessor` extracts them statically and refuses anything else — « 'LocalizedStringResource' must be initialized with a call to its initializer or a string literal » — and it fails **the whole target's metadata export**, not just the file, so the app ships with no App Intents at all. The inline `french ? … : …` form every other widget string uses is therefore illegal here: `ResumeControlIntent` carries `intent.resumeControl.*` keys resolved from the APP's catalogue (where they are read — Shortcuts, Siri), while the CONTROL's own gallery strings (`displayName`, `description`, the button `Label`) keep the inline form, being widget chrome rather than intent metadata.
- **RULE — never re-add a playback Live Activity.** The iOS Lock Screen / Dynamic Island banner shipped in 1.2.x and was REMOVED on 2026-09-13 at the product owner's request: it added nothing over `NowPlayingInfoController`, which already publishes title / artwork / S×E× / a live playhead to the Lock Screen, Control Center and the Apple TV Remote widget — for both engines and on both platforms. What went with it: `PlaybackLiveActivityController`, `PlaybackLiveActivityWidget`, the `PlaybackActivityAttributes` contract shared by source, `NSSupportsLiveActivities`, the `playback.liveActivity` setting and its row. `ResumeControl.swift` is now the ONLY type shared by source with the widget extension, so that mechanism's rationale lives there alone.
- **RULE — every binary needs its own `PrivacyInfo.xcprivacy`** (Apple's ITMS-91053 scan is per-`.app`/`.appex`): the app manifest is `Resources/PrivacyInfo.xcprivacy`; each extension carries its own (`Widgets/CinemaxWidget/PrivacyInfo.xcprivacy`, `TopShelf/CinemaxTopShelf/PrivacyInfo.xcprivacy`) — auto-bundled because each extension dir is already a `sources:` path. UserDefaults reason codes: the extensions declare `1C8F.1` — a deliberately conservative declaration kept after the plaintext-token drop (they no longer read the App-Group suite at all, but an over-declaration is never rejected, whereas re-adding an App-Group read without the entry is an ITMS-91053); `CA92.1` explicitly excludes data shared across binaries, so it's the wrong code there. The app declares BOTH `CA92.1` (its own `@AppStorage`/`UserDefaults.standard`) and `1C8F.1` (App-Group access in `ExtensionSessionBridge` — now the legacy-copy scrub); the app manifest ALSO declares `NSPrivacyAccessedAPICategoryFileTimestamp` reason `C617.1` for statically-linked Nuke's disk cache (`.contentAccessDateKey`, ships no manifest of its own). A new required-reason API on any target = update that binary's manifest. Validate edits with `plutil -lint`.
- **RULE — extensions do NOT link CinemaxKit** (widget memory budget; SDK pulls Nuke + generated entities). They read the session the app publishes via `ExtensionSessionBridge` (CinemaxKit/Persistence) and talk to Jellyfin endpoints directly (`JellyfinLite` in the widget, inline in `ContentProvider`). Publish hook: `AppState.refreshCurrentUser()` (covers login / switch / restore) + clear in `logout()`. **RULE — the in-process memo is taken only AFTER the Keychain write succeeded** (`memoAfterWrite`; audit 2026-09-22, S8): taken before, as it was, a failed write was then skipped by every later publish of the same state, and a failed clear at logout left the previous token with the widget for the rest of the process. A failed clear is retried by `ExtensionSessionBridge.retryFailedClear()` on every return to the foreground (a no-op unless one failed; any later successful publish resets it).
- **RULE — extension HTTP: token in the `Authorization` header, never the query string; ephemeral sessions only.** Both extensions send `MediaBrowser Token=` as a header on every request they issue themselves (JSON endpoints **and** the widget's poster fetch — Jellyfin image endpoints accept header auth, same split the app uses via `ImageURLBuilder` + `AuthenticatedImageFetch`), so no `ApiKey` query item rides along to be captured by URL logs or cache keys. Each extension owns a `URLSessionConfiguration.ephemeral` session with `urlCache = nil` — never `URLSession.shared`, whose disk-backed `URLCache` would persist authenticated responses inside the extension container. **No exception any more**: the Top Shelf image URLs handed to `TVTopShelfSectionedItem.setImageURL` — fetched by the SYSTEM, so no header can ride along — used to carry `ApiKey`, on the belief that the image endpoint needed it. It does not: `GET /Items/{id}/Images/{type}` has no `[Authorize]` from 10.9 to 12.0 (the app's own posters load unauthenticated), so the token bought nothing and landed in PineBoard's cache and in reverse-proxy logs on every shelf refresh (audit 2026-09-22, S5). Same for the player's chapter thumbnails and trickplay tiles, which now authenticate by header only (trickplay IS `[Authorize]`, and reads the header).
- **RULE — extension session store is a shared Keychain group ONLY — never plaintext UserDefaults**: the token lives in a **shared Keychain access group** `$(AppIdentifierPrefix)com.cinemax.shared` (`kSecAttrService = com.cinemax.jellyfin`, `kSecAttrAccount = extension_session`, accessible `AfterFirstUnlockThisDeviceOnly`) — device-only, never in backups. It replaced the old plaintext App Group `UserDefaults` copy (suite `group.com.cinemax.shared`, key `extension.session`), which the token was readable-at-rest from (backups / any group process). That transitional dual-write (1.0.3–1.0.6) is **gone**: `publish` writes the Keychain only, and `scrubLegacyDefaultsCopy()` **deletes** any leftover plaintext blob — presence-guarded (`object(forKey:)`, no write in the steady state) and run BEFORE the skip early-return, so an upgraded install is scrubbed on its first `publish` even when the session itself is unchanged. Readers (`KeychainService.readSharedSession`; inline in `JellyfinLite`/`ContentProvider`) are **Keychain-only** — no UserDefaults fallback. `appGroupId`/`sessionKey` on `ExtensionSessionBridge` survive solely as the scrub's target (locked by `ExtensionSessionContractTests`); **never re-add a token write to UserDefaults**. The full group string is resolved at runtime from the `AppIdentifierPrefix` Info.plist key (injected via `$(AppIdentifierPrefix)` on all 4 targets — avoids hardcoding the team id). **Keep the Keychain contract in sync across all three copies**: service/account/group + JSON shape (the extensions re-declare the literals; only the app links `KeychainService`). `keychain-access-groups` entitlement is on all 4 targets (xcodegen-generated); the app-private items (`server_url`/`user_session`/`access_token`/`device_id`, `servers`, `parental_lock`, `trusted_certificates`) live in the app's OWN group, which **must stay FIRST in the app targets' `keychain-access-groups`** (`$(AppIdentifierPrefix)$(PRODUCT_BUNDLE_IDENTIFIER)`): group-less writes land in the first group listed, and while the shared group stood alone every token of every server and the parental-lock verifier were readable by both extensions. `KeychainService.migrateToPrivateAccessGroupIfNeeded()` (first thing in `restoreSession`, one-shot, a `SecItemUpdate` MOVE — nothing is deleted) takes the items written by earlier builds out of the shared group; its account list is locked by `KeychainPrivateAccountsTests`. **Every write is UPDATE-then-ADD, never delete-then-add**: a failed add after the delete lost the token, the whole registry, or the parental lock (which then read as "no lock", i.e. open) — audit 2026-09-22, S1/Q1. **To validate on a signed device** (not provable in a simulator or CI): after first launch, the `agrp` of `access_token` is the app's own group. **Release: enable "Keychain Sharing" on the 4 App IDs before an App Store build** (transparent with local automatic signing). **`publish` short-circuits on an in-process memo BEFORE it reads the Keychain** (`lastPublishedInProcess`): `refreshCurrentUser()` calls it on every foreground and `SecItemCopyMatching` is a synchronous XPC round-trip to `securityd` made from the main actor — the same class of main-thread hop as `AVAudioSession`'s. Once this process has published, it knows what the store holds without asking, since nothing else writes that item (the extensions only read). The memo is a box, not a bare `Session?`, so "published nothing yet" (must consult the Keychain — the first publish of each launch) stays distinct from "published a cleared session" (must not). The Keychain check below it survives for that first publish: **`publish` early-returns before any Keychain write/notify when the decoded Keychain copy already field-matches the incoming session** (`ExtensionSessionBridge.isCurrent`, Keychain-only input) — skips the redundant `SecItemDelete`+`SecItemAdd`/`WidgetCenter.reloadAllTimelines()`/Top-Shelf poke on every no-op foreground revalidation; a corrupt/undecodable stored blob or a stale non-empty store on the clear path is always treated as changed.
- **RULE — a self-signed server's APPROVED certificate travels to the extensions inside the shared session blob too** (`Session.pinnedCertificateSHA256`; audit lot 6, 2026-09-25). The pins live in the app-PRIVATE group (`trusted_certificates`, moved there by S1), so the widget and the Top Shelf could not trust a server the app used every day: « not connected ». The app publishes the ACTIVE server's fingerprint (`ServerTrustDelegate.pinnedFingerprint(for:)`, `https` only), and both extensions install `ExtensionServerTrust` — ONE file shared by source (`Widgets/CinemaxWidget/ExtensionServerTrust.swift`, listed in the Top Shelf and both app targets; the apps carry it only so `ExtensionServerTrustTests` can test it). It mirrors `ServerCertificateTrust.decide`: a certificate the system accepts takes the default path, and a pin accepts one leaf on one `host:port` (key derived exactly like the app's — a test holds them equal). `publish(…pinnedCertificateSHA256:)` has no default, like the cap. **Known limit**: the Top Shelf's IMAGES are fetched by the system from `setImageURL`, which no delegate reaches — on such a server the shelf lists its items with blank artwork.
- **RULE — the parental content-age cap travels to the extensions INSIDE the shared session blob, and every query they make applies it** (#230). The cap lives in app-private `UserDefaults` (`privacy.maxContentAge`), which the extensions cannot read, so before this they applied **no rating filter at all**: with the cap set to 10, an 18-rated poster and title reached the iPhone Lock Screen (Continue Watching's accessory families) and the Apple TV Top Shelf — the family screen — **with no interaction whatsoever**. That is a complete bypass, where the parental lock (#177) only stopped the setting being *raised*. `ExtensionSessionBridge.Session.maxContentAge` is **`Int?` and must stay optional**: a blob written by a build predating it has to keep decoding, and the extensions read it with `try? JSONDecoder().decode` — a required field would turn every upgraded install's widget into "not connected" until the app next published. `publish(…maxContentAge:)` carries **no default value**, deliberately: a defaulted `nil` would let a future publish site forget the cap and ship a widget that silently ignores it, which is the defect itself; a new call site gets a compile error instead (same discipline as `MediaCardContextMenu`'s required `artwork:`).
  - **RULE — a cap change must call `AppState.republishExtensionSession()`** (`PrivacySecurityScreen.ageRow` does). The only publisher is `refreshCurrentUser()`, which runs on the session-establishing paths and on foreground — **never on a settings edit** — so without it the extensions keep the old ceiling until the next login or foreground, i.e. the setting looks applied and is not. `publish` is already idempotent (in-process memo + field-wise Keychain compare) and the cap is part of `Session`, so an unchanged cap costs nothing.
  - **RULE — the extensions mirror the app's per-endpoint choice, and ask for `OfficialRating` EXPLICITLY.** Server-side `maxOfficialRating` on the `/Items` family (what `getItems` / `searchItems` / `getPersonItems` do); a local filter everywhere else (what `getResumeItems` / `getNextUpEpisodes` / `getSeriesWithRecentEpisodes` do). Measured on the captured fixtures of all three supported generations: `/UserItems/Resume` returns `OfficialRating` **unasked** on 10.10.7, 10.11.11 and 12.0; **`/Shows/NextUp` returns it on none of them**; `/Items/Latest` is covered by no fixture. So the app-side habit of not passing `fields` is not a guarantee to inherit — every extension query that gets locally filtered sends `fields=OfficialRating`, which removes the unknown instead of shipping a filter with nothing to bite on. The favorites query ALSO keeps the local filter after sending the server parameter: whether a given endpoint honours it is not observable from the client.
  - **A consequence worth knowing about the APP, not just the extensions**: because `/Shows/NextUp` omits `OfficialRating` and `ContentRatingClassifier.age(forRating: nil)` answers `0`, **the app's own "À suivre" rail filter is a measured no-op**. That is half-deliberate — `ContentRatingClassifier` documents that missing ratings pass, since an episode inherits its rating from its series and arrives `nil`, and filtering on absent data would empty most catalogues — but the consequence had never been written down. Filtering episodes properly would need the SERIES' rating, which these endpoints do not return; the robust control stays the server's per-user `UserPolicy.maxParentalRating`. PLAYING such an episode is refused, though: `getPlaybackInfo` judges it on its series' rating (see the parental-lock RULEs in `Shared/Screens/Settings/CLAUDE.md`).
  - The rating table is now hand-copied into **three** binaries (the app's `ContentRatingClassifier`, `JellyfinLite.ContentRating`, the Top Shelf's own) for the same reason the `Session` shape is: the extensions link no package, and a test cannot reach their code. `ExtensionSessionContractTests` therefore locks the expected verdicts on the app side, plus the blob's wire shape in BOTH forms (with and without the cap) and the backward-compatible decode of a pre-cap blob.
- **Deep links**: `cinemax://item/{id}` (scheme registered in both Info.plists; widget posters + tvOS Top Shelf both emit it) **and, iOS only, Universal Links `https://b-raillard.github.io/item/{id}` / `/home`** (`applinks:` entitlement on the iOS target in `project.yml`; the AASA and its hosting recipe live in `docs/universal-links/` — it must be served at the HOST ROOT, which this repo's *project* Pages site cannot do, hence the user-site repo). `AppNavigation.onOpenURL` (which receives both carriers) → `AppState.handleDeepLink` → `pendingDeepLinkItemId`. **RULE — both carriers are read by the ONE pure `DeepLinkRoute.parse` (`Shared/Navigation/DeepLinkRoute.swift`, locked by `DeepLinkRouteTests`)**: same two destinations, same `isValidItemId` gate, host compared case-insensitively against `DeepLinkRoute.universalLinkHost` (the single constant the entitlement must match), extra segments / unknown verbs / query noise dropped. The Universal Link form is a safer CARRIER (iOS verifies the host's AASA against the Team ID before delivering it, so another app cannot claim it), not a richer one — the AASA `components` claim `/item/*` and `/home` only, and the no-play-verb RULE below applies to it verbatim. **RULE — an item deep link has exactly ONE route: the modal `MainTabView` presents from the tab root** (`deepLinkFallback` token → iOS `.sheet` / tvOS `.fullScreenCover`, its own `NavigationStack`, tvOS re-injects `playerCoordinator` + `.onExitCommand` dismiss), whatever the menu configuration is and whatever is already on screen. `HomeScreen` hosts **no** deep-link destination — it used to push one through a screen-root `navigationDestination(item:)`, and that is the route that dropped the link (see the RULE below). The single observer is `MainTabView.onChange(of: pendingDeepLinkItemId, initial: true)`; `initial: true` is load-bearing for a cold launch opened FROM a widget tap, where `handleDeepLink` sets the id during scene connect, before `MainTabView` mounts. The `cinemax://home` "See all" tile still just switches tabs (`pendingDeepLinkTabId`, untouched). **RULE — that modal DISMISSES ITSELF when the playback it was raised for ends** (`MediaDetailScreen.onIntentPlaybackFinished`, passed only by `MainTabView.deepLinkDetail`). The fiche is a vehicle, not a destination: the user never asked for it, and it went on covering the app — tab bar included — until « Terminé » was pressed. The signal is platform-split for one fact: iOS watches `siriPlayback` returning to nil (the `navigationDestination` popped), tvOS watches `VideoPlayerCoordinator.playerDismissals`, a counter bumped in both presenters' `onDismiss`. **That counter is for closing a HOST presentation, never a data-refresh hook** — the removal of the old `lastDismissedAt` is exactly that lesson, and tier-2 owns refreshes. `intentPlaybackInFlight` keeps an ordinary Play press, which shares the same players, from firing it. **RULE — why that one route is the modal, and why Home's push was removed rather than repaired** (#171): re-assigning a `navigationDestination(item:)` binding does **not** swap the top of a `NavigationStack`, and `HomeScreen` cannot pop a `NavigationLink` push because the stack belongs to `MainTabView` — so a link arriving while a fiche was already pushed cleared its pending state and did nothing at all, no navigation and no error (verified: the second link leaves the screen untouched). Inbound **playback** (App Intent, « Lire sur… », a Watch Together join) was moved to the modal first; a plain widget / Top Shelf `cinemax://item/{id}` kept the push route "to preserve widget UX" and kept the defect with it. Both now take the modal, which removes the defect **and** the variant — a menu with no Home tab already had no other route. Cost, accepted deliberately: a widget tap opens a sheet with « Terminé » instead of a push with a back button; that is the same reading that already makes this modal dismiss itself when its playback ends — the fiche is a vehicle, not a destination. **Repairing the push instead would have meant migrating Home to value-based navigation**: the app has zero `NavigationLink(value:)` and zero `navigationDestination(for:)`, so a `NavigationPath` cannot represent the six closure-based pushes Home makes, and the refactor would touch `TVBackCoordinator` registration plus the card-zoom transitions. `AppState.isPendingIntentPlayback(_:)` was **deleted** with this change: it existed only to keep the two observers in step, and there is one observer now. **RULE — the item id is shape-validated before dispatch** (`AppState.isValidItemId`): accepts ONLY the two Jellyfin forms — a 32-char undashed hex string OR a canonical dashed GUID — and drops anything else, so a malformed deep link can't drive a lookup with attacker-controlled path text.
- **RULE — `TVTopShelfContentProvider` under Swift 6 strict concurrency**: use the completion-based `loadTopShelfContent(completionHandler:)`, wrap the handler in an `@unchecked Sendable` final-class box, and keep the `Task` closure body minimal (one `await Static.run(handler:)` call). Returning the non-Sendable `TVTopShelfContent` from the async override — or inlining the guard/await flow in the Task closure — trips a region-isolation checker bug ("Please file a bug", Swift 6.2.3).
- **RULE — TopShelf target MUST link `OTHER_LDFLAGS: -e _NSExtensionMain`**: the tv-app-extension product type's default entry `_TVExtensionMain` is an **empty `ret` stub in the tvOS 26 simulator runtime** — main returns instantly and dyld exits the extension (code 3) before the provider is instantiated, with zero logs and no crash report; HeadBoard silently falls back to the static Top Shelf image (verified in lldb: `TVServices\`TVExtensionMain: ret`). Foundation's generic `NSExtensionMain` drives the NSExtension lifecycle correctly. Diagnosis kit if it regresses: `boot.c` C-constructor log + `init`/invoke logs (subsystem `com.cinemax`, category `TopShelf`), trigger HeadBoard on demand with `xcrun simctl spawn <udid> launchctl kickstart -k system/com.apple.PineBoard`.
- **RULE — WidgetKit `TimelineProvider` witnesses use the same HandlerBox pattern** (NOT `@escaping @Sendable` parameter annotations): the SDK's completion annotations differ between toolchains — `@Sendable`-annotated witnesses built on Xcode 26.2 fail CI's Xcode 26.5 with the `sending`-closure error. The `@unchecked Sendable` box + minimal `Task { await Self.deliver…(handler:) }` body compiles on both.

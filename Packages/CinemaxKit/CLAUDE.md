# CinemaxKit — API surface, networking, persistence

> Split out of the root `CLAUDE.md` on 2026-09-22 (audit lot 5), content moved verbatim. Loaded when you work under `Packages/CinemaxKit/`. Anything that adds or changes an API call, a cache, a URL, a session or a Keychain item starts here. The root file's cross-cutting rules (Swift 6, `@Observable` without `didSet`, lazy-container navigation, base-path URLs, xcodegen, tests) still apply. Lines tagged **RULE** override default behavior.

### API protocol split (`Packages/CinemaxKit/.../APIClientProtocol.swift`)

`APIClientProtocol = ServerAPI & AuthAPI & LibraryAPI & PlaybackAPI & AdminAPI & SyncPlayAPI & RemoteControlAPI & PlaylistAPI`. `SyncPlayAPI` and `RemoteControlAPI` both inherit **`RealtimeSocketAPI`** (one member, `makeRealtimeSocketEndpoint()`, defaulted to `nil`): the two consumers of the realtime socket need the same endpoint, and handing out a *socket* per slice is exactly the shape that let the app open two connections onto one server-side session. View models needing multiple domains take `APIClientProtocol`; leaf controllers narrow to a slice (`PlaybackReporter`/`SkipSegmentController` → `any PlaybackAPI`; `NowPlayingInfoController` → `any LibraryAPI`; `SyncPlayController` → `any SyncPlayAPI`; `RemotePlayModel` → `any RemoteControlAPI`; `AddToPlaylistModel` → `any PlaylistAPI`). `AdminAPI` is a privilege boundary — gated on `AppState.isAdministrator`; server enforces authoritatively. `SyncPlayAPI`, `RemoteControlAPI` **and `PlaylistAPI`** members all have default no-op implementations so test mocks compile without overriding.

- **RULE — server capability gating goes through `ServerVersion`, never a speculative request** (`Packages/CinemaxKit/.../Models/ServerVersion.swift`): numeric 4-component compare (string compare is wrong — `"10.9" > "10.10"`), parses the 2-to-4 component forms Jellyfin reports plus a `v` prefix and any `-rc1`/`+build` suffix. `JellyfinAPIClient` learns the version in `connectToServer`/`fetchServerInfo` (including the cache-hit path, so "we have server info" and "we know the version" can't disagree) and **clears it in `reconnect` ONLY when the URL names a DIFFERENT server** — a multi-server switch repoints the client and a stale higher version would fire a 12.0 feature at a 10.9 box, so that case must keep clearing; but a reconnect onto the server already pointed at is the COMMON case (`UserSwitchSheet`; a refused switch no longer reconnects at all — see the switch RULE under Multi-server) and **nothing re-learns the version on those paths**, so clearing there left the whole process on "version unknown" — which every gate reads as unsupported, i.e. on a 12.0 server the library Collections row, the `/Items/{id}/Collections` reverse lookup, the lightweight `fetchUserData` and the UPnP admin row all vanished after a simple account switch. Sameness is `ServerURLNormalizer.dedupKey` (the registry's own equivalence class), never raw `URL` equality, so a trailing slash or an uppercase host doesn't read as a different box — while a different sub-path on one host does. `serverSupports(_:)` answers `false` for an unknown version, which is the common state on every cold launch (the probe is dispatched in the background by `restoreSession`), so **every gate must treat unknown as unsupported**. Thresholds live as `static let`s on `ServerVersion` (`itemUserDataEndpoint` = 10.10, `mediaSegments` = 10.10 — `GET /MediaSegments/{id}`, the Skip Intro / Skip Credits source; below it, and while the version is unknown, `getMediaSegments` returns `[]` **without a request**, which is byte-identical to the 404 a 10.9 server answered minus one failed request and one log line per playback, `SkipSegmentController` already treating an empty list as "no skip buttons" — `collectionsReverseLookup` = **12.0.0** — `GET /Items/{id}/Collections`, jellyfin#15516, `Paths.getItemCollections` since SDK 3.0; below it, and while the version is unknown, `getCollections` matches the TMDb collection id against the boxset list without probing — that list is the WHOLE server's boxsets, so it is cached `boxsets-<userId>-<age>` for 300 s and fetched without userData or extra image types; it was re-fetched on every film's fiche on every 10.x server AND during the version-unknown window of every cold launch). **Jellyfin's release after 10.11 is 12.0 — there is no 10.12** — so every new threshold is written `ServerVersion(12, …)`, and the numeric compare is what keeps `12.0.0 > 10.11.11` true. Locked by `ServerVersionTests` and `ServerCompatibilityTests`.
- **RULE — the compatibility FLOOR is Jellyfin 10.9, not 10.8**, and it has been since the SDK 0.6.0 bump (spec 10.11), not since 3.1.0: the generator no longer emits the `/Users/{userId}/…` routes, and the app depends on their 10.9 replacements — `/UserItems/Resume`, `/Items/Latest`, `/UserViews`, `/UserPlayedItems`, `/UserFavoriteItems`, `/Users/Password`, `/Users/Configuration` — in the app, the Widget **and** the Top Shelf (the last two re-declare the routes by hand, so they are not covered by a future SDK fix). Supporting 10.8 again would mean hand-building ~10 routes; say "10.9+" rather than "10.8+" when stating what the client needs, and note that nothing below 10.9 is tested — and that 10.9 itself is not measured either: the strict-decode fixtures cover 10.10 / 10.11 / 12.0 (see the fixture RULE under Multi-server). A gate whose feature arrived in 10.10 or later is still written as a `ServerVersion` threshold — the floor removes 10.8 from the picture, it does not remove the gates.
- **RULE — targeted userData reads go through `LibraryAPI.fetchUserData`, never `getItemUserData` directly**: the lightweight `GET /UserItems/{id}/UserData` (uncached — its callers want server truth right after a mutation, which is exactly what the 10 s `item-` TTL would serve stale) returns `nil` on servers below 10.10 *and* while the version is unknown, so a bare call site would silently ship "no refresh happened". `fetchUserData` owns the fallback to a full `getItem`. It takes **ids and returns a DTO**, deliberately: handing a non-`Sendable` `BaseItemDto` *into* a nonisolated async call from a `@MainActor` view model is a region transfer of a value the main actor still holds, whereas returning a freshly-decoded one is fine — so the splice (`item?.userData = …`) happens at the call site. Consumer: `MediaDetailViewModel.refreshAfterPlayback`'s movie branch (playback changes nothing else about a movie). The mock inherits the `nil` default, so every pre-existing test still exercises the fallback.

- **RULE — a slice whose implementation lives in one `JellyfinAPIClient+*.swift` file declares its own conformance THERE**, not in the aggregate `extension JellyfinAPIClient: ServerAPI, AuthAPI, … {}` list in `APIClientProtocol.swift`. Precedent: `+SyncPlay.swift`, `+RemoteControl.swift`. Adding a slice to the `APIClientProtocol` typealias without touching either place compiles the whole package fine and fails only at the first `any APIClientProtocol` call site (`IntentSessionProvider`), with a "does not conform" error nowhere near the new code.

## Network awareness

- **`NetworkMonitor`** (`@MainActor @Observable` around `NWPathMonitor`): seeds `isOnline` synchronously from `monitor.currentPath`. Consumed by the session-expiry 401 logic (offline ⇒ never logout), `StreamTransportPolicy`'s IPv6 probe scheduling, and SyncPlay gating. **RULE — Bounded timeouts**: every `JellyfinClient` takes `JellyfinAPIClient.sessionConfiguration(acceptLanguage:)` (request 30s, resource 60s, `waitsForConnectivity=false`, **`urlCache = nil`** — every request on it is authenticated, and the default config would otherwise write those responses to a disk `URLCache`; freshness is already owned by the app's `APICache`); raw PlaybackInfo POST adds `request.timeoutInterval = 20` and runs on its own ephemeral, cache-less `playbackInfoSession` (its URL carries `ApiKey` — a shared-session disk `URLCache` would persist the token at rest). The hand-built SyncPlay REST path keeps the same discipline on its own ephemeral, cache-less `syncPlaySession` (a cached `GET /GetUtcTime` would poison the clock offset). **RULE — no authenticated request rides `URLSession.shared`** (whose default disk `URLCache` persists token-bearing URLs/responses at rest): `HLSManifestLoader` (manifest/VTT fetches carry the transcoding `ApiKey`), the extensions, and `ServerReachability`/`ServerSessionRevoker` each own a private `.ephemeral` `urlCache = nil` session. `waitsForConnectivity=false` + `NetworkMonitor` detect *offline* instantly, so these only bound the "online but slow server" case — they were 8s/20s/8s but that tore whole screens down to "Serveur injoignable" when a self-hosted server briefly stalled (e.g. libVLC flooding it with AVI range-requests). `AppState.restoreSession` hydrates from keychain immediately, dispatches server calls in detached Task (non-blocking offline launch).
- **RULE — a self-signed / private-CA server certificate is trusted by EXPLICIT per-host approval, through the single `ServerTrustDelegate` (`Packages/CinemaxKit/.../Networking/ServerCertificateTrust.swift`), and never by a global "ignore TLS" switch** (#186). ATS already allows arbitrary loads for media, but a home server on `https://` with a self-signed certificate failed with a generic error and pushed the user onto plain `http://` — strictly worse than pinning a leaf they checked. The pure `ServerCertificateTrust.decide` has three outcomes and the ORDER is load-bearing: a non-trust challenge and **a certificate the system already accepts** both fall through to `.performDefaultHandling` (so a server that later moves to a real CA, or renews inside a private CA the device now trusts, keeps working with nobody clearing anything), an **unpinned host also falls through** — that is the non-regression property that makes the whole feature invisible to every ordinary server — a matching fingerprint is accepted, and a **changed** fingerprint is refused and re-prompts rather than silently connecting. Wired into every session the app owns: the five `JellyfinClient(` constructions (via `sessionDelegate:`), `JellyfinSocket` (`wss://`, or « Lire sur… » and Watch Together would be the two features still broken after approval), both `ServerReachability` sessions (else the status dot reads « injoignable » on a server the app is happily using), `playbackInfoSession`, `HLSManifestLoader`, `CinemaxStreamProxy` and Nuke's pipeline (else the app signs in and browses with every image blank). **libVLC is covered through the loopback proxy**: it has its own TLS stack with no per-connection trust hook, so such a server routes through `CinemaxStreamProxy`, which fetches with `URLSession` and therefore through the delegate. Locked by `ServerCertificateTrustTests`.
  - **RULE — a redirect never carries the token to another host** (`AuthenticatedRedirect`, applied by `ServerTrustDelegate`'s task-level `willPerformHTTPRedirection`; audit 2026-09-22, S11). URLSession copies the original headers — `Authorization` included — onto the redirected request whatever host the `Location` names. The redirect is still FOLLOWED (a `.strm` item legitimately bounces elsewhere; refusing would be a playback failure), but onto another host, or from `https`/`wss` down to a clear scheme, the credential headers and any `ApiKey` / `api_key` query item are stripped. `Get`'s and Nuke's `DataLoader`s both forward this callback to the delegate they are handed (checked in their sources), so the one implementation covers every session. Locked by `AuthenticatedRedirectTests`.
  - **RULE — the delegate implements ONLY the TASK-level challenge callback (`urlSession(_:task:didReceive:completionHandler:)`), never the session-level one.** Measured in both libraries that own their own `URLSession`: `Get`'s `DataLoader` (which backs `JellyfinClient`) casts the delegate it is handed to `URLSessionTaskDelegate` and forwards only the task-level method, defaulting to `.performDefaultHandling` when nobody answers; Nuke's `_DataLoader` does exactly the same. A delegate implementing only the session-level method is accepted by both APIs and then **never called** — the certificate goes on being refused with no trace anywhere. For the sessions we construct ourselves, URLSession falls back to the task-level method when the session-level one is absent, so this single implementation serves both roles.
  - **RULE — the pin is keyed by `host:port` in ONE app-private Keychain item (`trusted_certificates`), NOT on `ServerEntry`** — a deliberate deviation from the issue, which proposed the field on the entry. The approval has to happen on `ServerSetupScreen` **before any entry exists**: you cannot reach the server to sign in until its certificate is accepted, and the entry is only created by a successful login. `host:port` is also exactly what a TLS challenge hands the delegate, so no resolution step can disagree with the lookup — and it keeps `ServerRegistry.upsert` and its user-owned-field rule untouched. `ServerCertificateTrust.trustKey` fills in the scheme's default port on both sides so `https://host` and `https://host:443` cannot name two pins, and a sub-path is dropped (it is not part of the TLS identity). `AppState.removeServer` forgets the pin — one outliving its server would pre-approve whatever answers on that host:port later.
  - **RULE — the delegate reads the pin store ITSELF, behind a 5 s cache, instead of having `AppState` push a map into it.** A pushed map needs an owner, an ordering and a refresh on every load path — the exact shape of the "who owns the refresh" defects this project keeps collecting — whereas a self-read has no initialisation order to get wrong, and a TLS challenge happens once per connection, not per request. An approval drops the cache so the very next challenge sees it.
  - **RULE — Nuke's existing `DataLoader` is MUTATED (`(config.dataLoader as? DataLoader)?.delegate = …`), never replaced.** `ImagePipeline.Configuration.withDataCache` has already configured that loader's session (notably its `urlCache`), so a fresh `DataLoader()` would silently restore Nuke's default HTTP cache on top of the 500 MB data cache. Nuke's own documentation prescribes this exact line for handling authentication challenges. In `CinemaxStreamProxy` the delegate is installed as the **session** delegate while every request keeps `UpstreamHandler` as its own **per-task** delegate; that type implements no challenge callback, so URLSession falls back to ours and the backpressure machinery is untouched.
  - **The approval prompt shows subject, serial and SHA-256 fingerprint — deliberately no issuer and no validity dates**, which the issue asked for: `SecCertificateCopyValues` is macOS-only and no public iOS/tvOS API exposes them, so rendering those two strings would mean hand-rolling an X.509/ASN.1 parser for a confirmation dialog. The fingerprint is what actually identifies the certificate and what gets pinned. The failure set that opens the prompt is wider than the issue's `-1202`: `-1200…-1204`, because a NAS certificate that is self-signed **and** out of date reports `-1201` and a private-CA one `-1203`. **Known gap, not closed**: the Widget and Top Shelf carry their own sessions and are NOT covered — they need the pin in the shared Keychain group, which is its own change.
- **Legacy-downloads janitor**: `AppNavigation.purgeLegacyDownloads()` (iOS, root `.task`) deletes the pre-1.0.5 `Application Support/Cinemax/Downloads/` tree + the `downloads.userFlagCache` UserDefaults key left by the removed offline-downloads feature (App Review 5.2.3).

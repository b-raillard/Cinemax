# Cinemax - Jellyfin Client for Apple Platforms

Native Jellyfin client for iOS 26+ and tvOS 26+. "Cinema Glass" design system (dark glassmorphism, editorial layouts, no borders). SwiftUI multi-platform, single Xcode project (iOS + tvOS targets). Swift 6 strict concurrency.

> This file = rules, gotchas, and non-derivable context. Feature *behavior* is derivable from the code — read the owning file. Lines tagged **RULE** override default behavior.

## Architecture

- **CinemaxKit** local Swift Package at `Packages/CinemaxKit` — networking, models, persistence.
- `@Observable` + `@MainActor` for all state. `JellyfinClient` wrapped with `NSLock` + `nonisolated(unsafe)` for Sendable.
- **RULE — iOS `NavigationStack`**: destinations pushed via `navigationDestination(item:)` render in a separate context — `@Observable` changes won't re-render unless the destination is a standalone `View` struct with its own `@Environment` properties, not an extension method returning `some View`.
- **RULE — Lazy-container navigation**: SwiftUI silently ignores `navigationDestination(item:)` inside `LazyVGrid/LazyVStack/LazyHStack/List`. Hoist the modifier to a non-lazy ancestor; bubble the action up via a callback that mutates a screen-level `@State`. Reference: `AdminItemMenu.onSelectDestination` → screen-level `@State AdminMenuPushIntent?`. Used by `MovieLibraryScreen`, `MediaDetailScreen`.
- **RULE — never `ForEach` over an index snapshot while subscripting the live collection**: `data: Array(vm.items.indices)` + `{ idx in card(vm.items[idx]) }` crashes with `Fatal error: Index out of range` the moment the collection shrinks. Observation invalidates the already-instantiated `LazyHStack`/`LazyVStack` children **directly**, so they re-run their body against the emptied array *before* the ancestor's `!items.isEmpty` guard gets a chance to remove the row. Always pass the elements themselves + a stable `id:` keypath. Reference: `HomeScreen.watchingNowRow` — `HomeViewModel.reload()` sets `activeSessions = []` as its first statement, so every pull-to-refresh with the "En direct" row on screen crashed. Applies to any `@Observable` collection rendered through `ContentRow`.
- **RULE — Singleton root stores** (`AppNavigation.swift`): `AppState`, `NetworkMonitor`, `MenuConfigStore` are `private static let` process singletons assigned into `@State` — scene-event struct recreation could otherwise redo main-thread disk work. `ThemeManager`/`ToastCenter` are NOT in this set.
- **RULE — Hand-built URLs must preserve the server base path** (`URLComponents+ServerPath.swift`): assigning `components.path` directly REPLACES the whole path, silently dropping the sub-path of sub-path-hosted servers (`https://host/jellyfin`) — every hand-built URL 404s while SDK-routed calls keep working. Always route through `setEndpointPath(_:preservingBasePathOf:)`. Applies to all hand-built endpoints (playback direct-stream, every `ImageURLBuilder` URL, SyncPlay REST/socket); Widget + Top Shelf carry a local copy (can't link CinemaxKit).

### iOS 26 / tvOS 26 API rules (all RULE)

- **`UIButton`**: use `UIButton.Configuration`; never `UIButton(type:)` + `setTitle/titleLabel?.font/backgroundColor/contentEdgeInsets`. Pattern in `NativeVideoPresenter`. Frosted bg via `config.background.customView = UIVisualEffectView(...)`.
- Free SwiftUI helpers returning `some View` that touch `PrimitiveButtonStyle.plain`/`Font`/etc. must be `@MainActor`.
- **iPad**: `UIRequiresFullScreen` removed (deprecated); split view / Stage Manager supported. Hero/backdrop heights are clamped to a viewport fraction via `containerRelativeFrame(.vertical) { min(fixedHeight, length * 0.55…0.62) }` (iOS only — tvOS keeps fixed heights) in `HomeScreen.heroSection` / `LibraryHeroSection` / `MediaDetailScreen.backdropSection` so short windows keep content below the hero reachable. New full-bleed heroes must follow the same pattern.
- **Toolbar + Liquid Glass**: iOS 26 auto-renders `ToolbarItem` buttons with Liquid Glass. **Never** add `.buttonStyle(.glass)`/`.glassProminent` on toolbar items (nests double capsules). Active state via `.tint(themeManager.accent)` + `.fill` icon variant.

### Dependencies

`jellyfin-sdk-swift` v0.6.0, `Nuke`/`NukeUI` v12.9.0, `AVKit`/`AVPlayer`, `SwiftVLC` (libVLC 4.0, Swift 6 — [harflabs/SwiftVLC](https://github.com/harflabs/SwiftVLC), pinned **exactVersion 0.3.0**; ≥0.4.0 needs swift-tools 6.3 / Xcode 26.3+, toolchain is Swift 6.2.3 / Xcode 26.2; 0.3.0 is newest tag both 6.2-compatible AND shipping the PiP API — bump on Xcode 26.3+).

- `import SwiftVLC` works iOS + tvOS (`Player` is `@Observable @MainActor`; `VideoView`/iOS-only `PiPVideoView` are SwiftUI representables hosted in UIKit presenters via a child `UIHostingController`). Both `Cinemax` (iOS) and `CinemaxTV` (tvOS) targets link it — VLC is the default online playback engine on both.
- **RULE — Never re-add `VLCKitSPM`** — libVLC 3.x + 4.0 in one binary collide on `libvlc_*` C symbols. SwiftVLC replaced it (native PiP, object-based `Track` API fixing the audio-switch silence bug, Swift-6-native).
- **RULE — Adding a new file under `Shared/` requires re-running `xcodegen generate`** before it builds (the PostToolUse hook auto-regens only on `project.yml` edits, not new files; symptom of forgetting: "cannot find type X in scope" for a type that exists) Remote/Linux sessions (Claude Code on the web) have no xcodegen — CI still passes because it regenerates the project itself, but the committed `project.pbxproj` goes stale and local builds break; the CI "Verify committed project.pbxproj" step fails the PR until someone runs `xcodegen generate` on a Mac and commits the result. xcodegen is **version-pinned** in `ci.yml`/`regen-project.yml` (`XCODEGEN_VERSION`, official release zip — never `brew install`: heterogeneous runner brew caches made the verify step a per-runner coin flip when a formula bump changed the output format); bump the pin, the local install, and the committed pbxproj together.)
- **RULE — `@Observable` properties must NOT carry `didSet`/`willSet`**: the macro instruments setters via `withMutation { ... }`; a property observer body runs *after* the observation commits, and on collection-of-`Codable`-value-types properties (e.g. `[MenuEntry]`) the combo intermittently fails to deliver SwiftUI re-renders (symptom: bottom tab bar doesn't update after a reorder until the user taps anywhere). Pattern: keep stored properties plain `var T`, expose explicit `set*(_:)` mutator methods that mutate + persist, and use custom `Binding(get:set:)` in Pickers/Toggles so writes go through the mutator. Reference: `MenuConfigStore.setMode`/`setCustomKind` and the `Binding` projections in `MenuSettingsScreen+iOS.swift`.

### API protocol split (`Packages/CinemaxKit/.../APIClientProtocol.swift`)

`APIClientProtocol = ServerAPI & AuthAPI & LibraryAPI & PlaybackAPI & AdminAPI & SyncPlayAPI & RemoteControlAPI`. View models needing multiple domains take `APIClientProtocol`; leaf controllers narrow to a slice (`PlaybackReporter`/`SkipSegmentController` → `any PlaybackAPI`; `NowPlayingInfoController` → `any LibraryAPI`; `SyncPlayController` → `any SyncPlayAPI`; `RemotePlayModel` → `any RemoteControlAPI`). `AdminAPI` is a privilege boundary — gated on `AppState.isAdministrator`; server enforces authoritatively. `SyncPlayAPI` **and `RemoteControlAPI`** members all have default no-op implementations so test mocks compile without overriding.

- **RULE — a slice whose implementation lives in one `JellyfinAPIClient+*.swift` file declares its own conformance THERE**, not in the aggregate `extension JellyfinAPIClient: ServerAPI, AuthAPI, … {}` list in `APIClientProtocol.swift`. Precedent: `+SyncPlay.swift`, `+RemoteControl.swift`. Adding a slice to the `APIClientProtocol` typealias without touching either place compiles the whole package fine and fails only at the first `any APIClientProtocol` call site (`IntentSessionProvider`), with a "does not conform" error nowhere near the new code.

### Swift 6 `nonisolated` escape hatches (safe when body only reads parameters)

1. `View, Equatable` sub-type inside a `@MainActor` screen needs `nonisolated static func ==` (`Equatable` isn't main-actor-isolated). See `PlayActionButtonsSection` in `MediaDetailScreen.swift`.
2. A `@MainActor` class's `static func` returning non-Sendable into a `TaskGroup @Sendable` closure needs `nonisolated private static func`. See `HomeViewModel.fetchGenreItems`.
3. A `nonisolated static func` reading a `static let` needs the constant `nonisolated` too (Sendable types only). See `SearchViewModel.sanitize` + `maxQueryLength`.
4. When `nonisolated static func ==` reads a non-Sendable DTO stored property, wrap the body in `MainActor.assumeIsolated { ... }` (safe — SwiftUI diffs on main actor). See the `MediaDetail*Section` / `MediaDetailEpisodeCard/Row` extractions.
5. **`@retroactive @unchecked Sendable` for SDK value enums**: the Jellyfin SDK doesn't annotate `BaseItemKind` (a `String`-raw enum). `@preconcurrency import` silences old warnings but Swift 6.1 region-based isolation still rejects `[BaseItemKind]?` crossing async/actor boundaries or being captured by `@Sendable` closures. Bridge in `Packages/CinemaxKit/.../Models/JellyfinSendable.swift`. Strictly scope these conformances to genuinely-safe value types (String-raw enum, no associated values).

## Design System (all RULE — `docs/design-system/conventions.md` rejection checklist is authoritative; read `docs/design-system/README.md` before editing UI)

- Tokens in `CinemaGlassTheme.swift`. All `CinemaColor` use `Color.dynamic(light:dark:)`. **Never `Color(hex:)` for new tokens.**
- **Shared toggle**: `CinemaToggleIndicator` (Capsule+Circle pill), parent-driven (`Button { value.toggle() }`). Never system `Toggle` in settings.
- **No 1px borders** — use color shifts. Glass panels: `.glassPanel()`.
- **Accent**: `themeManager.accent`/`.accentContainer`/`.accentDim`/`.onAccent` — never `CinemaColor.tertiary*`. All dual-mode.
- **Dark/Light**: always route through `themeManager.darkModeEnabled =` / `themeManager.accentColorKey =` — direct `@AppStorage` writes bypass `_accentRevision` and break reactivity. `.preferredColorScheme()` applied at root in `AppNavigation` only.
- **Hardcoded `.white`/`.black`**: only inside the video player (always dark) and on saturated `accentContainer`. Else `CinemaColor.onSurface`/`.onSurfaceVariant`.
- **Font scaling**: `CinemaScale.factor` = 1.4× base on tvOS × user `uiScale` (80–130%). **RULE — no bare `.font(.system(size: N))` numeric literals** — wrap `N` in `CinemaScale.pt(...)` or use a `CinemaFont.*` token, else it ignores `uiScale`/tvOS 1.4×. Exception: Play/Lecture labels hardcode 28pt on tvOS (computed var, not a bare literal).
- **tvOS focus**: `@FocusState` + `.focusEffectDisabled()` + `.hoverEffectDisabled()`, no white bg. Indicator = **3px accent `strokeBorder` + accent-tinted halo** (`cinemaFocus()`, was 2px@0.8 + a near-invisible grey `surfaceTint` glow). Cards **scale 1.06** + brightness on focus (`CinemaTVCardButtonStyle`); CTAs (`CinemaTVButtonStyle`) add an **accent focus ring + 3pt lift + ghost-fill brighten**; round portraits (`CastCircle`) draw their **own circular** accent ring (the rectangular `cinemaFocus()` is wrong for a circle). **RULE — the 1.06 card growth (~8pt on the 6-col/32pt-gutter tvOS grid, single-item focus) never overlaps neighbours, but every card-bearing scroll row MUST keep `.scrollClipDisabled()`** so the scaled edge card isn't clipped. Opt-in `dimUnfocusedPosters` (default off) dims non-focused posters for a spotlight effect — driven by a per-card `@FocusState` in the file-private `PosterCardContent` (`LibraryPosterCard.swift`), no grid-level plumbing. Settings rows: `.tvSettingsFocusable()`. **Trait caveat**: a focused `Button` flips `UITraitCollection` to light-mode inside its label; `tvSettingsFocusable` takes `colorScheme` and injects on content + background shape — always pass `themeManager.darkModeEnabled ? .dark : .light`. **Hero `.focusSection()` rule**: any hero whose Play/More Info buttons sit in `.overlay(alignment: .bottomLeading)` of a tall `Color.clear` sizing block (Home + Library) needs `.focusSection()` on the buttons row AND the immediate row above (`tvTopBar` etc.) must also be a focus section — else up-presses get absorbed in the hero bounds.
- **iOS focus**: `.cinemaFocus()` (accent border + shadow).
- **CinemaButton styles**: `.accent` = primary CTAs (saturated `accentContainer` + `.white` text). `.primary` = neutral gradient (only on `DestructiveConfirmSheet`). `.ghost` = secondary (Retry, Clear Filters).
- **Motion Effects**: `motionEffectsEnabled` env key (from `@AppStorage("motionEffects")`). When off, all `.animation()` → nil.
- **Haptics SSOT** (`DesignSystem/Haptics.swift`, `@MainActor` enum): ALL app haptics route through it — single owner of `UIFeedbackGenerator`, collapses to no-op on tvOS. `tap` (light impact — toggles), `success`/`warning`/`error` (notification — toasts), `selection` (info toasts). Exception: the VLC player HUD owns its own feedback in the presenter files.
- **VoiceOver on custom toggles** (`SettingsRowHelpers.swift`): `CinemaToggleIndicator` is visual-only — every toggle row collapses to one element via `.accessibilityElement(children: .ignore)` + `.accessibilityLabel` + `.accessibilityValue(a11y.toggle.on/off)` + `.accessibilityAddTraits(.isToggle)` + an `.accessibilityAction` that toggles and fires `Haptics.tap()`. New custom toggles must follow the same pattern.
- Platform-adaptive via `#if os(tvOS)` or `horizontalSizeClass`.

## Navigation

- `AppNavigation` → Keychain session check → `apiClient.reconnect()` + `fetchServerInfo()`. Injects `ThemeManager`, `LocalizationManager`, `ToastCenter`, `MenuConfigStore`; applies `.preferredColorScheme()` at root.
- Flow: no server → `ServerSetupScreen` → `LoginScreen` → `MainTabView` (top tabs tvOS, sidebar iPad, bottom tabs iPhone).
- **RULE — All play buttons use `PlayLink<Label>`** (Button+coordinator on tvOS, `NavigationLink` on iOS) — never direct `NavigationLink` to `VideoPlayerView`.
- **Session expiry / 401 — confirm before logout (RULE)**: a single 401 must NEVER log the user out directly (cold-wake sockets, transient server hiccups, a flaky proxy all produce spurious 401s on a still-valid token — the Apple-TV "disconnected overnight" bug). `JellyfinAPIClient.setOnUnauthorized` → posts `.cinemaxSessionExpired`; `AppNavigation` now runs `appState.handlePossibleSessionExpiry()` which **silently re-validates** the token (`ServerAPI.validateSession()` → `GET /Users/Me`, returns `SessionValidity {valid|invalid|indeterminate}`) with a bounded 0/0.4/0.8s retry, **gated on `NetworkMonitor.isOnline`** (offline ⇒ never logout) and **debounced** (`sessionRevalidationInFlight`). Only a confirmed `.invalid` calls `logout()` + posts `.cinemaxSessionConfirmedInvalid` (the toast). `.valid` ⇒ `refreshCurrentUser()` and stay signed in; `.indeterminate` ⇒ keep session. Same coordinator drives proactive re-validation on `scenePhase .active` after a >60s background gap. Detection is the precise `JellyfinAPIClient.isUnauthorized(_:)` SSOT — pattern-matches `Get.APIError.unacceptableStatusCode(401)` (Get is a direct dep) + `JellyfinError.unauthorized` (raw PlaybackInfo POST) + `NSURLErrorUserAuthenticationRequired`; **never** the old `(401)` substring (false positives). 6 hot paths + `getPlaybackInfo` call `notifyIfUnauthorized`. **Keychain** items use `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` (readable on tvOS cold-boot relaunch; `migrateAccessibilityIfNeeded()` one-shot re-saves legacy items in `restoreSession`). **VLC player** observes background/foreground: a stream that died during sleep re-resolves a fresh `getPlaybackInfo(engine:.vlc)` and resumes from `positionAtBackgroundMs` (`reResolveAndResume`) instead of a terminal error.

### Custom menu / dynamic tabs (`MenuConfigStore`)

`MainTabView` consumes `menuConfig.resolvedTabs` (a memoized `private(set)` stored cache of the resolution of `mode` / `customKind` / persisted entry arrays / `availableViews`; recomputed via `recomputeResolvedTabs()` at the end of every mutator that changes an input — `setMode`, `setCustomKind`, `toggleInternal`, `move`, `moveBy`, `reset`, `refreshAvailableViews`, `invalidateViews`, plus `init` — NEVER a `didSet`, per the `@Observable` RULE; the recompute is equality-guarded so an idempotent refresh fires no spurious re-render). Three modes:

- **`.default`** — the canonical 5 tabs (Home, Movies, TV Shows, Search, Settings).
- **`.custom + .contentType`** — user picks which of the canonical 5 are enabled and in what order.
- **`.custom + .library`** — user surfaces individual Jellyfin libraries (returned by `getUserViews`) as tabs, filtered to video-bearing kinds (`movies`/`tvshows`/`homevideos`/nil **plus `boxsets`/`playlists`** — see `LibraryView.nonVideoCollectionTypes` blacklist; `music`/`photos`/`livetv`/`trailers`/`folders` excluded). `boxsets`/`playlists` are folders-of-folders, so they route to a different destination (see Collections/Playlists RULE below), not the flat-grid `MediaLibraryScreen`.

- **RULE — `resolvedTabs` NEVER resolves empty** (`computeResolvedTabs` falls back to the canonical default 5 when the custom/library resolution comes up empty): `MainTabView` renders exactly this array, and zero tabs = a `TabView` with no content = a fully black screen with no recovery affordance. The empty state is reachable legitimately — `.custom + .library` whose cache was wiped (`invalidateViews()` on server switch) before a fresh login re-fetches views. Locked by `MenuConfigStoreTests` ("never empty" tests).
- **RULE — the library-mode view refresh has ONE owner: `AppNavigation.onChange(of: appState.currentUserId)`** — it fires on every transition that establishes/changes the signed-in user (cold-launch restore — `restoreSession` sets the id from inside `.task`; fresh login; user switch), gated on `newId != nil && oldId != newId` + library mode. The `.task` deliberately does NOT refresh (it attaches only) — re-adding a refresh there double-fires on restore, and the historical "skip `nil → some`, `.task` owns it" guard was the post-login black-screen bug: after a server switch emptied the cache, a fresh login never re-fetched views and the bar resolved to zero tabs until relaunch.
- **RULE — `MenuConfigStore.maxEnabledTabs = 5` caps the enable-*toggle*, NOT the resolved tab count**: the cap drives `applyCap` + the toggle refusal (`ToggleResult.refusedCapReached` → toast) so the *editor* won't push a menu past 5 enabled entries via the in-app toggles. But `.custom + .library` menus can still resolve to **>5 tabs** in practice (several libraries surfaced alongside Home/Search/Settings), and iPhone `TabView` in compact width then falls back to `UIMoreNavigationController` (the "More" overflow). **That overflow is tolerated, not a bug** (product decision) — a settled >5 library layout renders and navigates fine; its quirks are cosmetic: each More entry keeps its own nav stack (a pushed detail is retained when you revisit the entry) and a Back press can pop several levels at once. The hazard the cap actually guards against is a **live mutation crossing the 5↔6 boundary while the bar is on screen** (`UIScrollView does not support multiple observers … removing old observer <UIMoreNavigationController>`, user dumped back to the first tab) — a static overflow config never trips it. Don't "fix" a library menu into ≤5 tabs on the cap's account.
- **RULE — Library-mode tabs accept `parentId: String?` + `overrideTitle: String?` on `MediaLibraryScreen`** so each library tab scopes its queries to that view id. `BaseItemKind?` is nilable on `MediaLibraryScreen`/`MediaLibraryViewModel`: `nil` means "no `includeItemTypes` filter" — needed for `Mixed`/`Other` libraries where Jellyfin items aren't reliably typed.
- **RULE — Collections (BoxSets) + Playlists are folders-of-folders → `ResolvedTab.Destination.libraryFolders`**, not `.libraryView`. `MenuConfigStore.libraryTab` detects `collectionType == "boxsets"|"playlists"` and routes to `LibraryFolderBrowseScreen` (lists the folders; tapping one pushes a scoped `MediaLibraryScreen(parentId:)` for its contents). The flat-grid `MediaLibraryScreen` can't be used directly here — its cards open item *detail*, but a boxset/playlist card must drill into a *folder*. These appear only in `.custom + .library` menus on servers that expose Collections/Playlists views; not always-on tabs (keeps the 5-tab cap / focus machinery untouched).
- **RULE — Don't tag a tab with `role: .search`** on iPhone in this app: per Apple WWDC 2024, a search-role tab is force-placed at the trailing edge of the bar regardless of declaration order, which conflicts with user-reorderable menus and was the source of "redirected to Search" after a drag. Search is a regular `Tab` here.
- **RULE — Use `Tab(value:)` over `.tabItem + .tag` on both iOS and tvOS**: the pre-iOS-18 `.tabItem + .tag` pattern doesn't preserve child-view `@State` across a `ForEach` collection diff on tvOS — every `MenuConfigStore` mutation was remounting `SettingsScreen` and dropping its sub-nav before this migration. `Tab(value:)` builds identity off the `value` and survives collection mutations cleanly.
- **RULE — Settings sub-navigation state lives on `SettingsNavCoordinator`, not `SettingsScreen.@State`**: tvOS's `TabView` is bridged to `UITabBarController` which indexes child view controllers by **position**. Any layout shift in the tab bar (toggle off, reorder, kind change) — even with `Tab(value:)` — recreates the `UIHostingController` for the tab whose position changed, dumping the SwiftUI `@State` inside. `selectedCategory` / `selectedInterfaceSub` are stored on `SettingsNavCoordinator` (`@MainActor @Observable`) instantiated on `AppNavigation` (which never remounts during normal usage) and injected via `.environment`. `SettingsScreen` exposes thin computed-property pass-throughs (`get`/`nonmutating set`) so call sites keep using `selectedCategory = X`; the `$`-projection cases use `@Bindable var nav = settingsNav` + `$nav.selectedCategory`. iOS doesn't exhibit the position-remount bug but uses the same coordinator for symmetry.
- **RULE — `MainTabView` tvOS bar renders from a `@State displayedTabs` snapshot; iOS renders `menuConfig.resolvedTabs` LIVE (never freeze iOS)**: on tvOS, rendering off the live `@Observable` reconfigures the UIKit-backed bar on every fine-grained edit, which pulls focus off the row the user is touching onto the top-bar active pill (reads to the user as a "page reload"). The tvOS snapshot is **frozen while `settingsNav.selectedInterfaceSub == .menu`** so toggle / reorder / library-refresh edits keep focus stable inside the editor; **structural** mutations bypass the freeze and refresh live: `onChange(of: menuConfig.mode)` (covers Reset which forces `mode = .default`) and `onChange(of: menuConfig.customKind)` (entire entry set is being replaced). The bar catches up the moment the user backs out of the editor. iOS has no focus engine to disturb — freezing it too was itself a bug (edits looked like no-ops while the editor was open); the 5-tab cap keeps live iOS mutations inside `TabView`'s happy path.
- Persistence is explicit (`SettingsKey.menu*`) via mutator methods on the store, **never** through property `didSet` (see Architecture RULE on `@Observable`). `refreshAvailableViews()` is idempotent (`if views != availableViews { ... }`) to avoid spurious Observation cycles during user interaction. Mandatory IDs: `[settingsID]` only — Home and Search are non-mandatory but default-on.
- **MenuSettingsScreen tvOS Mode / Kind rows use a single `CinemaToggleIndicator`**, not two pills — same shape as `tvGlassToggle` in Apparence (Dark/Light Mode). Each toggle fires a `menu.refresh.confirm` toast on flip — the bar rebuilds (entries swap, focus jumps), and the pill is the only signal that explains the re-layout to the user. **Do NOT** toast on the "Refresh libraries" row: the row already conveys status via spinner + `lastFetchError` subtitle, a duplicate pill on every tap is noise. `MenuConfigStore.lastFetchError` stores the raw `(any Error)?` (the store has no `LocalizationManager`) and logs it; **both render sites map it through `loc.userFacingMessage(for:)`** — never render it verbatim (localization RULE).

## Server Setup & Login

Two-step pre-auth flow, shared mobile design (Server → Login feels like one journey). Discovery (`JellyfinServerDiscovery` + `ServerDiscoverySheet`): UDP broadcast port 7359; probes limited (`255.255.255.255`) **and** each interface's directed broadcast via `getifaddrs`. `scan()` auto-retries once after 800ms on empty (iOS local-network permission race). `NSLocalNetworkUsageDescription` in `iOS/Info.plist`. `AppState.disconnectServer()` → `ServerSetupScreen` ("Change server") — now only the last of the four `LoginScreen` escape-hatch shapes, see Multi-server below. **Both pre-auth screens are reused verbatim to ADD a server** (`isAddingServer`), so any change here must hold in add mode too.

- **Quick Connect** (`QuickConnectSheet`, both platforms): passwordless sign-in — initiate → show 6-char code → poll until the user approves it from another signed-in session, then exchange for a session. `AuthAPI.isQuickConnectEnabled/initiateQuickConnect/quickConnectAuthorized/authenticateWithQuickConnect`; `QuickConnectRequest {code, secret}` model (secret never shown). `LoginViewModel.startQuickConnect` owns the poll loop (≈3s) + shared `completeSession`. **RULE — a transient poll failure must NOT end the flow**: the code stays on screen, so an exited Task is indistinguishable from "waiting" while approval can never complete (one Wi-Fi blip on an Apple TV killed the sign-in). Each poll catches its own error and keeps going until `quickConnectFailureBudget` (5) **consecutive** failures, resetting on any success; only `quickConnectAuthorized` is budgeted, so the exchange (`authenticateWithQuickConnect`) still fails terminally as before. Cancellation exits immediately, and a cancel-induced `URLError.cancelled` never surfaces as an error. The CTA on `LoginScreen` (both layouts) is **gated on `isQuickConnectEnabled()`** (hidden when the server has it off / pre-10.x). iOS `.sheet`, tvOS `.fullScreenCover`. Biggest win on tvOS — no password typing on a remote.
- **Quick Connect authorize side** (`QuickConnectAuthorizeSheet`, Settings → Account): a signed-in user types the 6-char code another device shows on its login screen; approving completes that device's sign-in. iOS `.sheet` / tvOS `.fullScreenCover` (tvOS `.sheet` renders cramped). iOS auto-focuses the code field; tvOS deliberately does NOT (would force-open the full-screen keyboard over the instructions).
- **`ServerHelpSheet`** ("How do I find my server?", from `ServerSetupScreen`): static help content. **RULE — chrome is platform-branched**: iOS `NavigationStack`+toolbar; tvOS full-screen cover with custom header + accent close button, because tvOS `.toolbar` on a modal clips the title and renders the trailing button as an empty pill. `PrivacySecurityScreen` uses the same pattern (iOS `.sheet`, tvOS `.fullScreenCover`); when the modal's scroll content has focusable rows, the tvOS header needs `.focusSection()` or up-presses never reach the Done button.

- **RULE — LoginScreen mobile caveat**: ServerSetupScreen's `.padding(.horizontal, spacing4)` outside `.glassPanel` is silently dropped in `LoginScreen.mobileLayout` under iOS 26. Workaround: `.frame(maxWidth: formMaxWidth)` (350pt) on form panel + actions VStack. Don't "fix" without pixel-sampling.
- **Rainbow easter egg**: top icon block is a `Button` → `AccentEasterEgg.tap(…)` (resolver in `SettingsScreen.swift`). Cycles `AccentOption.cyclingCases`; unlock flips `@AppStorage(SettingsKey.rainbowUnlocked)`. `ThemeManager` checks `isRainbow` first → HSB driven by `_rainbowHue`.

### Multi-server

Several Jellyfin servers can be registered; **exactly one is active at a time** (no cross-server browsing, no merged libraries — see "Out of scope" below). UI: `ServersScreen` (Settings → Server → *Serveurs*, and from the pre-auth screens). Storage, decisions and orchestration are deliberately three separate layers: Keychain (`KeychainService`), pure logic (`ServerRegistry` / `ServerURLNormalizer`, `Packages/CinemaxKit/.../Models/`), stateful orchestration (`AppState`, `AppNavigation.swift`).

- **Storage layout** — two new **app-private** Keychain accounts on the existing `com.cinemax.jellyfin` service (never the shared extension group): `servers` = JSON `[ServerEntry]`, `active_server_id` = the active entry's id. `device_id` stays global (one device identity across all servers). `ServerEntry.id` is a **locally minted UUID**, not Jellyfin's server id — it survives a URL edit and exists before we've ever reached the server.
- **RULE — the legacy trio (`server_url` / `access_token` / `user_session`) is a DERIVED MIRROR of the active entry.** Every pre-existing read path (`AppState.restoreSession`, `SettingsScreen.username`, `ExtensionSessionBridge`) still reads only those items, which is why multi-server needed no changes there and why a total migration failure degrades to exactly today's behavior. **Writers are exhaustively**: `AppState.applyActiveServer` (every switch — writes all three), `LoginViewModel.completeSession` (every login — writes all three together, including `server_url`), and `ServerSetupViewModel.connect`, which writes `server_url` **only when `!appState.isAddingServer`**. That last exception is load-bearing: during an add the mirror must keep describing the server the user is still signed in to, or force-quitting between the server step and the login screen would pair the NEW url with the OLD token and reconnect to the wrong server on next launch. In first-run mode nothing reads the URL until a session lands, so the historical early write is kept.
- **Migration** (`SecureStorageProtocol.migrateToMultiServerIfNeeded()`, run from `restoreSession`): one-shot, idempotent, **non-destructive** — seeds one entry from the legacy trio and never deletes a legacy item. Idempotence is keyed on "the servers list is non-empty", never a flag, so a locked Keychain at first launch just retries next launch. **RULE — it lives in the protocol extension and must NOT be overridden by a conformer** (`KeychainService` and the test `MockKeychain` run the same code, so the migration tests exercise production behavior). `clearAll()` stays scoped to the legacy trio — a plain logout must never wipe the registry.
- **RULE — `logout(reason:)` has two behaviors, and the caller must consume `LogoutOutcome`.** Common to both: strip credentials from the **active entry only** (the entry itself stays, tokenless, so its card remains in the list ready to re-login), `keychain.clearAll()`, publish a nil session to the extensions, reset auth state. `.userInitiated` additionally revokes server-side (fire-and-forget) and **auto-hops** to `ServerRegistry.nextCandidate` when one still holds a token → `.switchedTo(entry)`; the hop is invisible otherwise, so **both** Settings call sites go through `SettingsScreen.performLogout()`, which toasts `servers.switchedTo`. `.sessionExpired` (from `handlePossibleSessionExpiry`) does **no** revoke and **no** hop, and deliberately keeps `hasServer`/`serverURL` so the user lands on the SAME server's `LoginScreen` behind the expiry toast — locked by `SessionResilienceTests`.
- **RULE — a switch is two-phase and `.indeterminate` never destroys a token** (`AppState.switchTo`): a pre-flight `ServerRegistry.decideSwitch` short-circuits the cases that must not reach the network (offline, no stored token), then `validateSession()` runs against the target. `.valid` → `applyActiveServer`; `.invalid` → clear **that entry's** credentials and go to its login; `.indeterminate` → roll back to the entry captured *before* the client was repointed (`rollBackFailedSwitch` — `reconnect` + rating-cap only, never the full commit path, or a flaky network would blow away the working server's loaded screens). Never resolve the rollback target lazily through `currentActiveEntry`: its most-recently-used fallback can return the refused target itself.
- **RULE — `applyActiveServer` sets `serverURL` BEFORE `currentUserId`, and the `AppNavigation` observer declaration order is load-bearing.** A switch mutates both in one transaction; SwiftUI delivers same-transaction `onChange` handlers in declaration order, and `onChange(of: serverURL)` (→ `menuConfig.invalidateViews()`) must land before `onChange(of: currentUserId)` (the single owner of `refreshAvailableViews()`). Refresh-then-invalidate throws away the views just fetched and resolves the tab bar to zero tabs — the historical black-screen bug. Do not reorder them, and never add a second refresh owner.
- **RULE — every `AppState` transition method that mutates `hasServer` / `serverURL` bumps `serverTransitionGeneration`**, and any transition that awaits re-checks it before writing (`beginReLogin`'s `connectToServer`, `applyActiveServer`'s background `fetchServerInfo` also re-checks `activeServerId`). Covers `applyActiveServer`, `beginReLogin`, `beginAddServer`, `restorePreviousServer`, `logout`, `disconnectServer`. Same pattern as `NowPlayingInfoController.generation`. Scoped to `AppState` on purpose: `ServerSetupViewModel.connect` also writes `serverURL`/`hasServer` (the pre-auth commit) and legitimately does NOT bump — it isn't racing an awaited transition, it *is* the transition the user just confirmed.
- **RULE — the per-server status probe and the session revoke are STANDALONE and unauthenticated/off-client** (`ServerReachability.ping`, `ServerSessionRevoker.revoke`): the ping hits the public `GET /System/Info/Public` on its own bounded `URLSession` with **no auth header**, so a 401 is structurally impossible and `notifyIfUnauthorized` / `.cinemaxSessionExpired` can never fire from a dead *secondary* server and log the user out of the active one. Neither helper may ever touch the shared `JellyfinAPIClient` — the revoker builds its own `MediaBrowser` header, since the target server is not the one the shared client points at.
- **`ServersScreen` RULEs** — (a) every "is this the server we're on?" test keys on `appState.activeServerId`, **never** `currentActiveEntry` (whose MRU fallback resolves to a server the app isn't on while signed out, which is exactly the state this screen renders in when opened from the pre-auth screens); (b) pending switch / delete hold an entry **id** and re-resolve from `appState.servers` at action time — the screen's own probe writes discovered name/version back into the registry, and `ServerRegistry.upsert` **replaces** rather than merges, so a captured row snapshot would regress metadata; (c) nothing reads authenticated state (the per-entry avatar is drawn locally — `imageBuilder` points at the *active* server, so a non-active entry's avatar URL would 404 / leak a cross-server request); (d) the reachability sweep is behind an attempt flag (the tvOS Settings surface re-fires its `.task` on every `MenuConfigStore` mutation); (e) iOS uses a native `List` — a deliberate exception mandated by swipe-to-delete (`.swipeActions` exists only on `List`), same class as `MenuSettingsScreen+iOS`; tvOS uses whole-card focusable buttons with delete on a `.contextMenu`, and the active card stays focusable but inert (a disabled first row reads as a missing card) with a toast explaining the no-op.
- **Dedup** (`ServerSetupViewModel.connect`, before any network call): a URL already registered **and carrying a usable session** (`ServerEntry.hasUsableSession` — token AND user id, i.e. exactly what `applyActiveServer` accepts) is refused with `server.alreadyAdded`. **RULE — never widen that gate**: a registered-but-signed-out entry must pass through, because logging out of your only server leaves precisely that shape behind and drops the user on `ServerSetupScreen` — refusing it would lock them out of the app. `upsert` dedups on the normalized URL regardless, so the permissive branch cannot create a duplicate.
- **URL normalization** (`ServerURLNormalizer`) is the SSOT for both the URL we dial and the dedup key: lowercase scheme + host, http(s) only, default port dropped, trailing slash stripped, query/fragment/credentials dropped, **sub-path preserved** (dropping `/jellyfin` would 404 every hand-built URL — see the `URLComponents+ServerPath` RULE). IPv6 literals round-trip with their brackets.
- **Escape hatches** — `ServerSetupScreen` shows "cancel adding" while `isAddingServer` and "My servers" whenever entries exist; `LoginScreen`'s hatch is four-shaped (cancel-add → back to the rollback server → open the servers list → `disconnectServer()`), rendered on **both** layouts (tvOS/iPad previously had none, making a re-login switch a dead end). `beginAddServer()` deliberately deletes nothing, so a cancelled add replays through `restorePreviousServer()`.
- **Out of scope, deliberately**: per-server settings profiles (accent/theme/menu/rating cap stay global `@AppStorage`; only `menu.cachedViews` is server-scoped, via the existing `invalidateViews()`), simultaneous connections, server-scoped search history, per-server extensions (Widget + Top Shelf follow the **active** server only), manual reordering/renaming (order is active-first then `lastUsedAt`; names come from the server).
- **Tests**: `Tests/CinemaxKitTests/ServerRegistryTests.swift` (normalization incl. IPv6 + sub-path, migration, active-entry resolution, sorting, upsert/dedup, `decideSwitch` truth table, `nextCandidate`, and `AppState` integration for switch/logout/add/rollback/remove), plus the multi-server cases in `ServerSetupViewModelTests` and `SessionResilienceTests`.

## Video Playback

### Playback engine (VLC default — fixes the MKV/Dolby-Vision freeze)

Online playback defaults to VLC on iOS + tvOS. Settings → Interface **"Use Native Player"** (`SettingsKey.forceNativeAVPlayer`, default `false`) falls back to `AVPlayer`/`NativeVideoPresenter`.

**Why:** `AVPlayer` can't open MKV → Jellyfin forced into a 4K HEVC + DV→SDR re-encode the server can't do real-time → frozen playback. No `AVPlayer` device profile makes Jellyfin remux DV-in-MKV (DV only passes through on DirectPlay/DirectStream, never in a transcode). VLC DirectPlays the raw file → zero server transcode, 4K/HEVC/DV preserved.

- **RULE — Device profile split** (`JellyfinAPIClient+Playback.swift`): `getPlaybackInfo(... engine:)`. `.vlc` → `buildVLCDeviceProfile` (one broad DirectPlayProfile, **no container restriction** → `/Videos/{id}/stream?static=true`, no transcode). `.native` → `buildAppleDeviceProfile` (AVKit-safe codec profiles). **API default is `.native`** so internal AVPlayer-only calls are unaffected; engine chosen explicitly at `VideoPlayerCoordinator` (tvOS) / `VideoPlayerView` (iOS) from `forceNativeAVPlayer`.
- **RULE — seek-heavy containers force a server HLS transcode on the VLC path** (`isSeekHeavyContainer`: `avi/divx/wmv/asf/flv/vob/mpg/mpeg/mpe/m2v`): these keep their index at EOF, storming libVLC/origin with byte-range requests (raw AVI/XviD froze on the reverse-proxied server on BOTH direct and loopback-proxy paths — true remux impossible for XviD). On failure the code falls back to the raw stream. **The forced-transcode profile (`buildVLCTranscodeProfile` → `_vlcTranscodingProfiles`) deliberately OMITS `mp1`/`mp2`/`mp3` from its `audioCodec` allow-list, precisely to FORCE the server to re-encode audio to AAC** — when the video is transcoded but a source MPEG-audio track is *copied* into the fMP4 HLS segments, MP3's encoder delay/priming is never re-timed against the new video, giving a constant audio offset (the "son décalé" on transcoded AVI/XviD); AAC muxes cleanly into fMP4 and stays locked to the re-encoded video. **Don't "widen" that list** — re-adding MPEG audio reintroduces the desync. The broad allow-list that DOES carry `mp1,mp2,mp3` is the separate **DirectPlay** profile (`_vlcDirectPlayProfiles`, used by `buildVLCDeviceProfile`), where nothing is re-encoded and copying is exactly the point — different profile, opposite goal.
- **`VLCStreamPresenter`** (iOS+tvOS): UIKit `UIViewController` shell + all controllers/HUD; SwiftVLC `events` `AsyncStream<PlayerEvent>` consumed in one `@MainActor` Task. Rendering: child `UIHostingController` hosting the shared `PlayerEngineSurface` — `PiPVideoView` on iOS (native PiP for ALL content incl. MKV/DV via `pip.enter` → `PiPController.toggle()`), `VideoView` on tvOS (no PiP — tvOS has none). Time strings via shared `PlayerTimeFormat`; leaf transport views live in `PlayerTransportViews.swift`. Object-based track selection (no silence bug); Jellyfin defaults applied once on `.tracksChanged` by ordinal-within-type. **libVLC 4.0 has no distinct `.ended`** — end-of-media is `.stopped`, disambiguated via `isTearingDown` flag + `lastPlayStart` (>1s) + near-end guard. Auth via `api_key` **query param** (libVLC can't reliably inject the header). Full feature parity. **AirPlay-to-TV video** still impossible on any libVLC path — deferred.
- **RULE — broken-IPv6 servers route through a loopback proxy** (`CinemaxStreamProxy.swift`): libVLC's HTTPS access (`vlc_tls_SocketOpenTLS`) hardcodes `AF_UNSPEC`, ignores the `ipv4`/`ipv6` options, and has **no Happy-Eyeballs** — so a dual-stack server whose IPv6 (AAAA) is black-holed makes libVLC stall ~75s on the dead route (`URLSession` is immune; it races families). No libVLC media flag can force IPv4. `StreamTransportPolicy.shared` (`@MainActor` singleton) probes once in the background (from `AppNavigation` on launch / server change / foreground / `network.isOnline` flip): resolves the host's AAAA, opens a short NWConnection (TLS, SNI=host) to that IPv6, and sets `preferProxy` only if it **hangs** (neither `.ready` nor fast `.failed` within 4s — the genuine black-hole; an IPv4-only network fast-fails and must NOT proxy). When `preferProxy`, `startPlayback` opens `http://127.0.0.1:<port>/…` and `CinemaxStreamProxy` re-fetches each request from the real HTTPS origin via `URLSession` (Happy-Eyeballs → IPv4), streaming back with `Range` preserved. A watchdog→proxy fallback also catches black-holes the probe missed (the retry stays on the proxy, never the broken direct URL). Healthy servers keep the **byte-identical direct path** — the proxy only runs when `preferProxy` or a first direct attempt already failed. **RULE — the loopback handler (`forward`) admits a request only through the pure `CinemaxStreamProxy.admission(method:path:hostHeader:)`** — defense-in-depth on top of the 127.0.0.1-only bind: the path must be a well-formed `/s/<id>` (else 400); the `Host` header, **when present**, must be an EXACT loopback name via `isLoopbackHost` — `127.0.0.1` / `localhost` / `::1` / `[::1]`, optional `:port` stripped (else 400) — never a `hasPrefix` test, which is precisely what a DNS-rebinding host (`localhost.evil.com`, `127.evil.com`) walks through; and the method must be `GET`/`HEAD` (else 405), since anything else would be replayed to the real origin **with the account's token attached**. A missing `Host` stays allowed (libVLC doesn't always send one). Every legitimate stream URL is `http://127.0.0.1:<port>/s/<uuid>` fetched with GET, so none of this touches the real path. `admission`/`isLoopbackHost` are pure + `static` (like `parseRange`) and locked by `StreamProxyTests`.
  - **RULE — the proxy registers the origin's DIRECTORY, not one URL, so it serves a whole HLS tree.** `localURL(for:)` stores an `OriginDirectory` (scheme/host/port + the target's path minus its last component) and returns `http://127.0.0.1:<port>/s/<id>/<name>?<query>` — **keeping the media's own name and query**. That is the entire mechanism: libVLC resolves a master playlist's relative children against the URL it opened, so `main.m3u8?…` becomes `/s/<id>/main.m3u8?…` and a segment becomes `/s/<id>/hls1/main/0.mp4?…`, and `route(path:)` re-attaches each `rest` to the registered directory. One registration serves master + variant + every segment, **with no manifest rewriting**, and the 6-entry `targets` bound stays per-STREAM instead of blowing up per-segment. `OriginDirectory` derives the directory from the target's own path, so a sub-path-hosted server keeps its base path (see the `URLComponents+ServerPath` RULE). **Never go back to registering a single URL under a bare `/s/<id>`**: a manifest's children then hit an unknown id (502) or fail admission (400), and the open dies with `libvlc demux error: Failed to create demuxer 0x0 Unknown` on a frozen 0:00 screen — which is what every forced AVI/XviD transcode did.
  - **RULE — `route(path:)` refuses any `rest` component that is a dot-segment OR decodes to something containing a separator.** `rest` is re-attached to the registered directory and fetched from the origin **with the account's token**, so traversal would read arbitrary origin paths as the user. Checking only for a decoded `".."` is not enough: `%2E%2E%2Fsecret` is ONE component on the wire that decodes to `../secret`, and origins disagree on whether `%2F` separates — so the decision must not depend on the origin's decoding quirks. Components that merely *contain* dots (`..foo.mp4`, `main..m3u8`) are legitimate names and stay allowed. Locked by `StreamProxyTests`.
  - **RULE — `StreamTransportPolicy` sets `preferProxy` when `getaddrinfo` can't resolve the server host** (`hostResolvesForLibVLC`, checked before the IPv6 black-hole probe). libVLC resolves through the BSD resolver *only*; on some networks — measured on a corporate Wi-Fi — `getaddrinfo` returns `EAI_NONAME` for every URL while `URLSession` fetches the very same URL with 200 in the same second, so **nothing libVLC opens directly can work** and the loopback proxy (URLSession + a literal `127.0.0.1` peer, zero DNS) is the only path. Deliberately probed with `getaddrinfo` and **not** URLSession/Network.framework: the whole bug is that the two disagree, and libVLC only gets the former. Without this the fix still costs a failed open + a retry (~7 s of dead time) on every playback, since the condition is otherwise only discovered after libVLC has lost. `noteDirectPlaybackFailed()` is therefore unconditional again — latching is correct when the proxy is the only thing that works. A transient resolver failure costs one needless trip through the proxy (which works everywhere); the reverse mistake costs a dead playback.
  - **DEBUG — `CINEMAX_FORCE_PROXY=1`** in the environment forces `shouldRouteThroughProxy`. The proxy path is otherwise unreachable on a healthy network, i.e. never exercised on a dev machine, and it is now load-bearing. Use `SIMCTL_CHILD_CINEMAX_FORCE_PROXY=1 xcrun simctl launch <udid> com.cinemax.ios` and confirm with the stats HUD (`Via proxy · …`) plus loopback traffic to the proxy port in the log.
  - **RULE — only `noteMediaOpened()` renews `didRetry`**, called from the two signals that prove a demuxer exists (a real `lengthChanged` > 0, a moving playhead) — the same two that stand the open watchdog down. **Never from `.playing`**: libVLC reports `.playing` as soon as the input starts, *before* the demuxer is built, so a stream that never opens still emits one. Renewing there voided the "retry once" bound — every watchdog fire re-entered the retry branch, looping silently every 30 s on a frozen 0:00 screen (HUD showing pause, i.e. "playing") instead of surfacing the error alert.
  - **RULE — the proxy's `URLSession` MUST use a CONCURRENT delegate queue** (`maxConcurrentOperationCount=8`, not the default serial one). The proxy applies backpressure by **blocking** `didReceive(data)` until each loopback `NWConnection.send` lands; MKV demuxing fires simultaneous `Range` requests (reads the SeekHead/Cues near EOF *while* the `bytes=0-` stream is still open). On a serial queue the main stream's blocked callback head-of-line-blocks the seek request → VLC times out the seek → `libvlc stream filter error: cannot seek` + `damaged file?`. URLSession still serializes callbacks per-task, so a concurrent queue is safe. One request per connection (`Connection: close`); each loopback URL carries a unique `/s/<id>` resolving to its own target so a retry/episode swap can't read the wrong stream.
  - **RULE — transparent mid-stream reconnect** (`UpstreamHandler`): a reverse-proxied / HTTP-2 origin routinely RSTs a long-lived range request mid-stream. On a non-cancelled error AFTER the head was sent, the handler re-issues the origin GET at `rangeStart + bytesDelivered` (a `Range` request) and **splices the body into the SAME loopback connection** — libVLC never sees EOF, just a brief feed pause absorbed by `:network-caching`, so a transient drop is **invisible** (this is the controllable version of `:http-reconnect`, which was removed because it hung libVLC silently). The reconnect's response head is NOT forwarded; a non-206 (origin ignored `Range`) bails to a clean close so libVLC re-opens. Bounded by `reconnectsLeft`, which renews ONLY after `progressRenewBytes` (256 KB) of progress since the last reconnect — a flaky-but-feeding stream recovers forever, a trickle-then-RST loop depletes the budget and gives up. `task` is lock-guarded (read on netQueue, written on the delegate queue during a reconnect); the other counters stay lock-free (per-task callbacks are serialized and strictly sequential across a reconnect). `finish()` is one-shot (a `.cancel` disposition re-fires `didCompleteWithError`).
- **RULE — the `AVAudioSession` is owned by `PlaybackAudioSession`, never activated inline on the main actor**: `setCategory`/`setActive` are synchronous XPC round-trips to `mediaserverd` (tens of ms, unbounded under load) — called from `@MainActor` they emit Apple's own `AVAudioSession_iOS.mm:978` / `SessionCore.mm:631` warnings and stall the player's open/teardown. Both presenters route through the shared enum, which serializes every hop on one background queue. **`activate()` is `async` and MUST be awaited before the engine opens its media** — never fire-and-forget it: libVLC's aout loops forever on `CannotStartPlaying` if it opens onto an inactive session (the black-screen-after-wake bug), which is exactly what the activation exists to prevent. **Every media-opening path activates**, including episode nav — autoplay-next after an unattended sleep is precisely the `CannotStartPlaying` scenario, and it was the one path that historically skipped it. VLC's two fresh-open paths (initial `startPlayback`, error retry) go through `activateSessionThenPlay(_:)` (activate → `play` → arm watchdog); `reResolveAndResume` and `navigateToEpisode` await inline (already async). **Guards on both sides of every await**: before it, so a torn-down player never enqueues an activation *behind* its own `deactivate()` (the queue orders enqueues, it can't cancel a superseded activation → session left active with no player) — needed only where the await isn't already in the same main-actor slice as a liveness check; after it, on `isTearingDown`/`playerVC != nil` AND (VLC) `navGeneration`, since `navigateToEpisode` bumps the generation synchronously then opens its own media, so a slow activation would otherwise replay the previous episode over the new one. `deactivate()` stays fire-and-forget (teardown — nothing downstream depends on it). Voice search's `.record` session (`SearchViewModel`) is deliberately NOT part of this owner.
- `PlaybackReporter` engine-agnostic via optional `TimeSource` closure (AVPlayer → nil reads `Context.player`; VLC injects VLC time). **That closure is also the unit-test seam**: injecting it bypasses `Context.player` entirely inside `currentState`, so tick-cadence logic is testable without AVFoundation (the older "not testable without an AVPlayer" note in `PlaybackReporterTests` is obsolete).
- **RULE — the playback-session lifecycle belongs to `PlaybackReporter`, never the presenters**: `reportStop()` reports the stop **with the `liveStreamId`** (carried by `PlaybackInfo` from `mediaSource.liveStreamID` — the server opens one on every negotiation, `isAutoOpenLiveStream=true`) **then** calls `stopEncoding`, sequentially: the server must record the resume position before the job is torn down. `DELETE /Videos/ActiveEncodings` fires **unconditionally**, without consulting `playMethod` — it's a server-side no-op with nothing to kill, and the server can transcode without the client having deduced it from the response. One owner ⇒ both engines inherit it; the presenters have distinct teardowns (iOS dismiss, tvOS delegate, episode nav, PiP) and duplicating the sequence across them guarantees one path gets missed. **Keep-alive**: `POST /Playback/Ping` every **30 ticks**, only when `playMethod == .transcode` **AND** playback is paused — while the engine pulls segments the job stays active on its own, and a DirectPlay session has no job to keep alive. Cost on ordinary playback: zero requests. Any unmet condition resets `pingCounter`, so a resume can't leave a residual ping to fire moments later. **No new timer** — it rides the existing `onTick()`. The **abandon path** (PlaybackInfo obtained, playback never started) is the sole case handled in the presenters (`VLCStreamPresenter.handlePlaybackError` after the retry is exhausted, `NativeVideoPresenter.showPlaybackErrorAlert` after `retryWithDirectURL` is exhausted): `closeLiveStream` + `stopEncoding`, since no stop report will ever be sent. The three `PlaybackAPI` methods carry **empty default implementations** (`SyncPlayAPI` model) so hand-written test mocks don't have to stub session-lifecycle calls they don't exercise.
- **RULE — a failed `navigateToEpisode` negotiation MUST recover, not just log** (`handleFailedEpisodeNav`): nav entry synchronously does `reporter?.reportStop()` + `progressTimer?.invalidate()`, so an `getPlaybackInfo` failure (offline blip, server hiccup) otherwise leaves the old episode playing with a closed server session (frozen resume position) and a dead 1 s heartbeat (no sleep timer / skip segments / now-playing). Recovery is surface-split by `isAutoplay`: manual Prev/Next re-arms `resetTicking` + `reportStart(startTime: live position)` + `startProgressTimer()` and flashes the transient `skipHUD` — deliberately **non-terminal**, the episode on screen keeps playing; the end-of-episode autoplay hand-off has nothing left playing, so it presents a terminal alert with a dismiss action (`showEndOfSeriesOverlay`'s precedent). Both branches sit behind the standard `isTearingDown` / `navGeneration` guards so a second nav press during recovery can't double-arm the timers.
- **VLC player extras (both platforms unless noted)**: trickplay scrub previews (`TrickplayController` — manifest rides the same `getItem` the chapter strip does; tiles auth like chapter thumbs; silently absent when the server hasn't run the Trickplay task); speed picker 0.5×–2× (`playbackRate` reapplied on `.playing` — libVLC resets rate per media; iOS long-press on video = hold-to-2×); audio/subtitle delay nudge pickers (`player.audioDelay/subtitleDelay`, µs `Duration`s, reset per media); stats overlay (1s-tick repaint; libVLC bitrates shown ×8000 as kb/s, matching VLC's own UI); next-episode countdown card during the outro segment (replaces Skip Credits when autoplay armed; Cancel sets `nextUpCancelledForThisItem`, also checked by `handlePlaybackEnded`). **tvOS info panel**: swipe-down (indirect) while HUD hidden; Menu press order is panel → HUD → dismiss; `presentPicker`/`endPicker` skip `showControls()` while the panel is up so the two chrome layers never stack. **Loading spinner** (`loadingIndicator`, centered `UIActivityIndicatorView`) shows while the engine is opening / (re)buffering / on a retry (driven by `.opening`/`.buffering` state + each (re)open call site) and hides the moment frames flow — a stall or reload reads as "loading", not a frozen frame. **RULE — a seek owns its own "settle window" (`beginSeekLoading`/`updateSeekLoading`/`endSeekLoading`), armed inside `engineSeek` so EVERY seek path (coalesced ±N skips, scrub release, chapter jump, skip intro/outro, resume-position seek, SyncPlay echo) is covered**: a seek re-opens libVLC's HTTP byte range, so on a slow origin the picture stays frozen for seconds — but VLC echoes the target as a time update *immediately*, so the plain `.playing` / time-tick paths cleared the spinner right away and the wait read as a freeze (the "no loader after a fast-forward" bug). While the window is open, every path that would hide the spinner (`onEngineTimeChanged`, the 1s heartbeat, `.playing`) defers to `updateSeekLoading()`, which calls the seek landed only on **observed forward motion between two consecutive position samples** (never on proximity to the target — a sparse-keyframe file legitimately resumes *before* it) — and demands **two** consecutive moving samples while the engine still reports `.opening`/`.buffering`. The spinner itself is delayed `seekSpinnerDelay` (0.35s) so an instant seek never flashes it. `.paused`/`.stopped`/error/`cancelPendingSeekCommit` close the window; a 30s backstop guarantees a missed engine signal can't strand a spinner over a playing picture.
- **tvOS transport is custom** (no `AVPlayerViewController`): `TVScrubBar` (focusable; clickpad left/right = ±10s only while focused), focusable control bar (Prev/Next/Audio/Subtitles — **no on-screen play/pause**, center glyph flash feedback), always-on chapter strip (peeks 40pt / expands 178pt on focus). `ChapterChip` draws own focus state. **Menu press peels one layer at a time** (matches system `AVPlayerViewController`): info panel open → close it; HUD visible → hide it (and cancel the auto-hide timer); bare video → `dismiss`. **RULE — Menu peel handled by `handleMenu()`, called from BOTH a `UITapGestureRecognizer(allowedPressTypes:[.menu])` on `view` AND `pressesBegan`, keyed on `controlsContainer.alpha` (the VISUAL truth, never the `controlsVisible` flag)**: tvOS routes the Menu press to different responders by focus state — while the HUD is visible `tvScrub` holds focus (`preferredFocusEnvironments`) so the recognizer wins over the system's default modal-dismiss; while the HUD is **hidden** no control is focused and `pressesBegan` is the only path that fires (same reason `handleRemotePlayPause` exists). Handling it in only one place left a gap: a HUD-hidden press fell through `pressesBegan`'s "reveal the HUD" branch → Menu re-opened the HUD instead of quitting (an infinite hide/reveal loop). `handleMenu` is called from both paths and debounced via `lastMenuHandledAt` (a single press can reach both within one event) so it acts exactly once. Keying on `controlsVisible` (a flag that can disagree with the on-screen alpha) was the original loop's root cause — always read `controlsContainer.alpha`. **RULE — the "wake a hidden HUD" branch is a whitelist (`hiddenHUDIntent(for:)`), NOT "any press"**: the tvOS *simulator* delivers a keyboard Escape as a spurious non-`.menu` press (observed `type.rawValue` 2041) that, under "any press reveals", un-hid the HUD one event *before* the real Menu press (type 5) arrived — so the Menu peel saw `alpha==1` and hid instead of dismissing, never quitting. `pressesBegan` treats `key?.keyCode == .keyboardEscape` as Menu (handled FIRST, early-return). Real remotes send a clean type-5 Back press, but the whitelist keeps the simulator (and any future stray press type) from breaking the peel — an unrecognized press maps to `nil` and is ignored. **A recognized wake press ALSO performs its action, not just reveal**: select/Enter → play/pause, left/right → skip ∓N s, up/down → reveal only. **`hiddenHUDIntent` matches BOTH Siri-remote `UIPress.PressType` AND hardware-keyboard `press.key?.keyCode`** — keyboard arrows/Enter arrive only as `key.keyCode` (no arrow `PressType`), so before this they did nothing on a hidden HUD; `revealControls()` then moves focus to `tvScrub` so the next press routes normally. After every programmatic seek `refreshTimeUISoon()` repaints (VLC emits no time updates while paused; it cancels its prior follow-ups so a scrub burst can't stack closures).
- **RULE — tvOS touch-surface scrubbing** (`TVScrubBar`): Siri Remote touchpad slide = variable scrub via an **indirect-only** `UIPanGestureRecognizer`. Must be **incremental** — consume `translation(in:)` then `setTranslation(.zero)` each `.changed` and accumulate; an absolute baseline gets stomped by the periodic tick → "jump then snap" glitch. Sensitivity is the `scrubGain` constant (0.2 = full swipe ≈ a fifth of the timeline; tune here — was 0.5, too fast on the Siri Remote 2nd-gen touch surface). A scrub only engages after the finger crosses the `activationThreshold` dead-zone (30pt) — the touch surface fires a pan on the faintest contact, so without it a resting thumb both started scrubbing and swallowed the ±N clickpad presses (`pressesBegan` bails while `isScrubbing`); a sub-threshold touch is a no-op. No engine seek during the drag (preview labels only); one `engineSeek` on release. `VLCStreamViewController.pendingScrubTargetMs` (shared by scrub release AND coalesced ±N skips / chapter jumps — see the seek-coalescing RULE) holds the bar/labels at the target until VLC's async seek actually lands (±1.2s) so the tick can't paint the stale pre-seek position. `refreshTimeUI` honors it on BOTH platforms now (via the shared `paintPosition`), not just tvOS. Presses ignored while `isScrubbing`; `refreshTimeUI` returns early while scrubbing on both platforms.
- **RULE — ±N skips are coalesced into one debounced seek** (`seek(bySeconds:)` → `accumulateSeek` → `commitPendingSeek`): EVERY skip entry point (iOS skip buttons, iOS double-tap, tvOS clickpad ±10s, chapter-chip taps) accumulates an ABSOLUTE target into `pendingScrubTargetMs` and commits ONE `engineSeek` `seekCommitDelay` (0.3s) after the LAST press — never an immediate `player.seek(by:)` per press. Mashing the button used to fire N relative seeks, each tearing down + reopening libVLC's HTTP byte-range request → a storm that overloads a self-hosted / reverse-proxied origin and can stall the stream. **Don't "fix" the 0.3s delay away** — the HUD jumps to the projected position instantly (`paintPosition`) so it feels responsive; the delay is what collapses N requests into 1. The pending seek is cancelled (`cancelPendingSeekCommit`) on scrub takeover, media reload, episode swap, and teardown so a stale target can't seek the wrong position / a fresh episode. The pure seek math lives in `SeekCoalescer` (`clamp(target:lengthMs:)` / `relativeTarget(...)`, `endGuardMs = 250` — never seek within 250ms of length, libVLC treats end-seek as EOF), extracted for unit testing (`SeekCoalescerTests`); the view controller keeps debounce/HUD/engine ownership.
- **Chapter thumbnails** from `getItem().chapters`; requests skipped when `imageTag` nil. Blank ⇒ server hasn't run Jellyfin Dashboard → Scheduled Tasks → "Chapter image extraction". Degrades to `film` icon + title + timestamp.
- **iOS controls** are the touch UI (`#if os(iOS)`: tap-to-toggle, `UISlider`, separate pickers, `pip.enter`). The SwiftVLC view is hosted with `isUserInteractionEnabled = false` so the `videoView` tap recognizer drives HUD toggles. **Swipe-down-to-dismiss** (iOS/iPadOS only, VLC path only): interactive `UIPanGestureRecognizer` on `videoView` — surface follows the finger (translate + fade + corner rounding; `.overFullScreen` keeps the app visible behind), dismisses past 25% height or a >900pt/s downward flick, springs back otherwise. Gated via `UIGestureRecognizerDelegate`: begins only on predominantly-downward velocity, receives only bare-`videoView` touches (HUD buttons / slider / chapter strip keep theirs), refused while `isScrubbing`. The slide-off itself plays the exit, so it ends in `dismiss(animated: false)` — teardown still runs (`isBeingDismissed` is true even for non-animated dismissal). Simulator has no HW HEVC/DV decoder and no PiP — judge on real hardware. **iPad hardware-keyboard shortcuts** (iOS only, VLC path): `keyCommands` on the presenter — space = play/pause, ←/→ = seek ∓10 s. Seeks route through the documented coalesced path (`iosSkipBack`/`iosSkipForward` → `seek(bySeconds:)` → `accumulateSeek`), never a direct engine seek; `wantsPriorityOverSystemBehavior` stops the system swallowing space/arrows; VC is first responder (`canBecomeFirstResponder` + `becomeFirstResponder()` in `viewDidAppear`). Independent of the gesture/HUD stack.

### SyncPlay / Watch Together

`SyncPlayController.shared` (`@MainActor @Observable` singleton, `Shared/Screens/VideoPlayer/SyncPlayController.swift`) owns the whole session: current group, participants, the realtime socket, the client↔server `clockOffset`, and a `PlaybackBridge` injected by the player surface. Depends on `any SyncPlayAPI` + `LocalizationManager` + `ToastCenter`, set on activation.

> **STATUS — UI hidden (as of 1.0.5)**: Watch Together is not production-ready, so **both UI entry points are gated off** behind `MediaDetailScreen.watchTogetherEnabled` — a `private static let = false` compile-time kill-switch. The button doesn't render on either platform and no group can form, so everything documented below (controller, socket, `WatchTogetherSheet`, VLC HUD participant pill) still compiles and is type-checked but is **unreachable at runtime**. Re-enable by flipping that flag to `true`; revisit after 1.0.5 ships.

- **API**: the Jellyfin SDK doesn't model SyncPlay — requests are hand-built `URLSession` (mirroring `rawPostPlaybackInfo`): `MediaBrowser` auth header, `setEndpointPath` (base-path RULE), 15s timeout, `notifyIfUnauthorized`. REST: `GET /SyncPlay/List`, `POST /SyncPlay/New|Join|Leave|Pause|Unpause|Stop|Seek|Ready|Buffering|SetNewQueue`, `GET /GetUtcTime`. Realtime: `SyncPlaySocket` (a Swift `actor` around `URLSessionWebSocketTask`, `wss?://…/socket?api_key=…&deviceId=…`, parsed `Sendable` frames via `AsyncStream`).
- **Group lifecycle**: `WatchTogetherSheet` (`MediaDetailWatchTogether.swift`) → `createGroup`/`joinGroup`. The socket comes up FIRST so the client hears the server's authoritative `GroupJoined` echo; create sets an optimistic placeholder refined by that echo. **v1 ties group lifetime to the player** — `playbackDidDismiss()` leaves the group on teardown.
- **Sync enforcement**: local taps never move the playhead directly. In a group, user play/pause/seek go to the server (REST); the server's `SyncPlayCommand` echo over the socket is what actually moves the playhead — all participants stay in lockstep. Commands carry a server-UTC `When` converted via NTP-style clock offset (3× `GetUtcTime` averaged, ~100ms accuracy); far-future timestamps capped at 30s. `Ready`/`Buffering` reports feed drift correction. **Transport-only** — content selection is NOT synced; each participant opens the item themselves.
- **RULE — bridge closures call the engine directly and must NEVER re-emit** (an inbound command must not loop back out); `isApplyingRemoteCommand` suppresses buffering/ready echoes while a remote command is applied.
- **RULE — `startSocket` snapshots the previous socket before the async stop** — racing the reassignment kills the NEW socket. `SyncPlayDateParser` uses `Date.ISO8601FormatStyle` (Sendable), never `ISO8601DateFormatter` (race across actor/URLSession paths).
- **Platform reach**: the sync binding exists ONLY in `VLCStreamPresenter` — `NativeVideoPresenter` has NO SyncPlay integration, so sync works only when playback routes through libVLC. UI entry (**currently gated off** — see STATUS above): `MediaDetailScreen` `person.2.fill` chip (iOS secondary actions) / tvOS action row, online-only, accent when `isInGroup`; VLC HUD shows a participant-count pill.

### Remote control — « Lire sur… » (`MediaDetailRemotePlay.swift`)

Sends an item's playback to **another** Jellyfin session (typically the Apple TV) from the detail screen. `RemoteControlAPI` slice (`getControllableSessions` / `playOnSession` → `Paths.getSessions(controllableByUserID:)` and `Paths.play(sessionID:)` with `PlayCommand.playNow`), pure target resolution in `RemotePlayTarget`, sheet + `RemotePlayPresentation` modifier on both platforms (iOS `.sheet` chip `tv.badge.wifi` in `secondaryActionsRow` / tvOS `.fullScreenCover` + ghost button in the action row).

- **RULE — send-only, and that's the validated design, not an omission.** After the command lands, the sender has **no** transport controls: `PlaybackLiveActivityController` and `NowPlayingInfoController` are attached by the **local** presenters only, and nothing plays locally on a remote send — so no Live Activity, no Now Playing entry, no Control Center banner on the phone. Not to be confused with AirPlay (phone is the source and keeps controls; also impossible on the libVLC path). Don't "fix" the missing controls by attaching those controllers to a remote session — they describe a local player. Adding controls means polling `/Sessions` from the sheet (option A′, deliberately not built) or a persistent banner with global state (option B, rejected).
- **RULE — `controllableByUserId` is what makes this non-admin, and the client STILL re-filters on `userID == currentUserId`.** The unfiltered `GET /Sessions` leaks every user's session to non-admins on some servers (jellyfin#5210 — the reason Home's "Watching Now" is admin-gated); a server that ignored the parameter would otherwise let one tap start a film on someone else's TV. A session with no `userID` is dropped (unverifiable). Consequence accepted: an admin with `EnableRemoteControlOfOtherUsers` can't drive another user's session from here.
- **RULE — the resolver is pure and lives in CinemaxKit** (`RemotePlayTarget.resolve(sessions:currentUserId:excludingDeviceId:)`), locked by `RemotePlayTargetTests`. Order of rules: non-empty session `id` → own-user → `isSupportsRemoteControl == true` → not our own `deviceID` (sending to ourselves is the Play button) → video capability, where an **absent or empty** `playableMediaTypes` is "unknown" and KEPT (older clients under-report) while an explicit audio-only list is dropped. Sort is a **total** order (name folded for case + diacritics, then session id) so the list can't shuffle under the user's finger between two polls.
- **RULE — discovery is a side `Task` after the main load** (`MediaDetailViewModel.loadRemoteTargets`, same discipline as `loadCollection`) and **fails silently**: having no target is the ordinary case (a session exists only while Jellyfin actually runs on the other device), so a failed probe degrades to "no button", never to an error state over an otherwise-fine detail screen. The affordance renders only when `!remoteTargets.isEmpty` — its appearance is what teaches the user the precondition. On tvOS the button is appended **last** in the action row so this late arrival can't steal focus from Play.
- **RULE — the sheet re-probes on open.** The screen-level snapshot decided whether to draw a button; the sheet's list is what a command gets sent against, so a device that slept in between must fall out first. Hence the empty state inside the sheet is reachable despite the non-empty gate.
- **What gets sent is what Lecture would have played**: `remotePlayIntent` goes through `resolvedPlayTarget(for:)` (the SSOT the Play button and Siri share), which gained `startTicks` for this. **RULE — `mediaSourceId` only travels when the play target is the item itself**: for a series the target is an episode, whose media sources aren't the ones the version row ranked (those belong to the parent).
- Glyph is `tv.badge.wifi`, deliberately **not** the AirPlay glyph — using it would misrepresent both the mechanism and what the phone keeps.
- **`activeWithinSeconds: 300`** bounds staleness explicitly instead of trusting the server's own notion of "active"; a stale entry costs only a no-op command the server drops. The call is deliberately **uncached** — the whole point is which devices are awake right now.

### Flow (native/AVPlayer path)

1. `getItem()`. 2. Resolve non-playable: Series → `getNextUp()` or first episode; Season → first episode (**must resolve to Episode** — Series/Season have no media sources). 3. POST PlaybackInfo with `DeviceProfile` (`isAutoOpenLiveStream=true`, `mediaSourceID`, `userID`). 4. URL: `transcodingURL` (HLS) if present, else `/Videos/{id}/stream?static=true`. 5. Fallback: direct stream without PlaybackInfo session.

- **RULE — DeviceProfile**: DirectPlay mp4/m4v/mov + h264/hevc; transcode to HLS mp4 with `hevc,h264` only. **Never include `mpeg4`** — not a valid HLS transcode target on Apple; Jellyfin injects `mpeg4-*` URL params AVFoundation rejects. `maxBitrate`: 120 Mbps (4K) / 20 Mbps (1080p) via `@AppStorage("render4K")`.

Owns `MPNowPlayingInfoCenter.default().nowPlayingInfo` (title / artwork / elapsed / duration / rate / `MPMediaItemPropertyAlbumTitle = seriesName` / `MPMediaItemPropertyArtist = "S{parentIndexNumber}E{indexNumber}"`). `attach` publishes a title-only placeholder immediately so the iPhone Lock Screen widget fills in <1s, then runs `getItem` (enrich series + S×E×). **RULE — artwork fetch is sequenced behind that same `getItem`, not fanned out in parallel**: only the resolved item exposes `primaryImageTagValue`, needed to cache-bust the poster URL now that it rides Nuke's disk cache (`AuthenticatedImageFetch`, see Image Patterns) — a tagless artwork URL would mask a server-side poster edit until LRU eviction. The `getItem` call is single-flighted + 10s-cached (Task 3), so the extra hop is normally a cache hit; the placeholder dict covers the visible gap. On enrichment failure the artwork still fetches, untagged, rather than being dropped. `update(elapsed:duration:rate:)` runs from each presenter's existing 1s tick (no second timer); both engines also call it from their play/pause state-change paths for sub-second widget sync. `RemoteCommandController` is the buttons; `NowPlayingInfoController` is the metadata — never merge them.
- **RULE — `MPMediaItemArtwork` request handler MUST be `@Sendable`**: MediaPlayer invokes it on a background queue. Without explicit annotation the trailing closure inherits the enclosing `@MainActor` Task's isolation and tvOS 26 traps it with `dispatch_assert_queue` ("Block was expected to execute on queue …"). Always write `MPMediaItemArtwork(boundsSize: image.size) { @Sendable [image] _ in image }`.
- **RULE — Episode-nav race guard on metadata fetch**: `NowPlayingInfoController` bumps an internal `generation: Int` at every `attach`/`detach` and re-checks it before writing back from the `getItem` enrich task and the artwork fetch task. A slow poster arriving after a next-track press must not overwrite the new episode's metadata — without the guard, the user sees the wrong artwork on the iPhone widget for several seconds.

## App extensions & deep links

- **Targets**: `CinemaxWidget` (iOS WidgetKit) and `CinemaxTopShelf` (tvOS Top Shelf). Both embed via target dependencies in `project.yml`; all four targets share App Group `group.com.cinemax.shared` (entitlements generated by xcodegen).
- **Widget kinds** (all in `Widgets/CinemaxWidget/CinemaxWidget.swift`, families `.systemMedium`/`.systemLarge`, 4-column poster grid with a trailing "See all" tile): **Continue Watching** (`/UserItems/Resume`), **Favorites** (`/Items?isFavorite`), **Next Up** (`/Shows/NextUp`), **Recently Added** (`/Items/Latest` — bare array, not the `{Items:[]}` envelope, so its own decode). All share one `CinemaxRailKind` enum + `PosterRailProvider` + `PosterRailWidgetView` pipeline; adding a kind = one enum case + one `loadEntry` dispatch + one `JellyfinLite.fetch*` + one `Widget` struct registered in `CinemaxWidgetBundle`. **RULE — widget display strings are inline `french ? … : …`** (the extension can't link the app's `LocalizationManager`), keyed off `Locale.preferredLanguages.first?.hasPrefix("fr")`.
- **Playback Live Activity (iOS)** — Lock Screen banner + Dynamic Island for the item currently playing (`Widgets/CinemaxWidget/PlaybackLiveActivityWidget.swift`, registered in `CinemaxWidgetBundle`; app side = `Shared/Screens/VideoPlayer/PlaybackLiveActivityController.swift`, wired into BOTH presenters next to `NowPlayingInfoController`). **RULE — the `PlaybackActivityAttributes` contract is shared by SOURCE, not linkage**: `Widgets/CinemaxWidget/PlaybackActivityAttributes.swift` is listed in the `Cinemax` target's `sources` in `project.yml` *in addition to* living under the extension's directory — the only way to share a type with an extension that links none of our frameworks. Keep it Foundation + ActivityKit only. **RULE — no per-second pushes**: `ContentState` carries `startedAt`/`duration`/`rate`, never a live elapsed; the widget derives the moving playhead client-side (`Text(timerInterval:)` / `ProgressView(timerInterval:)`) and the app pushes ONLY on a timeline discontinuity — play/pause flip, a **rate change**, a seek (drift > `PlaybackActivityThrottle.seekTolerance` from the projection), the runtime becoming known, item change, stop. The presenters feed it from their EXISTING 1 s tick (no new timer) and the throttle swallows the ordinary ticks. **RULE — the REAL engine rate must reach `update(...)`, never a collapsed 0/1**: VLC ships a 0.5×–2× picker (+ iOS hold-to-2×) and AVKit exposes its own speed menu; `startedAt` is anchored as `now - elapsed/rate` (a **wall-clock** anchor) and the throttle projects `elapsed + rate × Δt`, so steady playback at ANY speed pushes nothing. Collapsing the rate made 2× drift 1 s per second → a push every ~4 s (~675 per episode) *and* rendered a wrong playhead in between. Off-speed rendering swaps the elapsed label for a rate badge (`ContentState.isOffSpeed`) — SwiftUI's only live timer counts wall-clock, which is not media time at 2×; the bar and the "ends in" countdown stay live and correct because the range is wall-clock. **RULE — `ActivityAttributes` are frozen for an activity's lifetime** (only `ContentState` updates), so the title/subtitle lookup runs BEFORE `Activity.request` — `attach` defers the start behind a `getItem` (10 s cached + single-flighted, normally a cache hit off `NowPlayingInfoController`'s identical lookup, raced against a 1.5 s deadline so a stalled server can't hold the banner back) and buffers the newest playhead sample so a pause/seek inside that window isn't lost. **RULE — `Activity.request` THROWS FROM THE BACKGROUND**, so an episode swap while the phone is locked must NOT end the running activity — it could never be replaced. Lifecycle therefore goes through `desired` (what should be on screen) vs `presented` (what the activity carries) + `reconcile()`: foreground ⇒ end + re-request; background ⇒ keep the banner and only re-base its timeline (stale title until the user foregrounds — accepted v1 trade), with `UIApplication.didBecomeActiveNotification` driving the catch-up. The same path retries a request that failed for any other reason. **RULE — every ActivityKit mutation goes through `enqueue`**, a single chained `Task` — `update`/`end` are async and two loose Tasks can land out of order (a pause then a seek in one tick would leave the banner paused); the closure is `@MainActor`-isolated because `Activity` is not `Sendable`. `update` re-reads the settings toggle each tick so turning it off mid-playback ends the banner. Playback ending with no next episode detaches explicitly (the end-of-series overlay keeps the player up, which would otherwise strand a "paused at the end" banner). Orphans from a crash are swept per attach (sparing the one we own) and once at launch from `AppNavigation`'s root `.task`. `NSSupportsLiveActivities` sits on the APP target only — the extension needs no extra key or entitlement. **v1 is display-only; interactive pause/play via `LiveActivityIntent` is explicitly v2.** Pure logic (`ContentState.make`, `PlaybackActivityThrottle`, headline split) is unit-tested in `PlaybackLiveActivityTests`.
- **RULE — every binary needs its own `PrivacyInfo.xcprivacy`** (Apple's ITMS-91053 scan is per-`.app`/`.appex`): the app manifest is `Resources/PrivacyInfo.xcprivacy`; each extension carries its own (`Widgets/CinemaxWidget/PrivacyInfo.xcprivacy`, `TopShelf/CinemaxTopShelf/PrivacyInfo.xcprivacy`) — auto-bundled because each extension dir is already a `sources:` path. UserDefaults reason codes: the extensions declare `1C8F.1` — a deliberately conservative declaration kept after the plaintext-token drop (they no longer read the App-Group suite at all, but an over-declaration is never rejected, whereas re-adding an App-Group read without the entry is an ITMS-91053); `CA92.1` explicitly excludes data shared across binaries, so it's the wrong code there. The app declares BOTH `CA92.1` (its own `@AppStorage`/`UserDefaults.standard`) and `1C8F.1` (App-Group access in `ExtensionSessionBridge` — now the legacy-copy scrub); the app manifest ALSO declares `NSPrivacyAccessedAPICategoryFileTimestamp` reason `C617.1` for statically-linked Nuke's disk cache (`.contentAccessDateKey`, ships no manifest of its own). A new required-reason API on any target = update that binary's manifest. Validate edits with `plutil -lint`.
- **RULE — extensions do NOT link CinemaxKit** (widget memory budget; SDK pulls Nuke + generated entities). They read the session the app publishes via `ExtensionSessionBridge` (CinemaxKit/Persistence) and talk to Jellyfin endpoints directly (`JellyfinLite` in the widget, inline in `ContentProvider`). Publish hook: `AppState.refreshCurrentUser()` (covers login / switch / restore) + clear in `logout()`.
- **RULE — extension HTTP: token in the `Authorization` header, never the query string; ephemeral sessions only.** Both extensions send `MediaBrowser Token=` as a header on every request they issue themselves (JSON endpoints **and** the widget's poster fetch — Jellyfin image endpoints accept header auth, same split the app uses via `ImageURLBuilder` + `AuthenticatedImageFetch`), so no `api_key` query item rides along to be captured by URL logs or cache keys. Each extension owns a `URLSessionConfiguration.ephemeral` session with `urlCache = nil` — never `URLSession.shared`, whose disk-backed `URLCache` would persist authenticated responses inside the extension container. **The one exception**: Top Shelf image URLs handed to `TVTopShelfSectionedItem.setImageURL` MUST keep `api_key` in the URL — the SYSTEM fetches those, we never issue the request, so header auth is impossible there.
- **RULE — extension session store is a shared Keychain group ONLY — never plaintext UserDefaults**: the token lives in a **shared Keychain access group** `$(AppIdentifierPrefix)com.cinemax.shared` (`kSecAttrService = com.cinemax.jellyfin`, `kSecAttrAccount = extension_session`, accessible `AfterFirstUnlockThisDeviceOnly`) — device-only, never in backups. It replaced the old plaintext App Group `UserDefaults` copy (suite `group.com.cinemax.shared`, key `extension.session`), which the token was readable-at-rest from (backups / any group process). That transitional dual-write (1.0.3–1.0.6) is **gone**: `publish` writes the Keychain only, and `scrubLegacyDefaultsCopy()` **deletes** any leftover plaintext blob — presence-guarded (`object(forKey:)`, no write in the steady state) and run BEFORE the skip early-return, so an upgraded install is scrubbed on its first `publish` even when the session itself is unchanged. Readers (`KeychainService.readSharedSession`; inline in `JellyfinLite`/`ContentProvider`) are **Keychain-only** — no UserDefaults fallback. `appGroupId`/`sessionKey` on `ExtensionSessionBridge` survive solely as the scrub's target (locked by `ExtensionSessionContractTests`); **never re-add a token write to UserDefaults**. The full group string is resolved at runtime from the `AppIdentifierPrefix` Info.plist key (injected via `$(AppIdentifierPrefix)` on all 4 targets — avoids hardcoding the team id). **Keep the Keychain contract in sync across all three copies**: service/account/group + JSON shape (the extensions re-declare the literals; only the app links `KeychainService`). `keychain-access-groups` entitlement is on all 4 targets (xcodegen-generated); existing app-private Keychain items (`server_url`/`user_session`/`access_token`/`device_id`) are untouched so login is unaffected. **Release: enable "Keychain Sharing" on the 4 App IDs before an App Store build** (transparent with local automatic signing). **`publish` early-returns before any Keychain write/notify when the decoded Keychain copy already field-matches the incoming session** (`ExtensionSessionBridge.isCurrent`, Keychain-only input) — skips the redundant `SecItemDelete`+`SecItemAdd`/`WidgetCenter.reloadAllTimelines()`/Top-Shelf poke on every no-op foreground revalidation; a corrupt/undecodable stored blob or a stale non-empty store on the clear path is always treated as changed.
- **Deep links**: `cinemax://item/{id}` (scheme registered in both Info.plists; widget posters + tvOS Top Shelf both emit it). `AppNavigation.onOpenURL` → `AppState.handleDeepLink` → `pendingDeepLinkItemId`. **RULE — deep-link routing is tab-config-independent**: `MainTabView` switches to the Home tab when one exists (`HomeScreen` consumes it via a screen-root `navigationDestination(item:)` — lazy-container RULE applies); when the custom menu has **no** Home tab, `MainTabView` instead presents `MediaDetailScreen` modally from the tab root (`deepLinkFallback` token → iOS `.sheet` / tvOS `.fullScreenCover`, its own `NavigationStack`, tvOS re-injects `playerCoordinator` + `.onExitCommand` dismiss) so the link is never silently dropped. The `cinemax://home` "See all" tile still just switches tabs. **RULE — the item id is shape-validated before dispatch** (`AppState.isValidItemId`): accepts ONLY the two Jellyfin forms — a 32-char undashed hex string OR a canonical dashed GUID — and drops anything else, so a malformed deep link can't drive a lookup with attacker-controlled path text.
- **RULE — `TVTopShelfContentProvider` under Swift 6 strict concurrency**: use the completion-based `loadTopShelfContent(completionHandler:)`, wrap the handler in an `@unchecked Sendable` final-class box, and keep the `Task` closure body minimal (one `await Static.run(handler:)` call). Returning the non-Sendable `TVTopShelfContent` from the async override — or inlining the guard/await flow in the Task closure — trips a region-isolation checker bug ("Please file a bug", Swift 6.2.3).
- **RULE — TopShelf target MUST link `OTHER_LDFLAGS: -e _NSExtensionMain`**: the tv-app-extension product type's default entry `_TVExtensionMain` is an **empty `ret` stub in the tvOS 26 simulator runtime** — main returns instantly and dyld exits the extension (code 3) before the provider is instantiated, with zero logs and no crash report; HeadBoard silently falls back to the static Top Shelf image (verified in lldb: `TVServices\`TVExtensionMain: ret`). Foundation's generic `NSExtensionMain` drives the NSExtension lifecycle correctly. Diagnosis kit if it regresses: `boot.c` C-constructor log + `init`/invoke logs (subsystem `com.cinemax`, category `TopShelf`), trigger HeadBoard on demand with `xcrun simctl spawn <udid> launchctl kickstart -k system/com.apple.PineBoard`.
- **RULE — WidgetKit `TimelineProvider` witnesses use the same HandlerBox pattern** (NOT `@escaping @Sendable` parameter annotations): the SDK's completion annotations differ between toolchains — `@Sendable`-annotated witnesses built on Xcode 26.2 fail CI's Xcode 26.5 with the `sending`-closure error. The `@unchecked Sendable` box + minimal `Task { await Self.deliver…(handler:) }` body compiles on both.

## App Intents — Siri & Shortcuts (iOS-only)

`Shared/Intents/`, all `#if os(iOS)` except `IntentSessionProvider` (plain infrastructure, left ungated so the tvOS build keeps type-checking it). tvOS is excluded on purpose: none of the surfaces App Intents feeds — Siri phrases, Shortcuts, Spotlight, Control Center, the Action button — exist there.

Five intents (`CinemaxIntents.swift`): `ResumePlayback` (no parameter), `PlayMediaItem`, `PlayNextEpisode`, `OpenMediaItem`, `SearchLibrary`. All run `openAppWhenRun`.

- **RULE — entity identity is composite `(server, item)`** (`MediaEntityID`, raw form `serverId|itemId`), never the Jellyfin item id alone. A saved shortcut outlives the state it was built in; the composite lets `MediaItemQuery.entities(for:)` refuse a stale identity instead of resolving it against whichever server is active now — which would silently play the wrong thing. The guard is applied **twice**: in `entities(for:)` and again in `activeServerItemId(_:)` at perform time. The item component is shape-validated through `AppState.isValidItemId` (now `nonisolated` so intents share the ONE definition with the deep-link path) — a corrupted or hand-edited shortcut must fail, not resolve.
- **RULE — the entity query runs WITHOUT a scene, so session bootstrap can't go through `AppState`.** Siri resolves a spoken title before deciding what to run and the Shortcuts editor browses entities without presenting the app, so `restoreSession` (`@MainActor`, driven by SwiftUI `.task`) has not necessarily run. `IntentSessionProvider` rebuilds the client from the Keychain — same discipline as `ExtensionSessionBridge`, but in-process so it gets all of CinemaxKit. It reads the **registry entry** (authoritative, and the only carrier of the server id the composite identity needs), not the legacy mirror trio, and returns `nil` when `activeServerId` is absent (⇒ migration hasn't run ⇒ refuse cleanly rather than mint an id that later disagrees with the registry).
- **RULE — the headless client MUST apply `privacy.maxContentAge`** (`IntentSessionProvider.makeSession`). Without it an intent surfaces titles the app itself hides, making Siri a bypass of parental controls. Locked by `IntentSessionProviderTests`.
- **RULE — never add a "play" verb to `cinemax://`.** The URL scheme is public and unauthenticated; a play verb would turn it into "start playing an arbitrary id". Intents post `AppState.pendingIntentPlaybackItemId` **in-process** instead (paired with the existing `pendingDeepLinkItemId` for navigation). The scheme stays at `item` / `home`.
- **RULE — Siri-initiated playback routes through `MediaDetailScreen`, not straight to the player.** That is what gives it the same fidelity as a tap: series → next-up resolution, resume position, prev/next episode buttons, version pick. `MediaDetailScreen.consumeIntentPlaybackRequest()` consumes the request once after `load()`, guarded on the screen's own `viewModel.itemId` (the request is visible to every detail screen on the stack) and clearing it before any early return. A request naming an *episode* plays that episode — the view model has resolved the screen up to the parent series, so the Play button's next-up target would be wrong there. What gets played is single-sourced in `MediaDetailScreen.resolvedPlayTarget(for:)`, shared with the Play button.
- **Search routing**: `SearchLibraryIntent` posts `AppState.pendingIntentSearchQuery` + `pendingDeepLinkTabId = MenuEntry.searchID` (the existing tab-switch path, which already accepts any resolved tab id). `SearchScreen.consumeIntentSearchRequest()` consumes it from BOTH a `.task` and an `onChange` — the term can be raised before the screen exists (tab switched to afterwards) or while it's already on screen. It writes `viewModel.searchText` rather than searching invisibly, so the user sees and can edit what Siri heard; `search(using:)` cancels in-flight work, so the write's own `onChange` and the explicit call collapse into one query. The term goes through `LibrarySearchRanker.sanitize` — a Shortcuts-supplied string is as untrusted as a pasted one.
- **RULE — Siri PHRASES are localized in `Resources/{fr,en}.lproj/AppShortcuts.strings`, NOT `Localizable.strings`.** Separate table, read by the system on its own; a phrase in the wrong table simply never resolves — silent, no build error. Intent titles / descriptions / parameter titles / errors DO use `Localizable.strings` (via `LocalizedStringResource`, keys `intent.*`). Both tables are keyed on the **French** literals declared in `CinemaxShortcuts` (`developmentLanguage: fr`), and every phrase must contain `\(.applicationName)` / `${applicationName}`.
- **RULE — a phrase may only interpolate an `AppEntity` or `AppEnum`.** A `String` parameter is rejected at build time ("Invalid parameter type"), which is why `SearchLibraryIntent`'s phrases carry no term token — Siri prompts for it after matching.
- **RULE — intent statics are `static let`, never `static var`** (`title`, `description`, `openAppWhenRun`): Swift 6 rejects a mutable nonisolated static as shared mutable state. A `let` satisfies the protocol's get-only requirement.
- **RULE — intent user-facing errors can't use `LocalizationManager.userFacingMessage(for:)`** — that lives in the UI layer, absent in a headless context. `CinemaxIntentError: CustomLocalizedStringResourceConvertible` carries its own `intent.error.*` keys.
- `AppNavigation.sharedAppState` is deliberately **not** `private`: an intent has no environment to read from, and any other access point would be a *second* `AppState` (separate API client and auth state the UI would never observe).
- **Deliberately out of scope for this lot** (the socle is shaped to accept them, none are built): Spotlight / `CoreSpotlight` indexing, Control Center controls, the Action button, Lock Screen & StandBy widget families, the interactive Live Activity. Also out: poster thumbnails in the Shortcuts picker (would mean a network fetch per row with no session guarantee — entities use SF Symbols), and any background execution that doesn't open the app.

## Network awareness

- **`NetworkMonitor`** (`@MainActor @Observable` around `NWPathMonitor`): seeds `isOnline` synchronously from `monitor.currentPath`. Consumed by the session-expiry 401 logic (offline ⇒ never logout), `StreamTransportPolicy`'s IPv6 probe scheduling, and SyncPlay gating. **RULE — Bounded timeouts**: every `JellyfinClient` takes `Self.fastFailSessionConfiguration` (request 30s, resource 60s, `waitsForConnectivity=false`, **`urlCache = nil`** — every request on it is authenticated, and the default config would otherwise write those responses to a disk `URLCache`; freshness is already owned by the app's `APICache`); raw PlaybackInfo POST adds `request.timeoutInterval = 20` and runs on its own ephemeral, cache-less `playbackInfoSession` (its URL carries `api_key` — a shared-session disk `URLCache` would persist the token at rest). The hand-built SyncPlay REST path keeps the same discipline on its own ephemeral, cache-less `syncPlaySession` (a cached `GET /GetUtcTime` would poison the clock offset). **RULE — no authenticated request rides `URLSession.shared`** (whose default disk `URLCache` persists token-bearing URLs/responses at rest): `HLSManifestLoader` (manifest/VTT fetches carry the transcoding `api_key`), the extensions, and `ServerReachability`/`ServerSessionRevoker` each own a private `.ephemeral` `urlCache = nil` session. `waitsForConnectivity=false` + `NetworkMonitor` detect *offline* instantly, so these only bound the "online but slow server" case — they were 8s/20s/8s but that tore whole screens down to "Serveur injoignable" when a self-hosted server briefly stalled (e.g. libVLC flooding it with AVI range-requests). `AppState.restoreSession` hydrates from keychain immediately, dispatches server calls in detached Task (non-blocking offline launch).
- **Legacy-downloads janitor**: `AppNavigation.purgeLegacyDownloads()` (iOS, root `.task`) deletes the pre-1.0.5 `Application Support/Cinemax/Downloads/` tree + the `downloads.userFlagCache` UserDefaults key left by the removed offline-downloads feature (App Review 5.2.3). Keep until well past 1.0.5 adoption.

### Permissive weighted search (`LibrarySearchRanker`)

**RULE — matching lives in `LibrarySearchRanker` (`Shared/ViewModels/`), never back inside a view model.** It is the SSOT shared by the search screen AND the App Intents entity query, and that sharing is load-bearing: it is what makes resolving a *spoken* title viable without a local index, since the normalization folds exactly what dictation drops (punctuation, diacritics). Two copies would drift and Siri would silently stop matching titles the screen still finds. Members: `sanitize` (input hygiene, applied to typed, dictated and Shortcuts-supplied terms alike), `normalize`, `significantWords`, `score`, `rank`.

Jellyfin's `searchTerm` is contiguous + punctuation-sensitive — "Mission Impossible" misses "Mission : Impossible". `rank` (pure, non-isolated, takes `any LibraryAPI` which is `Sendable`) fans out **concurrent** `searchItems` calls for the full phrase **AND each significant word** (`TaskGroup`), unions/dedups by id, then ranks locally. **Stop words** (FR/EN articles/conjunctions, `LibrarySearchRanker.stopWords`) are dropped from per-word fetches + scoring so "the"/"le"/"de" don't match everything. `score` tiers (score 0 ⇒ filtered out): **(1)** full normalized query is a contiguous run in title (+bonus exact / prefix) **(2)** every query word present but separated **(3)** only some words present (× fraction). Scored against `name` **and** `originalTitle` (max). `normalize` folds diacritics + lowercases + collapses any non-alphanumeric run to a single space.

### Voice search (`SpeechRecognitionHelper`, iOS only) — RULES

- **RULE — every off-main framework callback must be `@Sendable` (nonisolated).** TCC permission callbacks, the `AVAudioEngine` `installTap` block (audio render thread), and the `recognitionTask` result handler all fire off the main actor; a `@MainActor`-isolated closure there traps with `dispatch_assert_queue_fail` / `_swift_task_checkIsolatedSwift`. Fixing only the one in the stack trace leaves the others crashing identically. Permission requests bridge through `nonisolated static func ... async` + `withCheckedContinuation`; the tap captures the request via `nonisolated(unsafe) let` (its `append` is thread-safe); the result handler is `{ @Sendable [weak self] … }` (a `@MainActor` class IS `Sendable`, so weak-self capture is legal) that extracts Sendable values then hops via `Task { @MainActor }`.
- **RULE — empty-transcript guard**: forward a transcript only when non-empty. On `stop()`, `endAudio()` finalizes and can emit a final result with an EMPTY `formattedString`; propagating it wipes `searchText` (and the results) the instant the mic turns off.
- **Silence auto-stop**: buffer recognition never self-reports `isFinal`. A `silenceTimer` (Task) armed at start with a longer `initialTimeout` (5s — server recognition has first-result latency, a short timeout would kill the session before any word lands) then re-armed at `silenceTimeout` (1.5s) on every partial transcript; firing calls `stop()`. `stop()` is idempotent (guards on `audioEngine.isRunning || recognitionRequest != nil`) since it arrives from timer / final result / manual tap.
- **RULE — every bail-out must clear `isListening`, and `onPermissionError` is the single owner**: `toggleListening` flips the flag optimistically, *before* the TCC prompts resolve. All five helper bail-outs (speech denied, mic denied, recognizer unavailable, `setCategory`/`setActive` throwing, zero sample-rate input route) fire `onPermissionError` and return **without** reaching `stop()` — whose idempotency guard early-returns before `onStopped` anyway, since nothing ever started. So the reset lives in the `onPermissionError` wiring in `setupSpeechCallbacks`, not on the individual paths; a new bail-out must route through that callback or the mic pill keeps pulsing "listening" over a dead recorder.
- **Listening UI**: the trailing toolbar mic button expands into a Liquid-Glass pill (`mic.fill` + `search.listening`, pulsing via `symbolEffect(.pulse, isActive: motionEffects)`) while `isListening` — no separate label, no `.glass` style (iOS 26 auto-wraps toolbar buttons; an explicit capsule would nest).

## Image Patterns (all RULE)

- `ImageURLBuilder` → `/Items/{id}/Images/{type}`. **Backdrop sizing**: use `ImageURLBuilder.screenPixelWidth` — never hardcode `1920`.
- **RULE — always pass the `tag:` cache-buster to `imageURL(...)`/`imageURLRaw(...)`**: without it the image URL is byte-identical across server-side poster/backdrop edits, so Nuke (keyed by URL) serves the stale image forever — a metadata/poster change is invisible until reinstall, and `clearCache()`/"Refresh Catalogue" don't help (they clear the JSON cache, not Nuke's). Pass `tag: item.primaryImageTagValue` for `.primary`, `tag: item.backdropImageTagValue` for `.backdrop` (helpers in `BaseItemDto+Metadata.swift`; backdrop helper mirrors `backdropItemID`'s parent-first resolution), `person.primaryImageTag` for cast. Every new live image call site must thread the tag. **Chapter thumbnails and now-playing artwork also carry a tag** — since both now ride Nuke's shared 500 MB disk cache via `AuthenticatedImageFetch` (see Player-image caching RULE below), an untagged URL there is just as stale-prone as a poster/backdrop; `ChapterController`/`VLCStreamPresenter` pass each chapter's `imageTag`, and `NowPlayingInfoController` passes `fullItem.primaryImageTagValue` (see its enrichment-sequencing note). **Trickplay tiles stay deliberately tag-less** — regenerating trickplay changes the manifest/`mediaSourceId`, which already busts the URL, and the player re-fetches the manifest every session anyway.
- **Image cache**: `AppNavigation.init()` configures `ImagePipeline.shared` with 500 MB disk + explicit `ImageCache` `costLimit = 256 MB` (Nuke's ~100 MB default evicts mid-render on tvOS — 4K backdrops decode to 4–8 MB each).
- **Prefetch (`PosterPrefetcher`, Shared/ViewModels)**: Home + Library warm card images via Nuke `ImagePrefetcher` after each data load. **RULE — prefetched URLs must be byte-identical to the consuming card's request** (same `maxWidth` AND `tag`) — Nuke keys on the URL, a near-miss warms nothing. Posters = primary/300, continue-watching = backdrop/600. Call `reset()` before a full catalogue refresh so refreshed tags re-prefetch.
- **Backdrop fallback**: `item.backdropItemID` (→ `parentBackdropItemID ?? seriesID ?? id`). **No-backdrop placeholder**: gate on `item.hasBackdropImage` (NOT `backdropItemID` — always non-nil) → `BackdropFallbackView` (centered `film` symbol over `surfaceContainerLow` + accent radial, under `CinemaGradient.heroOverlay`). Wired in `MediaDetailScreen.backdropSection`/`HomeScreen.heroSection`/`LibraryHeroSection`.
- **Always `CinemaLazyImage`** — never `LazyImage` directly. Card containers: `Color.clear` + `.aspectRatio()` + `.frame(maxWidth: .infinity)` + `.overlay { CinemaLazyImage }` + `.clipped()`. **Backdrop (full-bleed ZStack)**: `CinemaLazyImage` must have `.frame(maxWidth:.infinity, maxHeight:.infinity)` — else ZStack sizes from natural 1920px pushing title off-screen. Outer container `LazyVStack(alignment: .leading)`.
- **PosterCard title alignment**: hidden `Text("M\nM").hidden()` placeholder + actual title overlaid top-aligned → uniform row height.

## Build

```bash
# iOS
xcodebuild build -project Cinemax.xcodeproj -scheme Cinemax -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
# tvOS
xcodebuild build -project Cinemax.xcodeproj -scheme CinemaxTV -destination 'platform=tvOS Simulator,name=Apple TV 4K (3rd generation)'
# Regenerate Xcode project
cd Cinemax && xcodegen generate
```

**Build verification gotchas (RULE)**:
- Always pair pipes with `set -o pipefail` (`set -o pipefail; xcodebuild ... | grep ...`) — without it `tail`/`grep` swallow xcodebuild's exit code and a failed build returns 0. Confirm by reading output for `** BUILD SUCCEEDED **` / `** BUILD FAILED **`, not just shell exit.
- Don't run iOS + tvOS builds in parallel against the same DerivedData — they race on `build.db` ("database is locked"). Run serially.

**Tests**: unit tests (swift-testing) live in `Tests/CinemaxKitTests/` but the Xcode target/product is **`CinemaxTests`** (in-app bundle, `TEST_HOST = Cinemax.app`, `@testable import Cinemax`). Run via `xcodebuild test -scheme Cinemax ...`. **RULE — `-only-testing` silently runs 0 swift-testing tests** — run the full suite and grep for `Suite "Name"` / `✔`. **RULE — never add `package: CinemaxKit` to `CinemaxTests` in `project.yml`** (double-links the `Get` dependency → linker errors; the app target already carries it).

**Versioning**: `iOS/Info.plist` + `tvOS/Info.plist` use `$(MARKETING_VERSION)`/`$(CURRENT_PROJECT_VERSION)` — `project.yml` `settings.base` is SSOT. Bump `MARKETING_VERSION` per user-visible release; `CURRENT_PROJECT_VERSION` per archive/upload.

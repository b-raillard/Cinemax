### Remote control — « Lire sur… » (`MediaDetailRemotePlay.swift`)

Sends an item's playback to **another** Jellyfin session (typically the Apple TV) from the detail screen. `RemoteControlAPI` slice (`getControllableSessions` / `playOnSession` → `Paths.getSessions(controllableByUserID:)` and `Paths.play(sessionID:)` with `PlayCommand.playNow`), pure target resolution in `RemotePlayTarget`, sheet + `RemotePlayPresentation` modifier on both platforms (iOS `.sheet` chip `tv.badge.wifi` in `secondaryActionsRow` / tvOS `.fullScreenCover` + ghost button in the action row).

- **RULE — send-only, and that's the validated design, not an omission.** After the command lands, the sender has **no** transport controls: `NowPlayingInfoController` is attached by the **local** presenters only, and nothing plays locally on a remote send — so no Now Playing entry and no Control Center banner on the phone. Not to be confused with AirPlay (phone is the source and keeps controls; also impossible on the libVLC path). Don't "fix" the missing controls by attaching those controllers to a remote session — they describe a local player. Adding controls means polling `/Sessions` from the sheet (option A′, deliberately not built) or a persistent banner with global state (option B, rejected).
- **RULE — `controllableByUserId` is what makes this non-admin, and the client STILL re-filters on `userID == currentUserId`.** The unfiltered `GET /Sessions` leaks every user's session to non-admins on some servers (jellyfin#5210 — the reason Home's "Watching Now" is admin-gated); a server that ignored the parameter would otherwise let one tap start a film on someone else's TV. A session with no `userID` is dropped (unverifiable). Consequence accepted: an admin with `EnableRemoteControlOfOtherUsers` can't drive another user's session from here.
- **RULE — the resolver is pure and lives in CinemaxKit** (`RemotePlayTarget.resolve(sessions:currentUserId:excludingDeviceId:)`), locked by `RemotePlayTargetTests`. Order of rules: non-empty session `id` → own-user → `isSupportsRemoteControl == true` → not our own `deviceID` (sending to ourselves is the Play button) → video capability, where an **absent or empty** `playableMediaTypes` is "unknown" and KEPT (older clients under-report) while an explicit audio-only list is dropped. Sort is a **total** order (name folded for case + diacritics, then session id) so the list can't shuffle under the user's finger between two polls.
- **RULE — discovery is a side `Task` after the main load** (`MediaDetailViewModel.loadRemoteTargets`, same discipline as `loadCollection`) and **fails silently**: having no target is the ordinary case (a session exists only while Jellyfin actually runs on the other device), so a failed probe degrades to "no button", never to an error state over an otherwise-fine detail screen. The affordance renders only when `!remoteTargets.isEmpty` — its appearance is what teaches the user the precondition. On tvOS the button is appended **last** in the action row so this late arrival can't steal focus from Play.
- **RULE — the on-SCREEN probe is cached (30 s), the SHEET never is** (`getControllableSessions(userId:cached:)`, default `false`): the detail screen runs it on every open purely to decide whether to DRAW the button, and the answer is almost always the same — usually empty. The picker's list is what a command gets SENT against, so it must stay uncached. 30 s rather than the usual 10 because nothing here is userData, so no mutator sweeps the key, and a device waking up may take half a minute to earn its button. tvOS's `getLocalTrailers` probe takes a 300 s per-item TTL for the same reason (what sits beside an item changes only on a library scan).
- **RULE — the sheet re-probes on open.** The screen-level snapshot decided whether to draw a button; the sheet's list is what a command gets sent against, so a device that slept in between must fall out first. Hence the empty state inside the sheet is reachable despite the non-empty gate.
- **What gets sent is what Lecture would have played**: `remotePlayIntent` goes through `resolvedPlayTarget(for:)` (the SSOT the Play button and Siri share), which gained `startTicks` for this. **RULE — `mediaSourceId` only travels when the play target is the item itself**: for a series the target is an episode, whose media sources aren't the ones the version row ranked (those belong to the parent).
- Glyph is `tv.badge.wifi`, deliberately **not** the AirPlay glyph — using it would misrepresent both the mechanism and what the phone keeps.
- **`activeWithinSeconds: 300`** bounds staleness explicitly instead of trusting the server's own notion of "active"; a stale entry costs only a no-op command the server drops. The call is deliberately **uncached** — the whole point is which devices are awake right now.

#### Receiving side — being a target (`RemoteControlListener.swift`, `JellyfinSocket.swift`)

Until this was added the app could only **send**: it never declared its capabilities, so `SessionInfoDto.supportsRemoteControl` was false on every Cinemax session and `RemotePlayTarget.resolve` (which requires that flag) filtered it out of every picker — including this app's own. « Lire sur… » therefore could not target Cinemax on the Apple TV, its main use case.

- **RULE — capabilities and the socket are one feature; neither works alone.** `publishCapabilities(supportsMediaControl:)` (`POST /Sessions/Capabilities/Full`) is the only thing that makes the device *appear* in a picker; Jellyfin delivers session commands over the realtime socket and nowhere else, so capabilities without a socket subscription would list the device and then swallow every tap. Never ship one without the other.
- **RULE — an inbound `DisplayMessage` toast has the APP's title, never the sender's header** (`RemoteControlListener.displayMessageToast`; audit 2026-09-22, S11): « Message d'un autre appareil » (or « Message de <nom> » when the frame names its sender), the sender's header folded into the body. Anybody allowed to drive this session could otherwise raise a toast titled « Session expirée » and pass it off as the app. Jellyfin 10.9 → 12.0 never sets `ControllingUserId` on a `DisplayMessage` (`SessionManager.SendMessageCommand` → `SendGeneralCommand`, checked in the sources), so today the title is always the anonymous one; the id is parsed in case a server starts sending it, a zero GUID read as absent.
- **RULE — declare only what is honored.** `supportedCommands` lists `DisplayMessage` alone: advertising a `GeneralCommandType` the app doesn't execute renders a dead control in the sender's UI. Neither `Play` ("start this now") nor `Playstate` (honored since #176) is a `GeneralCommandType`, and neither needs a declaration — verified 2026-09-11 against jellyfin `master` and jellyfin-web: `SessionManager.SendPlaystateCommand` only looks the session up (+ `AssertCanControl` on the sender), `SessionInfo.SupportsRemoteControl` is `supportsMediaControl` + an attached socket controller, and jellyfin-web's `sessionPlayer` sends Playstate without consulting `SupportedCommands`. `GeneralCommandType.playState` exists in the SDK enum but nothing server-side reads it; don't add it. Being controllable is not the same as offering controls: this app's own SENDER stays send-only (see the « Lire sur… » RULE above).
- **RULE — inbound `Playstate` goes to the player on screen through `RemotePlaystateRouter`, a one-slot `@MainActor` registry; never through the SwiftUI layer.** Both presenters register on open (`VLCStreamViewController.viewDidLoad`, `NativeVideoPresenter.present`) and unregister on teardown (`teardown()` / `cleanup()`), and the router hands back a TOKEN: `unregister` clears the slot only when its token is still the live one, so a late teardown can't evict the player that replaced it, and a command arriving after teardown finds an empty slot and is dropped — the generation guard. `RemoteControlListener` routes with `inSyncPlayGroup: SyncPlayController.shared.isInGroup`: **a Watch Together group owns the playhead, so Playstate is ignored there** rather than drifting one participant out of lockstep. Mapping: pause / unpause / play-pause → the engine plus the local press's visible feedback; `Seek` → **VLC through `engineSeek`** (near-end clamp + settle window; pending ±N commit cancelled first; refused before `mediaConfirmedOpen`), native through the resume path's `safeResumeSeconds` clamp; `Stop` → the player's own dismissal, so the stop report + teardown run as for any close (VLC dismisses via its PRESENTING controller so a stacked alert/picker can't absorb it); next / previous → the presenters' existing `navigateToEpisode` (no navigator or no neighbour ⇒ not applied). `Rewind` / `FastForward` / unknown values and a `Seek` with no target are dropped at parse time. Every outcome logs one `CINEMAX-REMOTE ▸ Playstate <cmd> → applied|noPlayer|ignoredSyncPlay|notApplicable` line (command + ticks only). Note: a server with `InactiveSessionThreshold` > 0 (default 0 = off) itself sends `Stop` to a session paused longer than that — honoring Stop means such a server now closes a long-paused player, as it does on every other client. Locked by `RemotePlaystateRouterTests` + `JellyfinSocketParsingTests`.
- **RULE — no `deviceProfile` in the capability post.** The profile is engine-dependent (`buildVLCDeviceProfile` vs `buildAppleDeviceProfile`, chosen from `forceNativeAVPlayer`) and the app always negotiates its own `PlaybackInfo` when playback starts. Pinning one here would be a second, staler copy of that decision — exactly what makes a server pre-transcode for the wrong engine.
- **RULE — `MediaDetailScreen.consumeIntentPlaybackRequest()` is CROSS-PLATFORM and must stay that way.** It was `#if os(iOS)` while App Intents were its only producer. Remote control raises the same request on tvOS, so leaving the consumer gated shipped a feature that looked like it worked — the sender's command arrived, the Apple TV navigated to the detail screen, and then nothing happened, with no error anywhere. Playback itself is still platform-split, in `startIntentPlayback`: tvOS drives `VideoPlayerCoordinator` (resolving episode nav + the version override up front, since the coordinator takes them as arguments), iOS pushes `VideoPlayerView` via `navigationDestination`. Same split as `startWatchTogether` / `PlayLink`. Any new producer of `pendingIntentPlaybackItemId` inherits this consumer.
- **RULE — inbound playback routes through `MediaDetailScreen`, not the player**, by setting the SAME `pendingIntentPlaybackItemId` + `pendingDeepLinkItemId` pair an App Intent uses. That is what gives a remote-initiated play the fidelity of a tap (series → next-up, resume position, version pick, prev/next buttons). Consequence: an inbound `StartPositionTicks` is **not** threaded through — the receiver re-resolves the resume position itself, which lands on the same tick for this app's own sender and is the better answer for any other. The item id is shape-validated through `AppState.isValidItemId`, the same SSOT as the public `cinemax://` scheme. Only `PlayNow` is honored (no queue — `EpisodeNavigator` stays the single next/prev authority); the raw command string is kept unmapped so a future value is ignored rather than mistaken for `PlayNow`.
- **RULE — one socket per session, and `JellyfinSocketHub` is what keeps it.** Jellyfin keys a session on device + client + user, so two concurrent `/socket` connections from this app are the *same* session server-side and every message arrives twice. Remote control and Watch Together used to own an actor each (`SessionSocket` / `SyncPlaySocket`) and could only coexist because Watch Together was kill-switched — they were not variants of one idea, they were the same ~175 lines written twice, differing only in which `MessageType` cases they parsed. They are now one `JellyfinSocket` emitting one `JellyfinSocketMessage`, behind a **reference-counted hub**: the connection opens on the first subscriber and closes when the last leaves, so an idle Watch Together costs exactly what it did before. **Nothing may open a socket directly** — a new consumer adds a case to the enum and subscribes. Each consumer sees EVERY frame and ignores what isn't its own; a subscriber asking for a different URL (server switch, re-login) rebuilds the connection for everybody, which is correct, since the old URL names a session that no longer exists.
- **Lifecycle** (`RemoteControlListener.apply`, single reconciling entry point, idempotent via an `appliedState` snapshot): driven from `AppNavigation` on the root `.task`, `onChange(of: currentUserId)` (capabilities are per-session, so login / user switch must re-declare), `onChange` of the settings toggle, and `scenePhase`. Background **closes** the socket (a backgrounded app can't act on a play command and a held WebSocket is a standing radio cost); `.active` re-applies. A `generation` token is bumped by every `apply` **and** by `stop()`, and re-checked after the capability await and on every delivered frame, so a logout / server switch that lands mid-flight can't open a socket against the session it just left.
  - **RULE — `AppNavigation` also re-applies on `onChange(of: appState.isAuthenticated)`.** A fresh sign-in writes `currentUserId` BEFORE `isAuthenticated` (`LoginViewModel.completeSession` awaits `refreshCurrentUser` and the success dwell in between), so the `currentUserId` observer reached `apply` while it still read signed-out and stopped: after every first login, re-login and server add, the device was no « Lire sur… » target and heard no invitation until the next trip to the foreground (audit 2026-09-22, B3). `apply` is idempotent, so the double call on logout is free.
- **Opt-out** is `SettingsKey.remoteControlEnabled` (default `true`, Settings → Lecture, both platforms). Turning it off **re-posts with `supportsMediaControl: false`** rather than merely closing the socket — that is what actually removes a still-live session from other clients' pickers.
- Frame parsing (`JellyfinSocket.parsePlay` / `parseDisplayMessage` / `parsePlaystate` / `parseGroupUpdate`) is pure + `static` + internal so it is unit-testable without a live socket — same treatment as `CinemaxStreamProxy.admission`. Locked by `JellyfinSocketParsingTests` + `SyncPlayQueueParsingTests`.

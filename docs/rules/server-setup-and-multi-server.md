## Server Setup & Login

Two-step pre-auth flow, shared mobile design (Server → Login feels like one journey). Discovery (`JellyfinServerDiscovery` + `ServerDiscoverySheet`): UDP broadcast port 7359; probes limited (`255.255.255.255`) **and** each interface's directed broadcast via `getifaddrs`. `scan()` auto-retries once after 800ms on empty (iOS local-network permission race). `NSLocalNetworkUsageDescription` in `iOS/Info.plist`. `AppState.disconnectServer()` → `ServerSetupScreen` ("Change server") — now only the last of the four `LoginScreen` escape-hatch shapes, see Multi-server below. **Both pre-auth screens are reused verbatim to ADD a server** (`isAddingServer`), so any change here must hold in add mode too. **RULE — furniture common to the two lives in `PreAuthChrome.swift`** (`PreAuthErrorBanner`, `PreAuthHelperLink`, `PreAuthEasterEgg.tap`): they are one journey and had byte-identical copies of all three, which is how the tvOS « pastille » focus treatment came to exist on one copy first. The easter egg takes `Binding`s because its tap count stays per-screen `@State` and its unlock flag stays `@AppStorage` — a trip through the other screen must not reset the run — and its haptics now route through `Haptics` like everything else in the app (both copies called `UIFeedbackGenerator` directly, against the Haptics SSOT RULE). Anything specific to ONE screen stays at home: `LoginScreen`'s four-shaped escape hatch, `ServerSetupScreen`'s status pill.

- **RULE — the first-run onboarding is admitted by `OnboardingPolicy` (`Shared/ViewModels/`), and `AppNavigation` renders it BELOW the session check and ABOVE the no-server branch** (`OnboardingScreen`, both platforms, three pages: your own server / Quick Connect / personalisation). `shouldShow` demands a GENUINE first run — never seen, **no registered server**, no mirrored legacy server, and not `isAddingServer`. Every other shape describes somebody who already knows the app: an upgrade (the multi-server migration has seeded an entry), a logout from their only server (the tokenless entry stays behind), an add from Réglages — and three pages of introduction in front of them would be an obstacle, not a welcome. **`shouldStampSeen` latches the flag at launch whenever a server is already known**, and that is what keeps an upgraded install out for good: without it, deleting the last server from `ServersScreen` empties the registry and the gate greets a long-standing user as a newcomer. The PLACEMENT is load-bearing in both directions — above `hasCheckedSession` it would flash over a session still being restored on every cold launch, below `ServerSetupScreen` it could never show at all. Re-openable from Réglages → Serveur → « Découvrir l'app » (`isReplay: true`), which is the ONLY difference between the two hosts: `OnboardingExit.decide` makes Menu on the FIRST page dismiss a replay and **suspend the app** at first run (passing `nil`, per the tvOS Menu-button RULE), and finishing latches nothing on a replay since the flag is already set. **Deliberately NOT a paged `TabView`**: `PageTabViewStyle` does not exist on tvOS and a swipe is not an input there, so the pager is one switched page plus explicit controls on both platforms, with the iOS swipe added on top as a convenience. The accent CTA takes focus on every page change — without that the focus engine lands on whichever control comes first, which on a page carrying « Précédent » is the one going backwards. **RULE — the iOS footer lays its buttons out in EQUAL SLOTS (`ctaWidth = .infinity`, row capped at `proseWidth`), never fixed widths, and carries two buttons, not three**: three fixed 130 pt CTAs plus gutters came to 486 pt on a 402 pt iPhone and pushed the whole page past both screen edges (reported 2026-09-14 on « Quoi de neuf », which shares the footer), a `Spacer` beside shrinkable `CinemaButton`s steals their width until the labels truncate, and even three equal slots truncated « Précédent ». So on iOS « Passer » lives in the top trailing corner (`skipHeader`) and a button that does not apply on this page keeps its slot invisibly (`View.slotVisible`), so « Suivant » never moves under a thumb tapping through. tvOS keeps fixed `ctaWidth` CTAs and the spacer. Locked by `OnboardingPolicyTests` (the admission truth table, the page chain, the Menu mapping).

- **Quick Connect** (`QuickConnectSheet`, both platforms): passwordless sign-in — initiate → show 6-char code → poll until the user approves it from another signed-in session, then exchange for a session. `AuthAPI.isQuickConnectEnabled/initiateQuickConnect/quickConnectAuthorized/authenticateWithQuickConnect`; `QuickConnectRequest {code, secret}` model (secret never shown). `LoginViewModel.startQuickConnect` owns the poll loop (≈3s) + shared `completeSession`. **RULE — a transient poll failure must NOT end the flow**: the code stays on screen, so an exited Task is indistinguishable from "waiting" while approval can never complete (one Wi-Fi blip on an Apple TV killed the sign-in). Each poll catches its own error and keeps going until `quickConnectFailureBudget` (5) **consecutive** failures, resetting on any success; only `quickConnectAuthorized` is budgeted, so the exchange (`authenticateWithQuickConnect`) still fails terminally as before. Cancellation exits immediately, and a cancel-induced `URLError.cancelled` never surfaces as an error. The CTA on `LoginScreen` (both layouts) is **gated on `isQuickConnectEnabled()`** (hidden when the server has it off / pre-10.x). iOS `.sheet`, tvOS `.fullScreenCover`. Biggest win on tvOS — no password typing on a remote.
- **RULE — every pre-auth field goes through `credentialField(_:onSubmit:)` (`GlassTextField.swift`)**: `textContentType` (`.username` / `.password` / `.URL`) so iCloud Keychain offers the saved account and tvOS its « sign in with your iPhone », `submitLabel`, and an `onSubmit` — the username's Return moves on to the password through `GlassTextField(focusRequest:)` (a two-way mirror of the field's internal `@FocusState`), the password's and the server URL's submit. The main forms had none of it while `UserSwitchSheet`'s secondary one did (audit 2026-09-22, U2).
- **Quick Connect authorize side** (`QuickConnectAuthorizeSheet`, Settings → Account): a signed-in user types the 6-char code another device shows on its login screen; approving completes that device's sign-in. iOS `.sheet` / tvOS `.fullScreenCover` (tvOS `.sheet` renders cramped). iOS auto-focuses the code field; tvOS deliberately does NOT (would force-open the full-screen keyboard over the instructions).
- **`ServerHelpSheet`** ("How do I find my server?", from `ServerSetupScreen`): static help content. **RULE — chrome is platform-branched**: iOS `NavigationStack`+toolbar; tvOS full-screen cover with custom header + accent close button, because tvOS `.toolbar` on a modal clips the title and renders the trailing button as an empty pill. `PrivacySecurityScreen` uses the same pattern (iOS `.sheet`, tvOS `.fullScreenCover`); when the modal's scroll content has focusable rows, the tvOS header needs `.focusSection()` or up-presses never reach the Done button.

- **RULE — LoginScreen mobile caveat**: ServerSetupScreen's `.padding(.horizontal, spacing4)` outside `.glassPanel` is silently dropped in `LoginScreen.mobileLayout` under iOS 26. Workaround: `.frame(maxWidth: formMaxWidth)` (350pt) on form panel + actions VStack. Don't "fix" without pixel-sampling.
- **Rainbow easter egg**: top icon block is a `Button` → `AccentEasterEgg.tap(…)` (resolver in `SettingsScreen.swift`). Cycles `AccentOption.cyclingCases`; unlock flips `@AppStorage(SettingsKey.rainbowUnlocked)`. `ThemeManager` checks `isRainbow` first → HSB driven by `_rainbowHue`.

### Multi-server

Several Jellyfin servers can be registered; **exactly one is active at a time** (no cross-server browsing, no merged libraries — see "Out of scope" below). UI: `ServersScreen` (Settings → Server → *Serveurs*, and from the pre-auth screens). Storage, decisions and orchestration are deliberately three separate layers: Keychain (`KeychainService`), pure logic (`ServerRegistry` / `ServerURLNormalizer`, `Packages/CinemaxKit/.../Models/`), stateful orchestration (`AppState`, `AppNavigation.swift`).

- **Storage layout** — two new **app-private** Keychain accounts on the existing `com.cinemax.jellyfin` service (never the shared extension group): `servers` = JSON `[ServerEntry]`, `active_server_id` = the active entry's id. `device_id` stays global (one device identity across all servers). `ServerEntry.id` is a **locally minted UUID**, not Jellyfin's server id — it survives a URL edit and exists before we've ever reached the server.
- **RULE — the legacy trio (`server_url` / `access_token` / `user_session`) is a DERIVED MIRROR of the active entry.** Every pre-existing read path (`AppState.restoreSession`, `SettingsScreen.username`, `ExtensionSessionBridge`) still reads only those items, which is why multi-server needed no changes there and why a total migration failure degrades to exactly today's behavior. **Writers are exhaustively**: `AppState.applyActiveServer` (every switch — writes all three), `LoginViewModel.completeSession` (every login — writes all three together, including `server_url`), and `ServerSetupViewModel.connect`, which writes `server_url` **only when `!appState.isAddingServer`**. That last exception is load-bearing: during an add the mirror must keep describing the server the user is still signed in to, or force-quitting between the server step and the login screen would pair the NEW url with the OLD token and reconnect to the wrong server on next launch. In first-run mode nothing reads the URL until a session lands, so the historical early write is kept.
- **Migration** (`SecureStorageProtocol.migrateToMultiServerIfNeeded()`, run from `restoreSession`): one-shot, idempotent, **non-destructive** — seeds one entry from the legacy trio and never deletes a legacy item. Idempotence is keyed on "the servers list is non-empty", never a flag, so a locked Keychain at first launch just retries next launch. **RULE — it lives in the protocol extension and must NOT be overridden by a conformer** (`KeychainService` and the test `MockKeychain` run the same code, so the migration tests exercise production behavior). `clearAll()` stays scoped to the legacy trio — a plain logout must never wipe the registry.
- **RULE — `logout(reason:)` has two behaviors, and the caller must consume `LogoutOutcome`.** Common to both: strip credentials from the **active entry only** (the entry itself stays, tokenless, so its card remains in the list ready to re-login), `keychain.clearAll()`, publish a nil session to the extensions, reset auth state. `.userInitiated` additionally revokes server-side (fire-and-forget) and **auto-hops** to `ServerRegistry.nextCandidate` when one still holds a token → `.switchedTo(entry)`; the hop is invisible otherwise, so **both** Settings call sites go through `SettingsScreen.performLogout()`, which toasts `servers.switchedTo`. `.sessionExpired` (from `handlePossibleSessionExpiry`) does **no** revoke and **no** hop, and deliberately keeps `hasServer`/`serverURL` so the user lands on the SAME server's `LoginScreen` behind the expiry toast — locked by `SessionResilienceTests`.
- **RULE — a switch is two-phase and `.indeterminate` never destroys a token** (`AppState.switchTo`): a pre-flight `ServerRegistry.decideSwitch` short-circuits the cases that must not reach the network (offline, no stored token), then the target's token is validated **OFF the shared client** (`AppState.sessionValidator` → `ServerSessionValidator.validate`, `GET /Users/Me` on its own bounded, cache-less session, `ServerReachability.swift`; a 2xx counts only when its body is a user JSON with an `Id` — URLSession follows redirects, so an SSO login page or a captive portal answers 200, and the shared client's `validateSession` DECODES a `UserDto` for the same reason). `.valid` → `applyActiveServer`, the switch's ONE repoint; `.invalid` → clear **that entry's** credentials and go to its login; `.indeterminate` → `.unreachable` with nothing to undo. It used to repoint the shared client first and validate after (audit 2026-09-22, B10): for up to the 30 s timeout every screen still on the previous server requested the TARGET with the previous user id, a 401 in that window fed the expiry coordinator against the wrong server, and the rollback (`rollBackFailedSwitch`, now deleted) reconnected across servers, which clears the learned `ServerVersion` — every 10.10+/12.0 gate went dark on the working server after one flaky switch attempt (B4). **Never validate a switch target through the shared client again.** Tests route the seam to the mock (`makeState` sets `sessionValidator = { _, _ in await api.validateSession() }`).
- **RULE — the `AppNavigation` observer declaration order is load-bearing: `activeServerId` BEFORE `serverURL` BEFORE `currentUserId`.** A switch mutates all three in one transaction; SwiftUI delivers same-transaction `onChange` handlers in declaration order, and `onChange(of: activeServerId)` (→ `menuConfig.activate(serverId:knownServerIds:)`) must land before `onChange(of: currentUserId)` (the single owner of `refreshAvailableViews()`). Refreshing before the profile swap merges the NEW server's libraries into the PREVIOUS server's profile and persists them there. Do not reorder them, and never add a second refresh owner.
- **RULE — every `AppState` transition method that mutates `hasServer` / `serverURL` bumps `serverTransitionGeneration`**, and any transition that awaits re-checks it before writing (`beginReLogin`'s `connectToServer`, `applyActiveServer`'s background `fetchServerInfo` also re-checks `activeServerId`). Covers `applyActiveServer`, `beginReLogin`, `beginAddServer`, `restorePreviousServer`, `logout`, `disconnectServer`. Same pattern as `NowPlayingInfoController.generation`. Scoped to `AppState` on purpose: `ServerSetupViewModel.connect` also writes `serverURL`/`hasServer` (the pre-auth commit) and legitimately does NOT bump — it isn't racing an awaited transition, it *is* the transition the user just confirmed.
- **RULE — the per-server status probe and the session revoke are STANDALONE and unauthenticated/off-client** (`ServerReachability.ping`, `ServerSessionRevoker.revoke`): the ping hits the public `GET /System/Info/Public` on its own bounded `URLSession` with **no auth header**, so a 401 is structurally impossible and `notifyIfUnauthorized` / `.cinemaxSessionExpired` can never fire from a dead *secondary* server and log the user out of the active one. Neither helper may ever touch the shared `JellyfinAPIClient` — the revoker builds its own `MediaBrowser` header, since the target server is not the one the shared client points at.
- **`ServersScreen` RULEs** — (a) every "is this the server we're on?" test keys on `appState.activeServerId`, **never** `currentActiveEntry` (whose MRU fallback resolves to a server the app isn't on while signed out, which is exactly the state this screen renders in when opened from the pre-auth screens); (b) pending switch / delete / rename hold an entry **id** and re-resolve from `appState.servers` at action time — the screen's own probe writes discovered name/version back into the registry, and `ServerRegistry.upsert` **replaces** rather than merges (the two user-owned fields excepted — see the RULE below), so a captured row snapshot would regress metadata; (c) nothing reads authenticated state (the per-entry avatar is drawn locally — `imageBuilder` points at the *active* server, so a non-active entry's avatar URL would 404 / leak a cross-server request); (d) the reachability sweep is behind an attempt flag (the tvOS Settings surface re-fires its `.task` on every `MenuConfigStore` mutation); (e) iOS uses a native `List` — a deliberate exception mandated by swipe-to-delete (`.swipeActions` exists only on `List`) and `.onMove`, same class as `MenuSettingsScreen+iOS`; its context menu and swipes sit OUTSIDE the row's `.disabled`, so the active card stays renamable; tvOS uses whole-card focusable buttons with rename / move / delete on a `.contextMenu`, and the active card stays focusable but inert (a disabled card reads as a missing card and loses its menu) with a toast explaining the no-op.
- **Dedup** (`ServerSetupViewModel.connect`, before any network call): a URL already registered **and carrying a usable session** (`ServerEntry.hasUsableSession` — token AND user id, i.e. exactly what `applyActiveServer` accepts) is refused with `server.alreadyAdded`. **RULE — never widen that gate**: a registered-but-signed-out entry must pass through, because logging out of your only server leaves precisely that shape behind and drops the user on `ServerSetupScreen` — refusing it would lock them out of the app. `upsert` dedups on the normalized URL regardless, so the permissive branch cannot create a duplicate.
- **URL normalization** (`ServerURLNormalizer`) is the SSOT for both the URL we dial and the dedup key: lowercase scheme + host, http(s) only, default port dropped, trailing slash stripped, query/fragment/credentials dropped, **sub-path preserved** (dropping `/jellyfin` would 404 every hand-built URL — see the `URLComponents+ServerPath` RULE). IPv6 literals round-trip with their brackets.
- **Escape hatches** — `ServerSetupScreen` shows "cancel adding" while `isAddingServer` and "My servers" whenever entries exist; `LoginScreen`'s hatch is four-shaped (cancel-add → back to the rollback server → open the servers list → `disconnectServer()`), rendered on **both** layouts (tvOS/iPad previously had none, making a re-login switch a dead end). `beginAddServer()` deliberately deletes nothing, so a cancelled add replays through `restorePreviousServer()`.
- **Rename / reorder** (`ServerEntry.displayNameOverride` / `sortIndex`, both optional so a registry already in the Keychain decodes unchanged — a non-optional addition would fail the whole `[ServerEntry]` decode and `getServers()` would answer `[]`): every surface prints `displayName` (label, else the server's `name`). `ServerEntry.normalizedDisplayNameOverride` trims, caps at 60 and maps empty **or the server's own name** to `nil`, so clearing restores the server's name and a label that merely restates it keeps following a server-side rename. `ServerRegistry.sorted`: placed entries (`sortIndex != nil`) first by index — the active one included, promoting it would undo the arrangement on every switch; unplaced ones (servers added after a reorder) follow by the old active-first-then-`lastUsedAt` rule, which is also the whole order until the user first reorders. Writers: `AppState.renameServer` / `reorderServers` only, and `reorderServers` takes the COMPLETE displayed order (`ServerRegistry.applyingOrder` — a delta would collide with untouched indexes). UI: iOS context menu + leading swipe → rename alert, « Ordonner » edit mode (never forced on — rows are switch targets) + `.onMove`; tvOS card context menu → Renommer / Monter / Descendre / Supprimer (the `PlaylistDetailScreen` idiom). `SettingsScreen.serverName` reads `AppState.activeServerNameOverride` (keyed on `activeServerId`); `LoginScreen` keeps the server's own name, since `beginReLogin` leaves `activeServerId` on the previous server.
- **RULE — `ServerRegistry.upsert` ALWAYS keeps the stored entry's `displayNameOverride` / `sortIndex`; it never takes the incoming ones** (a brand-new entry keeps its own). Every `upsert` caller describes what it learned about the server (login, switch, rollback) and none owns the user's label or position — and several hand in a snapshot captured before the user acted (`pendingRollbackServer`, a switch target), which would silently revert a rename on the next switch. `updateServerMetadata` (the reachability sweep's write-back) mutates in place and never touches them either. Locked by `ServerRegistryTests` (sweep, switch, stale snapshot both ways, legacy decode).
- **RULE — search history is PER SERVER (`SearchHistoryStore`, `search.recentQueries.<serverId>`), and the legacy global list migrates ONCE into the first server that activates, keyed on a MARKER (`search.recentQueriesMigratedTo`), never on "no per-server list yet".** `MenuProfile` can key on emptiness because its profiles share one dictionary nothing empties; here each server owns a key that « Effacer » / removing the server deletes, so emptiness recurs and an emptiness-keyed migration would re-import the old list into whichever server is active — the cross-server leak per-server history exists to close. Marker set before copying; the legacy key is never deleted by the migration and an existing per-server list is never overwritten. Triggered next to `menuConfig.activate` (root `.task` + `onChange(of: activeServerId)`) and again, idempotently, by `SearchViewModel.loadHistory(forServer:)`, which `SearchScreen` calls from `.task(id: activeServerId)` (so a switch swaps the chips and a return from Privacy re-reads a wipe). A query is filed under the server captured when the search STARTED. `serverId == nil` reads/writes the legacy key (the `MenuConfigStore` no-profile degrade). **Turning `search.saveHistory` OFF wipes EVERY server's list plus the legacy one** (`SearchHistoryStore.clearAll` sweeps the `search.recentQueries.` prefix, orphans of removed servers included) — it is a privacy promise, not a per-server one; « Effacer » on the Search screen clears the active server's only; `removeServer` drops that server's list. Locked by `SearchHistoryTests`.
- **Out of scope, deliberately**: per-server settings profiles **other than the menu and search history** (accent/theme/rating cap stay global `@AppStorage`; the whole menu configuration is server-scoped — see the per-server `MenuProfile` RULE under *Custom menu*), simultaneous connections, per-server extensions (Widget + Top Shelf follow the **active** server only).
- **RULE — the SDK's strict-decode fields are locked by a FIXTURE of real server bytes, not by in-memory DTOs** (`Tests/CinemaxKitTests/Fixtures/jellyfin-{10.10,10.11,12.0}-*.json` + `ServerDTODecodingFixtureTests`, parametrised over the three): SDK 3.1.0 `decode`s — not `decodeIfPresent` — `UserItemDataDto.key`, `UserPolicy.authenticationProviderID` and `.passwordResetProviderID`, so a server omitting one fails **the whole DTO**, taking every rail, grid, login and `validateSession` with it. Every other test builds its DTOs in memory, which proves nothing about the wire: `UserItemDataDto(key:)` satisfies the compiler and never runs `init(from:)`. The fixtures are raw responses (`/Users/Me`, `/Items/{id}`, `/UserItems/Resume`, `/Shows/NextUp`, in the app's query shapes), decoded with the SDK's own decoder configuration (`JSONDecoder` + a mirror of the internal `OpenISO8601DateFormatter`), with paired controls per version — `Key` removed from the item and from ONE Resume entry (the whole list fails), each provider id removed from the user — that assert the decode FAILS, without which the presence of the field in the fixture would be incidental. **Scope, measured 2026-09-11: 10.10.7, 10.11.11 and 12.0 all send every strict field** (10.x from throwaway Docker servers via `scripts/fixtures/capture-jellyfin-fixtures.sh`; 12.0's item + user from the reference server, its Resume + Next Up from Docker 12.0.0); **the 10.9 floor is still unmeasured** — one script run away. One wire difference is pinned rather than papered over: 10.10.7 sends `Guid.Empty` as `UserData.ItemId` on every item (nothing reads `userData.itemID`). A new generation is a script run plus a `FixtureServer` case (recipe in `Fixtures/README.md`); the script never overwrites an existing file without `--force`, which is what keeps the richer reference-server 12.0 pair. Identifiers, titles and paths in the fixtures are placeholders of the same shape; every key the server sent is preserved with its original type. The fixtures ride `project.yml` as a **folder reference in the resources phase** (hence `Bundle.url(forResource:withExtension:subdirectory: "Fixtures")`), and `Tests/CinemaxKitTests` excludes `Fixtures/**` from its Swift sources.

# Media detail screen (« fiche »)

> Split out of the root `CLAUDE.md` on 2026-09-22 (audit lot 5), content moved verbatim. Read before touching `MediaDetailScreen`, `MediaDetail*`, `MediaDetailViewModel`, `MediaSourceQuality`, `PersonDetailScreen`, `getEpisodes` / `getEpisodeRefs` caching. The root file's cross-cutting rules (Swift 6, `@Observable` without `didSet`, lazy-container navigation, base-path URLs, xcodegen, tests) still apply. Lines tagged **RULE** override default behavior.

## MediaDetailScreen

**RULE — `.task` goes through `loadInitial` (latched by `hasLoaded`), never `load()` directly.** SwiftUI re-runs `.task` when this screen reappears after the player is popped on iOS, and it used to re-run the FULL load there: measured on device 2026-08-19, that full load fired **39 ms before** the targeted post-playback refresh, so the screen paid both — and the full one flips `isLoading`, which swaps the body for the spinner and drops the user's scroll position (returning from an episode jumped back to the top of the page). Playback now announces its own userData change (tier-2), so a reappearance needs no reload at all. The latch clears on a failed load so the next appearance retries; the Retry button still calls `load()` directly — **as does the tier-1 observer**, which is what re-fetches the screen after an admin metadata / identify change (see the two-tier refresh RULE). The latch is about the *reappearance* being a poor proxy for "something changed"; it is not a ban on reloading when a producer actually says so.

**RULE — « Titres similaires » is a SIDE task (`MediaDetailViewModel.similarTask` → `loadSimilar`), silent on failure, and `load()` clears `errorMessage` first** (audit 2026-09-22, P1). `/Similar` is one of the costliest Jellyfin queries and its row sits below the fold, yet the fiche waited for it before painting — and a failed `/Similar` replaced the whole fiche with the error screen. Nothing cleared `errorMessage` either, so after one failure the error screen stood even when Retry succeeded. A watched toggle (`togglePlayed`) splices `item.userData` (played, position 0) and then runs `refreshAfterPlayback`: the play chrome reads `item.userData` through `resolvedPlayTarget`, not `isPlayed`, so the flag alone left « Reprendre » on a film just marked watched (B6).

`MediaDetailViewModel` auto-resolves Episode/Season → parent Series (by `seriesID`, loads seasons + episodes) + `getNextUp()`. `selectSeason()` uses a generation counter for stale results; **`load()` and `refreshAfterPlayback()` share a second `loadGeneration` counter** (bump-at-entry, re-check after each await cluster, a superseded pass writes nothing — not even `isLoading`) so an initial load and a dismiss-refresh can't clobber each other's `@Observable` writes. Use `resolvedType` (not initial `itemType`) for layout. **Detail refresh after playback** (tier-2 observer, both platforms — it ignores notifications whose `object` is its own view model, since its watched toggles already refresh exactly what they changed): the screen runs the TARGETED `refreshAfterPlayback(using:)` — no `isLoading` spinner flash, no similar/seasons re-fetch — re-pulling only the userData-bearing slices (movie: its `getItem`; series: `getItem` + `getNextUp` + the visible season's `getEpisodes`, concurrently — all hit caches `reportPlaybackStopped` invalidated), NOT the full `load()`. Both episode refreshers (`refreshAfterPlayback`, `refreshVisibleEpisodes`) write `episodes` only while `selectedSeasonId` still names the season they fetched — a season picked during the round-trip is `selectSeason`'s, whose generation does not cover them (audit 2026-09-22, B8).

- **RULE — a BoxSet gets a COLLECTION fiche, and `isPlayableType` is what gates the play chrome.** The screen used to draw a collection with the full chrome of a work — title, Lecture, favori / vu / playlist, "Titres similaires" — with no year, runtime, genre or overview (a BoxSet carries none) and, worse, no list of what it holds, which is the only thing anyone opens it for. Pressing Lecture opened the player and then blamed the SERVER for a stream that never existed. Now: `metadataLine` renders "Collection · N titres · 2012–2019" (count + span derived from the members, so it fills in when they land), `MediaDetailViewModel.collectionChildren` loads them as a silent side task (`getItems(parentId:)` sorted by `premiereDate` — the one ordering a saga has that an alphabetical list destroys), "Dans cette collection" stands where "Titres similaires" does on a work, and `getSimilarItems` is not even requested for a BoxSet. `isPlayableType` answers `true` for a collection **exactly when a member has landed**, and `false` for every other streamless kind (folder, person). Entry point: `LibraryFolderBrowseScreen` pushes the fiche for a collection — before that it drilled straight into a scoped grid and the fiche was unreachable by any route.
- **RULE — "Tout lire" reuses `EpisodeNavigator`; it does NOT add a queue.** `EpisodeNavigator` is a `typealias` over a pure index lookup on any list of playable items — nothing about it is episode-specific but the name — so handing it `collectionChildren` gives the collection its in-player prev/next, its autoplay-next and its end-of-set card with no second next/prev authority beside it (the thing the project has refused three times elsewhere). Resolution goes through `resolvedPlayTarget(for:)`, the existing SSOT, via the `nextEpisode` field every caller already reads to learn the target is not the item itself — so "Lire sur…" and Siri inherit it. **`posTicks`/`totalTicks`/`isPlayed` must read the RESOLVED target, never key on `isSeries`**: a collection would otherwise describe the BoxSet's own (always absent) userData and both the progress bar and "Reprendre" would go silent. Where it starts is `CollectionPlayTarget.startIndex(playedFlags:)` — first unfinished member, else the first — the same reading `resolvePlayableEpisode` gives a series; the fallback is what matters, since a saga watched end to end must replay rather than refuse. Locked by `CollectionPlayTargetTests` (including a hole in the middle) and `CollectionDetailTests`.
- **RULE — the hero title is the work's LOGO when the server holds one AND the hero has room for it** (`item.hasLogoImage` → `ImageType.logo`, tagged `logoImageTagValue`, height-led with a max-width ceiling; one shared `titleBlock` path, the platform only supplies the box via `logoBox`): a logo's width varies enormously between titles, so pinning the width would make one mark tower over the next. The text title is the ORDINARY case, not an error path — most libraries have no logo. **tvOS always has room** (`CinemaTVLayout.logoHeight` / `logoMaxWidth`). **iOS draws it only when the MEASURED hero is ≥ `AdaptiveLayout.detailLogoMinHeroWidth` (600 pt — iPad, iPhone in landscape)**, never keyed on the size class (an iPhone in landscape is still `.compact`); an iPhone in portrait keeps the text, since the mark would shrink past its own legibility. The iOS box is 0.6 × tvOS (96 / 420 pt) **and capped at `detailLogoMaxHeroFraction` (0.3) of the CLAMPED hero height** — `onGeometryChange` sits AFTER the `containerRelativeFrame(.vertical)` clamp, because a landscape iPhone clamps the hero to ~200 pt and a full 96 pt mark would push the badges row out of the clipped top. The sizing is the pure `AdaptiveLayout.detailLogoHeight(forHero:)`, locked by `DetailHeroLogoTests`. The logo is ONE accessibility element labelled with the work's name, so VoiceOver reads the same thing either way. `CinemaLazyImage` gained a `contentMode` for this (`.fill` default, so no existing caller changed) and the logo passes `fallbackBackground: .clear` — it sits over the backdrop.
- **RULE — the tvOS accessory row uses `TVAccessoryActionButton` (icon over a short label), and the label is ALWAYS visible, never revealed on focus**: a button that grows a caption when focused reflows the row, moving its neighbours under the remote just as the user reaches for them. The five actions were unlabelled 28 pt glyphs, which asks the viewer to recognise `text.badge.plus` and `tv.badge.wifi` from three metres, where iOS posts labelled chips. Visible labels are the `detail.action.*` keys — short nouns, distinct from the `detail.favorite.*` / `remote.title` accessibility labels, which spell the whole action out.
- **RULE — the tvOS action row is ONE row at `CinemaTVLayout.actionRowHeight`** (`PlayActionButtonsSection`'s `#else` branch): Play (`ctaWidth`) then « Depuis le début » (`detail.playFromBeginning.short`, natural width via `fixedSize(horizontal:)`, VoiceOver keeps the full `detail.playFromBeginning`), then the `TVAccessoryActionButton`s (`accessoryButtonWidth × actionRowHeight`, glyph `pt(22)`). Before 2026-09-09 the secondary was STACKED under Play in a 240 pt pill, so it truncated to « Lire depuis le… » while the accessories — centred on Play through `.playActionRow` — floated mid-column; and the accessories sized themselves ~115 pt tall next to a 77 pt Play, growing further with the font-size slider. iOS keeps its own branch (Play + full label split one line). The hero title logo carries a FIXED `logoHeight` proposal (a `.fit` image under a bare `maxHeight` can fall back to its natural size); a logo whose ink fills a corner of a mostly transparent canvas (demo library: 94 × 32 px on 700 × 238) still renders as a sliver — that is the artwork. « 1 saison » / « 3 saisons » go through `loc.seasonCount(_:)` (the fiche said « 1 saisons » while the library hero said « 1 saison »).
- **Resume / next-up** (`actionButtons` → `PlayActionButtonsSection: View, Equatable`): custom `nonisolated static func ==` compares resume + prev/next identity, ignores closure → `.equatable()` short-circuits re-renders. Same pattern on extracted `MediaDetail{Cast,Similar}Section`/`Episode{Card,Row}` (wrap non-Sendable DTO reads in `MainActor.assumeIsolated` — escape hatch #4). tvOS episode list uses `LazyVStack`.
- Movie `playbackPositionTicks > 0` not `isPlayed`: progress bar + remaining + "Lecture" via `PlayLink(startTime:)`. Series: `nextUpEpisode`. **Play from beginning**: when `showResume`, secondary ghost `PlayLink` with `startTime: nil`. `userData.playbackPositionTicks`/`runTimeTicks` are `Int?`; `isPlayed` is `Bool?`.
- **Quality badges** (`MediaQualityBadges.swift`): gated on `@AppStorage("detail.showQualityBadges")`. A thin view — all classification lives in `MediaSourceQuality` (see below). Resolution by width OR height (4K/1080p/720p/SD — height alone mis-reads scope encodes), HDR (`VideoRangeType` → Dolby Vision/HDR10+/HDR10/HDR), codec, audio format (Atmos/TrueHD/DTS-HD/DTS/DD+/DD/FLAC/AAC/Opus/MP3), channels. `EmptyView()` when none.
- **RULE — multi-version items rank through `MediaSourceQuality` (`Packages/CinemaxKit/.../Models/MediaSourceQuality.swift`), and BOTH the badges and `getPlaybackInfo` must go through it.** An item can carry several `MediaSourceInfo` versions (4K remux + 1080p encode, IMAX + theatrical). Both call sites used to take `mediaSources.first` — accidentally consistent only because neither chose; the moment one ranks and the other doesn't, the detail screen advertises a version the player never opens. Ordering is lexicographic: **bitrate-cap fit → resolution → HDR → IMAX → audio format → channels → bitrate → source id**. Notes: the cap (`render4K`'s 120/20 Mbps) sorts FIRST and **gates rather than filters** (a library entirely over the cap must still play); a source reporting no bitrate is treated as within it. **IMAX is the one heuristic tier** — no structured field exists, so it string-matches the source `name`/`path`; safe because it only breaks ties *between sources of the same item*, so a title genuinely containing "IMAX" tags all of them and cancels out. The order is **total** (falls through to source id, then server order) precisely so the two call sites can rank independently and never disagree. Selection UI: a conditional "Version" row under the action buttons on `MediaDetailScreen` (`count > 1`), iOS `Menu` / tvOS `confirmationDialog`, threaded to the players as `PlayLink(mediaSourceId:)` → `getPlaybackInfo(mediaSourceId:)`. **RULE — the row ranks the RESOLVED play target (`versionTarget` = `resolvedPlayTarget.nextEpisode ?? item`), never the fiche item's own sources**: Jellyfin 12.0 lets EPISODES carry alternate versions (10.x was movies-only), so a series' row ranks its next-up episode — `getEpisodes` and the per-series `getNextUp` request `.mediaSources` for exactly this — and its title reads « Version · S01:E01 - Titre » so the user knows which episode the pick applies to. On 10.x an episode carries one source and the row stays hidden for series, which is why this needs no `ServerVersion` gate. The pick is **keyed by the target's id** (`MediaDetailViewModel.selectedMediaSourceIds`, mutated only through `selectMediaSource(_:for:)`): a single `String?` carried a pick made for episode 4 onto episode 5 once next-up advanced. A Siri / remote request naming a DIFFERENT episode gets no source id (`selectedSourceId(forPlaying:in:)`), and an in-player episode swap re-negotiates with the ranked default — `EpisodeNavigator` carries no source id, deliberately. Locked by `EpisodeVersionSelectionTests`. The override is **session-scoped, not persisted**: the standing "smaller files" preference is already `render4K`'s job. A stale id (server re-scan) silently falls back to the ranked pick via `MediaSourceQuality.resolve`.
- **Episode nav**: `episodeNavigation(for:)` O(1) from `episodeNavigationMap` (current season) or `nextUpNavigationMap` (cross-season next-up).
- **RULE — episode NAVIGATION goes through `LibraryAPI.getEpisodeRefs`, never `getEpisodes`** (`episoderefs-<seasonId>-<userId>`, TTL **300 s**, returning `[EpisodeReference]` — an `id` + `name` `Sendable` value type in CinemaxKit). `getEpisodes` was the app's single largest payload and its heaviest consumer read two fields of it: measured against Jellyfin 12.0 on 2026-09-10, one 23-episode season of *Arrow* is **164 069 bytes** with the `fields` the app asks for and **18 292** without — **9.0×** (Arcane 8.8×, Ahsoka 8.0×, 8.7× over the three) — and a single Home load resolves up to **40 distinct seasons**, re-resolving them on every tier-1 refresh and pull-to-refresh. Consumers: `HomeViewModel.fetchSeasonEpisodes` (both rails' nav maps), `fillMissingEpisodeNavigation`, `CardEpisodeNavigationResolver`. **The detail screen keeps `getEpisodes`** — it genuinely renders overview, media sources and per-episode userData (watched marks, progress bars). **RULE — `episoderefs-` is deliberately OUTSIDE `userDataCachePrefixes`, and that is why its TTL can be 300 s**: the payload is requested with `enableUserData: false`, no `fields` and `enableImages = false`, so it carries nothing a played-toggle could make stale — an episode's id and title change only on a library re-scan. Adding it to that sweep would re-fetch an identical answer after every watched toggle anywhere in the app. **No rating filter either, deliberately**: this feeds the prev/next buttons of an episode already playing and the list must stay contiguous — a hole punched mid-season by a rating cap would make "next" *skip* an episode rather than refuse it; `getPlaybackInfo` stays the authority on what may be played. `precomputeEpisodeRefs` / `buildEpisodeNavigation` carry an overload over `EpisodeReference`; that overload is the one place app-side `EpisodeRef` and CinemaxKit's `EpisodeReference` meet. Locked by `EpisodeRefsPayloadTests`.
- **RULE — `getEpisodes` has a 10s TTL cache** (`JellyfinAPIClient+Library.swift`, keyed `episodes-<seasonId>-<userId>`, mirroring `getItem`) — collapses the burst where Home's nav maps and the detail screen re-fetch the same season within seconds. Because a season's episode list carries per-episode userData (watched marks + resume position), **every userData mutator invalidates the whole `episodes-` prefix**: `markItemPlayed` / `markItemUnplayed` (a series-level toggle cascades to every episode; the mutator only knows the item id, so it can't scope to one season key) and `reportPlaybackStopped` (episode resume position). `refreshVisibleEpisodes` after a played toggle relies on this — without the invalidation it would re-serve the stale cached list and the checkmarks wouldn't update. Any new episode-userData write must add the same sweep — the three prefixes are single-sourced through `JellyfinAPIClient.userDataCachePrefixes` (`["episodes-", "seasons-", "nextup-"]`) so every mutator iterates one list and a new cached userData endpoint is one array entry. **`getSeasons` (`seasons-<seriesId>-<userId>`) and the per-series `getNextUp` (`nextup-<seriesId>-<userId>`) share this exact contract** — same 10s TTL, and the same three mutators drop all three prefixes together (a played toggle both cascades to every episode's watched mark AND moves the series' next-up pointer; `MediaDetailViewModel.refreshAfterPlayback` re-pulls `getNextUp` right after `reportPlaybackStopped`, so a missing `nextup-` sweep would re-serve the episode that just finished). The global `getNextUpEpisodes` (Home rail) is deliberately NOT cached — only the per-series overload. **Single-flight**: `getItem` also runs its network fetch through `APICache.coalesce(key:operation:)` (in-flight de-dup at `T == Void`, winner writes the TTL entry, awaiters read it back — `BaseItemDto` never crosses the coalescing boundary), so the playback-start burst's *concurrent* callers (which all miss the TTL before the first response lands) share one round-trip; in-flight entries are removed on success AND failure so a failed fetch never poisons retries. The VLC end-of-series card reuses `fetchChapters`' already-resolved `resolvedSeriesName` instead of re-fetching at playback end.
- **RULE — `APICache` refuses a write whose fetch began before a sweep that covers its key** (audit 2026-09-22). Every cached endpoint takes `let cacheStamp = cache.stamp()` BEFORE its `get` and hands it to `set(…, stamp: cacheStamp)`; `invalidate(prefix:)` / `clear()` log `(epoch, prefix)` (last 128), and `set` drops a value when a sweep covering its key ran after its stamp — so a fetch on the wire during a watched toggle can no longer re-cache the pre-toggle answer for the next TTL. **The stamp belongs to the FETCH, never to the key**: the first version remembered one miss per key, and the refresh raised by the very same mutation overwrote it, laundering the stale answer through in either landing order (adversarial review; `concurrentFetchesAroundASweep` locks both orders). A `set` without a stamp (tests, a prime) is stored as before; a log that no longer reaches the stamp means "cannot prove fresh" ⇒ not cached. A sweep also DETACHES matching in-flight `coalesce` entries, so a caller arriving after it starts a fresh fetch; each entry carries an id so the orphan's cleanup cannot remove its successor. **A new cached endpoint takes a stamp too.** Locked by `APICacheTests`.

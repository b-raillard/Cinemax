## Media Library (`MediaLibraryScreen`)

Unified, parameterized by `BaseItemKind`. State: `LibrarySortFilterState` (default `dateCreated` desc).

- **RULE — a series hero must carry episode navigation** (`MediaLibraryViewModel.loadHeroNavigation` → `LibraryHeroSection.heroPlay` → `PlayLink`). `handlePlaybackEnded` shows the "Vous avez terminé…" card only when `episodeNavigator != nil` and **dismisses silently otherwise** — so the library hero, the one play surface that passed `PlayLink(itemId:title:)` and nothing else (Home, `MediaDetailScreen` and the card menus all thread it), could never show that card, and had no in-player prev/next buttons either. Confirmed by a controlled on-device comparison: `hasNavigator=false` from the hero vs `hasNavigator=true` from Home's resume rail, same series. The hero therefore plays the **resolved episode**, not the series, so navigator and media always describe the same thing. **Resolution mirrors the server's `resolvePlayableEpisode` exactly — next-up first, ELSE the first episode of the first season**: `getNextUp` returns nil once every episode is played, i.e. precisely on the series you are about to reach the END of, so without that fallback the fix would have missed its own use case (verified on device). Probe is a side task off the critical path and fails silently (`loadRemoteTargets` discipline) — no navigation is an ordinary outcome, never an error over a loaded hero. **RULE — `heroPlay` must be RE-DERIVED when the user comes back, via `MediaLibraryViewModel.refreshHeroNavigation`**: `performLoad`'s side task is its only other writer and nothing revisited it, so the hero's Play button stayed pinned to the episode resolved when the page first loaded, at the resume offset it had *then* — measured on device 2026-08-14: after watching episode 2 to 2:02 and closing the player, Play reopened **episode 1 at 0:01**. Its single caller is the tier-2 userData notification, which **playback itself now posts** (`PlaybackReporter.reportStop`) — see the two-tier RULE. It briefly had two extra platform-specific hooks (iOS `.onAppear`, tvOS `lastDismissedAt`); both were deleted when playback gained a voice, because they were the same asymmetry that had left `HomeScreen` with no hook at all. Cheap by construction: a no-op unless the hero is a series, and all three probes are 10 s-cached. Locked by `LibraryHeroNavigationTests`.
- **RULE — the browse layout's « Collections » row is scoped to THIS library and gated on a KNOWN 12.0** (`MediaLibraryViewModel.collections` ← `loadCollections`, a side task off the first paint in the `loadHeroNavigation` discipline; `LibraryAPI.getLibraryCollections`; `ServerVersion.libraryScopedCollections` = 12.0.0). Jellyfin 12.0 resolves `GET /Items?includeItemTypes=BoxSet&parentId=<library>` through `linkedChildAncestorIds` (measured on the NAS: Films → 58 sagas, Séries → 0); **10.x silently drops `parentId` for BoxSets and answers with every collection on the server**, so below the threshold — and while the version is unknown — the client returns `[]` **without a request**: the query would not degrade there, it would put 58 film sagas under a series library. The scope is `LibraryCollectionsScope.libraryIds` (pure, `Shared/ViewModels/`): a library-mode tab is its own `parentId`; the default Films / Séries tabs carry NO id and resolve to every user view of the matching `CollectionType` (`movies` / `tvshows`) through one `getUserViews`; an untyped tab without an id asks for nothing — never the global query, which is Home's rail (`home.showCollections`) and must not be duplicated under every library. Cards open the collection FICHE (`MediaDetailScreen(itemType: .boxSet)`), never a scoped grid, and carry no context menu (a folder). No playlists row, deliberately: a playlist belongs to the user, not to a library. Locked by `LibraryCollectionsRowTests`.
- **Browse vs filtered**: browse layout (hero + genre rows + collections row + browse-genres grid) when `!isFiltered`; any filter → flat grid. `isFiltered` = genre chips OR `showUnwatchedOnly` OR `selectedDecades`. Both platforms honor `library.tvBrowseLayout` (`grid` forces flat grid even unfiltered) — the key keeps its legacy `tv` name but is platform-neutral (`LibraryBrowseLayout` enum; preserves existing on-device prefs).
- **RULE — `getGenres` takes `parentId`, and any caller that scopes its items MUST scope its genres too** (the cache key `genres-<userId>-<parentId>-<types>` carries it). While it didn't, every scoped library shared one server-wide list. The visible damage was not the ~30 chips leading to "0 films": `fetchGenreItems` only loads the FIRST `genreLoadLimit` (8) entries of that list, so a library whose own genres sat outside the server's first 8 rendered **no genre row at all** and collapsed to its hero (defect L, 2026-08-24 — Downton Abbey in *Drame/Romance*, against a paired control in *Action/Animation* which did render). The filter itself was always scoped, so this was a display defect, never a leak. Locked by `ScopedLibraryGenresTests`.
- **RULE — the A–Z jump bar RE-ANCHORS the grid; it does not only scroll** (`MediaLibraryViewModel.anchorGrid(atLetter:)` → `getItems(nameStartsWithOrGreater:)`). Jellyfin never reports an item's RANK, so "scroll to M" is not expressible as an offset — M's first title may sit hundreds of items past everything paged in. `firstItemID(for:)` searched only the loaded pages and the consumer had no `else` branch, so on a 503-film catalogue whose first page ended in the B's, **C through Z were dead from the moment the screen opened** — inert exactly where pagination made the bar necessary (defect M). Two paths, cheapest first: a loaded letter is a pure scroll; anything else asks the server for "everything from M onward", one request whatever the catalogue's size. `"#"` clears the anchor. Parts of the design, not oversights: titles before the anchor leave the grid; `shouldShowJumpBar` keys on `displayedTotalCount`, not the loaded count, or anchoring near Z hides the bar you need to get back; and **the header keeps the UNANCHORED total** (`unanchoredTotal`) plus a « · à partir de M » suffix, since an anchored query counts only its own slice and the header would otherwise drop from "503 films" to "210 films" on one tap. An anchor survives a tab round-trip (the filter stamp no-ops) but not a filter change. `AlphabeticalJumpBar.onSelect` returns `Bool` so the haptic FOLLOWS the outcome — firing it up front made a dead letter feel taken into account. Locked by `LibraryLetterAnchorTests`.
- Title count uses `isFiltered` (not `isNonDefault`). `loadInitial` guarded by `hasLoaded` (prevents re-randomization on tab switch); `reload(using:)` bypasses (pull-to-refresh, `.cinemaxShouldRefreshCatalogue`). **RULE — the browse genre fan-out is equality-guarded on `appliedGenreSortFilter`**: the tvOS browse scroll drives `reloadGenreItems` from a `.task(id: sortFilter)`, and `.task(id:)` fires on every *attach*, not only on id change — so a filtered-grid return / a tvOS hosting-controller recreation after a menu edit / a browse↔grid toggle each re-ran the whole 8-genre fan-out for byte-identical results. Only `reloadGenreItems` consults the stamp; every explicit refresh funnels through `reload(using:)` (which clears it) → `performLoad` → `fetchGenreItems` **ungated**. The stamp is written only after a clean pass, so a failed or cancelled fan-out never latches it. **RULE — the FILTERED grid carries the symmetric stamp, `appliedFilterStamp`, and for the same reason**: its `.task(id: viewModel.sortFilter)` also re-fires on every attach, and each one re-ran `applyFilter` → `filteredLoader.reset()` → page 0. Measured on device 2026-08-21: an « unwatched only » grid scrolled down to « Les Rayons et les Ombres / Le Parrain 3 / Dirty Dancing » was back on « La Petite Princesse », at the top, after a single trip through the Accueil tab — every tab round-trip cost the user their whole scroll. `applyFilter` no-ops when asked to re-apply the filter already on screen; `reload(using:)` clears both stamps together. **The guard is on the filter VALUE, never on `isFiltered`** — that shortcut is separately proscribed above, since `applyFilter` is also what loads an iOS grid in sort-only state. Stamped only once the pass produced items (or a legitimately empty list), so a failed fetch still retries on the next attach. Locked by `MediaLibraryRefreshSpanTests`.
- **RULE — `performLoad` renders progressively**: `isLoading` flips false right after the phase-1 genres + hero fetch (NOT after `fetchGenreItems`), so the hero paints while the genre rows fill in off `itemsByGenre`. Consequently a `fetchGenreItems` failure is **non-fatal** — it drops the rows (logged) rather than setting `errorMessage` and replacing the already-visible hero with the full error screen; only the phase-1 fetch throwing surfaces the blocking error. A cancellation in either phase still returns `false` (leaves state for the superseding load, doesn't latch `hasLoaded`). Genre fan-out is chunked at 6 concurrent (matching Home), bounded overall by `genreLoadLimit` (8 rows).
- Filters: Unwatched → `filters:[.isUnplayed]`; Decade `selectedDecades: Set<Int>` (starting year) → `expandedYears` for `getItems(years:)`.
- **RULE — tvOS Filters button opens `LibrarySortFilterSheet` via `.fullScreenCover`, not `.sheet`** (`.sheet` on tvOS 26 renders a narrow modal whose toolbar items show as broken white pills). Its content `ScrollView` is deliberately CLIPPED (nothing in it grows on focus) so the decade / genre chips cannot scroll under the sticky footer; the footer buttons are `ctaWidth`.
- `LibrarySortFilterSheet` split bodies: iOS `NavigationStack` + toolbar Apply/Reset; tvOS explicit title + scrollable sections + sticky footer (Reset `.ghost`, Apply `.accent`), sort hidden (lives in top-bar `confirmationDialog`), per-section Clear inline as trailing FlowLayout chip.
- **tvOS button styles** (`TVButtonStyles.swift`): `TVFilterChipButtonStyle` (capsule, press scale 0.95); `TVFilterRowButtonStyle` (full-width rows, **no press scale** — visibly shifts label on wide rows).
- **A–Z jump, both platforms**: the machinery (`jump` → `firstItemID`, else the server-side `anchorGrid`) is shared; only the AFFORDANCE differs. iOS overlays `AlphabeticalJumpBar`, a thin vertical strip tracked with a thumb. tvOS draws `MovieLibraryScreen.tvLetterStrip`, a horizontal row of focusable chips in its own `.focusSection()` — one click per letter, since a thumb-tracked bar is meaningless on a remote. Both offer `AlphabeticalJump.letters`, hoisted OUT of the iOS-gated `AlphabeticalJumpBar.swift` so a letter can't exist on one platform and not the other. Shown only when `sortBy == .sortName && sortAscending && displayedTotalCount > 20`.
- **RULE — Poster context menus** (`MediaCardContextMenu.swift`, `.mediaCardContextMenu(item:artwork:navigation:onRemoveFromResume:onGoToSeries:)`): shared long-press (iOS) / long-press-select (tvOS) menu, attached to the card's focusable `NavigationLink`/`Button` — **never its label** (tvOS focus) — on: library grid + genre rows, search results, watched history, the Favorites screen, person filmography, similar titles, and Home's six card rails (Continue Watching, Next Up, Recently Added, Home's own Favorites preview row, « Parce que vous avez vu », and the per-genre rows — the last four share one `recentlyAddedCard` helper). **Deliberately excluded**: `LibraryFolderBrowseScreen` (it lists folders, not media), `HomeScreen.watchingNowRow` (a `WideCard` of another user's live session — nothing on it belongs to the viewer), and the detail screen's own `MediaDetailEpisodeCard`/`MediaDetailEpisodeRow` (episode rows keep their existing tap-to-play + the season-level bulk "mark watched" action instead). Entries, in order: **play group** (Play / Resume, Play from beginning, "Play on…"), **navigation** (Go to series), **state** (watched, favorite, add to playlist), **destructive** (Remove from Resume). `onRemoveFromResume` and `onGoToSeries` default to `nil`, and each one's presence is what renders its entry — a screen that skips the plumbing shows no entry instead of a dead button; `navigation` also defaults to `nil` but only carries episode-nav data (prev/next/navigator) threaded into playback, not entry visibility. State actions post the tier-2 `.cinemaxItemUserDataChanged` / `.cinemaxFavoritesChanged` as before. Reads `AppState`/`LocalizationManager`/`ToastCenter` from the environment, plus `AddToPlaylistPresenter`, `CardActionPresenter` and (tvOS) `VideoPlayerCoordinator` as **optionals** — a non-optional `@Environment(Type.self)` for an `@Observable` traps at runtime when absent, and these cards also live inside modally-presented hosts that re-inject the environment by hand (`SettingsScreen.watchedHistorySheet`).
  - **RULE — the iOS long-press preview is EXPLICIT (`contextMenu(menuItems:preview:)`) and lifts the artwork alone**: the default preview lifts the whole attached view, and on a `PosterCard` that is the poster **plus its title and subtitle** — text with no background of its own, which floats over the next row's header (reported on Home's genre rows). `LibraryPosterCard` never had the bug because its `NavigationLink` wraps only the poster; the explicit preview makes every surface behave that way. **The preview URL must be byte-identical to the card's own request** (same `maxWidth`, same `tag`) — Nuke keys on the URL, so a near-miss re-downloads instead of reusing the decoded image and the preview shows blank for a beat; same discipline as `PosterPrefetcher`. The `artwork:` parameter exists because the modifier **cannot infer the shape**: the same movie/series appears as a 2:3 poster on seven surfaces (`.primary`/300/`primaryImageTagValue`) and as a 16:9 `WideCard` on Home's Continue Watching and Next Up (`.backdrop`/600/`backdropImageTagValue` off `backdropItemID`). It is the **one parameter here with NO default**, deliberately: every other one defaults to "feature off", so omitting it merely drops an entry, whereas omitting this one would be silently *wrong* — a wide card would lift a portrait poster instead of the backdrop under the finger. Required ⇒ a future wide-card surface gets a compile error instead of a mismatched preview. No `clipShape` on the preview — the system platter already rounds it. tvOS has no `preview:` overload and no lift to correct.
  - **RULE — "the menu acted on an item I never pressed" is a HIT-AREA defect, not a menu defect.** Every entry here, the "Go to series" gate and the add-to-playlist header all read the same `item` on the same modifier value, so they cannot disagree with each other or with the preview — chasing a divergence between them is a dead end (two campaigns spent there). What actually happens is that a NEIGHBOURING card wins the hit-test and then supplies both its menu and its preview: an episode's 16:9 still overflows its 2:3 slot and stays hit-testable past the clip. See the `.contentShape(Rectangle())` RULE under **Image Patterns** for the paired control that proves it. Same recognition rule as the full-width-`Button` case: an input that lands on the wrong thing while neighbouring controls on the same screen behave normally is a geometry problem, not a state problem.
  - **"Go to series" host wiring is one shared modifier**, `seriesDestinationHost(_:)` (declared next to `SeriesDestination` in `MediaCardContextMenu.swift`): each of the three host screens owned a byte-identical `navigationDestination(item:)` copy. Apply it **outside every lazy container** — that is the whole point of the callback contract, and SwiftUI gives no error when it's misplaced.
  - **RULE — playback and "Play on…" go through the root-hosted `CardActionPresenter`** (`Shared/Screens/CardActionPresenter.swift`), never a local presentation: the menu hangs off a card inside a lazy container, where SwiftUI ignores `navigationDestination(item:)` and a presentation dies with the recycled cell. tvOS calls the same `VideoPlayerCoordinator` `PlayLink` would; iOS raises a root `.fullScreenCover` onto the same `VideoPlayerView`. `RemotePlayPresentation` moved from `MediaDetailScreen` to the root for the same reason, and the detail screen now raises it through the presenter too.
  - **RULE — the play target resolver takes ids and scalars, never a `BaseItemDto`** (`Shared/ViewModels/CardPlayTarget.swift`): it is `nonisolated`, so handing it the non-`Sendable` DTO from a `@MainActor` view would be a region transfer of a value the main actor still holds (same discipline as `LibraryAPI.fetchUserData`). It deliberately does **not** pick which episode of a series to play — `getPlaybackInfo` already resolves Series/Season → Episode server-side (`resolvePlayableEpisode`) and a second authority could diverge; it only fetches the **resume offset** (one cached `getNextUp` for a series, zero network for a movie or episode). `resumeSeconds`/`isResumable` are the SSOT of "a residual position on a played item isn't a resume" and are consumed by Home's hero + Continue Watching rail as well as the menu — **never re-express the tick conversion inline**, which is how both Home sites silently dropped the `!isPlayed` half. Locked by `CardPlayTargetTests`.
  - **RULE — a card-launched playback resolves its own episode navigation; only Home's two rails supply one** (`CardEpisodeNavigationResolver`, same file). `navigation:` defaults to `nil` and Home's Continue Watching / Next Up rails are the only call sites that pass it — but `SearchScreen` and `WatchedHistoryScreen` also draw **episode** cards, from flat queries that never touched a season. Their menus therefore reached the player with `previousEpisode`, `nextEpisode` **and** `episodeNavigator` all nil, and a nil navigator costs far more than two buttons: `handlePlaybackEnded` gates autoplay on `nextEpisode != nil && episodeNavigator != nil` and the "Vous avez terminé…" card on the navigator alone, so an episode started from Search played to its end and closed in silence — the **same** defect as the library hero's, cured the same way (`loadHeroNavigation`). Measured on device 2026-08-21 with a paired control: the same episode of the same season drew **3** transport buttons launched from Search and **5** launched from the series page. The resolution is owned by `startPlayback`, **not** by each screen: a `contextMenu`'s content is built *synchronously* for every card a lazy container instantiates, so a per-card probe would be one season fetch per poster on every grid fill; here it runs only when the user actually starts something, off the 10 s `episodes-` cache, and it is **bounded by a deadline** (`ProbeRace`, now generic and shared with the next-up probe) because "Lecture" has no loading affordance — a slow server must cost the episode buttons, never a button that looks dead. Every failure mode (no season, one-episode season, failed fetch, deadline) returns `nil`, i.e. exactly the previous behaviour. Locked by `CardEpisodeNavigationTests`.
  - **RULE — the series next-up deadline is a REAL deadline: two unstructured `Task`s racing onto one single-resume continuation (`ProbeRace`), never a `withTaskGroup`.** A group awaits every remaining child after its body returns, so `group.next()` + `cancelAll()` yields the decision immediately but only *returns* once the loser has finished — the deadline was advisory. `ProbeRace` is `@unchecked Sendable` (an `NSLock`-guarded `CheckedContinuation`; resuming one twice is a crash and both racers can land together on a 1.5 s deadline). **The losing probe is deliberately NOT cancelled**: `getNextUp` populates its 10 s `nextup-` cache only when the response lands, so cancelling turned a one-off timeout into a repeated one. Consequence to know: `resolve` is cancellation-immune for up to `probeDeadline`. Locked by a clock-measuring test — a result-only assertion cannot tell an enforced deadline from an awaited probe, which is exactly how this shipped unnoticed.
  - **RULE — the menu and the iOS preview are standalone `View` types (`CardMenuContent`, `CardArtworkPreview`), never `@ViewBuilder` properties on the modifier.** `contextMenu`'s builders are **non-escaping**, so SwiftUI invokes them synchronously for every card a lazy container instantiates — it cannot defer them, and "the menu is built lazily" is false. What it *does* defer is a child view's `body`, which is where the ~6 `loc.localized` lookups, the `imageURL` build and the `knownRemoteTargetCount` read now live (≈300 lookups + 48 redundant URL builds per tvOS grid fill before this). For the same reason the modifier stores a scalars-only `CardMenuItem`, not a `BaseItemDto`: the ~7 escaping `Button` action closures each captured the enclosing value, i.e. a DTO copy and its retain traffic, per card. **Corollary — the `knownRemoteTargetCount` writer (`MediaDetailViewModel.loadRemoteTargets`) must keep its equality guard**: it is root-hosted state every card's menu reads, `@Observable` fires `withMutation` even on an identical value, and an unguarded write on every detail-screen open invalidated every card still mounted behind it.
  - **RULE — the play group must read the RESOLVED watched state, not the raw snapshot** (`CardPlayTargetResolver.isResumable(positionTicks:isPlayed:playedOverride:now:)`): the menu derived its watched *label* from the optimistic override while `localResume` and `resolvedCardPlayTarget` both re-read `item.isPlayed`, so "Marquer comme vu" flipped the label but left "Reprendre"/"Lire depuis le début" on offer — and Reprendre really did open the film mid-way on an item the app had just marked played (verified on device: `seek-fire target=4915487 from=0`). `OptimisticFlag` therefore lives in `CardPlayTarget.swift`, next to the rule it modifies, and all three call sites (label, play entries, `resolvedCardPlayTarget` — which `startRemotePlay` routes through) take the same input. Locked by `CardMenuOptimisticStateTests`.
  - **RULE — `OptimisticFlag` also expires (`setAt` + `lifetime`, 20 s), not just on a changed snapshot.** The `base == serverValue` test alone is not enough on a surface that never refreshes its DTOs: `SearchScreen` registers none of the three refresh observers, and a playback stop returns a just-marked-watched item to *unwatched* — i.e. back to `base` — so the override stood for the lifetime of the card's view identity and the entry kept reading "Marquer comme non vu" over server truth. Expiry is what bounds it, on every surface at once.
  - **RULE — the optimistic toggle mirrors carry the server value they derive from (`OptimisticFlag`), so fresh data discards them.** Nothing resets them and `@State` outlives a grid reload (same ids ⇒ same view identity), so a bare `Bool?` *shadowed* server truth: toggling watched here then unwatched from the detail screen left the menu offering "Remove from watched" on an unwatched item, and acting on it issued a redundant write plus a redundant notification fan-out.
  - **RULE — a series card's play entry is always labelled "Play", never "Resume"**: a `contextMenu` builds synchronously and cannot await the `getNextUp` that would reveal the offset. The resume is still applied at launch. Movie and episode cards carry their own `userData`, so they label correctly and additionally show "Play from beginning". Same reason "Play on…" reads `CardActionPresenter.knownRemoteTargetCount` (written only by the detail screen's own probe, `MediaDetailViewModel.loadRemoteTargets`, on load) instead of probing itself: a cold cache renders the entry optimistically, and the sheet re-probes independently on open, with its own `remote.noTargets.*` empty state.

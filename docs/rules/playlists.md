### Playlists (write) — « Ajouter à une playlist » (`AddToPlaylistSheet.swift`)

Playlists were browse-only (`LibraryFolderBrowseScreen` + a scoped `MediaLibraryScreen`); nothing could create one or add to it. `PlaylistAPI` slice (`getPlaylists` / `createPlaylist` / `addToPlaylist` / `removeFromPlaylist` / `movePlaylistItem` / `getPlaylistItems` / `getPlaylistPreview` / `deletePlaylist` / `renamePlaylist`, every member defaulted so mocks compile), implemented in `JellyfinAPIClient+Playlists.swift` which declares its own conformance there (the slice RULE above).

- **RULE — the sheet is hosted ONCE, at the root of `AppNavigation`**, and raised through the root-injected `AddToPlaylistPresenter`. The action comes from poster context menus living inside `LazyVGrid`s, where a presentation attached to the cell dies when it is recycled; hoisting it also lets the library grid, search results, watched history and the detail screen share one sheet with zero per-screen plumbing (same reasoning as `ToastOverlay`). The one exception: while the deep-link modal fiche is up, IT hosts the sheet (`host: .modal`) and the root stands down — the root cannot present over that modal (see the deep-link-modal RULE in `Shared/Navigation/CLAUDE.md`).
- **RULE — consumers read the presenter as an OPTIONAL** `@Environment(AddToPlaylistPresenter.self) var playlists: AddToPlaylistPresenter?`. A non-optional `@Environment(Type.self)` for an `@Observable` **traps at runtime** when absent, and these cards also live inside modally-presented hosts that re-inject the environment by hand (`SettingsScreen.watchedHistorySheet`). Optional degrades a forgotten injection into a missing menu entry instead of a crash.
- **RULE — a `contextMenu`'s content and `preview:` are a SEPARATE presentation context that does NOT carry injected `@Observable` objects.** Read them on the **`ViewModifier`** — which resolves in the attached card's own hierarchy — and forward them explicitly onto the menu and the preview (`MediaCardContextMenu.forwardingEnvironment`). Moving those `@Environment` properties down into the menu's child views is what a perf refactor naturally wants to do (it defers the localized lookups to the long-press), and it crashed every long-press on both platforms: `SwiftUICore/Environment+Objects.swift:34: Fatal error: No Observable object of type AppState found`. The trap is only the loud half — the **optional** reads (`AddToPlaylistPresenter`, `CardActionPresenter`, tvOS `VideoPlayerCoordinator`) resolve to `nil` there too, so "fix" it by making `AppState` optional and you get a menu that opens with "Play on…", "Add to playlist" and every playback action silently missing. Forwarding keeps the perf win intact: it's the child views' `body` that stays deferred, not the environment reads, which are plain property reads.
- **RULE — entry ids, not item ids**, for `removeFromPlaylist` / `movePlaylistItem`: the same film can sit in a playlist twice and Jellyfin addresses each occurrence by `BaseItemDto.playlistItemID`, which **only `getPlaylistItems` populates** — a plain `/Items?parentId=` read leaves it nil.
- What gets added is **the item on screen**, not `resolvedPlayTarget` — adding a series adds the series (Jellyfin expands it into ALL its episodes at add time: `Playlist.GetPlaylistItems` turns a folder into its non-folder items, recursively), where Play would resolve down to one next-up episode. Consequence: a playlist that starts with a series starts with a run of its episodes — see the cover's preview limit below.
- `createPlaylist` seeds the new playlist with the item (one round-trip, and no window where it exists but is empty) and passes `mediaType: .video`: without it Jellyfin infers the type from the seed, and an EMPTY seed silently becomes an **Audio** playlist (10.9 → 12.x).
- **RULE — a playlist is reached through `PlaylistDetailScreen`, never a scoped `MediaLibraryScreen`.** Two things only `getPlaylistItems` provides: the playlist's OWN order (a `parentId` query returns `dateCreated` order, meaningless for a playlist), and `playlistItemID` — the ENTRY id every mutation is addressed by. Routing a playlist at the generic grid also produced a page with **no contents at all**: the browse layout is a *library* idiom (hero → genre rows → browse-by-genre), and on a two-item playlist every part but the hero comes up empty, so the screen showed one arbitrary member and nothing else, not even scrollable (measured on device 2026-08-26, playlist « à regarder »). Entry points: Home's Playlists rail, and the `.custom + .library` Playlists tab via `LibraryFolderBrowseScreen`, whose `Source.playlists` reads `getPlaylists` directly so the "all playlists" screen does **not** depend on the server exposing a Playlists *view*. **The Playlists TAB reads `getPlaylists` too** (`MainTabView` passes `.playlists`, not `.parent(viewId)`): it is the read that carries `canDelete`, and through the view's children the tab's cards could not be managed while Home's « Voir tout » could. Collections keep `.parent`.
- **RULE — `PlaylistReorder.destinationIndex(from:to:)` converts SwiftUI's drop into Jellyfin's index.** `.onMove` hands `to` as an insertion point in the list *before* the row is lifted out; `movePlaylistItem` wants the entry's final 0-based index *after* the move. They agree dragging up and differ by one dragging down — the off-by-one drops the row a slot short of the finger and the server records it obediently. The move is optimistic and rolls the list back when the server refuses (a row left where the finger dropped it would have the screen contradicting the playlist). Locked by `PlaylistReorderTests`, whose fixture deliberately holds the same item twice so the test proves the ENTRY id travels, not the item id.
- **RULE — the iOS list does NOT force edit mode on**, unlike `MenuSettingsScreen+iOS` whose rows are all toggles: every row here opens an item, and an always-editing `List` swallows that tap. A localized « Trier » / « Terminé » button (`playlist.reorder` — « Ordonner » until 2026-11-27) drives `editMode` instead — **never the system `EditButton`**, which takes its title from the DEVICE language and read "Edit" over a French app on an English phone (the app's language is its own setting here). tvOS has no drag-and-drop: each row carries « Monter » / « Descendre » in its context menu, and the page's « Trier » mode gives every row its own buttons (see *Filling and reading a playlist* below).
- **Removal** ships since `5716d67`: iOS `.swipeActions` on the row, tvOS context-menu entry, optimistic with rollback, addressed by entry id, posts `.cinemaxPlaylistsChanged`; `PlaylistDetailViewModel.remove` returns a three-way `RemoveOutcome` (`removed` / `notFound` / `failed`) so a stale menu never toasts a removal that was not sent. Locked by `PlaylistReorderTests`. **Still not built (deliberate)**: there is **no player queue**: `EpisodeNavigator` stays the single next/prev authority, and a second queue machine inside `VLCStreamPresenter` would be a guaranteed source of bugs — which is also why a playlist card offers no « Lire » / « Lecture aléatoire ». **« Masquer de l'accueil »** is not built either: it needs a per-server persisted list and a screen to bring a hidden playlist back — a possible follow-up.

### Filling and reading a playlist from its page (lot 1, 2026-11-27 — `PlaylistDetailScreen`, `PlaylistAddTitlesSheet`, `PlaylistContents`)

A playlist was filled one title at a time from each title's own page, and its page only reordered and removed. Mock-ups: artefact « Playlists JellyGlass » ; design: `docs/superpowers/specs/2026-11-27-playlists-lot1-design.md`. The pure parts (`PlaylistGrouping`, `PlaylistMembership`, `PlaylistPickerSelection`) live in `Shared/ViewModels/PlaylistContents.swift`, locked by `PlaylistContentsTests`.

- **RULE — « Ajouter des titres » sends an ORDERED selection in ONE `addToPlaylist`** (`PlaylistAddTitlesModel.commit`). Each poster takes the number of its tap (`PlaylistPickerSelection`, 1-based; deselecting renumbers the ones after) and the ids go in that order — the number on the poster is a promise about the playlist's order, so never sort or `Set` the ids on the way. A server refusal keeps the selection. The picker is presented by the page (`.playlistAddTitles`, applied to the screen body like `.playlistManagement`), a sheet on iOS and a cover on tvOS wearing the ONE chrome: its single accent button reads « Ajouter N titres » with a selection and « Terminé » without one, the Menu button always backs out.
- The picker shows ONE page (`pageSize` 90, newest first) under four filters (Récents, Films, Séries, Favoris) and a debounced search; past the page the search field is the way to a title — it is not a second library screen. `searchItems` has no favourites filter, so « Favoris » + a query filters client-side. A film already in the playlist is marked « Déjà dans la liste » and disabled (by item id); **a series stays selectable** even when some of its episodes are in — it says how many — because adding the series is the only way to add the rest in one go.
- **RULE — a run of 3+ consecutive episodes of one series is drawn as ONE folded line, and that is display only** (`PlaylistGrouping.rows`, `minimumRun`). Jellyfin stores an added series as all its episodes, so a show opened the page with one line per episode. The entries keep their ids: the « Trier » mode shows the list FLAT (it is entries that move), removing a folded line sends every one of its entry ids in one `removeFromPlaylist` after a confirmation, and two episodes side by side stay two lines.
- **A row shows where the user stands** — watched tick, or progress bar + « N min restantes » — from `MediaCardStatus.make`, the derivation every poster card uses, so a row cannot say « vu » where the card of the same title shows a bar. `getPlaylistItems` always asked for user data; the row used to print title and year alone. An episode's row draws its SERIES' poster (`PlaylistCoverStack.poster(for:)`).
- **Removing one entry offers « Annuler » on iOS** (`ToastAction`; tvOS toasts carry no button): `PlaylistDetailViewModel.restore` re-adds the title, re-reads the playlist — the add's response carries no entry id, so the LAST entry of that title is the new one — and moves it back to its index. A bulk removal (folded series, « Retirer les titres vus ») has no undo and asks first instead.
- **« Ajouter à une playlist » (the sheet raised from a poster) ticks the playlists that already hold the title and STAYS open**: a press adds, or removes every entry standing for the title (`PlaylistMembership.entryIds(matching:)` — for a series, each of its episodes). Jellyfin has no « playlists containing this item » read, so `AddToPlaylistModel.loadMembership` asks each playlist's entries in parallel; a playlist that has not answered offers the add, as the sheet always did. Rows draw the poster-stack cover through `PlaylistPreviewStore`.
- **Layout**: two panes at regular width on iOS (`AdaptiveLayout.form`; the header in a 360 pt side pane, the `List` beside it). **RULE — at regular width « Trier » and the options live in the side pane, not in the navigation bar**: the floating tab bar takes the middle of that bar and the system folds both toolbar items into ONE overflow « … », which put « Trier » two taps away (seen on the iPad simulator); the toolbar carries them on a phone only. The picker's sheet asks for `.presentationSizing(.page)` — the default form sheet is a phone-wide column on an iPad.
- **RULE — on an open iPhone Duo the side pane runs to the MIDDLE OF THE WINDOW, read by a UIKit probe (`WindowMidlineProbe`), so the two panes meet on the hinge.** At the iPad's 360 pt the hinge (475 of 951 pt) ran through the list's titles; half of the SwiftUI container fell 41 pt short, because the container stops at the vertical tab bar and the hinge does not — and a background ignoring the safe area stops at that container too, so SwiftUI geometry cannot give the window's middle. Gated on `detectsIPhoneDuo`; an iPad keeps 360 pt. Checked on the Duo simulator (2026-11-27).
- **RULE — the picker reports its add from the presentation's `onDismiss`, never while it is closing** (`PlaylistAddTitlesPresentation.reportAdded`). The page reloads on that report; reloading while the tvOS cover was still closing took the focus off the page and left it on the tab bar (closing WITHOUT adding returned it correctly — that difference is what located the cause). For the same reason the tvOS page draws an empty playlist with the very view of a filled one.
- **tvOS page**: the header carries the actions (« Ajouter des titres », « Trier », « Options » → a `confirmationDialog`) and is the page's `.focusSection()`; **the cover is no longer a focus stop** — the buttons are the row an Up press lands on, and what an empty playlist opens on (a filled one opens on its first entry). No `.navigationTitle` on tvOS: it drew a large faint word across the entries.
- **RULE — tvOS « Trier » is three BUTTONS per row (« Monter », « Descendre », « Retirer »), never « pick the row up and carry it with up / down ».** The carry was built first (`grabbedEntryId` + `.onMoveCommand` on the held row, focus written back) and measured on the simulator: after one carry the focus engine stopped delivering move commands to the row — one press in three moved it, with or without the other rows disabled, and a grab dropped on `focusedEntryId == nil` ended after one slot because the focus reads `nil` while the row changes place. A button press is a plain action whatever the list did under the focus: three presses moved a row three slots (checked against the server). Each sort row is a `.focusSection()` (its buttons sit at the trailing edge, out of the header buttons' beam), and after a move the focus is written back to the SAME row's button (`focusedSortControl`, « entry id|control ») — at either end, to the button that still does something. The sheet's list keeps its rows while it reloads (a spinner in their place dropped the tvOS focus off the row just pressed).

### Managing a playlist — rename, delete, create (`PlaylistManagement.swift`)

- **RULE — a 401 on `deletePlaylist` means "not your playlist", NEVER "session expired": `deletePlaylist` does NOT call `notifyIfUnauthorized`.** Jellyfin refuses a delete with **401 Unauthorized** (`LibraryController.DeleteItem`: `if (!item.CanDelete(user)) return Unauthorized(…)`), and a playlist's `CanDelete` is "administrator or owner". Routed into the session-expiry coordinator, that refusal would re-validate the token for nothing — the exact kind of request that coordinator exists never to sign anyone out over. For the same reason the failure toast is a dedicated « Impossible de supprimer cette playlist » (`playlist.delete.failed`), never `userFacingMessage`, which reads any 401 as « session expirée » (an unreachable server still gets `error.network` as the toast's message). `renamePlaylist` (`POST /Playlists/{id}` with `UpdatePlaylistDto(name:)` alone — nil fields are not encoded, so entries and shares stay untouched; 10.9+) keeps the usual hook: its refusal is a 403, and a 401 there would be a real authentication failure. On success delete clears `APICache` (the admin `deleteItem` precedent); rename drops only the playlist's `item-` entry — no cached read lists playlists by name, and a full clear would refetch every rail for a rename.
- **RULE — `canDelete` is the guard.** `getPlaylists` asks for `fields = [.canDelete, .childCount]`; « Renommer » / « Supprimer la playlist » appear only when `canDelete == true` — on the card's menu (`playlistCardContextMenu`, no menu at all otherwise, not an empty one) and in the page's options — the iOS « … » (navigation bar on a phone, side pane at regular width) and the tvOS « Options » dialog (`PlaylistDetailScreen(canManage:)`, carried by `PlaylistDestination` / `FolderSelection`; defaults to `false` so an unknown call site offers nothing). Those destinations carry the playlist's RAW name: the page shows « Playlist sans nom » for a blank one through `displayTitle`, while « Renommer » pre-fills the real (empty) name — never the placeholder. **RULE — on Jellyfin 12.0 the LIST read's `canDelete` over-reports, so the host re-checks with the single-item read before opening a dialog.** 12.0's `/Items` path (`DtoService.GetBaseItemDtos`) computes `CanDelete(user, allCollectionFolders)`, which `Playlist` does not override — so `Playlist.CanDelete(User)` (owner or administrator) is skipped and every playlist the user can see reads `canDelete: true` (10.9 → 10.11 call the overridden check and are right). The single-item `GET /Items/{id}` (`LibraryAPI.getItem`, 10 s cache) applies the real rule on every version, so `PlaylistManagementHost.mayManage` asks it once when « Renommer » / « Supprimer » is picked; `false` toasts `playlist.manage.denied` and opens nothing, no answer (offline, an error) lets the dialog open — the server still decides. The menu itself keeps showing on the list value: one request per card to hide it would cost far more than the toast. Rename rides the same guard: an administrator who neither owns the playlist nor holds an editing share sees « Renommer » and gets the server's 403 as a generic error — accepted, the client cannot see `OwnerUserId`.
- **RULE — the request lives in a SCREEN-level `@State` (`PlaylistManagementRequest?`) and the host (`.playlistManagement($request, onDeleted:onRenamed:)`) is applied to the screen body**, outside every lazy container: the cards sit in a `LazyHStack` / `LazyVGrid`, where a dialog attached to the cell dies when it is recycled. The host consumes the request (sets it back to `nil`) and sets the field's text BEFORE presenting (the `ServersScreen` order), carries a `confirmationDialog` (visible title, « « %@ » sera supprimée de ton serveur… », destructive button, Annuler) and two `alert`s with a `TextField` (rename pre-filled with the current name; create with an empty seed — `createPlaylist(itemIds: [])` makes a Video playlist because it passes `mediaType: .video`; its message no longer says « depuis leur fiche », the page fills itself now). Success posts `.cinemaxPlaylistsChanged` and toasts; `onDeleted` pops the playlist's page, `onRenamed` retitles it (its `title` is `@State`). HomeScreen adds exactly ONE modifier for all of this (its body is at the type-checker's limit).
- The card menu's strings are resolved by the card (`PlaylistCardButton`) and captured — the `contextMenu` environment RULE above; its iOS `preview:` is the cover alone (`cornerRadius: 0`, the platter rounds it). Attached to the `Button`, never its label (tvOS focus). « Nouvelle playlist »: iOS toolbar of « Vos playlists » (no `.glass` — toolbar RULE), beside the tvOS in-scroll title (its own `.focusSection()`, so an Up press from the grid reaches it), and the empty state's action. **RULE — the tvOS grid of « Vos playlists » is a `.focusSection()` too**: the button is trailing and 240 pt wide, so with fewer than six playlists nothing lies under it and Down found nothing — focus bounced between it and the tab bar. On the playlist's page the tvOS header BUTTONS are the focus stops (since lot 1, 2026-11-27 — the cover used to be one, when the page had no action): Up from the first entry lands on them and an empty playlist opens on them.

### The playlist cover — « pile d'affiches » (`PlaylistCard.swift`, `PlaylistPreviewStore.swift`)

- **Why**: Jellyfin's own playlist image is a 2×2 mosaic that REPEATS its posters when the playlist holds one or two. The cover is drawn by the app instead: up to **3 distinct** 2:3 posters fanned out (front 0°; −9° / −15 %; +9° / +15 %; the stack 2 % below centre, the back two 3 % lower still; height 70 % of the side, corners 2.5 % of it, shadow black 55 % — the validated mock-up, style B) over the front poster blurred (`blur(opaque: true)`) under a `surfaceContainerLowest` veil. One poster stands alone, centred; two = front + left. **Never a repeat**: distinct by the item DRAWN, so the same film twice or three episodes of one show are one poster. **An episode is drawn with its series' poster** (`seriesID` + `seriesPrimaryImageTag`, filled by the server unasked): its own primary is a 16:9 still. Empty playlist → `surfaceContainerHigh` + `music.note.list` (`resizable`, sized from the side); not known yet, OR entries known but none drawable (all hidden by the age cap, id-less) → the NEUTRAL ground WITHOUT the icon (`.neutral`), so a full playlist never flashes « vide » and the icon never sits beside « 5 éléments ». Images are `primary` / 300 / tag — byte-identical to every poster card, i.e. served from Nuke's cache. The layout is pure (`PlaylistCoverStack`: `posters(from:)`, `slots(count:)`, `placed(_:)`, `content(preview:fallbackCount:)`), locked by `PlaylistCoverStackTests`. Used on Home's rail, « Vos playlists », the playlist page's header (built from the loaded entries, no extra request) and the card menu's preview. Home's `prefetchCardImages` no longer warms the playlists' server image (nothing draws it).
- **RULE — the card's count line is ALWAYS laid out** (a hidden placeholder holds its height while the count is unknown, like `PosterCard`'s title). `PosterCard` drew its subtitle only when `childCount` was non-nil, and Jellyfin returned it for one playlist and not another, so « Vos playlists » showed cards of two heights. Count = the preview's `totalCount` (the server counts before `limit`), else `childCount`, through `loc.itemCount` (« 0 élément » / « 1 élément »).
- **`PlaylistPreviewStore`** (`@MainActor @Observable`, process singleton `shared`): previews (posters + total) by playlist id, fetched by `getPlaylistPreview(limit: 24)` (no userData, primary tag only, `applyRatingFilter`). **RULE — the limit is 24, not 3 or 4**: a series in a playlist is stored as all its episodes (see above), so a playlist opening on a show starts with a run of one poster, and four entries drew a single poster on a three-title playlist. A card asks from its own `.task(id:)` — lazily, since the cards live in lazy containers — and the fetch runs in the store's task, so a card scrolled away does not cancel it. **One request in flight per playlist per generation. RULE — `.cinemaxPlaylistsChanged` and `.cinemaxShouldRefreshCatalogue` bump `generation` and KEEP every preview held** (the store observes them itself, so two screens alive at once cannot double-invalidate it; a pull-to-refresh on Home or « Vos playlists » calls `invalidate()` too — it is how a change made on another device arrives); cards key their task on `generation`, so each card on screen re-asks once and swaps its cover when the answer lands — no flash. An older answer never overwrites a newer one; a failure keeps what is shown; **another account or another content-age cap starts from nothing** (the card passes `SettingsKey.privacyMaxContentAge` into `load`: kept "until the refetch lands", a poster the new cap hides would stay drawn — for good if the refetch failed). No `didSet` (the `@Observable` RULE); writes are equality-guarded. Locked by `PlaylistPreviewStoreTests`.

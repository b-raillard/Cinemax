### Playlists (write) — « Ajouter à une playlist » (`AddToPlaylistSheet.swift`)

Playlists were browse-only (`LibraryFolderBrowseScreen` + a scoped `MediaLibraryScreen`); nothing could create one or add to it. `PlaylistAPI` slice (`getPlaylists` / `createPlaylist` / `addToPlaylist` / `removeFromPlaylist` / `movePlaylistItem` / `getPlaylistItems` / `getPlaylistPreview` / `deletePlaylist` / `renamePlaylist`, every member defaulted so mocks compile), implemented in `JellyfinAPIClient+Playlists.swift` which declares its own conformance there (the slice RULE above).

- **RULE — the sheet is hosted ONCE, at the root of `AppNavigation`**, and raised through the root-injected `AddToPlaylistPresenter`. The action comes from poster context menus living inside `LazyVGrid`s, where a presentation attached to the cell dies when it is recycled; hoisting it also lets the library grid, search results, watched history and the detail screen share one sheet with zero per-screen plumbing (same reasoning as `ToastOverlay`).
- **RULE — consumers read the presenter as an OPTIONAL** `@Environment(AddToPlaylistPresenter.self) var playlists: AddToPlaylistPresenter?`. A non-optional `@Environment(Type.self)` for an `@Observable` **traps at runtime** when absent, and these cards also live inside modally-presented hosts that re-inject the environment by hand (`SettingsScreen.watchedHistorySheet`). Optional degrades a forgotten injection into a missing menu entry instead of a crash.
- **RULE — a `contextMenu`'s content and `preview:` are a SEPARATE presentation context that does NOT carry injected `@Observable` objects.** Read them on the **`ViewModifier`** — which resolves in the attached card's own hierarchy — and forward them explicitly onto the menu and the preview (`MediaCardContextMenu.forwardingEnvironment`). Moving those `@Environment` properties down into the menu's child views is what a perf refactor naturally wants to do (it defers the localized lookups to the long-press), and it crashed every long-press on both platforms: `SwiftUICore/Environment+Objects.swift:34: Fatal error: No Observable object of type AppState found`. The trap is only the loud half — the **optional** reads (`AddToPlaylistPresenter`, `CardActionPresenter`, tvOS `VideoPlayerCoordinator`) resolve to `nil` there too, so "fix" it by making `AppState` optional and you get a menu that opens with "Play on…", "Add to playlist" and every playback action silently missing. Forwarding keeps the perf win intact: it's the child views' `body` that stays deferred, not the environment reads, which are plain property reads.
- **RULE — entry ids, not item ids**, for `removeFromPlaylist` / `movePlaylistItem`: the same film can sit in a playlist twice and Jellyfin addresses each occurrence by `BaseItemDto.playlistItemID`, which **only `getPlaylistItems` populates** — a plain `/Items?parentId=` read leaves it nil.
- What gets added is **the item on screen**, not `resolvedPlayTarget` — a playlist holds the series, where Play resolves down to a next-up episode.
- `createPlaylist` seeds the new playlist with the item (one round-trip, and no window where it exists but is empty) and passes `mediaType: .video`, without which Jellyfin can't infer the type of an empty seed.
- **RULE — a playlist is reached through `PlaylistDetailScreen`, never a scoped `MediaLibraryScreen`.** Two things only `getPlaylistItems` provides: the playlist's OWN order (a `parentId` query returns `dateCreated` order, meaningless for a playlist), and `playlistItemID` — the ENTRY id every mutation is addressed by. Routing a playlist at the generic grid also produced a page with **no contents at all**: the browse layout is a *library* idiom (hero → genre rows → browse-by-genre), and on a two-item playlist every part but the hero comes up empty, so the screen showed one arbitrary member and nothing else, not even scrollable (measured on device 2026-08-26, playlist « à regarder »). Entry points: Home's Playlists rail, and the `.custom + .library` Playlists tab via `LibraryFolderBrowseScreen`, whose `Source.playlists` reads `getPlaylists` directly so the "all playlists" screen does **not** depend on the server exposing a Playlists *view*.
- **RULE — `PlaylistReorder.destinationIndex(from:to:)` converts SwiftUI's drop into Jellyfin's index.** `.onMove` hands `to` as an insertion point in the list *before* the row is lifted out; `movePlaylistItem` wants the entry's final 0-based index *after* the move. They agree dragging up and differ by one dragging down — the off-by-one drops the row a slot short of the finger and the server records it obediently. The move is optimistic and rolls the list back when the server refuses (a row left where the finger dropped it would have the screen contradicting the playlist). Locked by `PlaylistReorderTests`, whose fixture deliberately holds the same item twice so the test proves the ENTRY id travels, not the item id.
- **RULE — the iOS list does NOT force edit mode on**, unlike `MenuSettingsScreen+iOS` whose rows are all toggles: every row here opens an item, and an always-editing `List` swallows that tap. A localized « Ordonner » / « Terminé » button drives `editMode` instead — **never the system `EditButton`**, which takes its title from the DEVICE language and read "Edit" over a French app on an English phone (the app's language is its own setting here). tvOS has no drag-and-drop: each row carries « Monter » / « Descendre » in its context menu.
- **Removal** ships since `5716d67`: iOS `.swipeActions` on the row, tvOS context-menu entry, optimistic with rollback, addressed by entry id, posts `.cinemaxPlaylistsChanged`; `PlaylistDetailViewModel.remove` returns a three-way `RemoveOutcome` (`removed` / `notFound` / `failed`) so a stale menu never toasts a removal that was not sent. Locked by `PlaylistReorderTests`. **Still not built (deliberate)**: there is **no player queue**: `EpisodeNavigator` stays the single next/prev authority, and a second queue machine inside `VLCStreamPresenter` would be a guaranteed source of bugs — which is also why a playlist card offers no « Lire » / « Lecture aléatoire ». **« Masquer de l'accueil »** is not built either: it needs a per-server persisted list and a screen to bring a hidden playlist back — a possible follow-up.

### Managing a playlist — rename, delete, create (`PlaylistManagement.swift`)

- **RULE — a 401 on `deletePlaylist` means "not your playlist", NEVER "session expired": `deletePlaylist` does NOT call `notifyIfUnauthorized`.** Jellyfin refuses a delete with **401 Unauthorized** (`LibraryController.DeleteItem`: `if (!item.CanDelete(user)) return Unauthorized(…)`), and a playlist's `CanDelete` is "administrator or owner". Routed into the session-expiry coordinator, that refusal would re-validate the token for nothing — the exact kind of request that coordinator exists never to sign anyone out over. For the same reason the failure toast is a dedicated « Impossible de supprimer cette playlist » (`playlist.delete.failed`), never `userFacingMessage`, which reads any 401 as « session expirée » (an unreachable server still gets `error.network` as the toast's message). `renamePlaylist` (`POST /Playlists/{id}` with `UpdatePlaylistDto(name:)` alone — nil fields are not encoded, so entries and shares stay untouched; 10.9+) keeps the usual hook: its refusal is a 403, and a 401 there would be a real authentication failure. Both clear `APICache` on success.
- **RULE — `canDelete` is the guard.** `getPlaylists` asks for `fields = [.canDelete, .childCount]`; « Renommer » / « Supprimer la playlist » appear only when `canDelete == true` — on the card's menu (`playlistCardContextMenu`, no menu at all otherwise, not an empty one) and in the page's iOS « … » (`PlaylistDetailScreen(canManage:)`, carried by `PlaylistDestination` / `FolderSelection`; defaults to `false` so an unknown call site offers nothing). Rename rides the same guard: an administrator who neither owns the playlist nor holds an editing share sees « Renommer » and gets the server's 403 as a generic error — accepted, the client cannot see `OwnerUserId`.
- **RULE — the request lives in a SCREEN-level `@State` (`PlaylistManagementRequest?`) and the host (`.playlistManagement($request, onDeleted:onRenamed:)`) is applied to the screen body**, outside every lazy container: the cards sit in a `LazyHStack` / `LazyVGrid`, where a dialog attached to the cell dies when it is recycled. The host consumes the request (sets it back to `nil`) and sets the field's text BEFORE presenting (the `ServersScreen` order), carries a `confirmationDialog` (visible title, « « %@ » sera supprimée de ton serveur… », destructive button, Annuler) and two `alert`s with a `TextField` (rename pre-filled with the current name; create with an empty seed — `createPlaylist(itemIds: [])` works because it passes `mediaType: .video`). Success posts `.cinemaxPlaylistsChanged` and toasts; `onDeleted` pops the playlist's page, `onRenamed` retitles it (its `title` is `@State`). HomeScreen adds exactly ONE modifier for all of this (its body is at the type-checker's limit).
- The card menu's strings are resolved by the card (`PlaylistCardButton`) and captured — the `contextMenu` environment RULE above; its iOS `preview:` is the cover alone (`cornerRadius: 0`, the platter rounds it). Attached to the `Button`, never its label (tvOS focus). « Nouvelle playlist »: iOS toolbar of « Vos playlists » (no `.glass` — toolbar RULE), beside the tvOS in-scroll title (its own `.focusSection()`), and the empty state's action.

### The playlist cover — « pile d'affiches » (`PlaylistCard.swift`, `PlaylistPreviewStore.swift`)

- **Why**: Jellyfin's own playlist image is a 2×2 mosaic that REPEATS its posters when the playlist holds one or two. The cover is drawn by the app instead: up to **3 distinct** 2:3 posters fanned out (front 0°; −9° / −15 %; +9° / +15 %; the stack 2 % below centre, the back two 3 % lower still; height 70 % of the side, corners 2.5 % of it, shadow black 55 % — the validated mock-up, style B) over the front poster blurred (`blur(opaque: true)`) under a `surfaceContainerLowest` veil. One poster stands alone, centred; two = front + left. **Never a repeat**: distinct by the item DRAWN, so the same film twice or three episodes of one show are one poster. **An episode is drawn with its series' poster** (`seriesID` + `seriesPrimaryImageTag`, filled by the server unasked): its own primary is a 16:9 still. Empty playlist → `surfaceContainerHigh` + `music.note.list` (`resizable`, sized from the side); loading → the neutral ground WITHOUT the icon, so a full playlist never flashes « vide ». Images are `primary` / 300 / tag — byte-identical to every poster card, i.e. served from Nuke's cache. The layout is pure (`PlaylistCoverStack`: `posters(from:)`, `slots(count:)`, `placed(_:)`, `content(preview:fallbackCount:)`), locked by `PlaylistCoverStackTests`. Used on Home's rail, « Vos playlists », the playlist page's header (built from the loaded entries, no extra request) and the card menu's preview. Home's `prefetchCardImages` no longer warms the playlists' server image (nothing draws it).
- **RULE — the card's count line is ALWAYS laid out** (a hidden placeholder holds its height while the count is unknown, like `PosterCard`'s title). `PosterCard` drew its subtitle only when `childCount` was non-nil, and Jellyfin returned it for one playlist and not another, so « Vos playlists » showed cards of two heights. Count = the preview's `totalCount` (the server counts before `limit`), else `childCount`, through `loc.itemCount` (« 0 élément » / « 1 élément »).
- **`PlaylistPreviewStore`** (`@MainActor @Observable`, process singleton `shared`): previews (posters + total) by playlist id, fetched by `getPlaylistPreview(limit: 4)` (no userData, primary tag only, `applyRatingFilter`). A card asks from its own `.task(id:)` — lazily, since the cards live in lazy containers — and the fetch runs in the store's task, so a card scrolled away does not cancel it. **One request in flight per playlist per generation. RULE — `.cinemaxPlaylistsChanged` and `.cinemaxShouldRefreshCatalogue` bump `generation` and KEEP every preview held** (the store observes them itself, so two screens alive at once cannot double-invalidate it); cards key their task on `generation`, so each card on screen re-asks once and swaps its cover when the answer lands — no flash. An older answer never overwrites a newer one; a failure keeps what is shown; another account starts from nothing. No `didSet` (the `@Observable` RULE); writes are equality-guarded. Locked by `PlaylistPreviewStoreTests`.

### Playlists (write) — « Ajouter à une playlist » (`AddToPlaylistSheet.swift`)

Playlists were browse-only (`LibraryFolderBrowseScreen` + a scoped `MediaLibraryScreen`); nothing could create one or add to it. `PlaylistAPI` slice (`getPlaylists` / `createPlaylist` / `addToPlaylist` / `removeFromPlaylist` / `movePlaylistItem` / `getPlaylistItems`), implemented in `JellyfinAPIClient+Playlists.swift` which declares its own conformance there (the slice RULE above).

- **RULE — the sheet is hosted ONCE, at the root of `AppNavigation`**, and raised through the root-injected `AddToPlaylistPresenter`. The action comes from poster context menus living inside `LazyVGrid`s, where a presentation attached to the cell dies when it is recycled; hoisting it also lets the library grid, search results, watched history and the detail screen share one sheet with zero per-screen plumbing (same reasoning as `ToastOverlay`).
- **RULE — consumers read the presenter as an OPTIONAL** `@Environment(AddToPlaylistPresenter.self) var playlists: AddToPlaylistPresenter?`. A non-optional `@Environment(Type.self)` for an `@Observable` **traps at runtime** when absent, and these cards also live inside modally-presented hosts that re-inject the environment by hand (`SettingsScreen.watchedHistorySheet`). Optional degrades a forgotten injection into a missing menu entry instead of a crash.
- **RULE — a `contextMenu`'s content and `preview:` are a SEPARATE presentation context that does NOT carry injected `@Observable` objects.** Read them on the **`ViewModifier`** — which resolves in the attached card's own hierarchy — and forward them explicitly onto the menu and the preview (`MediaCardContextMenu.forwardingEnvironment`). Moving those `@Environment` properties down into the menu's child views is what a perf refactor naturally wants to do (it defers the localized lookups to the long-press), and it crashed every long-press on both platforms: `SwiftUICore/Environment+Objects.swift:34: Fatal error: No Observable object of type AppState found`. The trap is only the loud half — the **optional** reads (`AddToPlaylistPresenter`, `CardActionPresenter`, tvOS `VideoPlayerCoordinator`) resolve to `nil` there too, so "fix" it by making `AppState` optional and you get a menu that opens with "Play on…", "Add to playlist" and every playback action silently missing. Forwarding keeps the perf win intact: it's the child views' `body` that stays deferred, not the environment reads, which are plain property reads.
- **RULE — entry ids, not item ids**, for `removeFromPlaylist` / `movePlaylistItem`: the same film can sit in a playlist twice and Jellyfin addresses each occurrence by `BaseItemDto.playlistItemID`, which **only `getPlaylistItems` populates** — a plain `/Items?parentId=` read leaves it nil.
- What gets added is **the item on screen**, not `resolvedPlayTarget` — a playlist holds the series, where Play resolves down to a next-up episode.
- `createPlaylist` seeds the new playlist with the item (one round-trip, and no window where it exists but is empty) and passes `mediaType: .video`, without which Jellyfin can't infer the type of an empty seed.
- **RULE — a playlist is reached through `PlaylistDetailScreen`, never a scoped `MediaLibraryScreen`.** Two things only `getPlaylistItems` provides: the playlist's OWN order (a `parentId` query returns `dateCreated` order, meaningless for a playlist), and `playlistItemID` — the ENTRY id every mutation is addressed by. Routing a playlist at the generic grid also produced a page with **no contents at all**: the browse layout is a *library* idiom (hero → genre rows → browse-by-genre), and on a two-item playlist every part but the hero comes up empty, so the screen showed one arbitrary member and nothing else, not even scrollable (measured on device 2026-08-26, playlist « à regarder »). Entry points: Home's Playlists rail, and the `.custom + .library` Playlists tab via `LibraryFolderBrowseScreen`, whose `Source.playlists` reads `getPlaylists` directly so the "all playlists" screen does **not** depend on the server exposing a Playlists *view*.
- **RULE — `PlaylistReorder.destinationIndex(from:to:)` converts SwiftUI's drop into Jellyfin's index.** `.onMove` hands `to` as an insertion point in the list *before* the row is lifted out; `movePlaylistItem` wants the entry's final 0-based index *after* the move. They agree dragging up and differ by one dragging down — the off-by-one drops the row a slot short of the finger and the server records it obediently. The move is optimistic and rolls the list back when the server refuses (a row left where the finger dropped it would have the screen contradicting the playlist). Locked by `PlaylistReorderTests`, whose fixture deliberately holds the same item twice so the test proves the ENTRY id travels, not the item id.
- **RULE — the iOS list does NOT force edit mode on**, unlike `MenuSettingsScreen+iOS` whose rows are all toggles: every row here opens an item, and an always-editing `List` swallows that tap. A localized « Ordonner » / « Terminé » button drives `editMode` instead — **never the system `EditButton`**, which takes its title from the DEVICE language and read "Edit" over a French app on an English phone (the app's language is its own setting here). tvOS has no drag-and-drop: each row carries « Monter » / « Descendre » in its context menu.
- **Removal** ships since `5716d67`: iOS `.swipeActions` on the row, tvOS context-menu entry, optimistic with rollback, addressed by entry id, posts `.cinemaxPlaylistsChanged`; `PlaylistDetailViewModel.remove` returns a three-way `RemoveOutcome` (`removed` / `notFound` / `failed`) so a stale menu never toasts a removal that was not sent. Locked by `PlaylistReorderTests`. **Still not built (deliberate)**: there is **no player queue**: `EpisodeNavigator` stays the single next/prev authority, and a second queue machine inside `VLCStreamPresenter` would be a guaranteed source of bugs.
